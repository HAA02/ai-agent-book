# AI Agent 입문

Cursor로 코드를 작성해 본 적이 있다면, 그것이 코드베이스를 검색하고 여러 파일을 편집하며 테스트가 통과할 때까지 실행하는 모습을 보았을 것입니다. Deep Research로 어떤 주제를 조사해 본 적이 있다면, 그것이 반복해서 검색하고 읽으며 완전한 보고서를 정리해 내는 모습을 보았을 것입니다. Manus로 브라우저를 조작해 온라인 작업을 처리해 봤거나, 두바오(豆包) 모바일 비서에게 표를 예매하거나 메시지를 보내게 해봤거나, Pine AI에게 통신사에 전화를 걸어 요금 인하를 협상하게 해봤다면—여러분은 이미 AI Agent를 사용하고 있는 것입니다.

이런 제품들은 형태는 제각각이지만 한 가지 공통점이 있습니다. 더 이상 "당신이 한 마디 물으면 그것이 한 마디 답하는" 수동적 대화가 아니라, 스스로 실행 단계를 계획하고 다양한 도구를 호출해 작업을 완수하며, 결과에 따라 끊임없이 전략을 조정하는 지능형 시스템이라는 점입니다. AI Agent는 우리가 컴퓨터와 상호작용하는 완전히 새로운 방식으로 자리 잡아 가고 있습니다.

이 장에서는 실천에서 출발해 AI Agent의 핵심 구성 요소를 이해합니다. 현대 Agent의 능력을 직접 체험하고, 그 뒤에 있는 아키텍처 원리를 이해하며, Agent 시스템을 구축하는 설계 패턴과 모범 사례를 익힙니다.

> **읽기 안내**: 이 장은 책 전체의 개념 지도입니다—Agent의 핵심 공식, 실행 순환, 엔지니어링 프레임워크와 설계 패턴을 빠르게 도입하여, 이후 장들을 위한 통일된 용어와 참조 좌표를 제공합니다. 처음 읽을 때 모든 개념을 하나하나 외울 필요는 없습니다. 먼저 전체적인 인상을 세우기를 권합니다. 이후 각 장이 이 장에서 언급한 어떤 한 측면을 자세히 다룰 것이며, 그때마다 여기로 돌아와 대조해도 좋습니다.

## 현대 Agent = LLM + 컨텍스트 + 도구

현대 Agent 시스템의 본질은 간결한 공식 하나로 표현할 수 있습니다: **Agent = LLM(대형 언어 모델, Large Language Model) + 컨텍스트 + 도구**. 이 공식은 간결하면서도 실용적이지만, 각 단어는 넓은 의미로 이해해야 합니다.

- **LLM은 Agent의 뇌입니다**: 단순한 모델 파라미터 집합이 아니라, Agent 전체의 의사결정 핵심입니다—의도를 이해하고, 사고하며 계획하고, 판단을 내립니다. 인간의 뇌가 뉴런의 집합에 그치지 않고 경험을 통해 형성된 사고방식까지 포함하듯, LLM의 능력 역시 두 부분에서 나옵니다: **사전훈련(Pre-training)**을 통해 축적된 세계 지식과 언어 능력, 그리고 **후훈련(Post-training)**을 통해 굳어진 의사결정 전략—후자의 구체적 기법(지도 미세조정과 강화학습 등)은 제7장에서 자세히 다룹니다.
- **컨텍스트는 Agent의 눈입니다**: 모델에 입력되는 그 텍스트 조각만이 아니라, Agent가 매 결정 시점에 볼 수 있는 모든 정보입니다—환경 정보, 사용자 메모리, 도메인 지식, 자신의 상태와 작업 진행 상황. 인간이 결정을 내릴 때 현재 상황을 명확히 보고 관련 경험을 떠올리며 참고 자료를 뒤져야 하듯, Agent의 컨텍스트 윈도우는 바로 지금 그것이 볼 수 있는 모든 것입니다.
- **도구는 Agent의 손발입니다**: 호출 가능한 몇 개의 API 함수만이 아니라, Agent가 할 수 있는 모든 일의 집합입니다—미리 정의된 도구 호출부터 온디맨드로 로딩되는 전문 기술(Skills)까지, 동적으로 코드를 생성해 새로운 능력을 창조하는 것부터 하위 Agent에게 위임해 협업하는 것까지, 사용자와 능동적으로 소통하는 것부터 외부 이벤트에 반응하는 것까지.

더 직관적으로 말하면: **Agent = 뇌 + 눈 + 손발**입니다. 뇌는 사고와 결정을 담당하고, 눈은 사고에 필요한 모든 정보를 제공하며, 손발은 결정을 현실 세계에 대한 변화로 전환합니다.

이 세 가지 구성 요소는 RL(제7장에서 자세히 다룸)의 세 가지 핵심 개념과 정확히 대응합니다. 아래 표는 **선택적으로 읽어도 되는** 내용입니다—RL 배경지식이 없다면 건너뛰어도 이후 이해에 지장이 없습니다. 이는 RL 배경이 있는 독자가 기존 지식을 이 책의 용어와 대응시킬 수 있도록 돕기 위한 것일 뿐입니다.

| 직관적 이해 | 구현 요소 | 학술 개념(선택) | 의미 |
|-----------|-----------|----------------------------|----------------------------------------------|
| **뇌** | LLM | **정책**(Policy) | Agent가 "다음에 무엇을 할지"를 결정하는 의사결정 로직—현재 보고 있는 정보를 바탕으로, 선택 가능한 모든 행동 중 가장 적합한 것을 골라내는 것 |
| **눈** | 컨텍스트 | **관측 공간**(Observation Space) | Agent가 볼 수 있는 모든 정보—무엇을 볼 수 있고, 무엇을 읽을 수 있고, 무엇을 기억할 수 있고, 어떤 시스템에 접근할 수 있는지 |
| **손발** | 도구 | **행동 공간**(Action Space) | Agent가 할 수 있는 모든 일의 집합—메시지 전송부터 코드 실행, 인터페이스 조작까지 어떤 "수단"을 쓸 수 있는지 |

이 세 가지의 역할과 상호관계를 이해하는 것이 효과적인 Agent 시스템을 구축하는 기초입니다. 가장 구체적인 손발(도구)부터 소개를 시작해, 점차 뇌(LLM)와 눈(컨텍스트)으로 깊이 들어가겠습니다. 먼저 서로 다른 유형의 Agent들이 이 세 차원에서 어떻게 펼쳐지는지 살펴봅시다.

| Agent 제품 | 눈(인지) | 손발(행동) | 정책 |
|----------------|----------------------|----------------------------|------------------------------|
| **Cursor 등 Coding Agent** | 요구사항 문서, 코드베이스, 터미널 환경 | 개방형(내부 사고, 코드 검색, 파일 읽기/쓰기, 명령 실행 등) | 점진적 개발: 요구사항 이해→관련 코드 검색→코드 편집→테스트 검증→디버그 수정 |
| **Deep Research 등 검색 Agent** | 웹 자원, 학술 데이터베이스, 로컬 파일 | 개방형(내부 사고, 검색 쿼리, 웹페이지 읽기, 요약 생성) | 반복 심화: 기존 정보를 바탕으로 검색 방향을 조정하며 점진적으로 완전한 보고서를 종합 |
| **Manus 등 컴퓨터 조작 Agent** | 컴퓨터 화면, 브라우저 페이지, 파일 시스템 | 개방형(내부 사고, 클릭, 입력, 스크롤, 스크린샷, 코드 실행 등) | 시각 인지+조작: 화면 관찰→목표 요소 식별→조작 실행→결과 검증 |
| **두바오 등 모바일 비서 Agent** | 휴대폰 화면, 설치된 앱 | 개방형(내부 사고, 클릭, 스와이프, 입력, 앱 열기 등) | 의도 이해+앱 조작: 사용자 요구 이해→목표 앱 위치 파악→조작 실행→완료 확인 |
| **Pine AI 등 개인 업무 대행 Agent** | 사용자 계정 정보, 이력 청구서, 서비스 제공자 지식베이스 | 개방형(내부 사고, 전화 걸기, 이메일 발송, 양식 작성, 사용자 확인) | 다단계 작업 실행: 정보 수집→협상 전략 수립→서비스 제공자 연락→협상→결과 보고 |

이런 Agent 시스템들에는 몇 가지 공통된 특징이 있습니다. 이들 모두 **개방형 행동 공간**을 사용합니다—제한된 몇 개의 버튼 중에서 고르는 것이 아니라, 임의의 자연어와 코드를 생성할 수 있습니다. 이들 모두 **내부적으로 사고**할 수 있습니다—행동을 취하기 전에 먼저 사고하고 계획합니다. 이들 모두 **지속적으로 상호작용**할 수 있습니다—환경 피드백에 따라 끊임없이 전략을 조정합니다. 이런 능력들은 바로 뇌, 눈, 손발—즉 LLM, 컨텍스트, 도구—의 협업에서 나옵니다.

### 도구: Agent의 손발

도구는 Agent가 외부 세계와 상호작용하는 다리이며, 인간의 손발처럼 Agent를 수동적인 관찰자에서 능동적인 실행자로 바꿔줍니다. 도구가 없으면 Agent는 그저 "탁상공론"할 수밖에 없습니다. 도구가 있어야 비로소 세계를 실제로 바꿀 수 있습니다.

도구를 체계적으로 논의하기 위해, Agent가 외부와 상호작용하는 방향에 따라 도구를 다섯 가지로 분류할 수 있습니다. 아래에서는 먼저 각 범주의 대표적인 시나리오를 빠르게 훑어 전체적인 인상을 세우고, 이후 장에서 하나씩 자세히 전개하겠습니다.

**인지 도구**는 Agent가 정보에 접근할 수 있게 해줍니다: 검색 엔진은 실시간 웹 데이터를 제공하고, 파일 시스템은 로컬 문서를 읽으며, API와 데이터베이스는 외부 서비스와 기업 핵심 데이터를 연결합니다.

**실행 도구**는 Agent가 세계를 바꿀 수 있게 해줍니다: 코드 실행, 파일 조작, 시스템 명령, 외부 API 호출—결정이 이를 통해 실제 행동으로 바뀝니다.

**협업 도구**는 Agent가 다른 Agent와 분업 협력할 수 있게 해줍니다: 하위 Agent에 특정 작업을 위임하고, 핵심 결정 시점에 사람의 확인을 요청하며, 다중 Agent 시스템에서 행동을 조율합니다.

**이벤트 트리거 도구**는 앞의 세 범주와 호출 방식에서 본질적으로 다릅니다—Agent가 능동적으로 호출하는 것이 아니라, 외부 입력으로서 Agent가 작업을 시작하도록 유도합니다. 예를 들어 새 이메일이 도착하거나, 미리 정한 시점이 되거나, 다른 시스템이 웹훅(Webhook) 콜백을 보내는 것과 같은 이벤트들이 Agent를 활성화해 이후의 사고와 행동을 시작하게 합니다. 이벤트 트리거는 Agent가 능동적으로 호출하는 것은 아니지만, Agent가 외부 세계와 상호작용하는 통로 중 하나이므로 넓은 의미의 도구 체계에 포함시킵니다.

**사용자 소통 도구**는 Agent가 능동적으로 사용자와 연결을 맺고 정보를 전달하는 통로입니다. 외부 세계를 바꾸는 실행 도구와 달리, 사용자 소통 도구는 정보의 전달과 상호작용에 집중합니다—문자 메시지, 음성 통화, 이메일 등의 방식으로 Agent의 실행 진행 상황이나 능동적인 관심 표현을 사용자에게 전달합니다.

위 다섯 가지 도구의 완전한 분류 체계와 설계 원칙은 제4장에서 자세히 논의합니다. 도구 설계의 품질은 Agent가 얼마나 멀리 갈 수 있는지를 직접 결정합니다—인터페이스 정의가 명확하지 않으면 모델이 도구를 오용하게 되고, 오류 처리가 미흡하면 도구 실패가 곧바로 Agent의 데드락이 되며, 권한 제어가 지나치게 느슨하면 Agent가 일단 실수했을 때 그 결과를 되돌리기 어렵습니다. MCP(Model Context Protocol, 모델 컨텍스트 프로토콜) 표준의 보급은 도구 접속을 마치 플러그인 설치처럼 만들어가고 있습니다—생태계는 빠르게 확장되고 있지만, 설계 원칙은 낡지 않습니다.

**도구 호출**(Tool Calling, Function Calling이라고도 함)은 현대 LLM Agent의 핵심 능력으로, 모델이 구조화된 방식으로 외부 도구를 호출할 수 있게 해줍니다. 이 능력은 LLM을 순수한 텍스트 생성기에서 실제 조작을 실행할 수 있는 지능형 시스템으로 바꿉니다. 이 책 이후로는 통일해서 "도구 호출"이라는 용어를 사용합니다.

도구 호출의 흐름은 네 단계로 나뉩니다: 먼저 컨텍스트에서 어떤 도구를 사용할 수 있는지(이름, 용도, 파라미터 포함) 모델에게 알려줍니다. 그다음 모델이 스스로 도구를 호출할지, 어떤 도구를 호출할지, 어떤 파라미터를 전달할지 판단합니다. 이어서 도구 실행이 끝나면 결과가 컨텍스트에 추가됩니다. 마지막으로 모델이 이를 바탕으로 다음 행동을 결정합니다. 이 순환이 바로 뒤에서 소개할 ReAct의 기초입니다.

날씨를 조회하는 시나리오를 예로 들면, 네 단계 흐름을 API 층위에서 간략히 표현하면 다음과 같습니다.

```
1단계: 도구 선언                    2단계: 모델이 호출 결정
tools: [{                          assistant: {
  name: "get_weather",               tool_calls: [{
  parameters: {                        function: "get_weather",
    city: "string"                     arguments: {city: "北京"}
  }                                  }]
}]                                 }

3단계: 결과가 컨텍스트에 추가됨              4단계: 모델이 결과를 바탕으로 응답
tool: {                            assistant: {
  tool_call_id: "call_1",            content: "北京今天 28°C，晴。"
  content: '{"temp":28,"sky":"晴"}'  }
}
```

개발자는 도구를 정의하고 도구 호출을 실행하기만 하면 되며, "호출할지 말지, 어떤 것을 호출할지, 어떤 파라미터를 전달할지"에 대한 결정은 모델이 스스로 완수합니다. 제2장에서 이 API 구조를 자세히 전개합니다.

Agent를 위해 도구를 설계할 때는 도구의 범용성을 최대한 유지해 LLM에게 더 큰 발휘 공간을 주어야 합니다. 예를 들어 전용 계산기 도구를 설계하는 대신, Python 코드 인터프리터를 제공하고 Agent를 위한 안전한 샌드박스 실행 환경을 만드는 편이 낫습니다. 작업 로그를 기록하는 도구를 설계하는 대신, 파일 읽기/쓰기 도구를 제공하고 Agent를 위한 가상 파일 시스템을 만드는 편이 낫습니다. 범용적인 도구는 Agent가 기초 능력을 조합해 창의적으로 문제를 해결할 수 있게 해줍니다.

### LLM: Agent의 뇌

대형 언어 모델(Large Language Model, LLM)은 Agent의 의사결정 핵심입니다. 사용자의 요청을 받으면, 먼저 진짜 의도를 파악해야 합니다(사용자가 말한 것이 종종 그가 진짜로 원하는 것이 아닙니다). 그런 다음 모호하거나 복잡한 작업을 실행 가능한 단계로 분해합니다. 실행 과정에서도 계속 판단을 내려야 합니다: 다음에 무엇을 해야 하는지, 도구를 호출해야 하는지, 어떤 도구를 호출할지, 어떤 파라미터를 전달할지. 이런 "이해-계획-실행" 능력은 사전훈련을 통해 축적된 지식에서 나오며, 워크플로우와 자율 Agent 모두가 의존하는 기반입니다.

LLM Agent의 독특한 능력 하나는 **내부 사고**입니다—실제 행동을 취하기 전에 Agent는 먼저 계획과 추론을 진행할 수 있습니다. 이 과정은 외부 환경을 바꾸지 않지만, 이후 행동의 품질을 크게 끌어올릴 수 있습니다. LLM이 효과적인 내부 추론을 할 수 있는 것은 사전훈련(Pre-training, 즉 방대한 인터넷 텍스트로 초기 훈련을 진행해 모델이 언어 규칙과 세계 지식을 익히도록 하는 것) 단계에서 습득한 능력 덕분입니다—모델이 추론할 때 따르는 것은 인간 지식 속에 이미 쌓여 있는 논리 규칙으로, 수학 법칙, 인과관계, 문제 분해 전략 등을 포함합니다. 따라서 Agent의 추론은 맹목적인 무작위 탐색이 아니라, 구조화된 지식 체계 위에서 펼쳐집니다.

이런 구조화된 추론 능력 덕분에 LLM Agent는 완전히 새로운 작업을 마주해도 바로 손댈 수 있습니다—아래에서 제로샷과 퓨샷이라는 두 개념으로 각각 설명합니다. 이 능력이 직접적으로 드러나는 것이 **제로샷 일반화**(Zero-shot Generalization)입니다: 한 번도 본 적 없는 작업이라도 LLM Agent는 기존 지식을 조합해 처리할 수 있으며, 어떤 예시도 필요하지 않습니다. 예를 들어 양자물리학에 관한 시를 쓰라고 가르친 적이 없어도, 기존의 언어 지식과 물리 지식을 바탕으로 그럴듯한 작품을 생성할 수 있습니다.

한 걸음 더 나아가, LLM Agent는 극소수의 예시만으로도 **퓨샷 적응**(Few-shot Adaptation)을 이룰 수 있습니다—프롬프트에 두세 개의 시범 예시만 제시해도 모델은 새로운 작업 패턴을 습득할 수 있습니다. 예를 들어 "사용자 리뷰 → 감정 라벨" 예시 몇 개를 보여주면, 새로운 리뷰에 대해서도 감정 분류를 할 수 있게 됩니다. 간단히 말해 제로샷은 "예시가 없어도 할 수 있는 것"이고, 퓨샷은 "몇 개의 예시만 보면 배울 수 있는 것"입니다.

#### 모델 자체가 Agent: 모델 자체가 제품이 될 때

"모델 자체가 Agent"(Model as Agent)라는 새로운 패러다임은 AI Agent 발전의 최신 방향을 대표합니다. 선진 모델들은 후훈련(특히 강화학습)을 통해 도구 호출 능력을 네이티브 능력으로 내재화합니다: 언제 도구를 호출할지, 어떤 것을 호출할지, 어떤 파라미터를 전달할지 모두 모델 스스로 결정하며, 사람이 편성(orchestration)할 필요가 없습니다. 하지만 이것이 프레임워크 계층이 덜 중요해졌다는 뜻은 아닙니다. 오히려 정반대입니다. 모델이 강력해질수록 모델을 둘러싼 Harness는 더욱 핵심적이 됩니다. Harness라는 단어는 원래 마구(馬具), 즉 말에 씌우는 고삐와 마구를 가리키며, 말의 질주 능력을 제한하기 위한 것이 아니라 그 힘을 올바른 방향으로 이끌기 위한 것입니다. Agent의 맥락으로 옮기면, 모델은 강력하지만 예측 불가능한 말이고, Harness는 그 능력을 신뢰할 수 있는 작업 실행으로 이끄는 엔지니어링 외피입니다. 레이서 주위의 안전 시스템 전체—안전벨트, 트랙 가드레일, 피트 스톱 팀—를 떠올려도 좋습니다. 레이서(모델)가 빠를수록 이 시스템은 더 중요해집니다. Agent에서 Harness는 컨텍스트 관리, 도구 인터페이스, 안전 제약, 검증과 교정 등의 인프라를 포함합니다(이 장 말미에서 자세히 다룹니다).

모델의 자율 결정 공간이 클수록 실수했을 때의 영향 범위도 커지므로, 신뢰성을 보장하기 위해 더 정교한 제약, 검증, 교정 메커니즘이 필요합니다. 모델 제공사의 진짜 우위는 "프레임워크를 얇게 만드는 것"이 아니라, 모델과 주변 Harness를 함께 최적화하며 지속적으로 반복할 수 있다는 데 있습니다.

하지만 여기에는 더 근본적인 질문이 걸려 있습니다: 모델이 계속 강해진다면, 오늘의 이런 Harness들은 결국 모델에 "먹혀버리는" 것 아닐까요? Rich Sutton은 《쓰라린 교훈》(The Bitter Lesson)에서 AI 연구 70년 동안 반복되어 온 한 장면을 돌아봅니다[^ch1-1]: 연구자들은 자신이 그 영역에 대해 이해한 바를 시스템에 코딩해 넣기를 거듭했고, 단기적으로는 효과가 있었지만, 장기적으로는 계산량과 데이터 규모 확장에 따라 지속적으로 성장할 수 있는 범용적 방법—탐색과 학습—에 늘 밀렸습니다. 이 기준으로 보면, Harness 안의 제약, 검증, 교정 중 얼마만큼이 "사람의 사전 지식"에 속하며, 결국 모델에 내재화될 운명인 걸까요? 이 책의 입장은 여덟 글자로 요약됩니다: **방향에는 동의하되, 리듬은 현실적으로**. 방향에서는 모델이 지속적으로 Harness를 흡수해 갈 것이라는 점을 이 책은 의심하지 않습니다—도구 호출, 장기 계획은 한때 모두 외부 편성에 의존했지만, 지금은 이미 모델의 네이티브 능력이 되었습니다. 그러나 리듬에서는 이 "흡수"가 직관보다 훨씬 느립니다: 훈련은 개월 단위로 이루어지고, 모델은 실제 비즈니스의 모든 제약과 선호를 한 번에 내재화할 수 없습니다. 모델이 지금 이 순간 가진 능력의 한계가 바로 Harness가 지금 이 순간 갖는 가치입니다. 따라서 Harness 엔지니어링은 쓰라린 교훈에 대한 저항이 아니라, 이 교훈을 엔지니어링 시간 척도에서 실천하는 것입니다: 모델이 아직 안정적으로 해내지 못하는 것은 Harness가 먼저 보완하고, 모델이 한 층을 내재화할 때마다 Harness는 그 층을 내려놓고 새로운 능력의 프런티어를 대신 감당합니다. 이 흐름은 책 전체를 관통합니다—제2장은 컨텍스트 엔지니어링의 관점에서 현실적인 답을 제시하고, 제8장은 Agent가 스스로 지식과 능력의 구조를 발견하는 방법을 논의하며, 후기에서는 "모델이 Harness를 흡수할 것인가"라는 질문에 대한 완전한 답으로 다시 돌아옵니다.

[^ch1-1]: Sutton, Rich. "The Bitter Lesson", 2019. http://www.incompletenessideas.net/IncIdeas/BitterLesson.html

#### Agent의 학습 메커니즘: 후훈련, 컨텍스트 내 학습, 외부화 학습

앞에서는 모델이 강화학습을 통해 도구 호출의 의사결정 전략을 네이티브 능력으로 내재화하는 과정을 논의했습니다. 하지만 Agent의 학습은 훈련 단계에서만 일어나는 것이 아닙니다—일부 독자는 Agent가 경험으로부터 학습한다고 하면 반드시 모델을 훈련시켜야 한다고 생각합니다. 사실 후훈련은 Agent가 경험으로부터 학습하는 유일한 방법이 아닙니다. Agent의 학습 메커니즘은 서로 보완적인 세 가지 패러다임으로 정리할 수 있습니다(그림 1-1).

![그림1-1 Agent의 세 가지 학습 패러다임](images/fig1-1.svg)

- **후훈련(Post-training)**: 강화학습을 통해 경험을 모델의 파라미터에 굳혀 넣으며, 가장 강력한 작업 간 범용성을 제공하지만 업데이트 비용이 높습니다(자세한 내용은 제7장).
- **컨텍스트 내 학습(In-Context Learning)**: 어텐션 메커니즘(Attention Mechanism, 즉 모델이 입력을 처리할 때 "어떤 정보에 주목할지"를 결정하는 메커니즘)을 통해 컨텍스트 안에서 패턴 검색식의 빠른 적응을 수행합니다. 예를 들어 프롬프트에 고객 상담 대화 처리 예시 몇 개(예: "사용자 불만 → 위로+보상안")를 보여주면, 비슷한 방식으로 새로운 고객 상담 대화를 처리할 수 있습니다—이것이 컨텍스트 내 학습입니다. 빠르게 적응할 수 있지만 일시적이어서, 세션이 끝나면 사라집니다. 참고로 이름은 "학습"이지만, 그 내부 메커니즘은 진짜 학습이라기보다는 **패턴 매칭에 더 가깝습니다**. 비유하자면: 동일한 유형의 수학 문제 세 개와 답을 보여준 다음 네 번째 문제를 준다면, 여러분은 대체로 그대로 흉내 내서 풀 수 있을 것입니다—이것이 바로 컨텍스트 내 학습이 하는 일입니다. 하지만 네 번째 문제가 완전히 새로운 풀이 사고를 필요로 한다면, 앞의 세 문제 답만 보는 것으로는 부족합니다. 다시 말해 컨텍스트 내 학습은 모델이 **이미 본 패턴을 적용**하게 해주지만, **완전히 새로운 규칙을 발견**하게 해주지는 못합니다—이는 후훈련과 본질적으로 다른 점입니다(제2장에서 어텐션 메커니즘의 관점으로 이 논지를 자세히 전개합니다).
- **외부화 학습(Externalized Learning)**: 지식과 절차를 지식베이스와 실행 가능한 도구 코드로 외부화하여, 지속성과 설명 가능성을 함께 갖춥니다.

이 세 가지 패러다임은 서로 다른 시간 척도에서 상호 보완적입니다: 후훈련은 기초 능력을 제공하고, 컨텍스트 내 학습은 빠른 적응을 실현하며, 외부화 학습은 신뢰성과 효율을 보장합니다. 제8장에서 세 가지 패러다임의 협력 관계를 체계적으로 비교합니다.

비유하자면: 후훈련은 교과서를 체계적으로 학습하는 것과 같습니다—다 배우고 나면 능력이 영구히 향상되지만 학습 비용이 높습니다. 컨텍스트 내 학습은 즉석에서 참고 자료를 찾아보는 것과 같습니다—자료가 있으면 잘할 수 있지만 덮으면 잊어버립니다. 외부화 학습은 개인 노트를 정리하는 것과 같습니다—정보가 영구히 보존되고 언제든 조회할 수 있지만, 전문적인 정리가 필요합니다.

### 컨텍스트: Agent의 눈

컨텍스트는 Agent가 매 결정 시점에 볼 수 있는 모든 정보입니다. 사람이 결정을 내릴 때 책상 위에 펼쳐진 모든 자료—작업 설명, 참고 매뉴얼, 이전 소통 기록, 최신 데이터—를 봐야 하듯, Agent의 컨텍스트 윈도우는 바로 그것의 "시야"입니다. API의 관점에서 보면(자세한 내용은 제2장), LLM을 호출할 때마다의 컨텍스트는 다음 다섯 부분으로 구성됩니다.

- **시스템 프롬프트**(System Prompt): 사용자가 매번 입력하는 프롬프트와 달리, 시스템 프롬프트는 개발자가 작성하며 대화 전 과정에서 변하지 않습니다. Agent의 "업무 안내서"와 같습니다—그것의 정체성, 권한, 행동 원칙을 정의합니다. 프롬프트 엔지니어링(Prompt Engineering)을 통해 시스템 프롬프트를 정교하게 설계함으로써 우리는 Agent의 작업 방식을 빚어낼 수 있습니다. 시스템 프롬프트에는 세션을 넘나들며 저장되는 **사용자 메모리**(사용자 선호, 이력 행동, 배경 설정 등 개인화 정보, 자세한 내용은 제3장)와 동적으로 주입되는 환경 상태도 포함됩니다.
- **도구 정의**(Tool Definitions): Agent가 사용 가능한 도구의 이름, 기능 설명, 파라미터 형식을 선언합니다. 도구 정의가 없으면 Agent는 어떤 도구도 인식하거나 호출할 수 없습니다—소거 실험(실험 1-1)이 이를 검증할 것입니다. 도구 정의는 시스템 프롬프트와 함께 대화 내내 변하지 않는 **정적 프리픽스**를 구성합니다(이는 기본 패턴입니다. 2026년 이후 프로덕션 프레임워크에서는 도구의 완전한 스키마를 프리픽스를 깨뜨리지 않고 컨텍스트 말미에 온디맨드로 동적 로딩할 수도 있습니다. 자세한 내용은 제2장의 도구 정의 절과 제4장 참고).
- **사용자 메시지**(User Messages): 사용자로부터의 입력입니다. 사용자 메시지에는 RAG(검색 증강 생성, Retrieval-Augmented Generation, 자세한 내용은 제3장)를 통해 동적으로 검색되어 도입된 **외부 지식**도 포함될 수 있습니다—훈련 데이터 마감 이후의 정보나 사설 도메인 지식을 다룹니다.
- **모델 응답**(Assistant Messages): 모델이 이전에 생성한 응답으로, 최대 세 부분으로 구성됩니다—사고 과정(`reasoning`, 즉 내부 사고 사슬로, 사고의 일관성과 의사결정의 설명 가능성을 유지), 텍스트 내용(`content`, 즉 사용자에 대한 응답), 도구 호출 요청(`tool_calls`, 즉 Agent가 행동을 취하는 방식). 하나의 구체적인 응답에서 세 가지가 반드시 동시에 나타나는 것은 아닙니다: 예를 들어 Agent가 도구를 호출하기로 결정할 때는 보통 `reasoning` + `tool_calls`만 있고, 최종 답을 낼 때는 보통 `reasoning` + `content`만 있습니다.
- **도구 실행 결과**(Tool Results): Agent 프레임워크가 도구를 실행한 후 반환한 결과입니다. 이 결과들은 Agent가 다음 사고를 진행하는 직접적인 근거이며, 실행 결과로부터 배우고 반복된 실수를 피할 수 있게 해줍니다.

앞의 두 항목(시스템 프롬프트 + 도구 정의)은 정적 프리픽스이고, 뒤의 세 항목(사용자 메시지 + 모델 응답 + 도구 실행 결과)은 상호작용에 따라 계속 늘어나는 동적 메시지 이력입니다. 이 다섯 부분이 함께 LLM이 매번 추론할 때의 컨텍스트를 구성합니다.

각 구성 요소가 정말로 필수적인지 검증하는 가장 직접적인 방법은 **소거 실험**(Ablation Study)입니다: 의사가 진단할 때 병인을 하나씩 배제해 가듯이—먼저 A 구성 요소를 빼서 시스템이 여전히 정상인지 보고, 그다음 B 구성 요소를 빼는 식으로 각 구성 요소의 기여도를 판단합니다. 실험 1-1은 정확히 이런 사고방식으로 위 다섯 구성 요소에 대해 체계적인 테스트를 진행했고, 결과는 다음과 같습니다: 도구 정의를 빼면 Agent는 행동 능력을 완전히 상실합니다. 도구 실행 결과가 없으면 이전 단계의 피드백을 볼 수 없어 Agent가 같은 도구를 반복 호출하며 무한 루프에 빠집니다. 모델 응답 중 사고 과정이 제거되면 전후 결정이 서로 모순되기 시작합니다. 이력 메시지의 경우, 그것이 없으면 Agent는 기억을 잃은 것과 같아서 작업 흐름 전체를 처음부터 다시 시작하며 이미 완료한 단계를 반복 실행합니다. 각 구성 요소의 역할은 이론적 추론이 아니라 실험적 증거로 뒷받침됩니다.

### 실험 1-1 ★★: 컨텍스트의 핵심 역할

체계적인 **소거 실험**(Ablation Study)을 통해, 우리는 서로 다른 컨텍스트 구성 요소가 Agent 행동에 미치는 영향을 탐구했습니다. 실험은 위 다섯 부분 중 네 개의 구성 요소를 골라 테스트했습니다—시스템 프롬프트는 Agent의 기본 정체성 정의이므로 소거 대상에서 제외했습니다. 시스템 프롬프트가 없으면 Agent는 기본적인 역할 인지조차 없어서 테스트할 의미가 없기 때문입니다. 그림 1-2에서 보듯, 다섯 개의 대조 실험은 모든 구성 요소를 유지하는 완전한 기준선 하나와, 각각 하나의 구성 요소가 빠진 네 개의 대조군으로 이루어져, 이를 통해 각 구성 요소가 Agent 성능에 미치는 영향을 관찰합니다.

![그림1-2 실험 1-1—컨텍스트 소거 실험 설계](images/fig1-2.svg)

실험 결과는 각 컨텍스트 구성 요소가 대체 불가능한 역할을 한다는 것을 드러냈습니다. **도구 정의**(Tool Definitions, 정적 프리픽스의 일부)는 Agent의 행동 능력의 기초이며, 이것이 없으면 Agent는 어떤 도구도 인식하거나 호출할 수 없습니다. **도구 실행 결과**(Tool Results)는 폐루프 제어의 핵심이며, 이것이 빠지면 Agent가 "맹목적으로" 실행해 무한 루프에 빠지게 됩니다. **사고 과정**(모델 응답 중 reasoning 부분)은 Agent가 이전 결정을 내린 이유를 보존해 사고 흐름을 더 일관되게 유지하고, 전후 모순된 결정을 피하게 해줍니다. **이력 메시지**(이전 라운드의 사용자 메시지, 모델 응답, 도구 실행 결과)는 불필요한 조작을 방지하고 작업 실행의 일관성을 유지하며, 같은 실수를 반복하는 것을 막습니다.

이 실험의 핵심 통찰은 이것입니다: **컨텍스트가 Agent가 무엇을 볼 수 있는지를 결정하며, Agent는 오직 자신이 본 정보를 바탕으로만 결정을 내릴 수 있습니다.** 사람이 눈을 가리면 합리적인 판단을 내릴 수 없는 것처럼, 어떤 컨텍스트 구성 요소가 빠지든 Agent의 의사결정 능력은 심각하게 퇴화합니다—도구 정의를 못 보면 어떤 도구를 쓸 수 있는지 모르고, 이전 실행 결과를 못 보면 이미 무엇을 했는지 모릅니다.

### ReAct 순환

Agent의 세 가지 핵심 구성 요소를 이해했다면, 자연스러운 질문은 이것입니다: 이들은 어떻게 협업할까요? ReAct 순환이 바로 LLM, 컨텍스트, 도구를 하나로 엮는 핵심 메커니즘입니다—Agent가 어떻게 한 걸음씩 사고하고 행동하는지 살펴봅시다.

Agent가 작업을 실행하는 핵심 패턴을 **ReAct**(Reasoning + Acting)라고 부릅니다. 이름에는 사고(Reasoning)와 행동(Acting) 두 단어만 담겨 있지만, 실제 순환에는 세 단계가 포함됩니다: 모델이 먼저 현재 무엇을 해야 하는지 **사고**하고, 도구를 호출해 **행동**하며, 다시 도구가 반환한 결과를 **관찰**하고 다음 단계를 계속 사고합니다. 이 "생각→실행→관찰→생각→실행→관찰"의 순환이 작업이 완료될 때까지 계속 반복됩니다.

다국통화 수입 집계라는 구체적인 예시를 통해 Agent의 **궤적**(trajectory)을 이해해 봅시다. 궤적이란 Agent가 작업을 실행하는 과정에서 계속 누적하는 메시지 이력입니다—사용자 메시지, 모델 응답(사고 과정과 도구 호출 포함), 도구 실행 결과. LLM을 호출할 때마다 그것이 받는 완전한 컨텍스트는 **정적 프리픽스**(시스템 프롬프트 + 도구 정의)와 **궤적**(동적 메시지 이력) 두 부분으로 구성됩니다(그림 1-3). 이는 핵심적인 사실 하나를 드러냅니다: **Agent의 컨텍스트 = 정적 프리픽스 + 궤적**. 구체적으로 말하면, 정적 프리픽스는 앞서 말한 다섯 구성 요소 중 앞의 두 항목(시스템 프롬프트 + 도구 정의)에 대응하고, 궤적은 뒤의 세 항목(사용자 메시지 + 모델 응답 + 도구 실행 결과, 상호작용에 따라 계속 늘어남)에 대응합니다. 이 완전한 컨텍스트를 바탕으로 LLM이 다음 단계의 응답을 생성하고, 이 응답은 다시 궤적에 추가되어 다음 호출에 사용됩니다.

![그림1-3 Agent 궤적—다국통화 집계 작업의 ReAct 순환](images/fig1-3.svg)

의사코드를 통해 Agent 궤적의 구조를 이해해 봅시다.

```
궤적 = [
  {role: "user" , content: "회사 분기별 수입에 따라: 1분기 250만 달러, 2분기 210만 유로, 3분기 180만 파운드, 4분기 3.8억 엔, 회사의 연간 총수입과 분기 평균 수입을 계산하라" },
  
  # 첫 번째 반복 - LLM이 위 궤적을 보고 응답 생성
  {role: "assistant" , 
   reasoning: "모든 통화를 USD로 환산해야 함..." ,
   content: "" ,  # 사용자에게 직접 응답하지 않음
   tool_calls: [
     {name: "convert_currency" , args: {amount: 2100000, from: "EUR" , to: "USD" }},
     {name: "convert_currency" , args: {amount: 1800000, from: "GBP" , to: "USD" }},
     {name: "convert_currency" , args: {amount: 380000000, from: "JPY" , to: "USD" }}
   ]},
  
  # Agent 프레임워크가 도구를 실행하고, 결과를 궤적에 추가
  {role: "tool" , content: "EUR->USD: 2282608.7" },
  {role: "tool" , content: "GBP->USD: 2278481.01" },
  {role: "tool" , content: "JPY->USD: 2541806.02" },
  
  # 두 번째 반복 - LLM이 도구 결과를 포함한 완전한 궤적을 봄
  {role: "assistant" ,
   reasoning: "환산 결과를 얻었으니, 이제 집계 계산이 필요함..." ,
   content: "" ,
   tool_calls: [
     {name: "code_interpreter" , args: {code: "total = 2500000 + 2282608.7 + ..." }}
   ]},
  
  {role: "tool" , content: "Total: $9,602,895.73, Average: $2,400,723.93..." },
  
  # 세 번째 반복 - LLM이 완전한 궤적을 보고 최종 답 생성
  {role: "assistant" ,
   reasoning: "모든 계산이 완료됨, 결과를 정리..." ,
   content: "FINAL ANSWER: 총수입 $9,602,895.73..." }
]
```

궤적 안에는 시스템 프롬프트와 도구 정의가 표시되지 않는다는 점에 유의하십시오—이들은 정적 프리픽스로서, LLM을 호출할 때마다 자동으로 궤적 앞에 붙습니다.

우리 실험에서 이 순환은 매우 뚜렷하게 나타났습니다. 첫 번째 라운드에서 Agent는 작업을 분석한 뒤 세 개의 통화 환산 도구를 병렬로 호출했습니다. 두 번째 라운드에서는 환산 결과를 바탕으로 코드 인터프리터를 호출해 복잡한 계산을 수행했습니다. 세 번째 라운드에서는 모든 계산이 완료됐음을 확인한 뒤 최종 답을 생성했습니다. 전체 과정은 단 3번의 반복, 4번의 도구 호출만으로 복잡한 다단계 작업을 완수했습니다.

이 설계의 정교함은 **컨텍스트의 누적성**에 있습니다. LLM을 호출할 때마다 완전한 궤적을 볼 수 있으므로, 지금 작업의 어느 단계에 있는지, 이전에 무엇을 시도했는지, 어떤 결과를 얻었는지를 이해할 수 있습니다. 사람이 문제를 해결할 때 끊임없이 돌아보고 정리하는 것처럼, Agent는 궤적을 통해 작업 전체에 대한 전역적 인지를 유지합니다. 동시에 궤적의 구조화된 특성은 시스템에 높은 설명 가능성과 디버깅 가능성을 부여합니다: 사용자 메시지, 모델 응답(사고 과정 + 도구 호출), 도구 실행 결과가 모두 명확히 구분됩니다.

궤적은 단순히 실행 기록이 아니라, Agent 능력의 구현이기도 합니다. 대량의 궤적을 분석함으로써 우리는 Agent의 행동 패턴을 발견하고, 결정 경로를 최적화하며, 도구 설계를 개선할 수 있습니다. 궤적 데이터는 지식베이스에 정리해 넣거나, 강화학습을 통해 더 나은 Agent 모델을 훈련하는 데도 쓸 수 있어, 경험으로부터 학습하는 폐루프 최적화를 실현합니다.


Agent의 실행 순환을 이해했으니, 두 개의 실험을 통해 서로 다른 모델이 이 순환을 어떻게 구동하는지 느껴봅시다.

#### 실험 1-2 ★: Kimi K3 네이티브 Agent 능력

이 실험은 **Kimi K3**의 네이티브 Agent 능력을 보여주며, "모델 자체가 Agent"라는 새로운 패러다임을 구현합니다. Kimi K3는 Moonshot AI가 2026년에 발표한, 약 2.8조 파라미터의 혼합 전문가(MoE, Mixture of Experts) 모델입니다—MoE는 전문가 팀으로 떠올려도 좋습니다: 서로 다른 유형의 문제를 마주할 때 시스템이 자동으로 가장 적합한 몇몇 전문가를 골라 답하게 하며, 모든 전문가가 동시에 나설 필요가 없어 능력과 효율을 동시에 보장합니다. 이 모델은 100만 토큰의 컨텍스트 윈도우, 네이티브 시각 이해 능력, 그리고 항상 켜져 있는 "사고 모드"(thinking mode)를 갖추고 있습니다. 모델은 강화학습을 통해 훈련되어 도구 호출의 **의사결정 전략**을 네이티브 능력으로 내재화합니다—언제 도구를 호출할지, 어떤 것을 호출할지, 어떤 파라미터를 전달할지 모두 모델이 스스로 결정하여, 웹 검색 등의 작업을 자율적으로 완수할 수 있습니다. 참고로 내재화된 것은 "언제 호출할지, 어떻게 호출할지"에 대한 결정이며, `web_search`, `code_runner` 등 도구 자체는 여전히 API 층위의 내장 도구로서 서버 측에서 실행됩니다(Kimi는 Formula라는 서버 측 스크립트 엔진을 통해 이런 공식 도구들을 실행합니다).

핵심 관찰 사항은 다음과 같습니다: 모델이 RL 훈련을 통해 자연스럽게 언제, 어떻게 도구를 쓸지 익혔기 때문에, 클라이언트는 더 이상 도구 호출 편성 로직을 수작업으로 작성할 필요가 없습니다. 모델이 스스로 언제 검색할지, 무엇을 검색할지 결정함으로써 진정한 자율성을 보여줍니다. 검색 결과에 따라 전략을 동적으로 조정하고, 정보가 충분한지 스스로 판단할 수 있습니다. 여기서 흔한 오해 하나를 짚고 넘어가야 합니다. 핵심은 두 가지 일의 귀속을 명확히 구분하는 것입니다. **강화학습이 모델에게 부여하는 것은 의사결정 능력**입니다—언제 도구를 호출해야 하는지, 어떤 것을 호출할지, 어떤 파라미터를 넣을지, 결과를 받은 뒤 계속할지, 수십에서 수백 번의 호출을 어떻게 일관된 추론으로 엮을지, 이런 "쓸지 말지, 어떻게 쓸지"의 판단이 모델 파라미터에 새겨집니다. **반면 도구 자체와 그 실행은 Agent 프레임워크(또는 API 내장 도구)가 제공**합니다—`web_search`, `code_runner`의 실제 구현, 코드 샌드박스 환경, 호출의 발신과 결과 회신은 모두 모델 바깥의 인프라에서 이루어집니다. RL이 최적화하는 것은 의사결정 전략이지, 검색 엔진이나 코드 샌드박스를 모델의 가중치 "안에 집어넣는" 것이 아닙니다. 따라서 편성 순환이 사라진 것이 아니라, 클라이언트에서 서버 측으로 옮겨간 것이며, 동시에 결정권이 모델에게 넘어간 것입니다[^ch1-2].

[^ch1-2]: 독자 asdlem 님이 GitHub Issue #30을 통해 "RL이 내재화하는 것은 도구 호출 의사결정 전략이지, 도구 실행 메커니즘이 아니다"라는 구분을 지적하고 명확히 해주신 데 감사드립니다. https://github.com/bojieli/ai-agent-book/issues/30 참고

Kimi K3가 Agent 작업에서 보여주는 두드러진 강점 하나는 **긴 도구 호출 사슬에서의 안정성**입니다—200~300회의 도구 호출을 연속으로 실행하면서도 사고의 일관성을 유지할 수 있으며, 이는 수십 회의 호출 이후 성능이 저하되기 시작하는 대부분의 모델보다 훨씬 뛰어납니다. K3는 장주기 코딩과 Agent 워크로드에 맞춰 최적화되었으며, 발표 시점에 K3 Max(대화와 Agent 작업 지향)와 K3 Swarm Max(대규모 병렬 처리 지향) 두 가지 사양을 제공합니다. 오픈소스 모델로서 소프트웨어 엔지니어링과 Agent 벤치마크 테스트에서 최상위 폐쇄형 시스템과 견줄 만한 성능을 보여주었으며, 강화학습을 통해 모델에 네이티브 Agent 능력을 부여하는 노선의 효과를 입증했습니다.

#### 실험 1-3 ★: GPT-5.6 네이티브 Deep Research 능력

두 번째 실험은 **OpenAI GPT-5.6**을 사용해, 선진 모델이 API 내장 도구를 활용해 서버 측에서 Deep Research의 "검색—읽기—분석" 편성 순환을 어떻게 폐루프로 완결하는지 보여줍니다. GPT-5.6은 세 가지 사양—Sol(플래그십 최전선 모델), Terra(일상 업무 지향의 균형 잡힌 모델), Luna(빠르고 경제적인 경량 모델)—을 제공하며, 모두 도구 호출 결정을 모델이 네이티브로 완수하도록 하여 클라이언트가 스스로 편성 프레임워크를 구축할 필요가 없습니다. 편리한 특성 하나는 **자유 형식 도구 호출**(Freeform Tool Calling)입니다—전통적인 방식에서는 모델이 도구를 호출할 때 모든 파라미터를 엄격한 JSON 형식(구조화된 데이터 형식)으로 패키징해야 했는데, 이는 마치 양식을 작성하듯 여러 형식 제약이 있었습니다. 자유 형식 도구 호출(API에서는 `type: "custom"` 도구 유형으로 선언)은 모델이 원시 텍스트(예를 들어 Python 코드 한 조각, SQL 쿼리 한 줄)를 도구에 직접 보낼 수 있게 해, JSON 이스케이프의 번거로움을 없애줍니다. 참고로 이는 API 파라미터 형식의 진화이지, 모델 아키텍처의 혁신은 아닙니다—클라이언트의 도구 호출 순환(`tool_calls` 감지 → 실행 → 결과 회신) 로직은 그대로 유지되며, 바뀐 것은 파라미터가 JSON 문자열에서 원시 텍스트로 바뀌었다는 점뿐입니다. GPT-5.6은 또한 Verbosity 파라미터(출력의 상세 정도를 제어)와 Reasoning Effort 파라미터(사고의 깊이를 조정하며, Sol에는 가장 충분한 추론 시간을 얻기 위한 max 등급이 추가됨)를 도입해, 개발자가 작업 복잡도에 따라 모델 행동을 정밀하게 제어할 수 있게 했습니다.

GPT-5.6은 Responses API의 **웹 검색과 코드 인터프리터** 내장 도구와 결합됩니다—이것이 바로 Deep Research의 핵심입니다: 모델이 스스로 웹을 검색해 실시간 정보를 얻고, 코드를 작성해 심층 분석을 수행함으로써 "검색 → 읽기 → 분석 → 재검색"의 반복적 연구 과정을 실현합니다. 예를 들어 "아세안 10개국 수도 간, 가장 가까운 수도 쌍의 거리는 얼마인가"와 같은 질문을 마주하면, GPT-5.6은 자동으로 각국 수도의 지리 좌표를 검색한 뒤 Python 코드를 작성해 모든 수도 쌍 사이의 대원 거리를 계산하고, 최종적으로 가장 가까운 쌍을 찾아냅니다. 또는 "최근 한 달간의 비트코인 추세를 검색해 기술적 분석을 하라"는 작업에서는, 여러 금융 데이터 소스에서 실시간 가격 데이터를 얻고, 전문적인 기술 분석 라이브러리를 활용해 이동평균선, RSI, MACD 등 기술 지표를 계산하며, 시각화 차트를 생성하고 거래 제안을 내놓을 수 있습니다.

더 중요한 것은, GPT-5.6이 **OpenAI Deep Research** 제품의 설계 철학을 모델 층위로 내재화하여 **의도 명확화 과정**을 도입했다는 점입니다. 사용자가 연구 요청을 제시하면, GPT-5.6은 곧바로 실행에 나서지 않고 먼저 일련의 질문을 통해 사용자의 진짜 의도를 명확히 합니다. "최근 한 달간의 비트코인 추세를 검색해 기술적 분석을 하라"를 예로 들면, 먼저 이렇게 물을 것입니다: "어떤 데이터 소스를 선호하시나요? 어떤 기술 지표를 분석해야 하나요?" 이런 상호작용식 의도 명확화를 통해 GPT-5.6은 더 정밀하고 사용자 요구에 부합하는 연구 보고서를 생성할 수 있습니다.

GPT-5.6은 "모델 자체가 Agent" 개념의 성숙한 사례입니다—웹 검색, 코드 인터프리터 등이 Responses API의 내장 도구로서 서버 측에서 폐루프로 실행되며, 편성 순환이 클라이언트에서 API 서버 측으로 옮겨가면서 클라이언트 구현이 단순해졌습니다. 모델은 여전히 표준적인 도구 호출을 출력하며, 클라이언트는 더 이상 "검색—읽기—분석"의 편성 프레임워크를 스스로 구축할 필요가 없습니다. 그중 가장 주목할 만한 것은 의도 명확화 메커니즘입니다: 모델은 작업을 받자마자 곧바로 실행하지 않고, 먼저 질문을 통해 사용자의 진짜 요구를 확인한 뒤 연구 전략을 세웁니다. 이는 "사용자가 말한 것"과 "사용자가 진짜로 원하는 것" 사이의 간극을 작업 실행 이전에 메워줍니다.

## Harness 엔지니어링: 모델 밖의 경쟁력

여기까지 왔다면 Agent의 핵심 작동 원리—LLM이 ReAct 순환을 통해 컨텍스트의 도움을 받아 도구를 사용해 작업을 완수하는 것—를 이해했을 것입니다. 앞선 실험들은 이 기본 메커니즘이 유효함을 증명했지만, 동시에 뚜렷한 취약점도 드러냈습니다: 모델이 환각을 일으킬 수 있고(존재하지 않는 도구나 파라미터를 지어낼 수 있고), 잘못된 도구를 고를 수 있으며, 오류를 만났을 때 스스로 회복하지 못할 수 있습니다. 실행되는 데모와 신뢰할 수 있는 제품 사이에는 여전히 거대한 간극이 있으며, 이런 취약점들이 바로 Harness 엔지니어링이 해결해야 할 문제입니다. 이 장 전반부는 "Agent란 무엇인가"에 답했고, 후반부는 "Agent가 프로덕션 환경에서 어떻게 신뢰성 있게 작동하는가"에 답합니다.

앞의 여러 절은 **Agent = LLM + 컨텍스트 + 도구**라는 핵심 공식을 세웠습니다. 이 공식은 Agent의 **내부 구성**, 즉 뇌, 눈, 손발을 각각 무엇이 담당하는지를 기술합니다. Harness 엔지니어링의 관점에서 보면, **엔지니어링 구현** 층위의 관점도 필요합니다: LLM을 하나의 핵심 구성 요소(Model)로 취급하고, 그 주위에 구축된 모든 지원 코드를 통틀어 Harness라고 부릅니다. 두 관점은 서로 대체되는 것이 아니라, 서로 다른 추상화 층위에서 동일한 시스템을 기술하는 것입니다. 더 범용적인 "Model"이라는 단어로 바꿔 쓰는 이유는, Harness 엔지니어링의 원칙이 특정 모델 유형에 국한되지 않고, 추론과 도구 호출 능력을 갖춘 어떤 모델에도 적용되기 때문입니다. Harness의 핵심은 원래 공식 속 "컨텍스트 + 도구"에 세 층위의 보장 메커니즘을 더한 것입니다: **제약**(Agent가 무엇을 할 수 있고 할 수 없는지 한정), **검증**(Agent가 제대로 했는지 확인), **교정**(잘못했을 때 어떻게 보완할지).

방정식으로 프로덕션 형태의 완전한 구성을 펼쳐보면 다음과 같습니다.

> **Agent = LLM + [컨텍스트 + 도구 + 제약 + 검증 + 교정] = Model + Harness**

최소한으로 작동하는 Agent는 LLM, 컨텍스트, 도구만 있으면 돌아갑니다. 하지만 그것이 프로덕션 환경에서 장기적으로 신뢰성 있게 작동하려면, 제약, 검증, 교정이라는 세 층위의 엔지니어링 외피를 보완해야 합니다—제약은 선을 넘는 것을 막고, 검증은 오류를 발견하며, 교정은 이상 상태를 회복시킵니다. 이 세 가지 메커니즘은 새로 추가된 "독립 모듈"이 아니라, "컨텍스트 + 도구"를 중심으로 구축된 보장 층위입니다. 다시 말해 최소 공식은 데모의 관점이고, 확장된 공식은 프로덕션의 관점입니다. 후자는 전자를 완전히 포함하면서 그 바깥에 안전망을 한 겹 더한 것입니다.

이해를 돕는 구체적인 예: 컨텍스트에 환불 정책을 심어 두는 것은 "컨텍스트"의 범주이고, 환불 금액이 주문 금액을 넘지 않는지 검증하는 것은 "제약"에 속합니다. 도구가 API 호출을 실행하는 것은 "도구"의 범주이고, API가 타임아웃됐을 때 자동으로 재시도하는 것은 "교정"에 속합니다. 모델은 기초적인 이해와 추론 능력을 제공하고, Harness는 이런 능력을 신뢰할 수 있는 작업 실행으로 이끌고, 제약하고, 증폭시킵니다. 이 모델 밖 인프라를 설계하고 최적화하는 엔지니어링 실천이 바로 **Harness 엔지니어링**(Harness Engineering)입니다.

구체적인 예를 통해 Harness의 가치를 이해해 봅시다. Agent에게 사용자를 위해 3일 전 주문을 환불 처리하게 한다고 가정해 봅시다. **Harness가 없을 때**: 모델은 환불 정책을 볼 수 없고(컨텍스트 부재), 어떤 API를 호출해야 할지 모르며(도구 부재), 환불 결과를 그냥 지어내 사용자에게 응답합니다(검증 부재). 사용자는 환불이 애초에 일어나지 않았다는 것을 발견합니다(교정 부재). **Harness가 있을 때**: 시스템 프롬프트에 7일 환불 정책이 명시되어 있고(컨텍스트), Agent는 `query_order`와 `process_refund` 도구를 호출해 작업을 완수하며(도구), 프레임워크가 환불 금액이 주문 금액을 넘지 않는지 검증하고(제약), 데이터베이스 상태를 검증해 환불 성공을 확인하며(검증), API 호출이 타임아웃되면 자동으로 재시도합니다(교정). 같은 모델이라도, Harness의 유무에 따라 결과는 하늘과 땅 차이입니다.

이 장 앞부분에서 든 마구 비유로 돌아가 보면: Harness가 없는 모델은 고삐 풀린 야생마와 같아서, 능력은 놀랍지만 신뢰성 있게 작업을 완수할 수 없습니다.

더 정확히 말하면, 모델 밖의 모든 인프라가 Harness에 속합니다. Harness의 핵심은 컨텍스트와 도구이며, 이를 중심으로 세 가지 유형의 엔지니어링 보장 메커니즘이 구축됩니다.

| 기능 | 한 줄 책임 | 컨텍스트/도구와의 관계 |
|--------------------|----------------------------------------|-----------------------------------|
| **Context(컨텍스트)** | 모델에 인지 정보를 제공 | 핵심 능력 |
| **Tools(도구)** | 모델에 행동 수단을 제공 | 핵심 능력 |
| **Constrain(제약)** | 행동 경계 설정—무엇을 할 수 있고 할 수 없는지 | 컨텍스트와 도구를 중심으로 구축된 안전 경계 |
| **Verify(검증)** | 조작 결과의 옳고 그름을 자동으로 판단 | 도구 실행 결과를 중심으로 구축된 검사 메커니즘 |
| **Correct(교정)** | 문제 발견 시 자동으로 수정하거나 되돌림 | 도구 호출 실패를 중심으로 구축된 회복 메커니즘 |

컨텍스트와 도구는 Agent가 "일을 할 수 있게" 합니다—작업을 이해하고 행동을 취하게 합니다. 제약, 검증, 교정은 Agent가 "잘못된 일을 하지 않게" 합니다—이들은 컨텍스트와 도구 밖의 독립적인 것이 아니라, 컨텍스트와 도구가 프로덕션 환경에서 신뢰성 있게 작동하도록 보장하는 엔지니어링 실천입니다. Agent 제품의 성숙도 곡선에서 둘의 중요성은 비대칭적입니다.

초창기 Agent 프레임워크는 주로 컨텍스트와 도구에 집중했습니다: 모델에 도구를 주고, 모델에 컨텍스트를 줘서 "일을 할 수 있게" 만드는 것입니다. 반면 프로덕션급 Agent 시스템의 중심은 이미 제약, 검증, 교정으로 옮겨갔습니다: 도구 호출이 안전한지, 컨텍스트가 관리되고 있는지, 오류가 회복 가능한지를 보장하는 것입니다.

Claude Code를 예로 들면, 그 Harness 안에서 절대다수의 코드는 컨텍스트와 도구가 아니라 제약, 검증, 교정입니다—도구 자체(파일 읽기/쓰기, 명령 실행, 검색)는 작은 일부일 뿐이며, 이런 도구를 중심으로 구축된 보장 메커니즘이야말로 진짜 핵심입니다. 이런 메커니즘은 다음을 포함합니다.

- **흐름 상태 관리**: Agent가 현재 어느 단계까지 실행됐는지 추적
- **다층 컨텍스트 압축**: 정보가 너무 많을 때 자동으로 간추림
- **권한 분류**: 어떤 조작이 사용자 확인을 필요로 하는지 제어
- **회로 차단기**(Circuit Breaker): 오류가 연속으로 발생하면 자동으로 "전원을 차단"해 재시도를 멈춤—집안 전기 회로가 합선되면 퓨즈가 자동으로 내려가 시스템 전체 붕괴를 막는 것과 같음
- **오류 회복 메커니즘**: 예외를 포착하고, 이전의 안정된 상태로 롤백하며, 재시도하거나 사람에게 넘김

**업계는 "일을 할 수 있는 것"에서 "신뢰성 있게 일을 하는 것"으로 전환하고 있으며, 이 때문에 Harness 엔지니어링이 Agent 시스템의 핵심 경쟁력이 되고 있습니다.**

### 프롬프트 엔지니어링에서 Loop 엔지니어링까지: 엔지니어링 패러다임의 진화

AI 응용 엔지니어링의 발전을 돌아보면, 뚜렷한 진화의 궤적을 볼 수 있습니다.

**소프트웨어 엔지니어링**(Software Engineering)은 기초입니다—전통적인 시스템 설계, 아키텍처, 테스트, 배포 실천입니다. **프롬프트 엔지니어링**(Prompt Engineering)은 첫 번째 물결입니다—모델에 입력하는 자연어 지시를 최적화해 출력 품질을 끌어올립니다. **컨텍스트 엔지니어링**(Context Engineering)은 두 번째 물결입니다—사람들은 단순히 프롬프트만 최적화하는 것으로는 부족하며, 모델이 볼 수 있는 모든 정보(시스템 지시, 도구 정의, 대화 이력, 외부 지식)를 체계적으로 관리해야 한다는 것을 깨달았습니다. **Harness 엔지니어링**은 세 번째 물결입니다—시야를 "모델이 무엇을 볼 수 있는가"에서 한 걸음 더 나아가 "모델이 어떤 시스템 안에서 작동하는가"로 확장하며, 제약 메커니즘, 검증 수단, 피드백 순환, 오류 회복 등 모델 밖의 모든 인프라를 포괄합니다. 가장 최신의 물결은 **Loop 엔지니어링**(Loop Engineering)입니다—시야를 한 번의 실행에서 여러 라운드에 걸친 지속적인 자율 작동으로 확장합니다: 다음에 해야 할 일을 누가 찾아내는지, 언제 검증하는지, 언제라야 진짜로 완료된 것으로 볼 수 있는지(제10장에서 다중 Agent 협업 시스템과 결합해 자세히 다룹니다).

이 다섯 단계는 서로를 대체하는 관계가 아니라, 겹겹이 포함하는 관계입니다: 프롬프트 엔지니어링은 컨텍스트 엔지니어링의 부분집합이고, 컨텍스트 엔지니어링은 Harness 엔지니어링의 부분집합이며, Harness 엔지니어링은 Loop 엔지니어링의 부분집합입니다. 각 층위는 이전 층위를 기반으로 엔지니어가 신경 써야 할 범위와 영향력을 확장합니다. **각 모델 간의 능력이 점점 비슷해져 더 이상 결정적인 차이 요인이 아니게 될 때, 경쟁 우위는 모델 밖의 엔지니어링 실천으로 옮겨갑니다.** 이 판단은 최근의 엔지니어링 실천에서 검증됐습니다—LangChain이 Terminal Bench 2.0(터미널 환경에서 복잡한 작업을 완수하는 Agent 능력을 평가하는 벤치마크 테스트)에서 보여준 실천이 강력한 예입니다: 그들의 Coding Agent는 52.8%에서 66.5%로 향상됐고(순위표 30위권 밖에서 상위 5위로 도약), 바뀐 것은 모델이 아니라 Harness였습니다: Agent가 스스로 자신의 실행 결과를 검사하게 하고, 반복 루프에 빠졌는지 감지하게 하며, 사고 전략을 최적화하는 등의 엔지니어링 수단이었습니다. OpenAI의 엔지니어링 팀도 비슷한 경험을 공개적으로 공유했습니다—엔지니어 3명이 5개월 만에 약 백만 줄의 코드와 약 1500개의 PR을 완성해, 전통적인 개발 속도의 약 10배에 달했습니다. 이 효율의 배후에는 모델이 얼마나 강한지가 아니라, Harness를 제대로 했다는 사실이 있습니다.

### Harness 다섯 기능의 핵심 원칙

앞의 표는 Harness의 다섯 가지 기능을 나열했습니다. 아래 표는 각 기능의 핵심 설계 원칙과 이 책에서 대응하는 장을 더 자세히 펼쳐서, 독자가 개념에서 실천으로 이어지는 대응 관계를 세울 수 있도록 돕습니다.

| 기능 | 핵심 원칙 | 실제 예 | 참고 |
|------|-----------------------------------------------|-----------------------------------|-------|
| **컨텍스트** | 정보 충분성: Agent가 매 결정 시점에 충분한 정보를 바탕으로 판단하게 함 | 시스템 프롬프트, 지식베이스, Agent 상태 표시줄, Sidecar 우회 조회 | 제2, 3장 |
| **도구** | 인터페이스 명확성: 도구 이름이 직관적이고, 파라미터에 예시가 있으며, 경계가 명시됨 | MCP 도구, 코드 인터프리터, 검색 도구 | 제4장 |
| **제약** | 안전 기본값(fail-safe default): 모든 능력이 기본적으로 꺼져 있고, 명시적으로 열어야 함(휴대폰 앱 권한 관리와 유사) | Claude Code에서 각 도구는 기본적으로 사용자 승인이 있어야 실행됨 | 제4장 |
| **검증** | 입력 격리: 안전 검사는 구조화된 데이터(예: 도구가 반환한 JSON 필드)만 보고, 모델이 자유롭게 생성한 텍스트는 보지 않음(공격자가 프롬프트 인젝션으로 모델 출력을 조작할 수 있기 때문) | 린터 검사, 타입 시스템, 도구 호출 결과 검증 | 제5, 6장 |
| **교정** | 회복 불가능함이 확인되기 전까지는 중간 상태를 노출하지 않음(예: 도구 호출 실패 시 먼저 조용히 재시도하며, 미완성 결과를 사용자에게 보여주지 않음) | 조용한 재시도, 이어서 생성, 연속 실패 시 사람의 판단으로 되돌아감(회로 차단 메커니즘) | 제2, 5장 |

다섯 기능은 하나의 폐루프를 이룹니다: 컨텍스트와 도구가 결정을 뒷받침하고, 제약이 오류를 예방하며, 검증이 편차를 발견하고, 교정이 순환을 닫습니다. 어느 한 단계라도 빠지면 시스템에는 신뢰성 공백이 생깁니다. 구체적인 편성 패턴과 가드레일 설계로 들어가기 전에, 먼저 Agent를 구축하는 핵심 원칙과 모델 선택 전략을 명확히 하겠습니다—이들은 이후 모든 설계 결정의 기초입니다.


### 효과적인 Agent를 구축하는 핵심 원칙

Anthropic의 경험에 따르면, 성공적인 Agent 시스템은 세 가지 핵심 원칙을 따릅니다.

**단순함을 유지하라.** 가장 단순한 방안에서 시작해, 정말로 필요할 때만 복잡도를 더합니다. 직접적인 API 호출이 복잡한 프레임워크보다 낫고, 명확한 코드가 영리한 추상화보다 낫습니다. 추상화 층이 하나 더 생길 때마다 이후 디버깅의 새로운 사각지대가 되기 때문입니다.

**투명함을 유지하라.** Agent의 계획 단계, 실행 로그, 결정 궤적을 명확히 드러냅니다—이는 디버깅 편의를 위한 것만이 아니라, 사용자가 신뢰를 쌓기 위한 전제이기도 합니다. 블랙박스 안에서 오류가 일단 발생하면, 외부 관찰자는 그것을 찾아낼 수도, 바로잡을 수도 없기 때문입니다.

**좋은 도구 인터페이스(ACI, Agent-Computer Interface)를 설계하라.** ACI가 강조하는 것은 Agent의 관점에서 인터페이스를 설계하는 것(Agent가 이해하고 사용하기 쉽게)이지, 전통적인 API처럼 프로그래머의 관점에서 인터페이스를 설계하는 것이 아닙니다. 도구의 이름과 파라미터는 직관적이어야 하고, 오용하기 쉬운 부분은 미리 방지해, 설계 자체로 오류가 발생할 수 없게 해야 합니다—예를 들어 USB 인터페이스는 한 방향으로만 꽂을 수 있어, 사용자가 거꾸로 꽂는 실수를 원천적으로 막습니다. 이런 "설계로 오류를 없애는" 사고방식은 제조업에서 전문 용어로 **포카요케**(Poka-yoke, 실수 방지)라고 불리며, 도요타 생산 방식에서 유래했습니다. 설계가 나쁜 도구는 아무리 강력한 모델이라도 자주 실수하게 만듭니다—모델과 도구 사이의 유일한 소통 통로가 바로 인터페이스 자체이기 때문에, 모호한 인터페이스는 모델에 의해 시스템적인 오류로 증폭됩니다.

아래 세 절은 Harness 엔지니어링에서 독립적이지만 중요한 세 가지 주제를 다룹니다: 모델 선택, 편성 패턴, 가드레일과 안전성. 이들은 모두 Harness 다섯 요소 자체에 속하지는 않지만, 엔지니어링 실천에서 피할 수 없는 결정입니다.

### 모델을 어떻게 선택할 것인가

편성 패턴을 논의하기 전에, 먼저 실무적인 질문 하나에 답해봅시다: Agent를 구동하는 데 어떤 모델을 골라야 할까요?

모델은 Agent의 지능 기반이며, 올바른 모델을 고르는 것이 프롬프트를 최적화하는 것보다 효과적인 경우가 많습니다. 모델의 반복 속도가 매우 빠르기 때문에, 이 절에서는 구체적인 모델 버전을 추천하지 않고 선택의 방향만 제시합니다.

**"빅3"를 알아두세요.** 현재 Agent 개발에서 가장 많이 쓰이는 세 개의 폐쇄형 모델 제공사는 OpenAI(GPT/o 시리즈), Anthropic(Claude 시리즈), Google(Gemini 시리즈)입니다. 각기 강점이 다릅니다: Claude는 복잡한 추론, 코딩, 도구 호출에서 두드러진 성능을 보여, 현재 Agent 개발에서 인기 있는 선택지입니다. Gemini는 초장문 컨텍스트 윈도우와 강력한 멀티모달 능력을 갖춰, 긴 텍스트와 이미지·영상 등 멀티미디어 시나리오에 적합합니다. GPT/o 시리즈는 각 방면의 능력이 고르게 균형 잡혀 있고, 사용자 수가 가장 많습니다. 모델을 고를 때는 순위표만 보지 말고, **여러분 자신의 작업에서 평가**해야 합니다(제6장 참고).

**국내 모델.** 애플리케이션을 특정 지역 내에 배포하거나 엄격한 비용 예산이 있다면, 그 지역의 모델이 현실적인 선택입니다. 예를 들어 두바오 시리즈는 지연 시간이 매우 짧아 실시간 상호작용에 적합합니다. 문지앙(月之暗面)의 Kimi는 Agent 능력이 강한 편이고, Qwen과 DeepSeek 같은 오픈소스 모델은 비용과 커스터마이징 측면에서 우위가 있습니다. 서로 다른 모델은 도구 호출 능력에서 차이가 크므로, 선택 전에 구체적인 시나리오에서 반드시 테스트해야 합니다.

**오픈소스와 폐쇄소스.** 폐쇄형 모델은 보통 능력 면에서 앞서지만, 비용이 높고 제공사의 API 정책에 제약을 받습니다. 오픈소스 모델은 비용이 낮고, 사설 배포가 가능하며, 미세조정 커스터마이징을 지원해, 비용에 민감하거나 데이터 규정 준수 요구가 있는 시나리오에 적합합니다.

**대다수 Agent는 사고(Reasoning)를 지원하는 모델이 필요합니다.** Agent는 다단계 사고, 도구 선택 등 복잡한 의사결정을 수행해야 하므로, 사고 능력이 없는 모델은 이런 작업에서 성능이 대체로 좋지 않습니다. 극소수의 예외적인 시나리오만 있습니다—예를 들어 단일 단계의 단순 작업만 수행하거나, Computer Use에서 고정된 위치를 클릭하는 것만 필요한 단순 GUI 조작 같은 경우입니다. 이런 경우에는 사고 능력이 없는 모델도 감당할 수 있습니다. 하지만 다단계 사고나 동적 결정이 관련되어 있다면, 반드시 사고를 지원하는 모델을 선택해야 합니다.

**출력 속도와 멀티모달 능력에 주목하세요.** 비용 외에도 쉽게 간과되는 두 차원이 있습니다. 하나는 **출력 토큰의 속도**입니다: Agent는 종종 여러 라운드의 추론이 필요하며, 매 라운드마다 모델의 출력이 끝나야 다음 단계를 실행할 수 있으므로, 출력 속도가 종단간 응답 지연 시간을 직접 결정합니다—만약 어떤 Agent 작업이 20라운드의 추론을 필요로 한다면, 각 라운드가 2초씩 느려질 때마다 총 40초를 더 기다려야 합니다. 다른 하나는 **멀티모달 지원**입니다: Agent가 이미지, 오디오, 영상을 이해해야 한다면 멀티모달 능력은 필수 요구사항이며, 이 부분에서 모델 간 차이가 큽니다.


### 편성 패턴: 워크플로우와 자율성

편성 패턴은 Harness 중 "컨텍스트와 도구" 층위의 조직 방식입니다—이것이 컨텍스트가 LLM 호출 사이에서 어떻게 흐르는지, 도구가 어떻게 스케줄링되는지, Agent의 실행 경로가 미리 정해진 것인지 동적으로 생성되는 것인지를 결정합니다. Agent 시스템의 편성 방식은 단순한 것에서 복잡한 것으로 진화해 왔으며, 각 패턴마다 적합한 시나리오와 감안해야 할 트레이드오프가 있습니다. Anthropic이 수십 개 팀과 협업해 LLM Agent를 구축한 경험에 따르면, 가장 성공적인 구현은 복잡한 프레임워크를 쓰는 것이 아니라 단순하고 조합 가능한 패턴을 채택하는 경우가 많았습니다.

LLM 애플리케이션을 구축할 때는 "단순함에서 복잡함으로"라는 원칙을 따라야 합니다: 먼저 단일 LLM 호출을 고려하십시오—프롬프트와 컨텍스트 예시를 최적화하는 것만으로 문제를 해결할 수 있다면, Agent 시스템을 도입하지 마십시오. 다단계 처리가 필요할 때, 고정된 하위 작업들로 명확히 분해할 수 있는 시나리오라면 워크플로우 사용을 고려하십시오. 동적 결정과 유연한 실행 경로가 필요할 때만 자율 Agent를 사용하십시오. 기억해야 할 것은: Agent 시스템은 보통 지연 시간과 비용을 더 나은 작업 성능과 맞바꾸므로, 이 교환이 그럴 만한 가치가 있는지 신중히 저울질해야 합니다.

#### 워크플로우 패턴: 결정론적 편성

**워크플로우**(Workflow)는 미리 정의된 코드 경로를 통해 LLM과 도구를 편성하는 시스템입니다. 그 실행 경로는 결정론적이며, 개발자가 미리 설계해 둡니다—각 단계에서 무엇을 할지, 다음에 어디로 갈지가 모두 코드에 고정되어 있고, LLM은 각 노드 내부에서 이해와 생성만 담당합니다.

항공권 예약 Agent를 예로 들면, 워크플로우는 네 개의 고정 노드로 설계할 수 있습니다.

1. **사용자 신원 확인**——신원 검증 API를 호출해 사용자가 누구인지 확인
2. **가능한 항공편 검색**——사용자 요구에 따라 항공편 데이터베이스를 조회
3. **결제 완료**——결제 인터페이스를 호출해 결제 처리
4. **예약 확정**——예약 API를 호출해 좌석을 잠그고 사용자에게 확인 메시지를 보냄

각 노드 내부에서는 LLM을 사용할 수 있지만(예를 들어 자연어로 사용자의 여행 요구를 이해하는 것), 노드 간의 흐름 순서는 코드로 고정되어 있습니다—시스템은 결제가 끝나기 전에 좌석을 예약하지 않으며, 신원 확인이 끝나기 전에 항공편 검색을 시작하지 않습니다.

워크플로우 패턴에는 두 가지 핵심 장점이 있습니다. 첫째는 **엄격한 흐름 제어**입니다: 개발자는 핵심 단계가 건너뛰어지거나 순서가 뒤바뀌지 않도록 보장할 수 있으며, "결제 전에는 예약할 수 없다"와 같은 비즈니스 규칙이 코드로 강제되어 LLM의 판단에 의존하지 않습니다. 둘째는 **안전성**입니다: 실행 경로가 결정되어 있으므로, 프롬프트 인젝션이나 모델의 실수가 미치는 영향은 기껏해야 현재 노드 내부로 국한되며, Agent가 실행되어서는 안 될 분기로 건너뛸 수 없습니다—공격 표면이 단일 노드 안으로 제한됩니다.

워크플로우의 주된 한계는 **유연성 부족**입니다. 미리 설정된 흐름이 다루지 못하는 상황이 발생하면(예를 들어 사용자가 결제 단계에서 갑자기 일정을 바꾸고 싶어 하거나, 항공편이 갑자기 취소되어 대체편을 추천해야 하는 경우), 고정된 노드 경로는 유연하게 대응할 수 없으며, 미리 설정된 예외 처리 분기를 따르거나 통제권을 사람에게 넘길 수밖에 없습니다.

#### 자율 Agent: 동적인 자율 결정

워크플로우의 고정 경로가 요구를 충족하지 못할 때, **자율 Agent**(Autonomous Agent)가 필요합니다. 자율 Agent와 워크플로우의 핵심 차이는 이것입니다: 실행 경로가 미리 정의되어 있지 않고, Agent가 **환경 피드백**에 따라 실시간으로 결정합니다.

항공권 예약을 다시 예로 들면: 자율 Agent는 네 개의 고정 노드를 미리 정의할 필요가 없습니다. 사용자가 "다음 주 수요일 상하이행 항공권을 예약해 줘"라고 말하면, Agent는 스스로 먼저 항공편을 검색하기로 결정하고, 로그인이 필요하다는 것을 발견하면 먼저 신원을 확인한 뒤 다시 검색으로 돌아가며, 가장 저렴한 항공편이 환승이 필요하다는 것을 발견하면 사용자에게 능동적으로 환승을 받아들일지 묻고, 사용자가 환승은 싫다고 하면 Agent는 검색 조건을 조정합니다……

이는 자율 Agent가 자율 계획 능력을 갖춰야 함을 의미합니다—실행 단계를 스스로 결정하고, 실패를 인식하고 전략을 조정할 수 있어야 하며, 오류가 났을 때 그냥 멈추기만 해서는 안 됩니다. 하지만 자율성이 무제한을 뜻하지는 않습니다—반드시 명확한 **정지 조건**(작업 완료, 최대 반복 횟수 도달, 회복 불가능한 오류 발생)을 설계해야 합니다. 그렇지 않으면 Agent는 무한 루프에 빠지거나 과도하게 실행되기 쉽습니다.

구현 관점에서 보면, 자율 Agent는 본질적으로 순환 속에서 도구를 사용하는 LLM이며, 지속적으로 환경 피드백을 얻어 작업을 진전시킵니다—이것이 바로 앞서 소개한 ReAct 순환입니다. 흔한 종료 조건으로는 최종 출력 도구 호출, 모델이 어떤 도구 호출도 없는 응답을 반환하는 경우, 또는 오류 발생, 최대 라운드 수 도달 등이 있습니다.

자율 Agent는 개방형 문제에 특히 적합합니다—이런 문제는 필요한 단계 수를 예측하기 어렵거나 불가능합니다. 전형적인 응용 시나리오로는 Coding Agent가 SWE-bench(Software Engineering Benchmark, 실제 GitHub 이슈를 자동으로 수정하는 Agent 능력을 평가하는 벤치마크 테스트) 작업을 해결하는 것, "컴퓨터 사용"(Computer Use) Agent가 사람처럼 컴퓨터 인터페이스를 조작하는 것, 반복적인 검색과 분석이 필요한 연구 작업 등이 있습니다.

다만 자율성은 더 높은 비용과 잠재적인 복합 오류 위험도 동반합니다. 따라서 자율 Agent를 배포할 때는 반드시 샌드박스 환경에서 충분한 테스트를 진행하고, 적절한 가드레일과 모니터링 메커니즘을 설정하며, 핵심 결정 시점에는 사람과의 협업 체크포인트를 넣는 것을 고려해야 합니다.

#### 두 패턴의 선택과 혼합

실전에서 워크플로우와 자율 Agent는 이것 아니면 저것이라는 양자택일 관계가 아닙니다—많은 시스템이 두 패턴을 혼합해서 씁니다: 핵심적이고 엄격한 규정 준수가 요구되는 흐름은 워크플로우로 신뢰성을 확보하고, 유연한 결정이 필요한 부분은 자율 모드로 전환합니다. 예를 들어 n8n은 성숙한 워크플로우 자동화 오픈소스 프레임워크로, 개발자는 시각적 인터페이스에서 기능 구성 요소를 드래그해 Agent를 구축하며, 같은 시스템 안에서 워크플로우 노드와 자율 Agent 노드를 동시에 사용할 수 있습니다.

| **CrewAI** | 역할 기반 다중 Agent 편성 | Multi-Agent 협업 | 코드 우선 | 팀형 작업 분해와 실행 |
| **OpenClaw** | 오픈소스 만능 개인 Agent | 자율 + 이벤트 기반 | 설정 + 코드(자체 호스팅) | 개인 비서, Deep Research, Computer Use, 다중 플랫폼 메시지 통합 |

"모델 자체가 Agent" 추세가 심화됨에 따라, 프레임워크의 핵심 가치는 더 이상 "LLM 호출을 편성하는 것"에 국한되지 않습니다—모델이 점점 더 자율적으로 결정할 수 있게 되지만, 모델을 둘러싼 컨텍스트 관리, 도구 생태계, 안전 제약, 오류 회복 등 Harness 엔지니어링은 오히려 더 중요해지고 있습니다. 프레임워크를 선택할 때 핵심 고려 사항은 프레임워크 자체의 복잡도가 아니라, 그것이 최소한의 추상화 층으로 여러분이 비즈니스 로직에 집중할 수 있게 해주는가입니다.

앞서 논의한 편성 패턴은 Harness 중 컨텍스트와 도구의 조직 문제를 해결했습니다—LLM 호출, 도구, 데이터 흐름을 어떻게 엮을지 말입니다. 하지만 일을 할 수 있는 것만으로는 부족하며, 제대로 하고 안전하게 하는지도 확인해야 합니다. 이어서 컨텍스트와 도구를 중심으로 구축된 제약, 검증, 교정 메커니즘 중 실전에서 가장 핵심적인 실현 수단인 가드레일에 대해 논의하겠습니다.

### 가드레일과 안전성

이 절에서는 가드레일에 대해 높은 수준의 개괄을 제공해 독자가 전체적인 인지를 세울 수 있도록 돕습니다. 구체적인 구현 세부사항과 실천 방법은 제2장(프롬프트 인젝션 방어), 제4장(도구 권한 제어), 제5장(코드 실행 안전)에서 각각 자세히 다루며, 처음 읽을 때 모든 세부사항까지 파고들 필요는 없습니다.

가드레일은 Harness 중 "제약, 검증, 교정" 층위의 핵심 실현 수단입니다—이들은 Agent 행동의 안전과 통제 가능성을 보장하는 계층화된 방어선을 구성합니다. 정교하게 설계된 **가드레일**(Guardrails)은 데이터 프라이버시 위험(예를 들어 시스템 프롬프트 유출 방지)이나 평판 위험(예를 들어 모델 행동이 브랜드 이미지와 일치하도록 보장)을 관리하는 데 도움이 됩니다. 먼저 이미 식별된 위험에 대해 가드레일을 설정한 뒤, 새로운 취약점이 발견될 때마다 점진적으로 새 가드레일을 추가할 수 있습니다.

가드레일은 계층화된 방어 메커니즘으로 이해할 수 있습니다. 단일 가드레일만으로는 충분한 보호를 제공하기 어렵지만, 여러 전문화된 가드레일을 조합해 사용하면 더 회복탄력성 있는 Agent 시스템을 구축할 수 있습니다.

#### 가드레일 유형

방어 위치에 따라 세 가지로 나눌 수 있습니다: 입력 측, 실행 측, 출력 측.

**입력 측** 가드레일은 요청이 Agent에 도달하기 전에 가로채며, 보통 네 가지 메커니즘을 포함합니다. **관련성 분류기**는 주제에서 벗어난 질의를 표시합니다. 예를 들어 프로그래밍 보조 도구가 "엠파이어 스테이트 빌딩은 얼마나 높습니까?"와 같은 무관한 질문을 받는 경우입니다. **안전 분류기**는 탈옥(Jailbreak, 즉 모델이 안전 제약을 우회하도록 유도하는 것)과 프롬프트 인젝션(Prompt Injection, 즉 입력에 악의적인 지시를 심는 것)을 탐지하는데, 이 둘의 핵심 차이는: 탈옥은 사용자 자신이 모델의 안전 제약을 우회하려는 시도이고, 프롬프트 인젝션은 공격자가 외부 데이터(예: 웹페이지 콘텐츠, 문서)를 통해 간접적으로 모델 행동을 조작하는 것이라는 데 있습니다. **콘텐츠 심사**는 폭력, 차별적 콘텐츠 등 유해하거나 부적절한 입력을 표시합니다. **규칙 기반 보호**는 결정론적 조치를 채택하며, 블랙리스트, 입력 길이 제한, 정규표현식 필터 등을 포함해 SQL 인젝션 등 이미 알려진 위협을 방지합니다.

**실행 측** 가드레일은 도구 호출 시 검증합니다. 그 핵심은 **도구 위험 등급 평가**입니다: 조작의 가역성 여부, 권한 등급, 재무적 영향에 따라 각 도구에 위험 등급(낮음/중간/높음)을 매기며, 고위험 조작에는 추가 검토나 사람의 확인이 필요합니다.

**출력 측** 가드레일은 응답이 사용자에게 반환되기 전에 검사합니다. **PII 필터**는 출력 속의 개인 식별 정보(예: 주민등록번호, 휴대폰 번호)를 검사해 불필요한 노출을 방지합니다. **출력 검증**은 콘텐츠 검사를 통해 응답이 브랜드 가치와 일치하도록 보장합니다.

일부 메커니즘(예를 들어 규칙 기반 정규표현식 필터)은 입력 측과 출력 측 모두에 쓸 수 있으며, 위 분류는 가장 흔한 배치 위치를 기준으로 한 것입니다.

#### 사람의 개입

**사람의 개입**(Human in the loop, 인간 개입 순환이라고도 함)은 핵심적인 보호 조치로, 사용자 경험을 해치지 않으면서 Agent의 실제 성능을 끌어올릴 수 있게 해줍니다. 이는 배포 초기에 특히 중요하며, 실패 패턴을 식별하고 경계 사례를 발견하며 견고한 평가 주기를 세우는 데 도움이 됩니다.

사람의 개입 메커니즘을 구현하면 Agent가 작업을 완수할 수 없을 때 통제권을 우아하게 이양할 수 있습니다. 고객 서비스에서는 이것이 문제를 상담원에게 에스컬레이션하는 것을 의미하고, Coding Agent에서는 통제권을 개발자에게 돌려주는 것을 의미합니다.

일반적으로 두 가지 주요 상황이 사람의 개입을 촉발합니다.

**실패 임계값 초과**
Agent의 재시도 횟수나 조작 횟수에 상한을 설정합니다. Agent가 이 한도를 넘으면(예를 들어 여러 번 시도했는데도 고객의 의도를 이해하지 못한 경우) 사람의 개입으로 에스컬레이션해야 합니다.

**고위험 조작**
민감하거나, 되돌릴 수 없거나, 위험도가 높은 조작을 다룰 때는 사람의 감독이 촉발되어야 합니다. 최소한 팀이 Agent의 신뢰성에 대해 충분한 확신을 가질 때까지는 그렇습니다. 전형적인 예로는 사용자 주문 취소, 거액 환불이나 결제 승인 등이 있습니다.

Harness 다섯 요소라는 본선으로 돌아가서—이제 이 책의 각 장이 이 프레임워크 안에서 어떻게 전개되는지 살펴봅시다.

### Harness 엔지니어링의 실천 지침으로서의 이 책

Harness 엔지니어링의 관점에서 이 책의 구조를 다시 살펴보면, 각 장이 체계적으로 Harness의 어떤 구성 요소를 구축하고 있음을 발견할 수 있습니다. 동시에 안전은 어느 한 장의 독립적인 주제가 아니라, 책 전체를 관통하는 횡단적 관심사(Cross-cutting Concern, 즉 시스템의 여러 부분에 영향을 미치는 문제로, 소프트웨어 엔지니어링에서 로깅이 모든 모듈에 스며들어야 하는 것과 비슷합니다)입니다. 아래 표는 Harness 기능, 안전 측면, 대응하는 장을 통일해서 보여줍니다.

| Harness 초점 | 대응 장 | 핵심 내용 | 안전 관심사 |
|---------------|-----------------|------------------------------------|---------------------------|

Anthropic이 장시간 실행되는 Agent를 구축할 때의 실천은 Harness 설계가 모델 자체로는 해결할 수 없는 문제를 어떻게 해결하는지 보여줍니다. 그들은 복잡한 작업을 "초기화 Agent"(환경을 설정하고 작업 목록을 분해)와 "실행 Agent"(각 세션에서 점진적으로 전진하며 명확한 인수인계 산출물을 남김)로 분해했고, 구조화된 Harness를 통해 Agent가 긴 작업에서 겪는 "컨텍스트 고갈"과 "성급한 완료 선언" 문제를 해결했습니다. 이후 장들에서는 Harness의 각 구성 요소를 하나씩 깊이 다룰 것입니다—제2장은 가장 핵심적인 컨텍스트 엔지니어링에서 시작하고, 제5장은 Coding Agent에서 Harness 엔지니어링의 완전한 실천을 전문적으로 다룹니다.

## 이 장의 요약

이 장은 실천에서 출발해 AI Agent를 이해하고 구축하는 기초 프레임워크를 세웠습니다.

**Agent = 뇌 + 눈 + 손발**: LLM은 뇌(의사결정 핵심)이고, 컨텍스트는 눈(무엇을 볼 수 있는지 결정)이며, 도구는 손발(무엇을 할 수 있는지 결정)입니다. 셋 중 어느 하나도 빠질 수 없습니다.

**눈(컨텍스트)이 결정적 요인입니다**: 컨텍스트는 정적 프리픽스(시스템 프롬프트 + 도구 정의)와 동적 궤적(메시지 이력)으로 구성됩니다. 소거 실험은 어떤 구성 요소를 빼든 시스템이 눈에 띄게 퇴화한다는 것을 보여주었습니다. ReAct 순환의 본질은 궤적을 계속 추가함으로써 모델이 작업을 지속적으로 전진시키게 하는 데 있습니다.

**Harness가 경쟁력의 원천입니다**: 모델 능력은 점점 상품화되고 있으며, 진짜 차이는 Harness에 있습니다——컨텍스트와 도구를 중심으로 구축된 제약, 검증, 교정 메커니즘이 Agent가 "신뢰성 있게 일하는" 것을 보장합니다. 프로덕션급 Agent 시스템에서는 Harness의 절대다수 코드가 이런 보장 메커니즘을 위한 것이지, 단순히 컨텍스트와 도구 자체만이 아닙니다.

**워크플로우에서 자율 Agent까지**: 먼저 프롬프트를 최적화하고, 그다음 워크플로우를 고려하고, 마지막에야 자율 Agent를 도입하는 것——이것이 예기치 못한 위험을 줄이는 가장 실용적인 순서입니다. 각 편성 패턴마다 적합한 시나리오가 있으며, 범용적인 최적해는 존재하지 않습니다.

**안전은 아키텍처의 문제입니다**: 가드레일, 사람의 개입, 정렬(alignment, 즉 모델의 행동을 인간의 의도와 일치시키는 것)——안전 문제는 첫 줄의 코드를 쓸 때부터 고려해야 하며, 출시 직전에 패치로 때울 것이 아닙니다. 안전 문제는 모델, 컨텍스트, 도구, 협업, 사회라는 다섯 층위를 관통합니다.

다음 장에서는 Harness에서 가장 핵심적인 구성 요소인 컨텍스트 엔지니어링을 깊이 살펴보겠습니다. 강화학습에서 Agent 개념의 학술적 연원, 그리고 전통적 RL과 현대 LLM Agent의 심층 비교는 제7장에서 체계적으로 전개하겠습니다.

아래 생각해 볼 문제들은 독자가 이 장의 핵심 개념을 더 깊이 탐구할 수 있도록 돕기 위한 것입니다.
