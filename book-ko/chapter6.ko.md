# Agent 평가

Agent 시스템을 구축할 때 개발자는 명확한 정답이 없는 수많은 설계 선택지에 부딪힙니다:

- 어떤 모델을 쓸 것인가?
- 모델이 어떤 도구를 호출할 수 있게 할 것인가?
- 지식 베이스에 어떤 데이터를 어떤 구조로 담을 것인가?
- 사용자 기억은 어떻게 구현할 것인가?
- 모델의 프롬프트와 Skills는 어떻게 조직할 것인가?
- Harness에는 어떤 제약을 걸어야 하는가?
- 이 Agent의 자기 진화와 자체 반복은 어떻게 이뤄야 하는가?

평가는 이런 결정에 과학적 근거를 제공합니다: 체계적인 대조 실험(변수 하나를 바꿔 효과 변화를 관찰)과 소거 실험(구성요소를 하나씩 꺼서 전체 성능 변화를 관찰함으로써 그 구성요소의 실제 기여도를 판단)을 통해, 진짜 능력 향상과 표면적인 변동을 구분하고 "참깨를 줍다 수박을 놓치는" 실수를 피할 수 있습니다. 소프트웨어 공학의 "측정 없이는 개선도 없다"는 말처럼, 재현 가능한 평가 체계 없이는 Agent의 반복 방향을 직감에만 의존할 수밖에 없습니다.

제1장에서 도입한 Harness 공학의 관점에서 보면, 평가는 Harness 안에서 "검증" 기능의 핵심 역할을 담당합니다. 여기서 중요한 인식은: **평가 대상은 모델 하나가 아니라 모델과 Harness의 조합체여야 한다**는 것입니다. 같은 모델이라도 Harness가 다르면 성능이 크게 갈릴 수 있습니다——일부 팀은 Harness만 최적화해서 동일 모델의 터미널류 작업 성능을 크게 끌어올렸습니다(자세한 내용은 제5장 참조). 즉 Agent가 평가에서 저조한 성적을 보일 때, 개선 방향은 모델 교체가 아니라 Harness의 어떤 구성요소(프롬프트, 도구 설계, 피드백 루프)를 최적화하는 것일 수 있습니다. 완성도 높은 평가 체계는 "모델 능력 부족"과 "Harness 설계 결함"이라는 본질적으로 다른 두 문제를 구분할 수 있어야 합니다. **이 두 문제를 구분하는 흔한 수단이 모델 교체 실험(model swap)**입니다——Harness를 고정한 채 더 강하거나 약한 모델로만 바꿔서 점수 변화 폭을 관찰합니다. 더 강한 모델로 바꿔도 점수가 오르지 않으면 병목이 Harness에 있다는 뜻이고, 더 약한 모델로 바꿨을 때 점수가 크게 떨어지고 모델 능력에 따라 점수가 크게 요동친다면 가장 직접적인 해석은 병목이 모델 능력 자체에 있으며 현재 성능이 주로 모델에 의해 결정된다는 것입니다(이것이 과제 자체가 어려워서인지, Harness가 모델 사전지식에 과도하게 의존해서인지는 추가 분석이 필요합니다). 이는 앞서 말한 "소거 실험"과는 다른 방법임에 주의해야 합니다——소거는 **Harness의 특정 구성요소를 끄고** 전체 성능이 어떻게 변하는지 보는 것이고, 모델 교체는 **Harness를 고정하고 모델만 바꾸는** 것입니다——전자는 Harness 내부 어느 부품이 중요한지 짚어내고, 후자는 병목이 모델에 있는지 Harness에 있는지 구분합니다.

평가 체계의 가치는 모델이 빠르게 진화하는 시대에 더욱 두드러집니다. 모델 능력은 여전히 빠르게 진화하고 있지만, 새 모델이 공개 벤치마크에서 더 좋은 성적을 낸다고 해서 여러분의 특정 과제에서도 더 낫다는 뜻은 아닙니다——오히려 성능 퇴행(regression, 즉 새 버전이 일부 측면에서 이전 버전보다 못한 것)이 나타날 수도 있습니다. 자신만의 평가 데이터셋으로 완전히 테스트해봐야 데이터 기반의 업그레이드 결정을 내릴 수 있습니다. 더 나아가, 완성도 높은 평가 체계가 있으면 "미래의 모델을 위한 제품 개발"이 실행 가능한 전략이 됩니다——현재 모델이 상용화를 지탱하기에 부족하더라도, 먼저 제품 개발과 평가 셋 구축을 마쳐두고 새 모델의 성능을 지속 추적하다가 임계값에 도달하는 순간 바로 출시할 수 있습니다.

> **본 장 안내**
>
> 본 장은 세 층위로 완전한 평가 체계를 구축합니다. 첫 번째 층위는 **평가 환경**("어디서 테스트하는가")입니다: 자동화되고 재현 가능한 테스트 환경을 어떻게 구축하는지, 도구 호출형과 인간-상호작용형 두 패러다임을 다룹니다. 두 번째 층위는 **평가 방법**("어떻게 판정하는가")입니다: 데이터셋 설계 원칙, 평가 지표 체계(무엇을 측정할 것인가)부터 LLM-as-a-Judge(대형 언어 모델을 평가위원으로 활용)를 통한 자동화 평가, 그리고 쌍대 비교와 모델 순위 매기기까지 다룹니다. 세 번째 층위는 **평가 기반 의사결정**("측정해서 무엇을 할 것인가")입니다: 평가 결과를 모델 선정, 아키텍처 최적화, 지속적 반복 개선을 위한 실행 지침으로 전환하고, 통계적 유의성을 통해 관찰된 점수 차이가 실제로 신뢰할 만한지 판단합니다. 이 외에도 본 장은 관측가능성(Observability)과 프로덕션급 Agent의 내부 평가 인프라를 다루며, 장 말미에서는 제7장 후속학습(post-training)으로 이어지는 시뮬레이션 환경을 소개합니다.
>
> 이 장 전체를 관통하는 핵심 이념은: **평가 체계의 첫 번째 가치는 현재 시스템에 점수를 매기는 것이 아니라, 모델의 진화를 빠르고 신뢰성 있게 따라잡을 수 있게 하는 것**입니다. 더 강하거나 더 저렴한 모델이 출시될 때, 완성도 높은 평가 체계를 갖춘 팀은 몇 시간 안에 교체 결정을 내릴 수 있지만, 평가 체계가 부족한 팀은 직감에 의존하거나 커뮤니티 피드백을 기다릴 수밖에 없습니다——경쟁이 치열한 Agent 시장에서 이런 속도 격차는 성패를 가를 수 있습니다.

## 구체적인 평가 예시

방법론을 깊이 파고들기 전에, 완전한 예시 하나로 직관을 세워보겠습니다. 고객 서비스 Agent를 구축했고, 환불 요청을 처리하는 능력을 평가한다고 가정합시다.

**테스트 케이스**: 사용자가 3일 전 주문(주문번호 #12345, 금액 ¥299)의 환불을 요청. 회사 정책: 7일 이내 전액 환불 가능.

**Agent의 실행 궤적**:

```
사용자：3일 전에 산 이어폰 환불하고 싶어요, 주문번호 12345요. （오늘은 2026-04-10）

Agent（생각）：사용자가 환불을 원함, 먼저 주문 정보를 조회해야 함.
Agent → 도구 호출 query_order(order_id="12345")
도구 반환：{status: "delivered", amount: 299, date: "2026-04-07", item: "블루투스 이어폰"}

Agent（생각）：주문일 2026-04-07, 오늘 2026-04-10까지 3일, 7일 환불 기한 내이므로 전액 환불 조건에 부합.
Agent → 도구 호출 process_refund(order_id="12345", amount=299)
도구 반환：{refund_id: "R-98765", status: "processing", eta: "3-5영업일"}

Agent：환불 신청을 완료했습니다. 주문 #12345（블루투스 이어폰, ¥299）의 전액 환불이 처리 중입니다,
      예상 3-5영업일 내 입금됩니다. 환불번호 R-98765로 진행 상황을 조회하실 수 있습니다.
```

**Rubric으로 채점**（네 가지 차원, 각 차원 1-4점）. 표6-1은 이 고객 서비스 환불 과제의 채점 예시로, Rubric이 하나의 Agent 실행 궤적을 검사 가능한 평가 차원으로 어떻게 분해하는지 보여줍니다.

표6-1 고객 서비스 환불 과제의 Rubric 채점 예시

| 차원 | 기준 | 점수 | 이유 |
|--------------------|-----------------------------------|---------|-------------------------------|
| 조작 정확성 | 환불 금액, 주문번호가 정확한가 | 4 | 정확히 조회하고 ¥299 전액 환불을 신청 |
| 정책 준수성 | 7일 환불 정책을 준수했는가 | 4 | 주문이 환불 기한 내이며 정책에 부합 |
| 정보 완전성 | 금액, 입금 시점, 환불번호를 안내했는가 | 4 | 세 가지 핵심 정보 모두 안내함 |
| 환각 검출（거부권 항목） | 존재하지 않는 정보를 지어냈는가 | 통과 | 모든 정보가 도구 반환 결과에서 나옴 |

환각을 등급 채점 차원이 아닌 **거부권 항목**으로 분류하는 이유는, 그것이 품질과 직교하는 문제이기 때문입니다——유창하고 상세하고 정중한 답변이라도 허위 사실을 담고 있으면, 짧지만 정확한 답변보다 사용자에게 훨씬 큰 피해를 줍니다.（거부권 메커니즘의 일반적 설계는 후술할 "Rubric 4원칙"에서 다룹니다.）

이 사례는 통과했습니다. 하지만 좋은 평가는 성공 시나리오만 테스트하지 않고 경계와 함정도 테스트해야 합니다——사용자가 15일 전 주문(환불 기한 초과)의 환불을 요청하면 Agent는 올바르게 거절할 수 있을까요? 사용자가 "고객센터가 이미 환불을 승인했다"고 주장할 때, Agent는 시스템 기록 없이 이를 그대로 믿을까요? 이런 경계 시나리오야말로 Agent 능력의 우열을 가르는 핵심입니다.

위 흐름——테스트 케이스 정의, Agent 실행, Rubric 채점, 결과 분석——이 평가의 기본 골격입니다. 본 장에서는 이제 이 각 단계의 설계 방법을 하나씩 펼쳐 보겠습니다.

## 자동 평가 환경

Agent 평가에는 반복 실행 가능한 자동화 환경이 필요합니다——개발 단계에서 변경 사항의 효과를 빠르게 테스트할 수 있어야 합니다. 이런 환경을 구축하려면 세 가지 질문에 답해야 합니다: 무엇을 평가하는가(과제 정의와 검증 기준), 누구를 상대로 평가하는가(Agent의 상호작용 대상을 어떻게 시뮬레이션할 것인가), 어떤 기준으로 점수를 매기는가.

### 평가 환경의 기본 구성

평가 환경은 다섯 가지 요소로 구성됩니다——이후 절에서 데이터셋 설계와 채점 기준 설계를 중점적으로 다룹니다:

**데이터셋(Dataset)**은 과제 집합을 정의하며, 초기 상태, 목표 서술, 선택적인 참조 해결책을 포함합니다.

**환경 상태(Environment State)**는 과제 수행 중 가변 정보를 유지하며, 실재성과 통제가능성 사이에서 균형을 잡아야 합니다. 예를 들어 고객 서비스 평가에서 환경 상태는 데이터베이스의 주문 기록과 사용자 계정 잔액을 포함합니다. Agent가 `process_refund`를 호출한 후 주문 상태가 'delivered'에서 'refunded'로 바뀌고 잔액이 증가하는 것——이것이 "가변 정보"입니다. "실재성"은 상태 변화가 비즈니스 로직에 부합해야 한다는 것(환불이 주문 금액을 초과하지 않음)을 요구하고, "통제가능성"은 매 테스트가 동일한 초기 상태로 리셋될 수 있어야 함을 요구합니다.

**도구 인터페이스(Tools)**는 Agent가 실행 가능한 조작 집합을 정의합니다——도구는 지나치게 고수준의 추상화(예: "사용자 문제 해결")를 제공해서는 안 되며, 원자적 조작(예: 주문 조회, 예약 수정, 이메일 발송)을 제공해 Agent가 계획과 사고를 통해 이 조작들을 조합하도록 강제해야 합니다.

**채점 기준(Rubric, 평가 준칙)**은 Agent의 성능을 정량화하며, 이진(통과/불통과), 연속(0~100점), 다차원(정확성, 효율성, 안전성 각각에 점수 부여) 형태일 수 있습니다.

**실행 프로토콜(Interaction Protocol)**은 상호작용 방식과 종료 조건을 규정합니다.

### 도구 호출형 평가 환경

코드 생성, 데이터 분석 등 주로 도구 사용에 의존하는 과제에서는 Verifiers 프레임워크가 전형적인 설계 패턴을 보여줍니다. Agent는 사전 정의된 도구를 호출해 과제를 완수하며, 검증은 실행 가능한 기준(테스트 통과 여부, 답 일치 여부)에 기반하고 사람의 주석이나 모델 평가에 의존하지 않습니다.

Verifiers는 계층화된 환경 설계를 도입합니다: `SingleTurnEnv`는 단일 턴 과제(간단한 질의응답)에 적합하고, `ToolEnv`는 다중 턴 도구 호출의 자율 루프를 지원하며, `StatefulToolEnv`와 `SandboxEnv`는 상태를 가진 도구와 장시간 실행되는 샌드박스 환경(코드 실행 등)을 지원합니다. 예를 들어 `SingleTurnEnv`는 수학 문제를 낸 뒤 답을 바로 검증하는 데 적합하고, `ToolEnv`는 여러 웹페이지를 검색해 종합 답변한 뒤 최종 결과를 검증하는 데 적합하며, `StatefulToolEnv`는 데이터베이스 레코드를 수정한 뒤 데이터베이스 상태 변화를 검증하는 데 적합하고, `SandboxEnv`는 샌드박스에서 코드를 실행한 뒤 출력 파일을 확인하는 데 적합합니다. 표6-2는 이런 환경 유형을 정리해 독자가 과제의 상태 유지, 도구 호출, 격리 필요성에 따라 적절한 평가 환경을 선택하도록 돕습니다.

표6-2 Verifiers 환경 유형 비교

| 환경 유형 | 상태 유지 | 도구 호출 | 전형적 사례 |
|---|---|---|---|
| SingleTurnEnv | 없음 | 없음 | 단일 턴 질의응답, 수학 문제 |
| ToolEnv | 없음 | 다중 턴 | 검색+정보 종합 |
| StatefulToolEnv | 있음 | 다중 턴 | 데이터베이스 레코드 수정 |
| SandboxEnv | 있음+격리 | 다중 턴 | 코드 실행과 테스트 |

프레임워크는 병렬 샘플링과 궤적 캐싱을 지원하며, 매 평가의 전체 궤적(관측, 행동, 보상)이 저장되어 후속 분석과 리플레이에 활용됩니다.

환경은 또한 조작의 상태 의존성도 처리해야 합니다——도구의 실행 효과는 현재 상태에 따라 달라지며, 실패 시 단순한 실패 플래그가 아니라 명확한 오류 정보를 제공해 Agent가 오류로부터 학습하고 전략을 조정할 수 있게 해야 합니다.

### 인간-상호작용형 평가 환경

많은 실제 과제는 도구 호출뿐 아니라 사람과의 대화도 필요로 합니다. 고객 서비스 Agent는 모호한 표현을 이해하고, 요구사항을 명확히 하고, 백엔드 시스템을 조회하고, 사용자에게 정보를 확인해야 합니다. 이런 과제의 평가는 근본적인 도전에 직면합니다: 자동화 환경에서 실제 사용자를 어떻게 시뮬레이션할 것인가?

핵심 설계 원칙은 **점진적 정보 공개(Progressive Information Disclosure)**로, 이는 인간-상호작용형 평가와 전통적 벤치마크 테스트(benchmark)의 근본적 차이입니다. 대부분의 benchmark는 처음부터 완전한 요구사항을 다 드러내지만, 현실에서 사용자는 처음부터 요구사항을 명확히 서술하는 경우가 드뭅니다——"제 비행기 편에 무슨 문제가 있는 것 같아요", "인터넷이 안 돼요" 정도만 말하는 경우가 많습니다. Agent는 능동적인 질문을 통해 요구사항을 명확히 해야 하며, 이 과정 자체가 능력의 중요한 표현입니다. 따라서 평가에서는 **처음부터 시뮬레이션된 사용자의 모든 정보를 Agent에게 노출해서는 절대 안 되며**, 정보는 필요에 따라 점진적으로 대화 중에 공개되어야 합니다.

τ-bench의 해결책은 **사용자 시뮬레이션(User Simulation)**입니다: 다른 LLM이 사용자 역할을 맡아 사전 정의된 지시에 따라 Agent와 대화합니다. 시뮬레이션 사용자는 과제 지시(예: "내일 비행편을 취소해야 해요")를 받고, 대화 중 필요한 정보를 점진적으로 Agent에게 공개하고 질의에 응답하며, 과제 완료 후 종료 신호를 보냅니다. 프롬프트는 시뮬레이션 사용자에게 "모든 정보를 한 번에 공개하지 말고, 현재 단계에 필요한 내용만 제공하라", "지시에 없는 정보를 지어내지 말라"고 요구합니다. 사용자 시뮬레이션의 설계는 실재성과 통제가능성 사이에서 균형을 잡아야 합니다: 행동은 실제 사용자에 가까워야 하고(모호한 표현, 불완전한 정보, 가끔의 감정 기복), 동시에 재현성을 보장하기 위해 일정한 각본을 따라야 합니다.

다음은 점진적 정보 공개의 다중 턴 대화 예시입니다(사용자 시뮬레이터는 고정 각본에 따라 행동):

> **사용자**: "제 비행편에 문제가 있어요."
> **Agent**: "어느 비행편인가요?"
> **사용자**(각본에 따라 공개): "델타 123편, 내일 아침 샌프란시스코에서 뉴욕으로 가는 거예요."
> **Agent**: "구체적으로 어떤 문제인가요?"
> **사용자**(각본에 따라 공개): "비행 시간이 너무 길어서 변경하고 싶어요."
> **Agent**: "새 비행편에 원하는 조건이 있나요?"
> **사용자**(각본에 따라 공개): "오후 비행편이면 다 괜찮아요."

사용자 시뮬레이터는 고정된 각본(이미 알고 있는 정보 + 공개 규칙)을 따라 평가의 재현성을 보장하는 동시에, 실제 사용자의 점진적 표현 방식을 시뮬레이션합니다.

τ-bench는 구조화된 비즈니스 흐름(항공 고객 서비스, 소매 고객 서비스 등)에서 Agent의 성능을 평가하는 벤치마크 테스트입니다. 그 검사는 구성요소 수준의 다차원적 검사입니다——한편으로는 데이터베이스 최종 상태가 올바른지(예약 기록 상태가 "취소됨"으로 변경되었는지) 확인하고, 다른 한편으로는 Agent가 대화 중 필요한 핵심 정보(환불 금액과 입금 시점 등, 특정 문자열이나 패턴을 검색해 검증)를 출력했는지 검증합니다. 이런 이중 검증은 조작 정확성과 소통 효과성을 동시에 살핍니다. 하지만 과제 수준에서 이런 검사들은 최종적으로 **0 또는 1의 이진 보상**으로 집계됩니다——모든 검사를 통과해야 1점, 하나라도 통과하지 못하면 0점입니다. 이진 보상은 Pass^k 등 신뢰성 지표(후술 "평가 지표 체계" 참조)를 통계적으로 다루기 편리하지만, 대가로 "조작은 정확했으나 비핵심 필드 하나를 놓친 경우"와 "완전히 실패한 경우"가 같은 점수를 받습니다.

개선판 **τ²-bench**의 핵심 증분은 채점 세밀도가 아니라 두 가지에 있습니다: 하나는 **양방향 제어 환경(Dual-Control)**——더 이상 Agent만 도구를 호출할 수 있는 것이 아니라 사용자 시뮬레이터도 동일한 공유 환경을 조작할 수 있습니다(예: Agent가 사용자에게 비행기 모드 전환을 안내하고, 사용자의 조작이 실제로 환경 상태를 바꿈)——이는 기술 지원처럼 사용자가 직접 손을 움직여 협조해야 하는 실제 시나리오에 더 가깝습니다. 다른 하나는 **더 정밀한 과제 명세와 조합형 과제 생성**——성공 조건의 모호함이 줄고, 구체적인 과제 인스턴스를 매개변수화해 대량 생성할 수 있습니다(자세한 검증 차원은 후술 "검증가능성과 객관성 보장" 절 참조).

> **실험 6-1 ★: τ²-bench 실행과 τ-bench 대비 진화 이해**
>
> 본 실험은 τ²-bench 평가 프레임워크를 실행함으로써 인간-상호작용형 평가 환경의 설계 요점을 이해하고, τ-bench와 τ²-bench의 차이를 비교함으로써 평가 데이터셋이 어떻게 반복 개선되는지 체감합니다.

>
>
> ![그림6-3 τ²-bench 평가 아키텍처](images/fig6-3.svg)
>
>
> τ-bench와 τ²-bench의 설계 차이를 비교하세요: τ-bench 초기 버전은 사용자 지시가 지나치게 단순해(Agent가 답을 추측할 수 있음), 성공 조건이 정밀하지 못하고(오판을 유발), 사용자 시뮬레이터가 지나치게 기계적이었습니다. τ²-bench는 이런 문제들에 대해 체계적으로 개선했습니다:
>
> - **더 상세한 과제 지시 도입**: "사실 근거 요구"(Grounding)를 포함, 즉 반드시 환경의 실제 상태에 근거해 답해야 함
> - **더 정밀한 평가 기준**: 예를 들어 "속도 테스트가 excellent를 반환해야만 해결로 인정"
> - **더 실제적인 사용자 시뮬레이터 행동 규범**: 점진적 정보 공개, 자연스러운 감정 기복
>
> τ²-bench가 새로 추가한 telecom 영역 과제에 특히 주목하여, 앞서 언급한 양방향 제어 환경 설계(사용자와 Agent가 동일한 공유 환경을 함께 조작)를 이해하세요.
>

도구 호출형 평가가 "관측 가능한 상태 변화의 완수 여부"에 중점을 두는 것과 달리, 인간-상호작용형 평가는 "사용자의 인지 또는 의사결정 변화를 이끌어냈는가"에 주목합니다——전자는 Agent의 행동 정확성을, 후자는 그 소통 전략의 합리성을 살핍니다.

평가 환경의 구축은 시뮬레이션 환경의 설계와도 연결됩니다——평가 환경이 대규모 반복 상호작용을 지원해야 할 때 시뮬레이션 환경으로 진화하며, 본 장 말미에서 간략히 다룹니다.

## 평가 과제 데이터셋의 설계

평가 환경이 "무대"라면 데이터셋은 "대본"입니다——대본 설계의 좋고 나쁨이 무대 자체보다 평가의 가치를 더 크게 좌우하는 경우가 많습니다. 설계가 부실한 데이터셋은 완벽한 환경에서 돌려도 얻는 것은 잡음뿐입니다. 본 절에서는 GAIA, AndroidWorld, SWE-Bench Verified（Software Engineering Benchmark, 소프트웨어 공학 벤치마크 테스트）, τ-bench와 τ²-bench, Terminal-Bench, OSWorld와 OSWorld-Verified 등의 벤치마크 설계 실천에서 반복적으로 검증된 몇 가지 원칙을 추려냅니다.

이 목록이 Agent 평가의 전 영역을 망라하지는 않습니다. Web/GUI 계열만 해도 각기 다른 강점을 가진 벤치마크가 여럿 있습니다: WebArena는 완전히 재현 가능한 웹사이트 세트(전자상거래, 포럼, 코드 호스팅 등)를 직접 구축해 "실제 웹페이지"의 통제 불가능성을 샌드박스에 가뒀고, Mind2Web은 반대로 수백 개의 실제 웹사이트에서 직접 일반화 능력을 테스트하며, BrowseComp는 심층 검색을 전문으로 다뤄——답이 깊이 숨어 있어 여러 단계의 탐색과 교차 검증을 거쳐야만 찾을 수 있습니다. 도구 호출 차원에는 BFCL(Berkeley Function-Calling Leaderboard) 같은 전문 함수 호출 순위표도 있습니다. 본 장은 모든 벤치마크를 나열하려는 것이 아니라, 두 가지 핵심 환경 패러다임(도구 호출형, 인간-상호작용형)과 데이터셋 사례를 관통하는 GUI 조작 시나리오를 선택해 그 설계 취사선택을 깊이 파고듭니다——패러다임을 이해하면 어떤 새 벤치마크를 마주하든 무엇을 테스트하는지, 유출 방지는 어떻게 되어 있는지, 결론을 어디까지 외삽할 수 있는지 빠르게 판단할 수 있습니다.

> **실험 6-2 ★: 벤치마크 테스트 과제를 직접 수행하기**
>
> GAIA, AndroidWorld, SWE-Bench Verified, τ²-bench, Terminal-Bench, OSWorld-Verified에서 각각 과제를 골라 직접 완수하세요. 각 데이터셋에서 쉬움, 보통, 어려움을 하나씩 완수할 것을 권장합니다——"어려움" 등급은 사람에게도 도전적입니다. 실행 결과를 정답과 비교해 차이의 원인을 분석하세요. 직접 체험을 통해 이해하세요: 과제 서술은 명확성과 개방성 사이에서 균형을 잡아야 하고, 검증 기준은 객관적으로 실행 가능해야 하며, 과제 난이도의 계층화는 서로 다른 능력 수준을 구분할 수 있어야 합니다.
>

### 과제 데이터셋 설계의 핵심 과제

**과제 1: 명확성과 개방성의 긴장.** 과제 서술은 평가의 재현성을 보장할 만큼 명확해야 하면서도, Agent의 창의성을 지나치게 제한할 만큼 경직되어서는 안 됩니다. GAIA는 하나의 본보기를 제공합니다: 과제는 "개념적으로 단순"하지만 실현 경로는 개방적입니다——예를 들어 NASA의 오늘의 천문 사진에서 우주비행사 정보를 찾으라는 요구는 목표(특정 우주비행사와 그 우주 체류 시간을 찾는 것)는 명확하지만, 어떻게 검색하고 걸러내고 검증할지는 전적으로 Agent의 자율적 결정에 달려 있습니다.

**과제 2: 실재성과 통제가능성의 균형.** 실제 과제는 불확실성과 잡음을 포함하며, 이는 강건성을 드러낼 수 있지만 재현성을 위협하기도 합니다. SWE-Bench 초기 버전은 GitHub의 실제 issue에서 직접 가져와 실재성은 보장했지만, 과제 서술이 모호하고 테스트 케이스가 불완전하며 평가 기준이 주관적이라는 문제도 낳았습니다. SWE-Bench Verified는 사람 전문가의 체계적 검증을 도입해, 문제가 명확하고 테스트가 충분하며 해결책이 분명한 500개의 고품질 과제를 선별함으로써 실재성을 유지하면서도 통제가능성을 크게 끌어올렸습니다.

**과제 3: 다양성과 체계성의 조화.** 효과적인 데이터셋은 전형적인 상황, 경계 조건, 오류 함정을 아울러야 하는 동시에 평가 결과가 구체적인 능력 부족을 진단할 수 있도록 체계적으로 구성되어야 합니다. AndroidWorld의 116개 과제는 20개의 실제 앱을 아우르며, 각 과제에는 필요한 핵심 능력(다단계 계획, 시각적 이해, 시간적 추론)이 주석 달려 있어, 평가 결과가 전체 성공률뿐 아니라 특정 능력 차원의 강약도 드러냅니다. 더 중요한 것은, 매개변수화 메커니즘을 통해 거의 무한한 과제 변형을 생성할 수 있다는 점입니다.

**과제 4: 평가 비용과 커버리지 범위.** 복잡한 Agent 과제는 완료까지 몇 분에서 몇 시간이 걸릴 수 있고 대량의 토큰을 소모합니다. 데이터셋의 규모는 전면성과 경제성 사이에서 균형을 잡아야 합니다. GAIA는 466문항을 정선해 3단계 난이도로 나눔으로써, 다양한 능력 차원을 아우르면서도 합리적인 비용으로 평가를 완료할 수 있게 했습니다. SWE-Bench Verified는 2294문항에서 500문항으로 선별했습니다(비용은 약 5분의 4 절감, 더 엄격한 품질 기준을 통해 신호 대 잡음비를 높였습니다).

**과제 5: 데이터 오염(Data Contamination) 방지.** 대형 언어 모델 시대에 데이터 오염은 평가가 직면한 심각한 도전입니다: 평가 데이터가 훈련 데이터에 포함되면, 평가가 측정하는 것은 일반화 능력이 아니라 기억력이 됩니다——시험 전에 답을 외운 것과 같아서, 성적이 좋아도 실제 실력을 증명하지 못합니다. 각 벤치마크는 서로 다른 방지 전략을 채택합니다: GAIA는 답의 유일성에 의존합니다——문제는 여러 정보원을 조합해야 답할 수 있고, 일부 과제에는 전용으로 제작된 첨부 파일(인터넷에 존재하지 않는 PDF/오디오/이미지)이 딸려 있어 단일 웹페이지만으로는 답을 직접 제공할 수 없습니다. SWE-Bench Verified 자체는 OpenAI가 원본 SWE-Bench를 사람이 품질 선별한 500문항 서브셋이며, 시간 차원의 유출 방지 설계는 담고 있지 않습니다. 진정으로 시간의 신선도로 유출을 방지하는 것은 SWE-bench-Live 등 후속 작업으로, 모델 훈련 마감일 이후 새로 생성된 issue를 지속적으로 수록해 평가가 항상 모델의 훈련 말뭉치보다 앞서 있도록 합니다. τ²-bench는 동적 매개변수 생성으로 방지합니다——구체적 과제 인스턴스(사용자 이름, 주문번호, 날짜 등)가 매번 무작위로 생성됩니다. AndroidWorld의 매개변수화된 과제 생성은 검증이 최종 UI 상태에 기반하고 조작 시퀀스에 기반하지 않기 때문에 태생적으로 유출 저항성을 가집니다. Terminal-Bench는 카나리 식별자(canary GUID, 즉 전역 고유 식별자, 일종의 유일한 추적 표식)를 삽입해 유출을 탐지 가능하게 만듭니다: 만약 모델이 해당 GUID를 포함한 내용을 출력할 수 있다면, 벤치마크 데이터가 훈련 세트에 유출되었다는 뜻입니다.

### 과제 서술의 정밀성 설계

GAIA는 명확한 정보원 제약, 시간 범위, 주제와 질의 목표를 통해 답의 유일성을 보장합니다. 예를 들어 Level 3 과제는 특정 날짜의 NASA 사진에서 출발해 시각적 이해로 우주비행사를 식별하고, 소속 우주비행사 그룹을 조회하고, 우주 체류 시간을 계산해 정밀하게 형식화된 출력("성, 세미콜론으로 구분, 천 단위 구분자")을 요구합니다——모든 세부 사항이 자동 검증에 기여합니다——형식과 내용이 완전히 일치해야만 통과입니다.

τ²-bench는 상황화된 설계를 도입해, 각 과제가 여러 층의 정보를 포함합니다: 표면적 문제("모바일 데이터가 작동하지 않음"), 성능 기대("절대적으로 뛰어난 속도를 원함"), 제약 조건("다른 속도는 받아들이지 않음"), 그리고 암시된 감정. 핵심 개선점은 "이미 알고 있는 정보"와 "과제 지시"를 분리한 것입니다: 이미 알고 있는 정보는 사용자가 현재 갖고 있는 사실이고, 과제 지시는 시뮬레이터가 점진적으로 정보를 어떻게 공개할지 안내하며, 여기에는 "사실 근거 요구"(Grounding Requirement, 즉 반드시 도구 호출의 실제 반환 결과에 근거해 답해야 하며 지어낼 수 없음)가 포함됩니다.

SWE-Bench Verified는 문제 서술, 재현 단계, 예상/실제 동작 등 구조화된 필드를 포함하며, 주석자가 서술과 테스트 케이스의 일치성을 검증합니다. Terminal-Bench의 과제 서술에서 모든 요소는 기계적으로 검증 가능합니다: 파일 경로 존재 여부, 권한 값의 정확성, 인증서 매개변수, 날짜 형식 등. 예를 들어 "build-linux-kernel-qemu"는 소스에서 Linux 커널 6.9를 빌드하고, `start_kernel`에 커스텀 printk를 추가하고, initramfs를 생성해 QEMU에서 실행할 것을 요구하며, 성공 기준은 부팅 로그에 커스텀 메시지가 나타나는 것입니다——Agent는 출력을 위조해서는 통과할 수 없고 반드시 전체 흐름을 진짜로 완수해야 합니다.

AndroidWorld는 **매개변수화 템플릿** 설계를 채택합니다. 하나의 과제는 정적인 텍스트가 아니라 동적으로 인스턴스화 가능한 템플릿입니다(예: "연락처 `[CONTACT_NAME]`의 전화번호를 `[NEW_PHONE]`으로 바꾸기"), 매 평가마다 다른 매개변수 값이 무작위로 생성됩니다. 이점은 세 가지입니다:

- **암기 방지**: 매개변수 값이 매번 달라 고정된 조작 시퀀스를 재생할 수 없음
- **데이터 다양성 증가**: 하나의 템플릿으로 거의 무한한 인스턴스를 생성 가능
- **대조 실험 지원**: 일부 매개변수를 고정하고 나머지만 변화시켜 특정 요인의 영향을 정밀하게 측정

검증은 최종 UI 상태(전화번호 필드에 예상 값이 포함되어 있는지 등)에 기반하며 조작 시퀀스에 기반하지 않습니다.

OSWorld의 과제는 대개 "깨끗한" 초기 상태에서 시작하지 않고, 정교하게 구성된 중간 상태에서 시작해 실제 사용 시나리오에 더 가깝습니다. 과제 서술은 다중 해법성("배경을 보라색으로 설정"은 모호함을 없애기 위해 구체적인 색상 코드를 제공해야 함, "두 CSV 병합"은 단일 헤더/이중 헤더 유지 등 모든 합리적 방식을 받아들여야 함)과 환경 불확실성(웹사이트 크롤러 방지, 앱 UI 변화, 타이밍 경쟁——OSWorld-Verified는 오프라인 페이지 스냅샷, 의존성 버전 고정, 명시적 대기 조건 등의 메커니즘으로 완화)을 처리해야 합니다.

### 과제 복잡도의 계층화 설계

GAIA는 3단계 난이도를 설계했습니다: Level 1은 1-2개 도구만 필요(사람 93.9% vs GPT-4 30.3%), Level 2는 다단계 사고가 필요(91.8% vs 9.7%), Level 3은 복잡한 조합이 필요(87.3% vs 0%). 계층화 설계의 진단 가치는: Level 1 실패는 기본 도구 사용 문제를, Level 2는 다단계 계획과 정보 통합을, Level 3은 장시퀀스 사고와 복잡성 관리를 가리킵니다——각 층위는 서로 다른 개선 방향(프롬프트 엔지니어링 vs 계획 메커니즘 vs 계층형 아키텍처/후속학습)에 대응합니다.

τ²-bench는 비즈니스 복잡도로 계층화합니다: 단순한 정보 조회부터, 다단계 프로세스(비행편 변경은 조회, 대안 제시, 확인, 차액 계산, 결제가 필요), 고장 진단(여러 가능한 원인을 체계적으로 점검하고 수정 검증), 마지막으로 정책 판단(정책에 부합하지 않는 요청 처리)까지 이어집니다.

Terminal-Bench는 기술 영역×조작 복잡도 이중 차원으로 계층화하며, 그 과제 레지스트리는 200여 개의 과제를 수록하고 있습니다(버전에 따라 핵심 평가 집합 규모가 다름, 예를 들어 2.0 버전은 커뮤니티 기여에서 89개의 고품질 과제를 선별)——단순한 mlflow 모델 등록부터, 중간 난이도의 7z 비밀번호 크래킹, 어려운 git 서버+webserver 다중 구성요소 통합, 가장 어려운 FEAL 차분 암호분석(암호학 지식+30초 시간 제약을 만족하는 알고리즘 최적화 필요)까지 아우릅니다.

### 검증가능성과 객관성 보장

GAIA의 답은 간결하고 명확하며, 엄격한 형식 규정으로 인해 검증을 정확한 문자열 매칭으로 완료할 수 있고, 이진 결과(일치 또는 불일치)가 객관성과 재현성을 보장합니다. 답의 희소성도 부정행위 방지 역할을 합니다——매우 구체적인 사실은 훈련 데이터에 원형 그대로 등장할 가능성이 낮습니다.

SWE-Bench Verified는 코드의 실행가능성에 기반해 검증하며, FAIL_TO_PASS(수정 전 실패, 수정 후 통과, 문제가 해결되었음을 증명)와 PASS_TO_PASS(수정 전후 모두 통과, 새 버그가 도입되지 않았음을 증명)를 구분해 이중 검증을 구현합니다. Verified 버전은 또한 테스트 자체의 품질이 신뢰할 만한지, 이따금 통과하고 이따금 실패하는 불안정한 테스트(flaky test)가 없는지도 확인합니다.

τ²-bench의 검증 체계는 다층 검사를 포함합니다(각 층 검사 결과는 과제 수준에서 여전히 이진 보상으로 집계되며, 전부 통과해야 성공):

- **데이터베이스 상태 검사**: 예약 기록 상태, 환불 기록 생성 여부
- **대화 내용 키워드 검색**: 사용자에게 환불 금액과 입금 시점을 확인해줬는지
- **프로세스 준수성**: 도구 호출 시퀀스 분석, 예를 들어 주문 수정 전 사용자의 명시적 확인을 받았는지

τ²-bench의 양방향 제어 환경(앞서 "인간-상호작용형 평가 환경" 참조)은 검증 층위에서 한 차원을 더 추가합니다: 사용자 시뮬레이터가 실제로 환경 상태를 바꾼 후, Agent는 도구 호출을 통해 이 변화를 관측하고 그에 따라 계속 조사해야 하며, 검증은 이를 통해 "Agent가 정말로 사용자 측 조작 결과를 읽었는가"까지 다룹니다.

OSWorld는 134개의 독립적인 평가 함수를 갖추고 있으며 완전한 OS 접근 권한을 가지고, 파일 시스템 구조, 프로세스 상태, 네트워크 연결, 앱 내부 상태까지 깊이 검사할 수 있습니다. 예를 들어 데이터베이스 조작 과제에서 평가 스크립트는 보고서 파일 존재 여부만 검증하는 게 아니라 데이터베이스에 직접 연결해 SQL이 올바르게 실행되었는지 확인합니다. 브라우저 과제에서는 DOM 트리를 분석하고 cookie/localStorage를 확인하며 백엔드에 검증 요청을 보내 폼이 실제로 작동했는지 확인합니다. 이런 심층 검사는 "겉으로는 완료됐지만 실제로는 틀린" 상황을 발견할 수 있습니다——예를 들어 Agent가 제출 버튼을 눌렀지만 필드 입력 오류로 서버가 거부한 경우입니다.

Terminal-Bench는 Docker 컨테이너 기반의 표준화된 환경에 파일 시스템 상태 검사(경로 존재 여부, 권한 값, 내용 형식)와 프로그램 실행 기능 검증(build-linux-kernel-qemu에서 실제로 QEMU를 부팅하고 커스텀 printk 메시지를 검색)을 결합하며, 카나리 GUID로 유출을 추적 가능하게 합니다.

### 과제 분포의 체계적 설계

과제 분포는 능력 차원, 난이도 차원, 시나리오 차원, 경계 상황을 체계적으로 커버해야 합니다. GAIA는 범용성을 추구합니다——대부분의 과제가 추론, 멀티모달, 브라우징, 도구 사용의 조합을 요구합니다. τ²-bench는 "함정 과제"를 전문적으로 설계했습니다——예를 들어 사용자가 "고객센터가 이미 취소를 승인했다"고 주장하지만 실제로는 정책에 부합하지 않는 경우, 압력과 오도 상황에서 Agent가 올바른 판단을 유지할 수 있는지 테스트합니다. OSWorld는 조작 유형(파일 IO / 데스크톱 앱 / 웹 앱 / 앱 간 흐름)과 앱 영역의 이중 차원 행렬에 기반하며, 세 개의 운영체제를 아우릅니다(연구에 따르면 OS 간 능력은 강한 상관관계를 가지며, 한 시스템에서 학습한 능력은 다른 시스템으로 전이될 수 있습니다). Terminal-Bench는 "기술 스택 교차 조합 과제"를 포함해 시스템적 사고를 테스트합니다(예: 데이터 처리 + 파일 조작 + Python 엔지니어링을 융합한 재분할 과제).

### 데이터 품질 관리와 반복 개선

SWE-Bench Verified는 품질 관리의 본보기입니다. OpenAI는 원본 2294개 과제 중 1699개를 무작위로 추출해 사람이 평가했으며, Python에 능숙한 개발자 93명을 모집했습니다. 주석자는 여러 검사를 수행해야 했습니다: 문제 서술이 명확한가(무엇을 해결해야 하는지 이해할 수 있는가), 테스트 케이스가 완전한가(모든 측면과 경계 조건을 커버하는가), 테스트가 안정적인가(환경이나 무작위성으로 인한 flaky test가 없는가), patch가 올바른가(새 오류를 도입하지 않았는가), 난이도가 합리적인가. 엄격한 선별을 거쳐 최종적으로 500개만 통과했습니다(29%)——이런 높은 탈락률은 평가 품질에 대한 필요한 투자입니다. 그들은 또한 표준화된 주석 지침을 마련해 각 검사에 대해 구체적인 기준과 예시를 정의함으로써 서로 다른 주석자 간 일관성을 확보했습니다.

τ²-bench는 "이미 알고 있는 정보"/"과제 지시" 분리(시뮬레이터 행동을 더 실제답게 만듦)와 더 엄격한 완료 조건(예: "excellent만 해결로 인정, poor/fair/good은 모두 불허")을 도입해 "적당히 넘어가는 수정"을 방지합니다.

OSWorld-Verified는 반복 개선의 본보기입니다. OSWorld는 2024년 4월 출시된 후 빠르게 멀티모달 Agent 평가의 중요한 벤치마크가 되었지만, 15개월간의 광범위한 사용에서 300개 이상의 문제가 드러났습니다. 이 문제들은 네 가지로 분류됩니다: 환경 문제(웹사이트 크롤러 방지 / CAPTCHA / 동적 콘텐츠 변화), 과제 서술 문제(모호한 표현), 검증 로직 문제(지나치게 엄격하거나 느슨함), 초기 상태 문제(불완전한 구성). 홍콩대학교 팀은 약 10명의 그룹을 꾸려 MoonShot AI, OpenAI, ByteDance Seed TARS, Anthropic, Simular 등과 두 달간 깊이 협력해 체계적으로 수정했습니다. 각 유형의 문제에 대해 수정 전략을 마련했습니다: 환경 문제는 버전 고정과 오프라인 백업으로 해결, 과제 서술은 모호한 표현을 다시 써서 해소, 검증 로직은 사람이 정확한 기준선을 세우고 조건을 조정해 균형을 맞춤, 초기 상태는 완전성 검증을 추가해 강화.

평가 인프라도 로컬 VM에서 AWS 클라우드 플랫폼으로 이전했으며, 탄력적 확장을 활용해 50배의 병렬 가속을 실현했습니다(10여 시간에서 몇 분으로 단축), Google Drive 과제 초기화 성공률은 50%에서 95% 이상으로 향상되었습니다. 모든 공식 평가 궤적 데이터는 HuggingFace에 공개되어, 커뮤니티가 모든 세부사항을 검토하고 결과를 재현하고 문제를 발견함으로써 지속적 개선의 선순환을 이룹니다.

한 가지 짚어둘 것은, 평가 환경과 후속학습 환경은 종종 뿌리가 같다는 점입니다: 잘 설계된 평가 환경은 약간만 개조해도 훈련 환경이 될 수 있습니다——SWE-Gym이 SWE-bench를 기반으로 훈련 과제를 구축한 대표적 사례이고, τ²-bench, AndroidWorld의 매개변수화 템플릿은 대량의 훈련 인스턴스를 일괄 생성할 수 있습니다. 하지만 하나의 레드라인은 분명히 그어야 합니다: 재사용할 수 있는 것은 **환경의 구축 메커니즘**이며, 평가 세트 자체의 구체적 문항들은 훈련 데이터와 엄격히 격리되어야 합니다——평가 문항이 훈련 세트에 들어가는 순간, 측정하는 것은 능력이 아니라 기억이 됩니다(자세한 내용은 제7장 참조).

## 평가 지표 체계

"어떤 과제로 평가할지"를 정했다면, 다음은 "어떤 차원을 측정해야 하는지"에 답해야 합니다. 본 절은 Agent 평가에서 자주 쓰이는 지표를 하나의 조회 가능한 "지표 사전"으로 정리합니다——과정에서 결과까지, 품질에서 안전까지 하나씩 정의와 적용 시나리오를 제시합니다. 앞서(τ-bench 절 등) 반복적으로 언급한 Pass@k, Pass^k 등 지표의 정밀한 정의도 여기서 제시합니다.

**과정 지표: 블랙박스에서 화이트박스로.**

최종 결과만 보는 것으로는 부족하며, Agent가 결과에 도달하는 과정도 마찬가지로 중요합니다. **행동 합법률**은 조작 중 유효하고 합법적인 비율을 측정합니다——무효 조작은 존재하지 않는 도구 호출, 잘못된 매개변수 유형 전달 등을 포함하며, 월권 조작은 권한 범위를 벗어난 행동을 가리킵니다. 높은 합법률은 Agent가 도구 생태계를 명확히 이해하고 있음을 보여줍니다. **도구 호출 정확률**은 한걸음 더 나아가 매개변수가 의미적으로 합리적일 것을 요구합니다: 검색 도구의 질의어는 정확히 요구를 표현해야 하고, 파일 조작의 경로는 올바른 대상을 가리켜야 합니다.

**경로 효율성**은 과제 완수의 경제성을 측정합니다: 스텝 수(사고-행동-관측 루프 횟수), 중복 동작(같은 키워드로 반복 검색, 같은 파일을 반복해서 읽기), 되돌리기 횟수(오류를 인지하고 수정하는 빈도——가끔의 되돌리기는 정상이지만, 빈번한 되돌리기는 사전 계획 부족을 나타냄). "합리적인 스텝 수"를 정의하려면 사람 전문가나 휴리스틱 알고리즘의 기준선을 세워야 합니다.

**검색 커버리지**는 정보 수집형 과제를 대상으로 합니다: Agent가 정보 공간을 충분히 탐색했는가? 검색 결과 첫 페이지만 보고 성급히 결론을 내리지는 않았는가? **비용과 지연**은 요청 횟수, 토큰 소모(입력/출력 비용 구분 필요, KV 캐시 재사용 고려), 벽시계 시간(모델 추론 + 도구 실행 + 네트워크 지연 포함)에 주목하며, 병목을 찾으려면 시간 분포를 추적해야 합니다.

**결과와 품질 지표.**

**과제 성공률**은 가장 직접적인 핵심 지표로, 계층화된 기준을 설계할 수 있습니다(핵심 목표는 반드시 달성해야 하고, 부차적 목표는 품질 점수에 영향). 통계 방식에서는 자주 혼동되는 두 지표를 구분해야 합니다:

- **Pass@k**: k번 시도 중 **최소 한 번**이라도 성공할 확률, "Agent가 할 수 있는가"에 답함
- **Pass^k**: k번 시도가 **전부 성공**할 확률, "Agent가 안정적으로 신뢰할 만한가"에 답함
- **Best@k**: k번 시도 중 **가장 좋은 한 번**의 점수(성공 여부가 아니라), "기회를 충분히 줬을 때의 품질 상한"을 측정하며 연속 점수를 가진 개방형 과제에 주로 사용

구체적인 숫자로 차이를 느껴봅시다: Agent의 단일 시도 성공률이 60%(즉 Pass@1 = 0.6)라고 가정하면, 5번 시도했을 때 두 지표는 각각: Pass@5 = 1 - 0.4^5 ≈ 99%(거의 확실히 최소 한 번은 성공), Pass^5 = 0.6^5 ≈ 7.8%(전부 성공할 확률은 매우 낮음)가 됩니다. 전자는 능력 상한을 평가하고 후자는 안정성을 평가하며, 혼용하면 오판을 부릅니다. 표6-3은 두 지표의 적용 시나리오와 오용 위험을 정리해, 회귀 테스트와 탐색적 평가 사이에서 올바른 지표를 선택하도록 돕습니다.

표6-3 Pass@k와 Pass^k의 적용 시나리오

| 평가 목적 | 어떤 지표를 쓸 것인가 | 오용 결과 |
|-----------------------------|-----------------|--------------------------------------------------|
| 안정성 검증（회귀 테스트） | Pass^k | Pass@k를 쓰면 불안정성을 은폐——Agent가 다섯 번 중 한 번만 성공해도 "통과"로 표시됨 |
| 능력 상한 평가（탐색적 과제） | Pass@k 또는 Best@k | Pass^k를 쓰면 우발적 변동으로 오탐——사소한 개선마다 실패로 판정됨 |

**안전과 준수 지표**는 프로덕션 배포에서 매우 중요합니다: 민감 조작 트리거(데이터 삭제 / 권한 수정 / 외부 통신 발송), 데이터 유출(로그에 비밀번호 출력 / 사적 문서를 외부 API로 전송), 위반 콘텐츠는 모두 **무관용 원칙**을 따라야 합니다——환각 거부권 항목과 같은 이치(후술 "Rubric 4원칙" 참조)——한 번의 심각한 안전 위반이 전체 평가를 부결시키며, 다른 차원의 우수한 성능으로도 면제되지 않습니다.

**강건성**은 불확실성 앞에서의 안정성을 측정합니다: 랜덤 시드 민감도(초기화가 다를 때 성능 차이가 얼마나 큰가), 페이지 변화 적응성(웹사이트 UI 업데이트가 완전한 실패를 유발해서는 안 됨), API 변동 허용도(임시 장애, 타임아웃, 형식 변화를 우아하게 처리할 수 있는가), 장기 기억 간섭(컨텍스트에 누적된 낡은 정보가 잘못된 결정을 유발하는가).

**실행 궤적과 최종 결과의 이중 커버리지**. 평가에서 간과하기 쉬운 구분 하나는: Agent가 실행 과정에서 "무엇을 말하고 무엇을 했는지"(즉 제1장에서 정의한 궤적, trajectory)와 "시스템이 최종적으로 어떻게 되었는지"(최종 결과, outcome)는 별개의 것이라는 점입니다. Agent가 "발권이 완료되었습니다"라고 말하는 것은 궤적 수준의 정보이고, 데이터베이스에 실제로 주문 하나가 생성된 것이 결과 수준의 검증입니다. 궤적만 보면 "말했지만 실제로 하지 않은" 경우를 놓치고, 결과만 보면 중간 단계가 잘못된 방향으로 갔는지 알 수 없습니다. Anthropic은 한 가지 예를 든 적이 있습니다: 항공권 예약 Agent가 실행 중 항공사 정책의 허점을 발견해 사용자에게 더 저렴한 방안을 찾아준 경우——만약 사전 설정된 실행 경로대로만 채점한다면 이 실행은 실패로 판정되지만, 최종 결과로 보면 사용자는 더 나은 방안을 얻었습니다. 따라서 두 유형의 평가를 모두 커버해야 체계적인 사각지대를 피할 수 있습니다.

**수동 표본 검사와 대항적 평가.**

자동 평가가 대부분의 경우 신뢰할 만하더라도 정기적인 수동 표본 검사가 필요합니다: 서로 다른 과제 유형, 성공/실패 사례, 경계 점수 부근의 모호한 사례를 커버하며, 결과뿐 아니라 채점 근거의 합리성도 검토해야 합니다. 수동 표본 검사는 한 걸음 더 나아가 **평가자 교정**으로 체계화할 수 있습니다: LLM 평가를 대규모로 투입하기 전에, 먼저 사람이 주석한 골드 세트(예: 각 과제 유형과 난이도를 아우르는 100-200개 사례)를 구축하고, 그 위에서 평가 모델(즉 LLM이 평가위원 역할을 하는 것, 그 메커니즘은 다음 절 LLM-as-a-Judge에서 자세히 다룸)과 사람 주석의 일치율(단순 일치율이나 Cohen's kappa 등의 일치도 지수, 후자는 우연히 맞춘 부분을 제거함)을 측정해, 사전 설정한 임계값(예: kappa 0.7 이상)에 도달해야만 평가 모델을 대규모 평가에 투입합니다. 이후 평가 모델이나 Rubric이 업데이트될 때마다 골드 세트에서 다시 교정해야 합니다. 이 단계가 없으면 LLM 평가의 점수는 인간 판단의 신뢰할 만한 대리가 아니라 그저 "또 다른 모델의 의견"일 뿐입니다. **대항적 평가**는 레드팀(Red Teaming)을 통해 도전적인 사례를 능동적으로 구성합니다: 겉으로는 완벽하지만 숨겨진 오류를 포함한 답변, 키워드를 쌓아 눈속임하는 답변, 평가 모델의 알려진 편향을 이용해 부당하게 높은 점수를 얻는 답변. **다중 평가위원 메커니즘**은 여러 독립적인 평가자가 각각 채점하고, 가중 평균이나 일치성 검사를 통해 최종 결과를 정합니다——평가자 간에 심각한 의견 불일치가 있으면 추가 수동 검토가 필요하다고 표시합니다.

## 자동화 평가 방법

평가 환경, 데이터셋, 명확한 지표 체계가 갖춰졌다면, 다음 핵심 문제는: 어떻게 점수를 매길 것인가입니다. 명확한 정답이 있는 과제(수학 문제, SQL 쿼리 등)는 단순한 이진 판정(맞음/틀림)만으로 충분하지만, 개방형 과제(고객 서비스 대화, 보고서 작성 등)는 더 정교한 평가 방법이 필요합니다.

코드 자동 검증은 표준 답이 있는 시나리오만 커버하며, 개방형 과제의 채점이야말로 본 절의 주제입니다. 그중 보상 신호의 밀도 설계(이진 보상에서 과정 보상, 생성형 보상까지)와 보상 모델의 훈련 방법은 제7장 후속학습 부분에서 체계적으로 논의하며, 본 절은 더 기초적인 문제에 답합니다: LLM으로 개방형 과제 출력의 품질을 어떻게 자동으로 평가할 것인가.

### LLM-as-a-Judge: 자동화 평가의 핵심

![그림6-4 LLM-as-a-Judge 파이프라인](images/fig6-4.svg)

왜 LLM-as-a-Judge가 필요할까요? 개방형 과제(보고서 생성, 고객 불만 처리, 창의적 콘텐츠 등)는 자동으로 비교할 표준 답이 없고, 수동 평가는 비용이 높고 규모화하기 어렵습니다. LLM-as-a-Judge는 언어 모델이 전문가가 정의한 채점 기준(Rubric)에 따라 평가하게 함으로써, 자동화 규모와 인간의 전문적 판단 사이에서 균형을 이룹니다. 하지만 이 방법에도 알려진 한계가 있습니다: 평가 모델은 자체 편향을 가질 수 있고(가장 전형적인 것이 **길이 편향**——내용이 더 정확하지 않더라도 더 길고 상세한 답변에 높은 점수를 주는 경향), 동일한 입력을 여러 번 평가해도 변동이 생길 수 있습니다. 길이 편향은 특히 별도로 방지해야 하며, 흔한 대응책은 세 가지입니다: Rubric에 장황함을 명시적으로 감점하도록 규정하고 같은 유형의 과제에 답변 길이 상한을 정하는 것, 쌍대 비교 시 두 후보의 길이를 먼저 비슷하게 맞춘 뒤 평가하는 것, 그리고 채점과 답변 길이의 상관관계를 정기적으로 감사하는 것——고득점이 거의 항상 긴 답변에 몰려 있다면 평가가 이미 길이에 치우친 것이므로 Rubric을 다시 손봐야 합니다. 이런 도전에 체계적으로 대응하려면 Rubric 설계가 다음 준칙을 따라야 합니다:

**Rubric（채점 기준）: LLM 평가의 근거.**

**Rubric 4원칙**（Scale AI, "Rubrics as Rewards"）:

（1）**전문가 지침 기반**——반드시 영역 지식을 반영해 핵심 사실과 추론 단계를 포착해야 합니다. 예를 들어 의료 질의응답의 Rubric은 진단 기준과 반드시 피해야 할 의학적 오류를 포함해야 하며, 전문적 기반이 부족한 Rubric은 언어의 유창성 같은 표면적 특징만 포착할 수 있습니다.

（2）**전면적 커버리지**——사실 정확성, 논리적 일관성, 완전성, 안전성을 아우르며, 긍정적 기준만 정의하는 것이 아니라 **함정(Pitfall)**——즉 고위험의 흔한 오류(의료 조언에서 검증되지 않은 치료법 추천 등)도 명확히 규정해야 합니다.

（3）**기준 중요도 가중치**——필수 항목(Essential), 중요 항목, 선택 항목, 함정 항목으로 나눕니다. **거부권 메커니즘(Veto)**을 지원합니다: 예를 들어 고객 서비스 시나리오에서 환각(허위 정보를 지어내는 것)은 전형적인 거부권 차원입니다——다른 차원이 아무리 우수해도 허위 정보가 나타나면 반드시 거부되어야 합니다. 이는 키워드 쌓기식 보상 부정행위를 방지하는 데도 도움이 됩니다.

（4）**자기 완결적 평가**——각 평가 항목은 독립적으로 조작 가능해야 하며 평가자의 영역 지식에 의존해서는 안 됩니다. "응답이 깊은 이해를 보여준다" 같은 추상적 기준은 피하고, "적어도 두 개의 권위 있는 이론을 인용해 결론을 뒷받침하는 방식을 정확히 설명했다" 같은 검증 가능한 기준으로 바꿔야 합니다.

핵심 실천: 각 차원마다 객관적으로 검증 가능한 채점 등급을 정의하고, 구체적인 예시와 **경계 사례**를 제공해 모호한 상황을 구분하도록 돕습니다. **보상 부정행위(Reward Hacking)**——즉 Agent가 과제를 실제로 완수하지 않고 높은 점수를 얻는 "지름길"을 찾아낸 경우——를 능동적으로 방지해야 하며, 환각, 사용자 비위 맞추기, 키워드 쌓기, 까다로운 문제 회피를 명확히 감점해야 합니다. Rubric은 반복적으로 개선되는 산물입니다——시범 사용을 통해 평가자 간 의견 불일치를 수집하고 점진적으로 다듬어, 추상적 준칙에서 상세한 판례집으로 점차 진화시켜야 합니다.

사용자 기억 Agent를 예로 들어, 4원칙을 충족하는 완전한 Rubric을 보여드리겠습니다. 테스트 질문: "제 딸의 소아과 의사가 누구죠?"（답을 얻으려면 두 번의 대화를 연결해야 함: 첫 번째 대화에서 "딸 이름은 Lily"라고 언급, 두 번째 대화에서 "Lily를 데리고 Dr. Chen을 만났다"고 언급）.

```yaml
rubric:
  dimensions:
    - name: 사실 정확성
      weight: essential        # 필수 항목
      scoring:
        4_우수: "정확히 Dr. Chen이라고 답하고, 딸 Lily와 연결함"
        3_양호: "정확히 Dr. Chen이라고 답했으나 Lily의 의사임을 언급하지 않음"
        2_보통: "올바른 의사를 제시했으나 불확실한 추가 정보를 덧붙임"
        1_미흡: "잘못된 의사 이름을 제시하거나 모른다고 답함"

    - name: 정보 완전성
      weight: important        # 중요 항목
      scoring:
        4_우수: "관련 정보(지난 진료 시점, 진단 결과 등)를 능동적으로 보충함"
        3_양호: "핵심 질문에 답했으며 누락 없음"
        2_보통: "핵심 질문에 답했으나 활용 가능한 연관 정보를 누락함"
        1_미흡: "핵심 정보가 빠짐"

    - name: 사고 정확성
      weight: important
      scoring:
        4_우수: "'딸=Lily'와 'Lily의 의사=Dr. Chen'이라는 두 세션 간 정보를 정확히 연결함"
        3_양호: "연결은 정확하나 사고 경로가 명확하지 않음"
        2_보통: "부분적으로만 정확히 연결함"
        1_미흡: "잘못 연결함（예: 사용자 자신의 의사를 딸의 의사로 착각）"

    - name: 환각 검출
      weight: veto             # 거부권 항목: 발동 시 총점 0점
      scoring:
        pass: "모든 정보가 과거 대화 기록에서 출처를 추적할 수 있음"
        fail: "대화에 없는 정보를 지어냄（예: 가상의 진료일, 진단 결과）"

  edge_cases:
    - "사용자에게 딸이 여러 명이고 각각 다른 의사를 만난다면, 어느 딸인지 되물어야 함"
    - "기억에 'Dr. Chen'과 '천 의사'가 동시에 존재하면 동일 인물로 인식해야 함"
```

**좋은 Rubric vs 나쁜 Rubric**: 위의 각 채점 등급은 검증 가능한 구체적 행동("정확히 Dr. Chen이라고 답함")을 제시하며, "기억에 대한 깊은 이해를 보여줌" 같은 객관적으로 판정 불가능한 서술이 아닙니다. 거부권 항목은 하한선을 명확히 합니다: 다른 차원이 모두 만점이라도 환각이 발생하면 즉시 0점으로 판정됩니다.

이 Rubric을 Agent의 실제 답변과 함께 평가 모델에 보내면, 평가 모델은 차원별로 점수를 매기고 이유를 제시합니다. 수십 개의 테스트 케이스에서 실행함으로써 Agent의 능력 부족을 체계적으로 발견할 수 있습니다——예를 들어 "세션 간 연결" 차원의 평균 점수가 2.1점에 불과하다면, 이는 기억 검색이나 정보 연결의 부족을 명확히 가리킵니다.

>

>
> 4단계 채점(우수/양호/보통/미흡)을 하고, 각 등급에 추상적 서술이 아닌 구체적인 판정 기준을 붙이세요. 환각 차원은 거부권 항목으로 설정하세요. 각 차원마다 예시와 경계 사례를 제공하세요.

>
> **목표**: 동일한 평가 세트에서 구조화된 기억과 비구조화된 검색의 우위 경계를 공정하게 비교합니다. 제3장의 두 프로젝트를 재사용해, `ch3/user-memory-evaluation`의 60개 테스트 케이스에서 세 가지 구성을 비교합니다——순수 Advanced JSON Cards(구조화 카드가 항상 컨텍스트에 상주, 검색 불필요), 순수 RAG(대화를 청크로 나눠 벡터 저장소에 저장, 반드시 검색 필요), 하이브리드 시스템(핵심 사실은 상주 + 원본 대화는 필요 시 검색).
>
> **검수 기준**: 세 가지 복잡도 층위(기초 회상 / 다중 세션 명확화 / 세션 간 숨겨진 연결)에서 성공률, 평균 스텝 수, 도구 호출 횟수, 지연, 비용을 기록하고, 각 방식의 실패 경계를 명확히 설명하세요——구조화가 무엇을 잃는지, 검색이 무엇을 놓치는지, 하이브리드가 실제로 시너지를 내는지. 구성 세부사항과 테스트 케이스는 부속 저장소를 참고하세요.
>

**동일 계열 모델 문제와 다중 소스 평가.**

Agent와 평가 모델이 같은 계열에서 나올 때, Agent는 평가 모델의 선호와 맹점을 이용하는 법을 학습할 수 있습니다.

**이는 정확히 굿하트의 법칙(Goodhart's Law)이 말하는 바입니다: 하나의 측정 지표가 최적화 목표가 되는 순간, 그것은 더 이상 좋은 측정 지표가 아니게 됩니다.** Agent가 특정 채점 시스템에서 훈련되거나 조정될수록, 진짜 능력을 향상시키기보다 그 시스템의 허점을 파고드는 경향이 강해집니다.

더 은밀한 문제는, Agent가 점차 평가 모델이 잘 탐지하지 못하는 유형의 오류를 회피하는 법을 학습해, 채점 시스템이 겉으로는 아무 문제 없어 보이게 만드는 것입니다.

완화 전략은 **다중 소스 이종 평가**입니다——서로 다른 모델 계열의 LLM 여러 개로 각각 평가합니다(예: Agent는 Claude를 쓰고, 평가는 GPT-5와 Gemini를 씀). 서로 다른 계열의 편향은 대개 직교적이라, Agent가 모든 평가자를 동시에 "속이기"는 어렵습니다. 동일한 Rubric을 사용해 모두가 같은 목표를 평가하도록 보장하고, 가중 평균이나 일치성 검사를 통해 결과를 집계합니다. 배포 단계에서는 단일 모델로 빠르게 평가할 수 있지만, 정기적으로 완전한 다중 소스 평가로 품질을 감사해야 합니다.

다중 소스 평가는 "어떤 모델로 평가할 것인가"의 문제를 해결하며, 이어서 "어떤 모달리티를 평가할 것인가"의 문제를 다뤄야 합니다——LLM-as-a-Judge의 능력을 텍스트에서 음성, 이미지, 영상으로 확장하는 것은 평가 커버리지의 또 다른 차원입니다.

**멀티모달 LLM-as-a-Judge.**

멀티모달 평가는 LLM-as-a-Judge를 음성, 이미지, 영상 영역으로 확장하며, 흔한 네 가지 방향은 다음과 같습니다.

- **TTS 평가**（TTS는 Text-to-Speech, 텍스트 음성 변환）: 정확성, 자연스러움, 음색 일관성, 감정 표현을 판단합니다. 이런 차원은 전통적인 WER（Word Error Rate, 단어 오류율）로는 포착하기 어려운 운율 문제를 발견할 수 있습니다.
- **ASR 평가**（ASR는 Automatic Speech Recognition, 음성 인식）: 의미적 영향을 판단합니다——"오늘 날씨"를 잘못 인식해도 큰 문제는 없지만, "천 원 송금"이 "만 원"으로 바뀌면 심각한 결과를 초래할 수 있습니다.
- **UI 평가**: **제안자-검토자**（Proposer-Reviewer） 메커니즘을 채택해 텍스트 오버플로우, 색상 대비, 버튼 위치 등의 문제를 검사합니다. 여기서 제안자-검토자는 **평가 방법**으로 사용되며, 제5장에서 **생성 시스템 구성요소**로 쓰인 용법과는 다르지만 핵심 메커니즘은 동일합니다——하나의 모델이 생성하고 다른 모델이 독립적으로 검토합니다.
- **영상 편집 평가**: 키프레임을 통해 편집 시작/종료 지점과 특수효과 적용이 올바른지 검증합니다.

> **실험 6-5 ★★: 완전 자동화 TTS 품질 평가 파이프라인 구축**
>
> 본 실험은 완전한 멀티모달 LLM-as-a-Judge TTS 품질 평가 시스템을 처음부터 설계하고 구현하도록 요구합니다.
>
> TTS 다차원 Rubric을 설계하세요: 정확성 차원은 모든 텍스트를 정확히 읽어냈는지(누락/오독/추가 없음) 검증하고, 자연스러움 차원은 음성이 유창한지(기계적 느낌, 부자연스러운 정지 유무, 운율이 인간의 습관에 부합하는지) 평가하며, 감정 표현 차원은 어조가 텍스트의 감정 색채에 부합하는지(의문문 상승조, 감탄문 강조, 슬픈 내용은 느린 말속도와 낮은 어조) 검사하고, 음색 일관성 차원은 참조 음성이 있을 때 화자 유사도를 평가합니다(멀티모달 모델이 참조 음성과 합성 음성을 함께 받아 비교).
>
> 다양한 테스트 말뭉치를 구축하세요: 다양한 길이(단문→긴 문단), 문체(뉴스/이야기/대화), 감정(중립/흥분/슬픔), 특수 도전(숫자/고유명사/다음자/방언 어휘). 평가 파이프라인을 구현하세요: TTS 생성 모듈은 주요 서비스(OpenAI, ElevenLabs, Fish Audio, Minimax, 두바오)에 연결하고, 멀티모달 평가 모듈은 Gemini 3.5 Flash를 사용해 합성 음성, 원본 텍스트, 참조 음성, Rubric을 함께 입력해 차원별로 점수를 매기고 상세 이유를 제시합니다. 평가 결과의 분포를 분석해 여러 TTS 모델이 각 차원에서 보이는 강약점을 식별하세요——어떤 모델은 정확성은 우수하지만 자연스러움이 부족할 수 있고, 다른 모델은 자연스러움은 높지만 특수 어휘에서 오류가 잦을 수 있습니다.
>

사람이 정의한 Rubric 외에도, 전용 **생성형 보상 모델**을 훈련해 평가를 자동화할 수 있습니다——이는 보상 모델의 훈련 방법과 관련되며, 제7장에서 자세히 논의합니다.

실제 모델 선정에서 자주 마주치는 질문은: "A와 B 중 어느 것이 더 나은가?"입니다. 쌍대 비교는 절대 점수에 의존하지 않는 평가 방식을 제공합니다.

### 쌍대 비교와 모델 순위 매기기

![그림6-5 Elo 평점과 쌍대 비교 순위](images/fig6-5.svg)

**Elo 평점**（원래 체스에서 쓰이던 순위 시스템）은 대량의 일대일 대결을 통해 모델의 상대적 능력을 정량화합니다: 점수 차가 클수록 강자의 예상 승률이 높아집니다. 예를 들어 모델 A가 1200점, 모델 B가 1000점이면, Elo 시스템은 A의 승률을 약 76%로 예측합니다. 만약 B가 뜻밖에 승리하면 B는 점수를 더 많이 얻고 A는 더 많이 잃습니다——이변의 결과가 더 큰 점수 조정을 가져오는 이 메커니즘이 순위를 실제 실력으로 빠르게 수렴시킵니다. 그 배후의 통계적 기반은 **Bradley-Terry 모델**입니다: 각 모델을 하나의 잠재적 "실력 점수"로 추상화하고, 일대일 대결에서 승패의 확률은 두 점수 차이로 결정되며, Elo는 이 모델을 온라인 업데이트 형태로 구현한 공학적 결과입니다.

Chatbot Arena는 익명 무작위 대결을 채택합니다——사용자가 모델의 정체를 모르는 상태에서 더 나은 응답을 선택하고, 수백만 번의 투표로 순위를 도출합니다. 이 방법의 장점은 "절대적 기준"을 정의할 필요가 없다는 것입니다——그저 "A와 B 중 어느 것이 더 나은지" 인간이 판단하기만 하면 됩니다. 하지만 한계도 있습니다: 순위 결과는 사용자가 어떤 질문을 던졌는지에 좌우됩니다——만약 많은 사용자가 마침 프로그래밍 문제를 물었다면, 프로그래밍에 능한 모델의 순위가 높게 나오지만 이것이 다른 과제에서의 실제 실력을 반영한다고 보기는 어렵습니다.

인간이 아닌 LLM이 쌍대 평가를 수행할 때는 **위치 편향(Position Bias)**도 방지해야 합니다——평가 모델은 특정 위치(대개 먼저 등장하는 쪽)에 나타난 후보를 체계적으로 선호하는 경향을 보이며, 두 후보의 내용을 완전히 맞바꿔도 판정이 바뀌지 않을 수 있습니다. 표준적인 완화 방법은 **순서를 바꿔 두 번씩 평가하기**입니다: A가 먼저 나올 때 한 번, B가 먼저 나올 때 한 번 평가해 두 결과의 평균을 냅니다. 더 엄격한 방식은 두 번의 판정이 일치할 때만 반영하고, 불일치하면 무승부로 기록하거나 사람에게 재검토를 보내는 것입니다. Chatbot Arena의 방식도 본질적으로 동일합니다——두 답변의 표시 위치를 무작위화해서, 대규모 표본에서 위치 편향이 서로 상쇄되도록 합니다.

**평가에서 훈련으로: 쌍대 비교 신호의 전이**. 쌍대 비교는 평가 수단일 뿐만 아니라 후속학습의 중요한 신호 원천이기도 합니다. 제7장에서 소개할 **GRPO**（Group Relative Policy Optimization, 그룹 상대적 정책 최적화）알고리즘은 바로 "어느 쪽이 더 나은지 비교하는" 평가 방식을 모델 훈련에 도입한 것입니다——핵심 아이디어는 같은 문제에 대해 여러 후보 답을 샘플링하고, 그들 사이의 상대적 우열(절대 점수가 아니라)로 우위(advantage)를 추정함으로써 PPO에서 별도로 가치망(critic, 기준선을 추정하는 데 쓰임)을 훈련하는 수고를 덜어낸다는 것입니다——GRPO가 덜어내는 것은 가치망이지 보상 신호 자체가 아니라는 점에 유의해야 합니다. 여전히 보상 모델이나 검증 가능한 보상 규칙에 의존해 각 후보의 우열을 평가합니다. 여기서는 복선만 깔아두며, 완전한 알고리즘 유도, PPO/DPO와의 비교, Agent 후속학습에서의 구체적 구현은 모두 제7장에서 다룹니다.

> **실험 6-6 ★★: 쌍대 비교 데이터로 모델 리더보드 구축**
>
> 본 실험은 Elo rating 계산 시스템을 처음부터 구현함으로써 Bradley-Terry 모델이 대량의 쌍대 비교에서 상대적 능력 점수를 어떻게 추출하는지 깊이 이해합니다. Chatbot Arena가 공개한 실제 투표 데이터셋(수백만 번의 사용자 익명 투표 포함)을 사용합니다.
>
> Elo rating 반복 업데이트 알고리즘을 구현하세요: 초기에 모든 모델 점수를 1000점으로 설정하고, 투표 기록을 시간 순으로 처리합니다. 매 대결마다 두 모델의 현재 점수 차이로 예상 승률을 계산하고, 실제 결과와 예상을 비교해 고정된 학습률로 조정합니다——승자는 가점, 패자는 감점, 조정 폭은 예상과의 편차에 비례합니다(이변의 패배는 더 큰 점수 변동을 유발). 최종 점수를 내림차순으로 정렬하고 일대일 승률 행렬을 계산해 공식 순위표와 비교하고, 순위가 대체로 일치하는지 검증하면 됩니다. 점수 하나하나까지 완전히 일치시킬 필요는 없습니다: Chatbot Arena 공식은 Bradley-Terry 최대우도 적합(전체 대국을 한 번에 풀며, 투표 순서와 무관)을 쓰는 반면, 여기서 구현하는 것은 온라인 증분 업데이트 방식의 Elo(결과가 학습률 K 계수와 처리 순서에 영향받음)입니다. 두 알고리즘은 전체 순위에서는 부합해야 하지만 구체적인 점수 값은 정확히 일치하지 않습니다.
>
> 실험 두 번째 부분에서는 순위 변화 애니메이션을 만드세요: 투표 데이터를 시간 단위(주 또는 월)로 나눠 각 시점마다 Elo 점수 스냅샷을 계산합니다. D3.js로 막대그래프 경주 애니메이션을 구현하세요(수평 막대 길이=점수, 세로 위치=순위, 시간에 따라 부드럽게 변화). 애니메이션을 관찰해 기술적 돌파 시점(특정 모델의 점수 급등), 경쟁 구도 변화, 모델 생애주기를 식별하세요.

## 평가 기반 모델 선정

모델 선정은 단순히 "가장 강한 모델을 고르는" 것이 아니라, 응용 시나리오에 따라 여러 차원 간에 평가 기반으로 절충하는 것입니다.

### 선정의 핵심 차원

**처리량**과 **지연**은 자주 혼동되는 두 지표이며, 대형 모델 추론이 두 단계로 나뉜다는 것만 알면 명확히 정리됩니다. **Prefill（선행 채움）**은 전체 컨텍스트를 한 번에 읽어들여, 사용자가 엔터를 누른 시점부터 첫 글자가 나타나기까지의 **첫 토큰 지연**을 결정합니다(업계에서는 **TTFT**, Time To First Token으로 측정)——컨텍스트가 길수록 prefill이 느려지고 TTFT가 커집니다. **Decode（디코딩）**는 이후 토큰 단위로 답을 생성하며, 후속 출력 속도(tokens/초)를 결정하고 사고 시간도 직접 좌우합니다: 50 tokens/s의 모델이 2000개의 사고 토큰을 생성하면 사고에만 40초가 걸립니다.

이 두 단계를 중심으로, 주요 처리량과 지연 지표는 다음과 같습니다:

- **입력 처리량 / 출력 처리량**: 각각 Prefill과 Decode의 속도에 대응합니다.
- **TTFT**: 대기 시간 더하기 Prefill 시간과 같으며, 사용자가 체감하는 "반응 속도"입니다.
- **사고 지연**: 서로 다른 모델이 생성하는 사고 토큰 수는 몇 배까지 차이날 수 있고, 사고 길이가 과제 효과와 반드시 양의 상관관계인 것도 아닙니다——공개 순위표만 보고 추론하지 말고 자신의 워크로드에서 각 모델의 사고 토큰 사용량과 그에 따른 이득을 실측해야 합니다.
- **p95 꼬리 지연**: 95%의 요청이 초과하지 않는 지연 시간. 평균값보다 실제 사용자 경험을 더 잘 반영합니다——평균은 대량의 빠른 요청에 의해 낮아져, 일부 사용자가 겪는 심각한 지연을 가려버립니다.

**비용**: 입력/출력/캐시 토큰의 가격 책정. 비용은 독립적으로 평가해서는 안 됩니다——저렴하지만 성공률이 낮은 모델은 잦은 재시도가 필요해 실제 지출이 오히려 더 클 수 있습니다. 과제별 평균 비용과 비용-성능비를 계산해야 합니다.

**성능**: Pass@1, Pass^k, Pass@k, Best@k 네 지표의 정밀한 정의는 앞서 "평가 지표 체계"를 참고하고, 여기서는 선정 맥락에서 어떻게 취사선택할지만 말합니다——일상적 시나리오에서는 가장 많이 쓰이는 Pass@1(단일 시도 평균 성공률)을 보고, 핵심 조작 시나리오에서는 Pass^k를 우선시해 "매번 오류가 없는지"의 안정성을 살피며, 탐색적 과제에서는 Pass@k나 Best@k를 우선시해 기회를 충분히 줬을 때의 능력 상한을 보고, 개방형 과제는 Rubric의 다차원 점수를 사용합니다.

**속도 제한과 신뢰성**: RPM(분당 요청 수)/TPM(분당 토큰 수) 제한은 동시성 능력에 영향을 미치며, 일부 API는 피크 시간대에 동적으로 한도를 조정하기도 합니다. 강건성 측면에서는 분포 외 데이터, 적대적 입력, 장시간 실행 안정성(모드 붕괴, 주의력 분산 등의 문제가 발생하는지)에 주목해야 합니다.

실무에서는 여러 모델을 함께 쓰는 전략을 채택할 수 있습니다: 경량 모델로 단순 요청을 처리해 비용을 낮추고, 강력한 모델로 복잡한 과제를 처리해 품질을 보장하거나, 특정 하위 과제(이미지 이해, 코드 생성 등)를 전문 모델에 맡기고 하위 Agent 메커니즘으로 협력하게 할 수 있습니다. 이런 이종 조합은 평가를 통해 검증해야 하며, 전체 이익이 증가한 시스템 복잡성을 초과하는지 확인해야 합니다.

### Agent 시스템의 비용 분석

비용은 모델 선정에서 과소평가되기 쉬운 차원입니다. 여러분의 Agent가 이미 프로덕션 환경에 있거나 진입을 준비 중이라면, 이 절의 비용 분석은 건너뛰어서는 안 됩니다.

앞 절에서는 비용을 모델 선정의 핵심 차원 중 하나로 꼽았지만, Agent 시나리오의 비용은 단순한 토큰 가격 책정보다 훨씬 복잡합니다——다중 턴 추론, 도구 호출, 컨텍스트 누적이 비용을 비선형적으로 증가시킵니다. 체계적인 비용 분석은 평가 체계에서 빠질 수 없는 부분이며, 프로덕션 배포의 필수 전제이기도 합니다.

**비용의 구성 요소.**

Agent 시스템의 비용은 세 층위로 분해할 수 있습니다:

**모델 추론 비용**은 가장 직접적인 부분으로, 입력 토큰과 출력 토큰의 소모량으로 결정됩니다. 하지만 Agent 시나리오에서는 자주 간과되는 두 가지 증폭 요인이 있습니다. 하나는 **컨텍스트 누적 효과**입니다: Agent가 매 턴 LLM을 호출할 때마다 이전의 모든 대화 이력과 도구 반환 결과를 함께 보냅니다(모델이 컨텍스트를 이해하려면 필요한 일). KV 캐시(즉 이미 처리된 컨텍스트를 캐싱해 중복 계산을 피하는 것)를 잘 활용하지 못하면 비용이 매우 빠르게 증가합니다——1턴에서 1000토큰, 2턴에서 2000토큰, 3턴에서 3000토큰을 보내면, 총량은 3×1000=3000이 아니라 1000+2000+3000=6000이 되며, 턴 수가 많아질수록 차이가 커집니다. 다른 하나는 **사고 토큰 비용**입니다: 사고를 지원하는 모델은 대량의 사고 토큰을 생성하며, 이 토큰들은 사용자에게 보이지 않아도 마찬가지로 비용에 산정됩니다.

**도구 호출 비용**은 외부 API 비용(검색 엔진 건당 과금, 데이터베이스 쿼리가 소모하는 컴퓨팅 자원), 코드 실행의 샌드박스 자원, 그리고 간과하기 쉬운 간접 비용——도구 반환 결과가 컨텍스트에 주입된 후 발생하는 토큰 비용을 포함합니다. 한 번의 웹 검색이 반환하는 내용이 2000-5000 토큰을 차지할 수 있고, 이후 매 턴의 추론에서 입력으로 반복 과금됩니다.

**인프라 비용**은 벡터 데이터베이스(RAG 검색용), 메시지 큐, 관계형 데이터베이스, 로그와 추적 저장소(관측가능성용) 등의 운영 오버헤드를 아우릅니다.

구체적인 예시로 비용의 비선형 증가를 설명하겠습니다. 표6-4는 본 장 서두의 고객 서비스 환불 Agent를 예로 들어, 예시적인 토큰 가격 매개변수를 사용해 3턴 호출 비용을 분해함으로써 다중 턴 컨텍스트 누적과 캐시 적중이 비용에 미치는 영향을 보여줍니다.

표6-4 고객 서비스 환불 Agent의 3턴 비용 예시

| 턴 | 조작 | 입력 토큰 | 출력 토큰 | 이번 턴 비용 |
|--------|-----------------------------------|-------------------------------|----------|---------|
| 1 | 시스템 프롬프트 + 사용자 질문 → 주문 조회 결정 | 2,500（이 중 2,000은 시스템 프롬프트） | 150 | $0.0098 |
| 2 | 이전 턴 전체 + 도구 반환 → 환불 신청 결정 | 3,200（2,000 캐시 적중） | 120 | $0.0060 |
| 3 | 이전 턴 전체 + 환불 결과 → 사용자 응답 | 3,800（3,200 캐시 적중） | 200 | $0.0058 |
| **합계** | | **9,500** | **470** | **$0.022** |

주: 입력 $3/백만 토큰, 출력 $15/백만 토큰의 예시 가격으로 계산했으며, 캐시 적중분은 입력 가격의 10%로 과금된다고 가정합니다(업체마다 할인율이 다름, 예를 들어 Anthropic의 캐시 쓰기는 입력 가격의 약 1.25배, 읽기는 약 0.1배이며, 여기서는 읽기 할인만 고려해 단순화함).

세 턴의 호출 합계는 $0.022로——얼핏 매우 저렴해 보입니다. 캐시를 전혀 쓰지 않았다면 3턴 입력 비용은 약 $0.029, 출력을 더하면 합계 약 $0.036입니다——이 예시에서 캐시는 입력 비용의 절반 가까이를 절감했으며, 후술할 "KV 캐시는 입력 비용을 30%-60% 낮출 수 있다"는 경험적 구간과 일치합니다. 하지만 몇 가지 증폭 요인에 주의해야 합니다: 사고 모드를 켜면 턴마다 추가로 500-2,000개의 사고 토큰이 생성되어 비용이 3-5배로 뛸 수 있습니다. 어느 한 턴에서 도구가 5,000토큰짜리 웹페이지 내용을 반환하면 이후 매 턴마다 이 토큰들에 대해 비용을 지불해야 합니다. Agent가 우회로를 타서 10턴이 걸려 완수한다면, 컨텍스트가 20,000+토큰까지 누적되어 비용이 위 단순 시나리오를 훨씬 초과합니다. 따라서 비용 최적화의 핵심은 저렴한 모델을 고르는 것이 아니라 턴 수와 컨텍스트 증가를 통제하는 것입니다.

**비용 최적화 전략.**

정량적 관점에서 입력 측에 작용하는 세 가지 지렛대가 가장 효과적입니다: **KV 캐시 재사용**（접두사를 안정적으로 유지해 반복되는 시스템 프롬프트, 도구 정의, 이전 턴을 캐시 가격으로 과금——입력 토큰 비용을 30%-60% 낮출 수 있으며, 위 3턴 예시에서도 캐시가 입력 비용의 절반 가까이를 절감했습니다）, **컨텍스트 압축**（이력 궤적을 압축하고 중복된 도구 반환 결과를 잘라내 컨텍스트 증가 속도를 직접 통제하며, 장기 과제에서 효과가 특히 두드러짐）, **모델 계층형 라우팅**（단순 요청은 경량 모델에, 복잡한 사고는 강력한 모델에 맡김）. 이 세 가지 수단의 구체적 구현——접두사 안정성 설계, 압축 시점과 전략, 라우팅 메커니즘——은 이미 제2장에서 자세히 논의했으므로 여기서는 재론하지 않습니다. 본 장에서는 평가와 운영 관점에 특화된 두 가지 수단을 추가로 다룹니다.

**비동기 일괄 처리**는 실시간이 아닌 과제를 모아 일괄 처리함으로써 API 제공사의 대량 가격 할인을 활용합니다. 자체 배포 시나리오에서는 유휴 시간대의 GPU 활용률을 높일 수도 있습니다.

**비용 모니터링과 예산 통제.**

프로덕션 환경에서는 실시간 비용 모니터링 체계를 구축해야 합니다: 과제 유형, 모델, 사용자 등의 차원으로 토큰 소모와 API 비용을 추적합니다. 동시에 과제별 비용 상한을 설정해——Agent가 루프에 빠지거나 지나치게 깊이 탐색할 때 자동으로 종료함으로써 단일 과제가 비정상적으로 높은 비용을 초래하는 것을 방지합니다.

> **실험 6-7 ★: Agent 과제의 엔드투엔드 비용 분석**

### 평가 기반의 지속적 반복

모델 선택은 일회성 결정이 아니라, 모델의 진화에 따라 동적으로 조정해야 하는 지속적인 과정입니다. 본 장 서두에서 이미 "평가 체계를 갖추면 모델 진화를 빠르게 따라잡을 수 있다"는 핵심 이념을 제시했습니다. 아래에서는 구체적인 모델 전환 사례를 통해, 이 체계가 실제 의사결정에서 어떻게 작동하는지 설명하겠습니다.

여러분의 Agent 시스템이 현재 Claude를 기반으로 구축되어 있고, 도구 호출과 복잡한 오케스트레이션에서 우수한 성능을 보인다고 가정합시다. 어느 날 Gemini가 새 모델을 출시했고, 공개 벤치마크에 따르면 여러 지표에서 Claude를 앞서며 가격도 더 저렴합니다. 이때 마주하는 문제는 "Gemini가 Claude보다 강한가"가 아니라 "**내 특정 과제에서 Gemini가 Claude보다 나은가? 얼마나 나은가? 전환 비용은 무엇인가?**"입니다.

완성도 높은 평가 체계를 갖춘 팀은 몇 시간 안에 답을 낼 수 있습니다: 자신의 평가 데이터셋에서 새 모델을 실행해 과제 성공률, 도구 호출 정확률, 지연, 비용을 비교합니다. 새 모델이 단순 과제에서는 확실히 더 우수하고 저렴하지만, 복잡한 다중 턴 도구 오케스트레이션이 관여하는 핵심 시나리오에서는 오히려 성공률이 5% 하락한다는 것을 발견할 수도 있습니다——이 차이가 잡음 대역폭을 넘어선다는 것을 확인한 후(후술 "평가 결과의 통계적 유의성" 참조), 여러분의 결정은 "단순 과제는 새 모델로 이전해 비용을 낮추고, 복잡한 과제는 기존 모델을 유지해 품질을 보장한다"는 차별화 전략이 되며, 무분별한 전면 전환이 아니게 됩니다. 이런 정교한 데이터 기반 의사결정은, 사전에 평가 체계를 구축해 두었을 때만 가능합니다.

> **실험 6-8 ★★: 다차원 모델 성능 벤치마크 테스트**
>
> 주류 LLM과 서로 다른 API 제공사에 대해 전면적인 벤치마크 테스트를 수행해, 다차원 모델 선정 의사결정 데이터베이스를 구축합니다.
>
> 테스트 범위를 선택하세요: GPT 계열, Claude 계열, Gemini 계열, Doubao 계열 등 폐쇄형 SOTA 모델과 Qwen, Kimi, DeepSeek 등 오픈소스 모델. 동일 모델에 대해 서로 다른 API 제공사를 테스트하세요(예: DeepSeek 공식 vs Siliconflow), 제3자 성능 모니터링 플랫폼(Artificial Analysis 등)의 결과를 검증하세요.
>
> 표준화된 테스트 워크로드를 설계하세요: 입력 처리량 테스트는 고정 길이 컨텍스트(8K/32K/128K 토큰)를 사용하고, 출력 처리량 테스트는 고정 길이 응답(512/2048 토큰) 생성을 요청합니다. 지연 테스트는 TTFT(첫 토큰 생성 시간)와 엔드투엔드 지연을 포함하며, 사고를 지원하는 모델은 사고 길이와 사고 지연을 별도로 측정하세요. 각 구성마다 최소 100번의 요청으로 표준편차/p50/p95/p99를 계산하세요——높은 지연 편차는 사용자 경험이 불안정하다는 뜻입니다.
>
> API의 가용성과 안정성을 평가하세요: 일주일 동안 매시간 한 번씩 탐지해 성공률, 오류 유형, 장애 시간을 기록합니다. 장애율, MTTR(평균 복구 시간), 최대 연속 가용 시간을 계산하세요. 속도 제한의 실제 임계값을 테스트하세요——동시성을 점진적으로 높여 제한점을 찾아 RPM/TPM 상한을 기록합니다. 종합 비용을 계산하세요: 가격 정보(입력/출력/캐시 토큰 단가)를 수집하고 KV 캐시의 영향을 고려해 전형적인 다중 턴 Agent 과제의 평균 비용을 계산하세요.
>
> **실험 6-9 ★★: 사용자 기억 시스템의 엔드투엔드 선정 평가**
>
> **전제 조건**: 제3장의 컨텍스트 검색 또는 에이전틱 RAG 실험을 완료해야 합니다.
>
> **목표**: 사용자 기억 검색 Agent에 대해 전체 체인 선정 평가를 수행하여, 임베딩 모델, reranker, Agent 주 모델 세 가지 선택 지점이 검색 품질, 지연, 비용에 어떻게 함께 영향을 미치는지 살펴봅니다. `ch3/contextual-retrieval-for-user-memory` 또는 `ch3/agentic-rag-for-user-memory`를 재사용해, 60개 테스트 케이스에서 비교합니다.
>
> **검수 기준**: 세 가지 선택 지점을 각각 훑어보세요——임베딩 모델(BGE-M3 / OpenAI / 두바오 등, top-5 검색 정확도, 지연, 비용 기록), reranker(reranker를 사용하지 않는 기준선 포함, 한계 가치 정량화), 주 모델(동일한 검색 구성에서 성공률과 도구 사용 효율 비교). 핵심은 구성요소 간 시너지를 읽어내는 것입니다: 더 강한 임베딩이 reranker를 불필요하게 만들 수도 있고, 더 강한 주 모델이 검색의 부족함을 메울 수도 있습니다——선정은 개별 최강을 고르는 것이 아니라 체계적인 절충입니다. 구성 세부사항은 부속 저장소를 참고하세요.
>

## 평가 결과의 통계적 유의성

"몇 시간 안에 전환 결정을 낸다"에는 암묵적 전제가 있습니다: 관찰된 점수 차이가 실제 신호이지 표본 잡음이 아니라는 것입니다. 평가 세트 규모가 제한적이고 모델 출력에는 불확실성이 있으니, 이 전제가 자동으로 성립하지는 않습니다.

잡음 대역폭을 대략 추정하는 도구는 **이항 분포의 표준오차**（standard error, 성공률이 표본 무작위성으로 인해 요동치는 폭을 나타내며, 값이 클수록 그 성공률의 신뢰도가 낮음을 의미）입니다. n개의 테스트 케이스에서 성공률 p를 측정했다면, 표준오차는 약 √(p(1-p)/n)입니다. 구체적인 예를 들면: 100개 케이스, 성공률 70%면 표준오차 ≈ √(0.7×0.3/100) ≈ 4.6%입니다. 직관적으로 95% 신뢰구간(실제 성공률이 그 안에 있을 확률이 약 95%인 범위)은 약 p ± 표준오차 2개, 즉 70% ± 9퍼센트포인트입니다. 즉 "새 모델 73% vs 기존 모델 70%" 같은 3퍼센트포인트 차이는 완전히 잡음 대역폭 안에 있습니다——두 성공률을 서로 독립적이라 가정하고 비교하면, 차이값의 표준오차는 개별의 √2배 정도입니다(여기서는 약 6.5%). 하지만 강조할 점이 있습니다: 이 √2는 "두 측정이 서로 독립적"이라는 계산이며, 실전에서 두 구성은 대개 **같은 배치의 과제**에서 실행되어 표본이 독립적이지 않습니다——독립 가정은 그저 "이 정도 차이가 신뢰할 만한지"를 빠르게 판단하기 위한 다소 보수적인 상한선일 뿐입니다. 이 보수적 기준으로 봐도, 3%의 점수 차는 6.5%의 잡음 규모보다 훨씬 작으므로, 이를 근거로 모델을 전환하는 것은 동전 던지기와 별 차이가 없습니다.

Agent 평가에는 한 층의 불확실성이 더 있습니다: 같은 모델, 같은 데이터셋이라도 두 번의 실행 결과가 표류할 수 있습니다——온도 샘플링, 도구 반환의 변동, 환경 타이밍이 모두 무작위성을 유입시킵니다. 따라서 단일 실행 수치를 의사결정의 근거로 삼아서는 안 되며, **여러 번 실행해 평균을 내야** 합니다(각 구성을 3-5회씩 실행 등), 평균과 변동 범위를 함께 보고해야 합니다. 후술할 가상 사례에서 각 구성마다 "5회 실행(서로 다른 무작위 시드 사용)"이라고 명시하는 것도 바로 이 때문입니다.

여기서 실용적인 원칙 하나가 나옵니다: **점수 차이가 잡음 대역폭보다 작으면 전환 결정을 내리지 않는다**. 하지만 "전환하지 않는다"고 결론짓기 전에, 먼저 더 민감하고 더 정확한 분석 방법으로 전환해야 합니다. 같은 배치의 과제에서 두 구성을 비교하는 올바른 기본 방법은 **대응 분석(paired analysis)**입니다: 문항별로 두 구성의 승패를 비교해, 결과가 다른 케이스(한쪽은 맞고 한쪽은 틀림)만 살펴보고, McNemar 검정 같은 방식으로 차이가 유의한지 판단합니다. 대응 분석은 "문항 자체의 난이도"라는 공통 잡음원을 제거하기 때문에, 같은 표본 크기에서 "두 독립 성공률의 차"보다 훨씬 민감합니다——앞서 독립 가정에 기반한 √2 추정은 인터넷 연결 없이 암산으로 할 수 있는 보수적인 거름망일 뿐, 명백히 미달인 차이를 빠르게 걸러내는 데 쓰입니다. 대응 분석으로도 여전히 차이가 불확실하다면 표본 확대를 고려하세요: 표준오차는 √n에 비례해 줄어들므로, 표본을 100에서 400으로 늘려야 잡음 대역폭이 절반으로 줄어들어 확대 비용이 매우 큽니다. 반대로 어떤 개선의 예상 이득이 겨우 2-3퍼센트포인트인데 평가 세트가 몇십 개 케이스에 불과하다면, 이 평가로는 그 개선이 실제로 효과가 있는지조차 분별할 수 없습니다——이럴 때는 Agent를 계속 반복하기보다 평가 세트를 확충하는 것이 우선입니다.

또 하나 간과하기 쉬운 함정은 **다중 비교**입니다. 여러 가설을 병렬로 검증할 때 "적어도 하나의 결론이 거짓 양성일" 확률은 가설 수에 따라 빠르게 누적됩니다——각 개별 결론이 95% 신뢰도를 사용했더라도, 6개의 가설을 동시에 보면 적어도 하나에서 거짓 양성이 나올 확률은 1 − 0.95^6 ≈ 26%입니다. 병렬로 실행하는 가설이 많을수록 "뭔가 하나는 유의해 보이는" 우연을 피하기 어렵습니다. 대응 방법은 두 가지입니다: 다중 가설 시나리오에서는 개별 결론의 신뢰 문턱을 조여야 하거나(Bonferroni 방식으로 가설 수에 따라 유의성 임계값을 엄격히 조정), 도출된 긍정적 결론에 대해 독립적인 검증성 재실행을 해서 재현된 경우에만 채택해야 합니다. 후술할 "데이터에서 가설로" 절에서는 H1-H4 네 가지 진짜 병렬 가설을 검증합니다(H5, H6은 조건부로 시작되며 앞의 넷과 동시에 실행되지 않음). 이는 바로 이 함정의 전형적인 시나리오입니다.

평가 기반 의사결정은 고품질 데이터에 의존하며, 이 데이터는 Agent 실행 과정에 대한 체계적 기록에서 나옵니다——이것이 관측가능성이 해결하는 문제입니다.

## Agent의 관측가능성

평가 기반 의사결정(모델 선정이든 지속적 반복이든)은 모두 고품질 실행 데이터에 의존합니다. 아래에서는 먼저 이런 데이터를 체계적으로 수집하는 방법(관측가능성)을 소개하고, 이어서 평가 결과를 시스템 개선으로 전환하는 방법을 논의합니다.

![그림6-6 관측가능성 기술 스택](images/fig6-6.svg)

관측가능성（Observability）이라는 개념은 분산 시스템 분야에서 빌려온 것입니다: 시스템 내부를 직접 열어 무엇을 하고 있는지 볼 수는 없고, 시스템이 출력하는 로그, 지표, 추적 데이터를 통해 무슨 일이 일어났는지 추론할 수밖에 없습니다——의사가 환자 체내를 직접 볼 수 없고 체온, 혈압, 영상 등 외부 신호를 통해서만 문제를 진단하는 것과 비슷합니다. Agent 시스템은 이를 더 어렵게 만듭니다: 같은 입력이라도 다른 출력을 낼 수 있고, 다중 턴 추론과 도구 호출로 실행 경로가 극도로 복잡하며, 모델의 "사고" 과정은 외부에서 완전히 불투명합니다.

관측가능성의 가치는 먼저 **문제 진단**에 있습니다: 완전한 궤적이 있으면 개발자가 추측이 아니라 전체 과정을 리플레이할 수 있습니다. 그다음은 **지속적 최적화**의 기반입니다——어떤 과제가 다중 턴 반복이 필요한지, 어떤 도구의 성공률이 가장 낮은지, 어떤 검색 쿼리가 항상 빈 결과를 반환하는지 볼 수 있습니다. **비용 관리** 측면에서는, Agent 실행 비용이 과제에 따라 한두 자릿수 차이가 날 수 있어, 추적을 통해 비정상적으로 높은 비용의 사례를 식별할 수 있습니다. 마지막으로, 누적된 궤적 데이터는 후속 시스템 최적화와 모델 개선에도 기반을 제공합니다.

Agent 관측가능성의 데이터 기반은 **추적(Trace)**이며, 그 데이터 구조는 분산 시스템의 span 트리 모델을 그대로 사용합니다: 하나의 과제 실행이 하나의 trace에 대응하고, 그 안의 매 LLM 호출, 매 도구 호출, 매 검색이 하나의 **span**(입력 출력, 시작·종료 시간, 토큰 소모, 오류 정보를 기록하는 실행 단위)이며, span 간의 부모-자식 관계가 하나의 실행 트리를 이룹니다——예를 들어 "Agent 메인 루프" span 아래에 여러 개의 "LLM 호출"과 "도구 호출" 자식 span이 걸려 있습니다. 이 계층에는 이미 표준화된 프로토콜이 있습니다: **OpenTelemetry**는 범용 분산 추적 표준이고, **OpenInference** 등의 규격은 그 위에서 LLM 애플리케이션 고유의 의미론적 규약(프롬프트, 모델 매개변수, 토큰 사용량 등을 어떻게 기록할지)을 정의합니다. 표준 프로토콜을 채택하는 이점은 수집과 분석을 분리할 수 있다는 것입니다——같은 추적 데이터를 서로 다른 분석 백엔드에 연결할 수 있어 단일 플랫폼에 종속되지 않습니다.

LangSmith는 이 분야의 대표적인 플랫폼 중 하나이며(비슷한 위치의 Langfuse, Arize Phoenix 등도 있음), 관측가능성, 평가, 최적화를 하나의 폐쇄 루프로 통합합니다. 매 실행마다 추적 세션을 생성하며, 그 안의 모델 호출, 도구 사용, 지식 검색이 독립적인 실행 단위로 기록되고, 인과관계 사슬로 연결되어 하나의 실행 트리를 형성합니다. 각 단위는 완전한 입력 출력, 시간 정보, 비용 데이터, 오류 정보를 기록합니다. 플랫폼은 비동기 일괄 데이터 수집을 채택해 추적 자체가 Agent의 응답 지연에 영향을 주지 않도록 합니다.

플랫폼은 또한 A/B 테스트(일부 사용자 트래픽을 새 버전으로 라우팅해 각 지표를 자동으로 비교하고, 빠른 롤백이나 점진적 확대를 지원), 프롬프트 버전 관리(각 버전이 런타임 성능 데이터와 연결됨), 협업적 개발(팀원이 추적 데이터와 문제 사례를 공유)을 지원합니다. 프로덕션 환경의 대량 실제 데이터는 지속적 개선의 금광입니다——예상치 못한 시나리오를 발견하고 가장 최적화가 필요한 기능 지점을 식별할 수 있습니다.

관측가능성 데이터의 가장 가치 있는 활용처는 **평가 자산으로의 환류**입니다. 실용적인 폐쇄 루프 하나는: 프로덕션 궤적에서 실패와 의심 사례를 걸러냄 → 비식별화 처리(사용자 프라이버시, 키 등 민감 필드 제거) → 평가 세트의 새로운 사례와 회귀 테스트로 정착시킴. 이렇게 하면 평가 세트는 더 이상 일회성으로 구축된 정적 집합이 아니라, 제품 진화에 따라 지속적으로 실제 사용자 분포에 가까워지는 살아있는 자산이 됩니다——오늘 온라인에서 드러난 실패 패턴이 내일이면 그 하한선을 지키는 회귀 케이스가 됩니다. 이것이 바로 관측가능성과 본 장 평가 주제의 접점입니다: 관측가능성은 실제 세계에서 무슨 일이 일어났는지 "보는" 역할을 맡고, 평가는 이런 관찰을 반복 검증 가능한 기준으로 굳히는 역할을 맡습니다.

관측가능성은 몇 가지 도전에 직면합니다:

- **데이터량과 프라이버시의 균형**: 트래픽이 많은 시스템은 매일 수 TB의 추적 데이터를 생성하는 동시에 데이터 보호 규정을 준수해야 합니다.
- **인과 귀속의 복잡성**: 궤적에서 근본 원인을 자동으로 식별하려면 여전히 더 지능적인 분석 알고리즘이 필요하며, 최신 연구는 인과 추론과 반사실적 분석을 시도하고 있지만 아직 성숙하지 않았습니다.
- **다중 Agent 시스템의 추적 난제**: 여러 Agent를 넘나드는 실행 흐름 추적은 마이크로서비스 간 API 호출보다 더 복잡하고 의미론적입니다.
- **실시간 방어와 사후 분석의 균형**: 고위험 시나리오는 능동적 방어가 필요하지만, 이는 추가적인 지연과 오탐을 초래합니다.

ML 기술이 도구 체인에 깊이 통합됨에 따라, 미래의 관측가능성 플랫폼은 이상을 자동으로 식별하고 근본 원인을 찾아낼 수 있을 것으로 기대됩니다.

완비된 평가 체계와 데이터셋이 갖춰졌다면, 관건은 평가 결과를 실질적인 시스템 개선으로 전환하는 것입니다.

## Benchmark 보고서에서 시스템 개선까지

**아래는 시범적인 가상 사례입니다**, 구체적인 데이터로 Benchmark 보고서에서 시스템 개선에 이르는 완전한 의사결정 흐름을 설명합니다. 데이터는 가상의 값이며, 방법론을 시연하는 것이지 실제 실험 결과를 보고하는 것이 아닙니다.

![그림6-7 Benchmark에서 개선까지의 폐쇄 루프](images/fig6-7.svg)

Harness 공학의 관점에서 보면, 이 절은 본질적으로 Harness 반복 최적화의 방법론을 다룹니다——평가 데이터로 Harness의 취약 지점을 짚어내고(컨텍스트 부족? 제약 결여? 검증 부족? 피드백 지연?), 목표를 정해 개선한 뒤 다시 평가하여, Harness가 지속적으로 진화하는 폐쇄 루프를 형성합니다.

Benchmark 보고서 분석을 시작하기 전에, 간과하기 쉬운 원칙 하나가 있습니다: **Agent 성능이 하락한 것을 발견하면 먼저 평가 시스템 자체를 점검하고, 그다음에 Agent를 손대야 합니다**. 흔한 오류는 점수 하락을 보자마자 바로 Agent 코드를 수정하면서, 평가 시스템 자체에 문제가 먼저 생겼을 가능성을 간과하는 것입니다——왜곡된 신호에 기반해 방향을 조정하면, 애초에 방향 자체가 틀렸을 수 있습니다. 평가 시스템의 흔한 오류 원인으로는: 실행 환경의 자원 부족으로 프로세스가 강제 종료됨(무작위적인 실패로 나타남), 평가기 자체에 버그가 있어 정답을 실패로 판정, 테스트 케이스와 프로덕션 시나리오 간의 괴리 등이 있습니다. 이런 문제들은 결과 수치상으로는 모델 퇴화와 완전히 똑같이 보이며, 완전한 궤적을 검토해야만 구분할 수 있습니다.

### Benchmark 보고서 읽기: 문제 발견의 기예

구체적인 사례로 Benchmark 보고서를 읽는 방법을 설명하겠습니다. AndroidWorld에서 어떤 Agent를 평가해 두 개의 핵심 보고서 표——문항별 성능 목록과 능력 태그별 성능 행렬——를 얻었다고 가정합시다. 보고서의 가치는 전체 성공률이라는 단일 숫자에 있는 게 아니라, 그것이 드러내는 구조적 약점에 있습니다.

문항별 표는 명확한 패턴을 보여줍니다: 대부분의 일반적인 과제의 성공률이 거의 100%에 가깝습니다. 이런 성공 과제는 녹음, 사진 촬영, 연락처 관리, 메모 작성, 파일 조작, 시스템 설정 등 흔한 시나리오를 아우르며, 평균 십여 스텝의 조작이 필요하고, 가장 복잡한 것은 수십 스텝에 이릅니다. Agent가 이렇게 긴 조작 시퀀스를 유지하며 성공적으로 완수한다는 것은, 표준 시나리오에서의 계획과 실행 능력을 증명합니다.

실패는 소수의 영역에 고도로 집중되어 있습니다: 문자 메시지 답장, Wi-Fi 켜기/끄기 및 상태 확인, 할 일 목록 조회, Wi-Fi+블루투스 조합 조작, VLC 재생목록 생성 등. 겉으로는 이런 과제들이 서로 무관해 보이지만, 능력 태그 행렬이 그들의 공통점을 드러냅니다.

**능력 태그 행렬**은 진단의 핵심입니다——모든 과제를 필요 능력과 난이도로 교차 분류합니다. 보고서에는 흔히 성공률이 극히 낮은 몇 개의 능력 차원이 나타납니다: transcription(이미지/영상에서 정보를 전사, 시각적 이해의 결함을 드러냄), math_counting(문제는 수학 능력 자체에 있지 않고——현대 LLM의 수학 능력은 강력함——Agent가 계산이 필요함을 인식하고, 인터페이스에서 숫자를 추출하고, 그 결과를 조작 시퀀스로 매핑할 수 있는지에 있음), complex_ui_understanding(표준화된 UI 패턴에 크게 의존해, 비표준 레이아웃을 만나면 붕괴함).

두 표를 결합해 분석하면 실패 원인이 명확해집니다: 할 일 목록 조회 실패는 해당 앱의 비표준 UI가 Agent로 하여금 과제 목록을 읽고 걸러내지 못하게 함을, Wi-Fi 조작 실패는 시스템 설정 화면의 컨트롤 계층 구조가 Agent의 이해 범위를 넘어섬을, VLC 재생목록 실패는 전문 앱의 복잡한 인터페이스에서 Agent가 생성 진입점을 찾지 못함을 가리킵니다.

### 데이터에서 가설로: 개선 로드맵 구축

**표층 가설**（비용이 낮고 서로 독립적이며 병렬 검증 가능）: H1은 Wi-Fi 조작에 시스템 설정 내비게이션 힌트 추가(Agent가 스위치를 조작할 수는 있지만 진입 페이지를 못 찾을 수 있음), 설정류 과제의 집중 실패 해결을 기대함. H2는 할 일 앱에 UI 요소 식별 규칙 제공, 할 일류 과제의 실패 해결을 기대함.

**중층 가설**（마찬가지로 독립적이며 병렬 가능）: H3은 멀티모달 입력 파이프라인 수정——실패 궤적을 리플레이해보니 이미지가 파이프라인에서 유실되거나 텍스트 설명으로 변환되는 것을 발견, 아무리 강한 멀티모달 모델이라도 전사할 방도가 없음. H4는 계수류 실패를 해결하기 위해 전역적으로 사고를 활성화.

**심층 가설**（검증 비용이 높아, 표층과 중층 개선 후에도 complex_ui 성공률이 40% 미만일 때만 시작）: H5는 시각적 이해가 더 강한 모델(GPT-5)로 교체, H6은 스크린샷 외에 UI 요소 트리 정보 추가(UI Automator가 추출한 구조화 DOM과 스크린샷을 교차 검증). 두 가지는 2×2 대조 실험을 구성할 수 있습니다(Claude/GPT-5 × 스크린샷만/스크린샷+요소 트리), "모델 능력과 정보 풍부도 중 무엇이 더 관건인지, 둘 사이에 시너지가 있는지"에 답합니다.

각 구성을 완전한 116개 과제 세트에서 5회 실행하며(서로 다른 무작위 시드 사용), 성공률, 평균 스텝 수, 실행 시간을 기록합니다.

### 결과에서 결정으로: 데이터 기반 절충

가상의 실험 데이터가 다음과 같이 나왔다고 가정합시다（**아래 데이터는 모두 가상 값**）: H1은 설정류 과제를 0%에서 75%로 향상, 입력 토큰 8% 증가; H3은 전사를 0%에서 80%로 향상, vision 토큰 15% 증가, 스텝당 지연 1초 증가; H4는 계수를 0%에서 70%로 향상, 하지만 스텝당 지연이 4초에서 12초로, 비용은 3배로 증가; H6은 complex_ui를 17%에서 52%로 향상, 토큰 30% 증가, 스텝당 지연 2초 증가; H5（GPT-5）는 complex_ui를 17%에서 35%로 향상, 하지만 스텝당 지연이 4초에서 15초로 급증.

결정은 효과가 있는 개선을 모두 채택하는 것이 아닙니다:

**H1+H3은 명확히 배포**: H1은 비용이 낮고 이득이 크며 부작용이 없습니다. H3은 vision 토큰 비용 15%와 지연 1초를 늘리지만, 전사 능력이 무에서 유로 바뀌었고, "입력 파이프라인이 멀티모달 정보를 유실"하는 아키텍처적 결함을 고치는 것이라 다른 시각적 이해 과제도 덩달아 개선될 수 있습니다.

**H4 전역 사고는 수용 불가**: 전체 성공률이 88%에서 91%로 올랐지만, 능력 태그 분포를 보면 계수 관련 과제는 전체의 약 8%뿐입니다——소수 과제를 위해 전체 과제가 3배의 지연과 비용을 감당하는 것은 전형적인 "소 잡는 칼로 닭을 잡는" 격입니다. 다만 H4는 사고가 계수 과제에 효과적임을 증명했으므로, 다음 라운드의 조건부 활성화의 기반이 될 수 있습니다.

**H6이 H5보다 우수**: H5（GPT-5）는 스텝당 지연이 4초에서 15초로 급증했지만 complex_ui는 35%까지밖에 오르지 않아, 병목이 모델의 사고 능력이 아니라 입력 정보의 충분성에 있음을 시사합니다. H6（요소 트리 정보 추가）은 30%의 토큰 증가와 2초의 지연으로 35퍼센트포인트의 향상을 얻어 훨씬 가성비가 좋습니다. H5+H6 조합의 성적이 가장 높지만(68%), 대규모 배포에서는 과제 소요 시간이 수용 불가하므로, 핵심 비동기 과제(은행 송금, 진료 예약)에서만 선택적으로 활성화하고, 일반 시나리오에서는 H6만으로 충분합니다.

**H2는 확장성 문제에 직면**: 비표준 앱마다 전용 규칙을 작성하는 것은 지속 가능하지 않으며, 임시방편으로만 쓸 수 있고, 장기적으로는 Agent의 일반화 능력을 향상시켜야 합니다.

### 지속적 반복: 첫 번째 개선에서 시스템 진화까지

H1, H3, H6 세 가지 개선을 구현한 후(H4는 배포하지 않음), Agent의 AndroidWorld 성공률은 88%에서 94%로 향상되었습니다. 완전한 benchmark를 다시 실행하니, 새 보고서는 다른 실패 패턴을 보여줍니다: 전사, 설정류, 복잡한 UI 과제는 모두 크게 개선되었고, 남은 약 6%의 실패는 아직 해결되지 않은 계수 과제, 여전히 변동이 있는 Wi-Fi 상태 확인(0%에서 60%로 올랐지만 불안정), 그리고 소수의 새로 나타난 실패(프롬프트가 길어졌거나 요소 트리 정보가 지나치게 많아 모델의 주의력이 분산되었을 가능성)에 집중됩니다.

새 보고서와 H4 실험의 통찰을 바탕으로 새로운 가설을 세울 수 있습니다. H7: 조건부 사고 활성화——과제 시작 전 빠른 LLM 호출 한 번(약 1-2초)으로 과제 서술을 분석해, 계수나 복잡한 추론이 관여하는 과제에만 사고 모드를 켜서, 지연 증가를 정말 필요한 과제로 한정합니다. H8: 동작 공간 확장, 복잡한 제스처(핀치 줌, 길게 눌러 드래그, 멀티터치) 지원——남은 실패 궤적을 리플레이해보면, 일부 과제가 지도 확대, 이미지 자르기, 목록 롱프레스 메뉴 등의 조작을 필요로 함을 발견할 수 있습니다.

이런 benchmark 피드백 기반의 지속적 반복은 Agent 능력의 나선형 상승을 이끕니다. Benchmark는 일회성 시험이 아니라 지속적인 능력 건강검진입니다. 정기적인 평가 메커니즘(매주 완전한 테스트를 한 번 실행하는 등)을 구축하면, 능력의 진화 곡선을 모니터링하고, 퇴화(새 기능이 버그를 유입)를 제때 발견하고, 개선(최적화가 정말 효과가 있음)을 검증하고, 지식(어떤 유형의 개선이 대개 효과적이고 어떤 것이 역효과를 내기 쉬운지)을 축적할 수 있습니다. 이런 데이터 기반, 가설 검증, 지속적 반복의 방법론은 Agent 공학을 경험 기반의 "연금술"에서 데이터 기반의 과학 공학으로 전환하는 핵심 경로입니다.

> **실험 6-10 ★★★: AndroidWorld의 평가와 개선**
>
> 본 실험은 평가 보고서에서 시스템 개선에 이르는 완전한 폐쇄 루프 실천입니다. `ch6/android-world`의 AndroidWorld 평가 보고서를 시작점으로 삼습니다.
>
> 1단계: 진단. 문항별 표와 능력 태그 행렬을 교차 분석해, 표면적인 과제 실패를 심층적인 능력 결함으로 매핑하세요. 예상보다 낮은 성공률의 능력 태그와 집중된 실패 과제 영역을 식별하세요.
>
> 2단계: 가설 구축. 3층 프레임워크(표층→중층→심층)에 따라 개선 가설을 세우고, 각 가설마다 예상 성공률 향상 목표와 검증 방법을 명확히 하세요.
>
> 3단계: 단계별 실험. 가설을 검증할 대조 실험을 설계하세요. 1단계는 저비용 표층 가설(프롬프트 최적화, 도구 설명 보완)을 테스트하고, 2단계는 중층 능력 가설(입력 파이프라인 수정, 사고 모드 전환)을 테스트하며, 특정 능력 태그 하의 과제 개선 폭에 주목하는 동시에 부작용을 측정하세요.
>
> 4단계: 데이터 기반 결정. 비용 대비 효과에 따라 배포 결정을 내리세요——효과 있는 모든 개선을 단순히 채택하는 게 아니라, 각 개선의 적용 범위, 지연 영향, 비용 오버헤드를 절충해야 합니다. 저비용 고수익 개선은 우선 배포하고, 고비용 개선은 핵심 시나리오로 한정하세요.
>
> 5단계: 반복. 개선을 완료한 후 평가 데이터셋을 다시 실행하고, LLM을 사용해 평가 결과를 분석해 새 보고서를 생성하세요. 새 보고서는 다른 실패 패턴을 보여주며, 다음 라운드 반복의 시작점이 됩니다.

## 외부 평가에서 내부 평가로: 프로덕션급 Agent의 평가 인프라

앞 절들에서는 외부에서 Agent 시스템을 평가하는 방법——평가 환경 구축, 데이터셋 설계, Benchmark 보고서 분석——을 다뤘습니다. 하지만 가장 우수한 Agent 제품은 외부 평가만 받는 것이 아니라, **지속적인 자기 평가 인프라를 내장**하고 있습니다. 아래에서는 제5장에서 소개한 오픈소스 범용 Agent OpenClaw를 예로 들고, 주요 Coding Agent 제품의 공개 기술 분석과 업계 종사자의 공유 내용을 결합해, 본받을 만한 내부 평가 체계——ML 연구의 실험 방법론을 제품 공학에 체계적으로 내장한 것——를 보여드리겠습니다.

### 소거 인프라: 각 특성의 실제 기여도 이해

ML 연구자들은 오랫동안 소거 실험(Ablation Study)을 사용해 모델의 어떤 구성요소가 정말 중요한지 이해해왔습니다——소위 소거란, 특정 구성요소를 하나씩 "제거"해 전체 성능이 얼마나 떨어지는지 보는 것입니다. OpenClaw는 이 방법론을 제품 공학에 도입했습니다: 시스템에 총 스위치를 내장해, 여러 주요 특성(사고 모드, 컨텍스트 압축, 자동 기억, 백그라운드 과제 등)을 동시에 비활성화하고 "맨몸 모델" 기준선을 만들 수 있습니다. 이를 통해 팀은 핵심 질문에 답할 수 있습니다: **특정 특성이 정말 사용자 경험을 개선했는가, 아니면 그저 유용해 보이는 것뿐인가?**

소거를 일회성 연구가 아닌 정규 공학 실천으로 삼는 것에는 몇 가지 실질적인 의미가 있습니다. 우선, 소거 스위치는 시작 경로의 극초기에 주입되어야 합니다——어떤 모듈 수준 상수가 설정값을 캡처하기 전에——이는 소거 인프라가 사후에 덧붙이는 것이 아니라 처음부터 시스템 아키텍처에 설계돼 있어야 함을 의미합니다. 다음으로, 소거 실험을 정기적으로(예: 대형 버전 출시 전마다) 실행하면 "특성 부채"——한때는 효과적이었지만 모델이 진화하면서 더 이상 필요 없어진 특성——를 발견할 수 있습니다. 프로덕션 Agent를 구축하는 어떤 팀에게든 권장되는 실천은: **모든 주요 특성은 독립적으로 끌 수 있어야 하고, 팀은 각 특성의 실제 기여도를 정기적으로 검증해야 한다**는 것입니다.

### AB 테스트 방법론: 메커니즘과 목표의 구분

성숙한 Agent 제품은 자신의 행동에 대해 엄격한 AB 테스트(즉 사용자를 무작위로 두 그룹으로 나눠, 한 그룹은 구버전을, 다른 그룹은 신버전을 사용하게 하고, 두 그룹의 실제 데이터를 비교해 변경이 효과적인지 판단)를 수행합니다. 잘 설계된 Agent AB 테스트 사례는 몇 가지 핵심 방법론적 원칙을 보여줍니다:

**이진이 아닌 다중 팔**. "있음"과 "없음"만 비교하는 것이 아니라 여러 점진적 변형을 설계합니다(예를 들어 서로 다른 강도의 프롬프트 제약을 테스트할 때, 대조군과 세 개의 점진적으로 더 엄격한 실험군을 설정). 이런 설계는 용량-효과 관계를 드러내 최적점을 찾는 데 도움이 됩니다.

**메커니즘 지표와 목표 지표를 구분**. 가장 저지르기 쉬운 실수입니다——자신이 바꾸고 있는 것을 최적화 목표로 착각하는 것입니다. 예를 들어 "Agent의 계획 파일 길이 줄이기"를 테스트한다면, 계획 길이는 메커니즘 지표(직접 바꾸는 것)이지 목표가 아닙니다. 진짜 목표는 "세션 단위 비용 낮추기"일 수 있습니다. 계획 파일을 줄이면 비용이 낮아질 수도 있지만, 계획이 충분히 상세하지 않아 더 많은 편집-검사-편집 순환을 유발해 오히려 총 출력량이 늘어날 수도 있습니다. 항상 자신에게 물어보세요: **내가 바꾸는 것(메커니즘)과 내가 정말 신경 쓰는 것(목표)이 같은가?** 다르다면 목표를 기준으로 삼아야 합니다.

**가드레일 지표 설정**. 목표 지표가 개선되었더라도, 사용자 만족도가 하락하거나 조작 횟수가 늘거나 오류율이 오르면 실험을 중단해야 합니다. 가드레일 지표는 "악화되어서는 안 되는 하한선"입니다.

**기준선 통계 기록**. 표본 크기, 분포 백분위, 상관관계 분석(예: "계획 크기가 커질수록 거부율이 단조 증가")을 포함해, 실험 결과 해석에 필요한 맥락을 제공합니다. 기준선 없이는 실험 결과가 통계적으로 유의한지 판단할 수 없습니다.

### 이중 계층 특성 스위치 시스템

Agent 제품은 첫날부터 특성 스위치(Feature Flag) 인프라를 설계해야 합니다——소위 특성 스위치란, 원격으로 제어 가능한 스위치로, 코드를 다시 배포하지 않고도 특정 기능을 사용자에게 켜거나 끌 수 있게 하는 것입니다. 이는 동시에 세 가지 목적——실험, 점진적 출시, 긴급 차단——에 쓰입니다.

**컴파일 타임 스위치**는 빌드 단계에서 관련 코드를 산출물에서 물리적으로 제거합니다. 내부 전용 특성은 외부 빌드에 아예 존재하지 않습니다——리버스 엔지니어링을 해도 제거된 기능을 발견할 수 없습니다. 이는 또한 깔끔한 소거 메커니즘이기도 합니다: 특정 특성을 끄는 것이 런타임에 로직을 건너뛰는 게 아니라, 해당 코드가 물리적으로 존재하지 않는 것입니다.

**런타임 스위치**의 구성은 서버에서 내려받아 로컬 디스크에 캐시됩니다. 설계상 다소 오래된 캐시 구성을 읽더라도, Agent가 네트워크 요청을 기다리느라 시작이 막혀서는 안 됩니다. 구체적인 그룹 결정은 실험 플랫폼(GrowthBook 등)을 통해 이뤄지며 AB 테스트 그룹을 배정하는 데 쓰입니다. 핵심 설계 세부사항 하나는: 각 특성의 노출 이벤트가 세션당 최대 한 번만 기록되어, 중복 기록이 실험 데이터를 오염시키는 것을 방지한다는 점입니다.

Agent 개발자에게 주는 시사점: 특성 스위치는 디버깅 도구가 아니라 **일급 아키텍처 구성요소**입니다.

### 프롬프트 민감도 평가

시스템 프롬프트는 Agent 행동의 핵심 "코드"이지만, 일반 코드와 동등한 버전 관리와 회귀 테스트가 결여된 경우가 많습니다. OpenClaw의 방식은 지정된 git 버전에서 완전히 렌더링된 시스템 프롬프트를 추출할 수 있는 전용 도구를 제공하는 것입니다——모든 동적 조건이 전개된 최종 텍스트를 포함합니다. 이를 통해 팀은 정확히 답할 수 있습니다: **어느 커밋이 프롬프트를 바꿨는가? 평가 세트에 미친 영향은 무엇인가?**

모든 Agent 팀에게 권장되는 실천은: (1) 시스템 프롬프트는 결정론적으로 렌더링될 수 있어야 함(동일한 설정 입력이 주어지면 항상 동일한 출력을 낳음); (2) 프롬프트의 버전화 스냅샷 메커니즘을 구축할 것; (3) 매 프롬프트 변경마다 평가 세트에서 회귀 테스트를 실행할 것——코드 변경이 CI를 통과해야 하는 것과 마찬가지입니다.

### 프라이버시 인식 분석을 평가의 기반으로

평가는 좋은 데이터에 의존하지만, Agent 제품은 대개 사용자의 민감한 콘텐츠를 다룹니다. OpenClaw는 타입 시스템을 통해 이 모순을 해결합니다: 분석 인터페이스는 특수한 타입으로 감싸진 값만 받아들이며, 타입 이름 자체가 감사 단서가 됩니다——"이것이 코드나 파일 경로가 아님을 이미 검증했다"고 명시적으로 선언하는 것입니다. 이런 설계는 프라이버시 제약을 문서화된 규범에서 컴파일 타임에 강제되는 타입 검사로 바꿉니다.

핵심 원칙은: **처음부터 프라이버시 제약을 설계에 반영하고, 사후에 덧붙이지 않는다**는 것입니다. 분석 시스템이 데이터를 안전하게 수집할 수 없다면, 효과적으로 평가할 수도 없습니다. 프라이버시와 평가는 대립하지 않습니다——프라이버시 인식 설계는 오히려 *정말로 무엇을 측정해야 하는지*를 진지하게 고민하게 만들어, 더 정확한 평가 지표를 낳습니다.

### 외부에서 내부로: 평가 사고방식의 전환

본 절의 핵심 메시지는: **앞의 여러 절이 Agent를 외부에서 어떻게 평가하는지 가르쳤다면, 본 절은 최고의 Agent 제품이 내부에서 스스로를 어떻게 평가하는지 드러낸다**는 것입니다. 외부 평가는 "Agent가 얼마나 좋은지"를 알려주고, 내부 평가 인프라는 "어떤 변화가 그것을 더 좋게 만들었는지"를 알려줍니다. 소거 실험은 어떤 특성이 정말 중요한지 찾아내고, AB 테스트는 각 변경의 영향을 정량화하며, 특성 스위치는 실험과 롤백의 인프라를 제공하고, 프롬프트 민감도 평가는 시스템 프롬프트를 CI 체계에 편입시키며, 프라이버시 인식 분석은 데이터 수집의 준법성을 보장합니다. 이 다섯 구성요소가 함께 평가 기반 제품 공학을 이룹니다——가끔 평가를 한 번 하는 것이 아니라, 모든 제품 결정에 평가를 내장하는 것입니다.

## 시뮬레이션 환경: 평가에서 후속학습으로의 다리

평가의 종착점은 채점이 아니라 개선입니다. 본 장은 이미 개선의 두 경로——Harness 조정(Benchmark 보고서에서 시스템 개선까지)과 제품 공학에 평가를 내장하는 것(내부 평가 인프라)——를 보여드렸습니다. 그리고 개선의 가장 강력한 형태는 훈련입니다——목표가 "현재 능력을 평가하는 것"에서 "새로운 능력을 길러내는 것"으로 확장될 때, 특히 제7장에서 다룰 후속학습 기술을 통할 때, 평가 환경은 **시뮬레이션 환경**으로 진화해야 합니다: Agent가 반복 연습하고 자동으로 점수를 받을 수 있는 가상의 놀이터입니다. 시뮬레이션 환경과 평가 환경의 핵심 차이는: 상호작용 빈도가 훨씬 높고(수백만 번 vs 수천 번), 무작위화가 필요하며(특정 설정을 그대로 암기하는 것을 방지), 즉각적인 피드백을 반드시 제공해야 한다는 점입니다. 응용 영역으로 보면, 시뮬레이션 환경은 디지털 환경(정보 처리 과제)과 체화 환경(물리 세계 인지와 조작) 두 부류로 나뉩니다.

이 다리의 양 끝은 이렇게 연결됩니다. 평가 측에서 이미 축적한 자산은 거의 매끄럽게 훈련 신호로 전환될 수 있습니다: 명확하게 정의된 Rubric이나 검증기는 본질적으로 **검증 가능한 보상(RLVR, Reinforcement Learning with Verifiable Rewards)**의 보상 함수입니다——채점 스크립트가 곧 보상 스크립트이며, 테스트 통과 여부나 상태 도달 여부가 평가의 판단 근거이자 강화학습의 보상이기도 합니다. 하지만 훈련은 평가 단계에서는 신경 쓸 필요 없던 새로운 요구사항을 제기합니다. 첫째는 **신뢰할 수 있는 reset 시맨틱**입니다: 훈련은 수백만 개의 episode(하나의 episode는 초기 상태에서 과제 종료까지의 완전한 상호작용 한 회)를 실행해야 하며, 매 episode는 반드시 확정적이고 깨끗한 초기 상태로 리셋될 수 있어야 합니다. 그렇지 않으면 그래디언트 신호가 이전 라운드의 잔여 상태에 오염됩니다. 둘째는 **평가보다 훨씬 높은 처리량**입니다: 평가는 몇천 번이면 결론을 낼 수 있지만, 훈련은 수용 가능한 벽시계 시간 안에 모델에게 수백만 번의 상호작용을 먹여야 하며, 환경의 병렬도와 단일 인스턴스 오버헤드가 훈련의 실현 가능성을 직접 좌우합니다. 이 두 가지——보상 함수화된 검증기, 훈련 지향의 reset과 처리량——는 모두 제7장에서 전개됩니다.

### 신뢰도 절충과 도메인 무작위화

고신뢰도 환경은 실제 세계로의 전이가 더 잘 되지만 계산 비용이 큽니다. 신뢰도의 또 다른 차원은 무작위화 정도입니다: 적절한 무작위화는 일반화 능력을 높이지만, 과도한 무작위화는 과제를 지나치게 어렵게 만듭니다. **도메인 무작위화(Domain Randomization)**는 시뮬레이션과 현실의 격차(sim-to-real gap)를 줄이는 핵심 기술입니다: 물리 매개변수, 시각적 외관, 센서 노이즈 등에서 광범위한 무작위 변화를 도입합니다——다양한 조명과 각도에서 파지 연습을 해두면, 실제 환경에서도 빛의 변화 때문에 실패하지 않는 것과 같은 원리입니다. 디지털 환경에서 sim-to-real은 인터페이스 렌더링, 응답 시간 등의 차이로 나타나며, 지연과 실패의 무작위화를 도입해 완화할 수 있습니다.

여기까지 평가 환경은 마지막 진화를 완수했습니다: 능력을 측정하는 시험장에서 능력을 길러내는 훈련장으로. 제7장에서는 AWorld-train이 이런 시뮬레이션 환경을 훈련 가능한 장으로 어떻게 개조하는지, 그리고 그 안의 공학적 도전을 소개합니다——본 장에서 세운 평가 체계와 시뮬레이션 환경이 바로 후속학습의 두 초석입니다.

## 본 장 요약

본 장은 하나의 핵심 질문을 중심으로 전개되었습니다: Agent가 정말로 좋아졌는지 어떻게 판단할 것인가? 재현 가능한 테스트 환경 구축부터, 유출 검증을 견딜 수 있는 데이터셋 설계, LLM이 평가위원 역할을 맡게 하는 것, 마지막으로 평가 결과로 모델 선정과 반복을 이끄는 것까지——이 사슬의 매 고리가 결론의 신뢰성에 영향을 미칩니다. 프로덕션급 Agent의 평가는 가끔 한 번 치르는 시험이 아니라, 모든 제품 결정에 내장된 지속적 검증입니다.

핵심 방법론: 관찰→가설→실험→검증→새로운 인식→새로운 가설, 이는 Agent 공학을 경험 기반의 "연금술"에서 데이터 기반의 과학 공학으로 전환시킵니다.

본 장이 소개한 평가 체계는 완전한 폐쇄 루프를 이룹니다: **평가 환경**이 자동화된 테스트 인프라를 제공 → **평가 데이터셋**이 테스트 케이스를 정의 → **자동화 평가 방법**（LLM-as-a-Judge와 Rubric）이 Agent 성능을 채점 → **Benchmark 분석**이 개선 방향을 드러냄 → **시스템 개선**이 문제를 수정 → 평가 환경과 데이터셋을 업데이트해 새로운 반복 라운드를 시작.

제1장에서 도입한 Harness 공학의 관점에서 보면, 본 장의 평가 방법론은 Harness 안 "검증" 기능의 체계적 구현이며, "Benchmark 보고서에서 시스템 개선까지"의 폐쇄 루프는 Harness 반복 최적화의 핵심 메커니즘입니다——평가는 Agent의 현재 능력을 측정할 뿐 아니라 Harness의 지속적 진화 방향을 이끕니다.

본 장에서 세운 평가 체계는 현재 시스템의 최적화뿐 아니라, 다음 장의 모델 후속학습을 위한 핵심 기반도 제공합니다——평가 환경과 데이터셋은 후속학습의 중요한 입력이며, 시뮬레이션 환경은 후속학습의 연습장입니다. 다음 장에서는 평가에서 모델 층위의 개선으로 전환해, SFT와 RL을 통해 어떻게 상호작용 전략을 모델 매개변수에 새겨 넣는지 깊이 탐구합니다.

## 생각해 볼 문제

1. ★★ LLM-as-a-Judge는 언어 모델로 언어 모델의 출력을 평가합니다. 이런 "자기 평가"에 체계적인 사각지대가 있지 않을까요——예를 들어 모델이 특정 스타일의 답변에 일관되게 높은 점수를 주는데, 이 선호가 인간의 판단과 일치하지 않는다면? 이런 편향을 어떻게 검출하고 교정할 수 있을까요?
2. ★★★ 평가 데이터셋의 "유출 방지" 설계는 매우 중요합니다. 하지만 오픈소스 생태계에서는 benchmark 데이터가 공개되는 순간 빠르게 훈련 데이터로 편입됩니다. 이 "쫓고 쫓기는 게임"에 종착점이 있을까요? 데이터 오염에 근본적으로 저항하는 평가 방법을 설계해보세요.
3. ★★ Scale AI의 4원칙(전문가 지침 기반, 전면적 커버리지, 기준 중요도 가중치, 자기 완결적 평가)은 평가의 주관성을 없애는 것을 목표로 합니다. 하지만 일부 과제 차원(예: "답변이 도움이 되는가", "어조가 적절한가")은 본질적으로 주관적입니다. 이런 주관적 차원을 위해 신뢰할 만한 Rubric을 어떻게 설계할 수 있을까요?
4. ★★ τ-bench는 실제 사용자 행동을 시뮬레이션해 Agent를 평가합니다. 하지만 시뮬레이션 사용자 자체도 LLM입니다——일부 경계 시나리오(감정이 격앙되거나 표현이 불명확한 사용자 등)를 체계적으로 과소평가할 수 있습니다. 시뮬레이션 사용자 자체의 품질을 어떻게 검증할 수 있을까요?
5. ★★ 쌍대 비교(Bradley-Terry 모델)는 선호가 이행적이라고 가정합니다(A > B이고 B > C이면 A > C). 하지만 인간의 선호는 종종 이행성을 위반합니다. Agent 평가에서 비이행적 선호는 어떤 시나리오에서 나타날 수 있을까요? 이것이 순위의 신뢰성에 어떤 영향을 미칠까요?
