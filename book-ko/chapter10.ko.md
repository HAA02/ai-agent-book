# 멀티 에이전트 협업

OpenAI가 제시했던 AI 능력 5단계 구분(Level 1 대화자, Level 2 사색가(Reasoners), Level 3 에이전트, Level 4 혁신가, Level 5 조직(Organizations))에서 멀티 에이전트 협업은 흔히 다섯 번째 단계로 가는 경로 중 하나로 비유된다—다만 여기서 Organizations는 "AI가 조직 전체의 일을 해낼 수 있는" 능력 수준을 가리키는 것이지, 시스템 아키텍처에 대한 요구사항이 아니라는 점을 짚어둘 필요가 있다. 충분히 강력한 단일 에이전트도 이론적으로는 이 수준에 도달할 수 있다. 하지만 오늘날의 엔지니어링 현실에서, 단일 에이전트는 결국 자신이 쓰는 모델의 능력 한계와 컨텍스트 윈도우에 제약을 받는다.

여러 에이전트를 협업시키는 것의 의미는 서로 다른 전문성을 지닌 에이전트가 "장단점을 보완"하는 것에 그치지 않는다. 더 근본적인 지점은 이것이다: **집단의 지능은 개체의 지능보다 높을 수 있다.** 인류 문명이 바로 그 증거다—한 사람의 지능은 유한하지만, 분업·협력·논쟁과 세대 간 지식 축적을 거치며 전체로서의 인류 사회가 보여주는 지능은 어떤 천재 개인도 훨씬 뛰어넘는다. 에이전트 집단에서도 이런 집단 지능이 나타날 수 있다: 개별 에이전트가 인간 전문가 수준에 불과하더라도, 조직만 잘 되면 전체 능력이 모든 인간 전문가의 총합을 넘어설 수도 있다. Google DeepMind는 《From AGI to ASI》에서 "대규모 멀티 에이전트 집단"을 초지능(ASI)으로 가는 핵심 경로 중 하나로 꼽는다—인간의 범용 지능이 개체를 넘어서는 사회·조직으로 응집되듯, 다수의 AGI급 에이전트가 협업해 형성하는 "집단 지능" 역시 구성원 단순 합산을 훨씬 뛰어넘는 인지 능력을 보일 수 있다는 것이다[^agi-asi]. 따라서 멀티 에이전트 협업은 단일 모델의 컨텍스트 윈도우와 능력 한계를 돌파하는 엔지니어링 수단일 뿐 아니라, "전문가급 AI"에서 "인류 전체를 능가하는" 단계로 나아가는 근본적인 경로일 수도 있다.

[^agi-asi]: "대규모 멀티 에이전트 집단"을 범용 인공지능에서 초지능으로 가는 핵심 경로 중 하나로 꼽은 내용은 Google DeepMind, *From AGI to ASI.* arXiv:2606.12683, 2026 참조.

## 멀티 에이전트 협업의 분류 프레임워크

멀티 에이전트 시스템을 구축하려면 먼저 두 가지 핵심 설계 차원을 이해해야 한다. 이 두 차원이 함께 시스템의 기본 아키텍처와 구현 방식을 결정한다.

### 차원 1: 컨텍스트 공유 여부

이는 가장 기초적인 아키텍처 결정으로, 여러 에이전트 간 정보 전달 방식을 결정한다.

**컨텍스트 공유**란 후속 에이전트가 이전 에이전트의 완전한 대화 이력과 궤적(제1장에서 정의한 trajectory)을 그대로 이어받는다는 뜻이다. 각 단계마다 시스템 프롬프트와 도구 집합을 바꾸면 새로운 에이전트가 되지만(정체성·직무·능력이 모두 달라지므로), 이전 에이전트의 모든 기억은 그대로 유지한다. 예를 들어 어느 팀에서 요구사항 분석가가 요구사항 문서를 작성한 뒤, 개발자는 문서만 받는 게 아니라 분석가와 사용자 간의 모든 소통 기록까지 볼 수 있다—그는 새로운 역할이지만 이전 컨텍스트를 완전히 보존한 채 일한다. 장점은 정보 손실이 없다는 것이다—모든 에이전트가 이전 어느 단계의 세부사항도 되돌아볼 수 있다. 과제는 컨텍스트가 빠르게 팽창할 수 있다는 것이다.

**컨텍스트 비공유**란 각 에이전트가 완전히 독립적인 컨텍스트와 대화 이력을 유지하며, 서로 상대의 "사고 과정"에 직접 접근할 수 없다는 뜻이다. 이는 서로 다른 부서 간 협업과 비슷하다: 각자 자신의 자리에서 독립적으로 일하고, 공유 문서와 회의록을 통해 정보를 교환할 뿐, 상대의 화면을 계속 지켜보지 않는다. 이 모드는 모듈성과 격리성이 더 뛰어나다—각 에이전트는 자신의 직무와 관련된 정보에만 집중하면 된다. 시스템 확장과 유지보수도 더 쉽다—새 에이전트를 추가할 때 기존 에이전트의 내부 로직을 건드릴 필요가 없고, 인터페이스와 데이터 형식만 잘 정의하면 된다.

에이전트 간 컨텍스트를 공유하지 않으므로, 명시적인 통신 메커니즘을 통해 정보를 전달해야 한다. 흔히 쓰이는 세 가지는 다음과 같다:

- **도구 호출의 파라미터**: 상류 에이전트가 구조화된 데이터를 파라미터로 하류 에이전트의 도구에 전달한다. 타입이 명확하고 구조가 분명한 상황에 적합하다.
- **공유 파일 시스템**: 에이전트 간에 공유 디렉터리 아래의 문서, 코드 등 중간 산출물을 읽고 씀으로써 정보를 교환한다. 산출물이 크거나 영속화가 필요한 상황에 적합하다.
- **메시지 버스(Message Bus)**: 에이전트 간 메시지 전달을 전담하는 중계소로, 에이전트는 서로를 직접 호출하지 않고 메시지를 메시지 버스에 보내면 버스가 대상 에이전트에게 전달한다.

메시지 버스는 본질적으로 **비동기 통신**을 지원한다—발신자와 수신자가 동시에 온라인 상태일 필요가 없다. 마치 회사 내부 이메일 시스템처럼: 동료에게 메일을 보낼 때 상대가 그 순간 컴퓨터 앞에 있을 필요가 없다. 메일은 우선 서버에 저장되고, 동료가 접속하면 처리한다. 이 방식은 여러 에이전트가 병렬로 작업하며 서로 조율이 필요한 상황에 특히 적합하다(자세한 내용은 본 장의 "병렬 협업 형태" 절 참고).


![그림10-1 컨텍스트 공유와 비공유 비교](images/fig10-1.svg)


짚고 넘어갈 점은, 두 아키텍처 모두 진정한 멀티 에이전트 시스템이라는 것이다(각 단계의 시스템 프롬프트와 도구 집합이 다르면 그 자체로 다른 에이전트이기 때문). 차이는 조율 방식에 있다. **컨텍스트 공유**는 암묵적 조율에 의존한다—후속 에이전트가 이전 에이전트의 완전한 컨텍스트 이력을 이어받아 이전의 사고 과정을 "볼 수" 있고, 정보는 컨텍스트 자체를 통해 전달된다. **컨텍스트 비공유**는 명시적 조율에 의존한다—에이전트 간에 파일, 메시지 또는 구조화된 데이터 인터페이스를 통해 정보를 교환하며, 각 에이전트는 자신과 관련된 내용만 본다.

비유하자면: 전자는 팀 전체가 한 테이블에 둘러앉아 토론하며 모두가 모든 발언을 듣는 것에 가깝고, 후자는 서로 다른 부서가 이메일과 문서로 협업하며 각자 자신의 작업 공간을 갖는 것에 가깝다.

표10-1은 하위 작업 수, 컨텍스트 윈도우, 병렬도, 정보 격리, 비용 예산이라는 다섯 관점에서 두 아키텍처의 선택 근거를 정리한 것으로, 초기 아키텍처 선정 시 체크리스트로 활용할 수 있다.

표10-1 컨텍스트 공유와 비공유의 선택 근거

| 선택 근거 | 컨텍스트 공유 | 컨텍스트 비공유 |
|----------|-------------------------------------|------------------------------------------------|
| 하위 작업 수 | 적음(2-3개 역할) | 많음(병렬 처리 필요) |
| 컨텍스트 윈도우 | 모든 역할의 정보를 담기에 충분 | 하나의 윈도우로는 부족 |
| 병렬도 | 주로 순차적(역할들이 같은 궤적을 이어받아 순서대로 진행) | 대규모 병렬 가능(컨텍스트가 서로 독립적이라 서로 막지 않음) |
| 정보 격리 | 불필요(모든 역할이 정보를 공유) | 필요(예: 보안 검토는 원본 사고 과정을 보아서는 안 됨) |
| 비용 예산 | 하나의 궤적이 이어받으며 진행, 토큰이 단계에 따라 누적 | 여러 에이전트가 각자 전개, 전체 토큰이 보통 수 배에서 한 자릿수 이상 높음 |

**간단한 판단 기준**: 누적 예상 컨텍스트가 윈도우의 50%를 넘을 것으로 예상되면(이는 경험 법칙이지 정확한 임계값은 아니다) 비공유를 택해야 한다. 정보 무손실이 작업 정확성의 필수 제약이라면 공유를 택해야 한다. 대다수 실제 시스템은 "단계 전환식" 방안을 채택한다—앞선 몇 개 에이전트는 공유하고, 정보가 포화되는 지점부터 비공유 컨텍스트 + 명시적 핸드오프(handoff, 즉 상류 에이전트가 능동적으로 어떤 정보를 하류에 인계할지 결정하는 것)로 전환한다.

### 차원 2: 협업 토폴로지

두 번째 차원은 협업 토폴로지—에이전트 간에 통제권과 정보가 어떤 구조로 흐르는가이다. 협업 토폴로지와 컨텍스트 공유 여부는 **개념적으로는 독립적이지만 실무에서는 연관되어** 있다: 개념적으로 독립적이라 함은, 컨텍스트를 공유하는 시스템에도 토폴로지가 존재하기 때문이다—예컨대 본 장 뒤에서 소개할 `transfer_to_agent`(실험 10-2)는 본질적으로 컨텍스트 공유 상태에서의 체인형 핸드오프의 한 형태다. 실무에서 연관되어 있다 함은, 컨텍스트를 공유하는 순간 토폴로지가 대개 퇴화하기 때문이다(아래 참고)—즉 두 차원의 값은 임의로 조합할 수 있는 것이 아니다. 다만 컨텍스트를 공유할 때는 핸드오프가 "무엇을 전달할지" 결정할 필요가 없다—완전한 이력이 자연히 보존되기 때문—토폴로지는 대개 역할 전환의 순차 시퀀스로 퇴화하며, 그다지 많은 아키텍처 결정을 내릴 필요가 없다(둘 사이의 예외적 중간 형태는 본 장 후반의 탈중앙화 절에서 다룰 group chat식 다자간 협업이다). 반면 컨텍스트를 공유하지 않기로 하면 "정보가 어떻게 흐르는가, 누가 조율하는가"가 반드시 명시적으로 설계해야 하는 문제가 된다.

바꿔 말하면, 이 두 차원은 원칙적으로 2×3 조합 행렬(공유/비공유 × 세 가지 토폴로지)을 이루지만, 컨텍스트 공유 쪽 행에서는 토폴로지가 대개 역할 전환 시퀀스 하나로 퇴화해 아키텍처 결정의 여지가 별로 없다(이것이 바로 뒤에서 다룰 "다단계 역할 전환"이 논의하는 형태다). 따라서 본 장은 컨텍스트 비공유의 세 칸만 자세히 다룬다. 아래는 컨텍스트를 공유하지 않을 때 협업 토폴로지가 취하는 세 가지 전형적인 형태로, 복잡도가 증가하는 순서다:

- **대등 협업 패턴**(Peer Collaboration Pattern): 소수의 에이전트(보통 2-3개)가 대등한 신분으로 상호작용하며 반복 개선 루프를 형성한다—논문을 쓸 때 한 사람이 초안을 쓰고 다른 사람이 코멘트를 달아 수정하기를 몇 차례 반복하면 혼자 쓴 것보다 훨씬 나아지는 것과 비슷하다.
- **관리자 패턴**(Orchestration Pattern): 중앙화된 Manager 에이전트가 작업 계획과 스케줄링을 담당하고, 여러 하위 에이전트가 각자 특정 하위 작업을 맡는다—프로젝트 매니저가 몇 명의 전문 엔지니어와 함께 프로젝트를 진행하는 것과 비슷하다.
- **탈중앙화 패턴**(Decentralized Pattern): 런타임의 중앙 통제자가 없고, 에이전트들이 인간처럼 서로 소통하며 협업해 작업을 완수한다.

각 패턴의 상세한 설계와 적용 시나리오는 이어지는 전문 절에서 다룬다.

## 멀티 에이전트가 단일 에이전트보다 정말로 나은 경우

구체적인 협업 아키텍처로 들어가기 전에, 더 근본적인 질문에 먼저 답해보자: **언제 정말로 여러 에이전트가 필요하고, 언제 하나의 에이전트로 충분한가?** 이 질문의 답은 이후 모든 엔지니어링 방안의 총괄 기준이 된다. 최근의 일련의 연구는 명확한 판단 프레임워크를 제시한다—핵심 판별 기준은 단 하나다: **협업 과정이 단일 에이전트가 생성 시점에는 얻을 수 없었던 새로운 정보를 도입했는가?**

표10-2는 서로 다른 협업 모드가 새로운 정보를 도입하는지 여부를 정리한 것으로, 멀티 에이전트 협업이 단일 에이전트에 비해 실질적 가치를 갖는지 판단하는 데 쓰인다.

표10-2 멀티 에이전트 협업 모드의 정보 증분 비교

| 협업 모드 | 새 정보 도입 여부 | 효과 |
|---|---|---|
| 동일 모델의 자기 검토(자기 출력을 다시 읽음) | 아니오 | 대개 무효하거나 오히려 해로움 |
| 서로 다른 에이전트가 같은 텍스트를 두고 토론 | 아니오 | 동일 연산량 기준 단일 에이전트와 동등 |
| Reviewer가 테스트 실행 결과를 이용해 코드 검토 | 예(실행 피드백) | 뚜렷한 향상 |
| Reviewer가 렌더링 스크린샷을 보고 프런트엔드/PPT 코드 검토 | 예(시각 피드백) | 뚜렷한 향상 |
| Reviewer가 외부 도구로 사실을 검증 | 예(도구 피드백) | 뚜렷한 향상 |

2025년의 RLEF(Reinforcement Learning from Execution Feedback)[^rlef-2025]는 이를 입증했다: 강화학습으로 모델이 코드 실행 피드백을 활용해 코드를 반복 개선하도록 훈련하면, 모델이 독립적으로 여러 번 샘플링하는 것보다 효과가 훨씬 뛰어났다. 핵심은 매 반복마다 **실제 실행 결과**(컴파일 오류, 테스트 실패, 런타임 예외)라는 정보가 도입된다는 점이다—이 정보는 모델이 코드를 작성하는 시점에는 존재하지 않았다. 2025년의 WebGen-Agent[^webgen-agent-2025]는 웹페이지 생성 작업에서, 여러 계층의 시각적 피드백(스크린샷 + 비전 언어 모델 설명)으로 구성된 피드백 스캐폴딩을 통해, 해당 벤치마크에서 Claude 3.5 Sonnet의 성능을 26.4%에서 51.9%로—거의 두 배 가까이—끌어올렸다고 보고했다.

[^rlef-2025]: Gehring, J., et al. *RLEF: Grounding Code LLMs in Execution Feedback with Reinforcement Learning.* arXiv:2410.02089, 2025.
[^webgen-agent-2025]: Lu, Z., et al. *WebGen-Agent: Enhancing Interactive Website Generation with Multi-Level Feedback and Step-Level Reinforcement Learning.* arXiv:2509.22644, 2025.

이 "새 정보" 프레임워크는 얼핏 모순적으로 보이는 현상을 설명해준다: 학술 연구는 "단일 에이전트로 충분하다"고 말하지만, 엔지니어링 실무에서는 멀티 에이전트가 확실히 더 잘 작동한다는 것이다. 모순의 근원은 양측이 논하는 "멀티 에이전트"의 유형이 다르다는 데 있다—학술 연구에서 비교하는 것은 대개 "여러 에이전트가 같은 텍스트를 보며 서로 토론"하는 방식(토론 등)이고, 엔지니어링 실무에서 효과적인 멀티 에이전트 시스템은 대개 외부 피드백 루프(코드 실행, 시각 렌더링, 도구 호출)를 포함한다. 전자는 새 정보를 도입하지 않았고, 후자는 도입했다. 본 장 뒤에서 다룰 대등 협업, 관리자, 탈중앙화라는 세 아키텍처 중 실제로 효과가 있는 용례는 거의 모두 이 판별 기준에서 근거를 찾을 수 있다.

**단계 예산과 에이전트 성능.** 관련된 한 연구 방향은: 에이전트에게 서로 다른 단계 예산(즉 허용되는 도구 호출 횟수 또는 반복 라운드 수)을 부여하면 성능이 어떻게 달라지는가이다. 직관적으로는 더 많은 단계가 더 나은 결과를 가져와야 한다—30단계 예산에서는 에이전트가 핵심 기능만 빠르게 구현할 수 있지만, 300단계 예산에서는 먼저 계획하고, 구현하고, 다시 테스트하고, 다시 개선할 수 있다. 하지만 2025년 Google의 논문 《Budget-Aware Tool-Use Enables Effective Agent Scaling》은 반직관적인 결론을 발견했다: **단순히 에이전트가 쓸 수 있는 단계 수를 늘리는 것만으로는 성능 향상이 보장되지 않는다**. 표준적인 에이전트는 "예산 인식"이 부족하다—300단계 예산이 있어도 여전히 얕은 탐색을 수행하는 경향이 있고, 금세 "포화" 상태에 이른다. 더 많은 단계를 실제로 더 나은 결과로 전환하려면, 에이전트에게 남은 자원에 따라 전략을 동적으로 조정하는 명시적인 예산 인식 메커니즘이 필요하다—초반에는 폭넓게 탐색하고, 후반에는 가장 유망한 방향에 집중하는 식으로. 2026년의 BAVT(Budget-Aware Value Tree Search)는 한 걸음 더 나아가 단계 수준의 가치 평가를 제안했다—매 단계마다 남은 예산 비율에 따라 탐색과 활용의 가중치를 조정하며, 예산이 줄어들수록 에이전트는 "넓게 훑기"에서 점차 "깊이 파기"로 전환한다.

이러한 발견은 멀티 에이전트 시스템 설계에 직접적인 시사점을 준다. 예컨대 관리자 패턴에서 Manager 에이전트는 단순히 작업을 하위 에이전트에 분배하고 결과를 기다리기만 해서는 안 되며, 작업의 복잡도에 따라 **단계 예산을 동적으로 배분**해야 한다—단순한 하위 작업에는 적은 단계를, 복잡한 하위 작업에는 충분한 단계를 부여해야 한다. 동시에 하위 에이전트가 이 예산을 합리적으로 활용하도록(먼저 계획하고, 구현하고, 테스트하고, 개선하도록) 유도해야지, 무작정 뛰어들어 손부터 대게 해서는 안 된다.

모든 설계에 앞서 반드시 놓아야 할 한 가지가 더 있다: **비용**이다. 멀티 에이전트의 병렬 탐색과 반복 개선에는 모두 돈이 든다—Anthropic은 자사의 멀티 에이전트 연구 시스템의 토큰 소비량이 일반 대화의 약 15배에 달하며, 토큰 사용량 자체가 성능 차이의 약 80%를 설명한다고 밝힌 바 있다. 이는 멀티 에이전트의 효과 이득이 수 배에서 한 자릿수 이상의 추가 비용을 상쇄할 만큼 커야 함을 뜻하며, 그렇지 않다면 잘 조율된 단일 에이전트가 더 경제적인 선택인 경우가 많다.

## 컨텍스트 공유형 멀티 에이전트 협업

컨텍스트 공유형 멀티 에이전트 협업에서는 각 단계가 독립적인 에이전트(자신만의 시스템 프롬프트와 도구 집합을 지님)이지만, 이전 에이전트의 완전한 궤적을 이어받는다—후임 동료가 전임자가 남긴 모든 업무 일지를 열람할 수 있는 것과 비슷하다. 이 "이어받기식 협업"의 핵심 강점은 정보 무손실이다—모든 에이전트가 이전 어느 단계의 세부사항이든 되돌아볼 수 있다. 과제는 현재 에이전트가 물려받은 방대한 이력 정보에 휘둘리지 않고 자신의 핵심 직무에 집중하도록 하는 방법에 있다.

### 다단계 역할 전환

먼저 정의상의 논쟁 하나를 명확히 짚어두자: 제1장의 언어로 말하면, 다단계 역할 전환은 일종의 **워크플로형 오케스트레이션**이다—실행 경로(예: 요구사항 확인 → 구현 → 검토)가 사전에 정의되어 있다. 본 장이 이를 멀티 에이전트 프레임워크에 재조명하는 이유는 에이전트 정체성과 컨텍스트라는 관점에서다: 각 단계의 시스템 프롬프트, 도구 집합, 관심사가 모두 다를 때, 이를 여러 에이전트가 하나의 궤적을 공유하는 것으로 보면 실질적인 설계상의 이득이 있다—각 "정체성"의 프롬프트와 도구 집합을 독립적으로 다듬을 수 있고, 단계 경계가 자연스럽게 품질 게이트 지점이 된다.

복잡한 작업에서는 에이전트의 역할과 직무가 단계에 따라 크게 달라질 수 있다. 항상 동일한 정적 시스템 프롬프트를 쓴다면, 지나치게 포괄적이라 세밀함이 부족하거나, 모든 단계의 지침을 하나에 다 욱여넣어 지나치게 장황해지기 마련이다. 다단계 역할 전환의 방식은: 현재 단계에 따라 시스템 프롬프트와 도구 집합을 동적으로 전환하여, 에이전트가 매 단계에서 가장 적합한 "정체성"으로 일하게 하는 것이다. 이 전환은 새 인스턴스를 만들거나 새 프로세스를 띄울 필요 없이, 같은 실행 세션 안에서 컨텍스트만 갱신하면 된다. 핵심은, 역할이 바뀌더라도 대화 이력과 작업 상태는 항상 연속적으로 공유된다는 점이다—에이전트는 새 역할에서도 이전 단계에서 쌓인 모든 정보에 접근할 수 있다.


![그림10-2 단계 기반 역할 전환](images/fig10-2.svg)


> **실험 10-1 ★★: 실행 단계에 따라 시스템 프롬프트를 결정하기**
>
> 본 실험은 Coding 에이전트의 전체 워크플로를 통해, 단계화된 시스템 프롬프트가 에이전트 성능을 어떻게 향상시키는지 보여준다.
>
> **작업 시나리오**: 사용자가 소프트웨어 개발 요구를 제시하면, 에이전트는 요구사항 확인, 코드 구현, 품질 검토라는 세 단계를 순서대로 거친다.
>
> **1단계: 요구사항 확인**(역할: 요구사항 분석가)
>
> 시스템 프롬프트가 강조하는 것:
> - "당신의 임무는 사용자의 요구를 충분히 이해하는 것이다. 모호한 부분은 질문으로 명확히 하여, 사용자가 원하는 기능·사용 시나리오·성능 요구를 완전히 파악하라."
> - "구현을 서두르지 마라. 이 단계에서 당신의 임무는 질문하고 확인하는 것이지, 코드를 작성하는 것이 아니다."
> - "모든 핵심 요구사항이 명확해졌다고 확인되면 `complete_requirements_analysis()` 도구를 호출해 이 단계를 마쳐라."
>
> 도구 집합은 제한적이다: 사용자에게 확인 질문을 하는 `ask_clarifying_question(question)`, 확인된 요구사항을 기록하는 `save_requirement(key, value)`, 단계 완료를 표시하는 `complete_requirements_analysis()`.
>
> 에이전트는 사용자와 여러 차례 대화를 나눈다: "이 스크립트가 어떤 유형의 파일을 처리해야 하나요?" "하위 폴더도 재귀적으로 처리해야 하나요?" "파일 이동 후 원본 파일명을 유지해야 하나요?" 이런 질문들을 통해 에이전트는 완전한 요구사항 이해를 점진적으로 구축하고 구조화하여 저장한다. 에이전트가 요구사항이 충분히 명확해졌다고 판단하면 `complete_requirements_analysis()`를 호출해 역할 전환을 촉발한다—시스템이 단계 완료 신호를 감지해 자동으로 다음 단계 설정으로 전환한다.
>
> **2단계: 코드 구현**(역할: 소프트웨어 엔지니어)
>
> 새 시스템 프롬프트가 강조하는 것:
> - "당신의 임무는 확인된 요구사항에 따라 고품질의 Python 코드를 작성하는 것이다."
> - "모범 사례를 따르라: 코드는 모듈화되어야 하고, 적절한 오류 처리를 포함해야 하며, 필요한 주석을 담아야 한다."
> - "코드 작성을 마치고 기본 테스트를 통과하면 `submit_for_review()`를 호출해 검토 단계로 넘어가라."
>
> 도구 집합도 크게 바뀐다: 이전의 요구사항 확인 도구는 제거되고, 대신 `write_file(path, content)`, `read_file(path)`, `execute_code(code)` 등 개발 도구가 주어진다. 에이전트는 1단계에서 저장된 요구사항을 바탕으로 코드 작성을 시작한다—먼저 주요 로직을 작성하고, 오류 처리를 추가하고, 마지막으로 테스트를 작성해 검증한다. 이 전 과정에서 에이전트는 여전히 1단계의 대화 이력에 접근해 요구사항 세부사항을 확인할 수 있지만, 행동 양식은 완전히 달라진다—더 이상 질문하지 않고 구현에만 집중한다. 완료 후 `submit_for_review()`를 호출한다.
>
> **3단계: 코드 검토**(역할: 코드 리뷰어)
>
> 새 시스템 프롬프트가 강조하는 것:
> - "당신의 임무는 방금 작성된 코드를 검토하여, 기능 정확성·코드 규범·오류 처리·성능 최적화·보안성 등 여러 차원에서 품질을 평가하는 것이다."
> - "비판적 사고를 채택해, 코드에 존재할 수 있는 문제와 개선 여지를 찾아내려 시도하라."
> - "심각한 문제를 발견하면 `request_revision(issues)`를 호출해 구현 단계로 되돌려라. 품질이 수용 가능하면 `approve_code()`를 호출해 작업을 완료하라."
>
> 도구 집합은 다시 한 번 바뀐다: `run_linter(file)`, `run_tests(file)`, `analyze_complexity(file)` 등 코드 품질 분석 도구로 교체된다. 에이전트는 검토자의 시각으로 코드를 다시 살펴보고, 정적 분석을 실행하며, 잠재적 버그·성능 문제·보안 위험을 점검한다.
>
> 이 3단계 설계는 에이전트가 매 단계에서 현재 핵심 작업에 집중할 수 있게 한다. 더 중요한 점은, 명확한 단계 전환 메커니즘이 작업 실행의 완전성을 보장한다는 것이다—에이전트는 요구사항 분석을 건너뛰고 곧바로 코드를 쓰지 않으며, 검토를 거치지 않은 채 결과물을 전달하지도 않는다.
>
> **실험 요구사항**:
> 1. 각 단계별로 명확한 역할 정의와 행동 지침을 가진 3단계 시스템 프롬프트를 구현하라
> 2. 각 단계에 맞는 도구 집합을 구성하라
> 3. 단계 전환 트리거 메커니즘을 구현하라(특정 도구 호출을 통해)
> 4. 단계 간 컨텍스트 연속성을 확보하라
> 5. 되돌림 상황을 처리하라—코드 검토에서 문제가 발견되면 구현 단계로 복귀할 수 있어야 한다
> 6. 각 단계의 실행 로그를 기록해, 서로 다른 프롬프트가 어떻게 서로 다른 행동 양식을 만들어내는지 보여라
>

### 영역 간 역할 전환

앞서 본 다단계 역할 전환은 단일 작업 유형(소프트웨어 개발) 안에서의 단계화된 실행을 보여준다. 영역 간 역할 전환은 한 걸음 더 나아가, 에이전트가 여러 작업 유형 사이에서 자율적으로 전환하는 것을 탐구한다—사전에 계획된 선형 흐름이 아니라, 사용자 요구의 변화에 따라 에이전트가 스스로 어느 전문 역할로 전환해야 할지 판단한다.

> **실험 10-2 ★★: 다중 역할 전환**
>
> **전제 조건**: 먼저 제2장의 Agent Skills 메커니즘을 이해하는 것을 권장한다.
>
> **시스템 아키텍처**: 다섯 가지 역할—
>
> - **triage(프런트 분류, 기본 진입점)**: 사용자의 전체 요구를 이해하고, 이를 순서가 있는 하위 작업으로 나누어 적합한 전문 역할에 순차적으로 인계하며, 모든 하위 작업 완료 후 마무리 확인을 한다. 자체 전문 도구는 없고 transfer 도구만 갖는다
> - **research(정보 검색 전문가)**: `web_search`로 데이터, 사실, 자료를 찾는다
> - **coding(프로그래밍 전문가)**: `execute_python`으로 코드를 작성·실행해 프로그램 로직/스크립트 문제를 해결한다
> - **data_analysis(데이터 분석 전문가)**: `calculate` / `descriptive_stats`로 정량 계산과 통계를 수행한다(전년 대비 성장률, 연평균 복합 성장률 CAGR, 평균 등)
> - **writing(작문 전문가)**: 검색된 데이터와 계산 결론을 매끄럽고 지정된 독자층에 맞는 완성본으로 다듬는다(`count_characters`로 분량을 대략 점검할 수 있다)
>
> **핵심 메커니즘: transfer_to_agent 도구**
>
> 모든 역할에는 `transfer_to_agent(target_role, reason)` 도구가 장착되어 있다. 호출 시 시스템은 순서대로: 1) 현재 대화 이력을 저장하고, 2) 목표 역할의 프롬프트와 도구 집합을 로드하고, 3) 대화 이력을 새 역할에 전달해 컨텍스트를 이해시키고, 4) 새 역할의 신분으로 실행을 이어간다.
>
> **실험 시나리오**: 시스템은 기본적으로 triage(프런트 분류) 신분으로 동작한다. 사용자가 영역을 넘나드는 복합 작업을 던진다: "투자자에게 보여줄 자료를 준비 중인데, 중국의 2021·2022·2023년 3년간 신에너지 자동차 판매량을 조사해서, 이 3년간의 연평균 복합 성장률을 계산하고, 투자자 대상으로 120자를 넘지 않는 중국어 요약문을 써 달라." triage는 이를 "데이터 조회 → 지표 계산 → 원고 작성"으로 나누고, 먼저 검색으로 인계한다:
>
> ```python
> transfer_to_agent(target_role="research", reason="먼저 3년간 신에너지 자동차 판매량 데이터를 조회해야 함")
> ```
>
> research는 `web_search`로 판매량을 조회한 뒤, 핵심 데이터를 대화에 적어 넣고, 데이터 분석으로 인계한다:
>
> ```python
> transfer_to_agent(target_role="data_analysis", reason="데이터가 준비됨, 3년 CAGR 계산 필요")
> ```
>
> data_analysis는 `calculate`로 성장률을 계산해 writing에 인계하여 완성문을 만들고, writing이 작성을 마치면 다시 triage로 인계해 마무리 확인을 한다. 전체 체인은 triage → research → data_analysis → writing → triage이며, 각 역할이 완전한 대화 이력을 볼 수 있으므로 다음 역할은 앞서 무엇이 이루어졌는지 자연스레 알게 된다.
>
> 역할 전환의 결정은 시스템 프롬프트의 지침에 의존한다. triage의 프롬프트에는 라우팅 규칙이 명확히 나열되어 있다: 데이터/자료 조회는 research로, 코드 작성·실행은 coding으로, 정량 계산·통계는 data_analysis로, 원고 다듬기는 writing으로. 판단 기준은 간단하다: 작업이 특정 영역의 심층 지식이나 전문 도구를 요구하면 해당 전문 역할에 인계한다. 전문 역할의 프롬프트에도 자신의 몫을 완료한 뒤 누구에게 인계할지 또는 triage로 돌아갈지가 안내되어 있다.
>
> **실험 요구사항**:
> 1. 최소 세 가지 전문 역할의 시스템 프롬프트와 전용 도구 집합을 구현하라
> 2. 동적 전환을 지원하는 `transfer_to_agent` 도구를 구현하라
> 3. 역할 전환 후 컨텍스트 연속성을 확보하라
> 4. 순환 전환 문제를 처리하라—에이전트가 역할 사이를 계속 오가지 않도록 하라
> 5. 여러 영역을 넘나드는 복잡한 작업 흐름을 설계해, 역할 전환의 가치를 보여라
>

## 컨텍스트 비공유형 멀티 에이전트 협업

컨텍스트 비공유는 진정한 멀티 에이전트 협업을 대표한다. 이 아키텍처에서는 모든 에이전트가 독립된 개체로서 자신만의 컨텍스트, 궤적, 상태를 지닌다. 에이전트 간에는 서로의 "내면 활동"에 직접 접근할 수 없으며, 협업은 전적으로 명확하고 구조화된 데이터 전달 메커니즘에 의존한다—본 장 서두에서 소개한 세 가지 통신 메커니즘(도구 호출 파라미터, 공유 파일 시스템, 메시지 버스)이 그것이다.

이 격리는 몇 가지 실질적인 엔지니어링 이점을 가져온다: 각 에이전트를 독립적으로 개발·테스트할 수 있고, 새 능력을 추가할 때 기존 코드를 건드릴 필요가 없으며, 어느 에이전트가 오류를 일으켜도 그 상태가 다른 에이전트에게 전염되지 않고, 여러 에이전트가 진정한 의미에서 동시 실행될 수 있다—컨텍스트가 완전히 독립적이므로 자원 경쟁이 없다.

하지만 컨텍스트 비공유에도 대가가 있다. 가장 뚜렷한 것은 정보 동기화 문제다: 각 에이전트가 작업 상태에 대해 어떻게 일관된 이해를 유지할 것인가? 전달 과정에서 정보가 유실되거나 중복되지는 않는가? 디버깅도 훨씬 어려워진다—문제가 생기면 여러 에이전트의 로그를 뒤져야 전체 실행 과정을 재구성할 수 있다. 이런 문제들 때문에 인터페이스 규격, 데이터 형식, 통신 프로토콜의 설계가 매우 중요해진다.

컨텍스트 비공유형 명시적 협업은 토폴로지와 무관한 두 가지 기반 인프라에 의존한다. 하나는 **공유 파일 시스템**으로, 에이전트 간 산출물 교환 및 사용자와의 파일 교환을 위한 영속 매체이자 협업의 데이터 평면을 이룬다. 다른 하나는 **통신 및 제어 메커니즘**으로, 에이전트 간 메시지 전달, 상태 조회, 실행 종료를 지원하며 협업의 제어 평면을 이룬다. 아래 세 가지 토폴로지는 모두 이 두 가지 위에 세워진다.

### 에이전트 눈에 비친 파일 시스템

본 장 서두에서 "공유 파일 시스템"을 컨텍스트 비공유의 세 가지 통신 메커니즘 중 하나로 꼽았다. 실제 시스템에서 에이전트가 접근하는 것은 단일 저장소가 아니라 하나의 **가상 파일 시스템**(virtual filesystem)이다: 출처, 수명, 권한이 제각각인 저장소들이 동일한 디렉터리 트리에 마운트(mount)되고, 에이전트는 통일된 `read_file`/`write_file`/`list_dir` 인터페이스로 접근하며, 그 하부는 로컬 임시 디스크, 영속 객체 스토리지, 서드파티 클라우드 드라이브의 API, 또는 읽기 전용 시스템 리소스 팩일 수 있다. 이 디렉터리 트리의 구성—각 영역의 가시성과 수명—을 명확히 해두는 것이 멀티 에이전트 협업 설계의 전제조건이다: 상당수의 동시성 충돌과 정보 유출은 본래 격리되어야 할 영역을 뒤섞어 놓은 데서 비롯된다. 성숙한 멀티 에이전트 시스템의 파일 시스템은 보통 다음 네 가지 영역으로 구성된다:

**첫째, 에이전트 전용 작업공간(Scratchpad)**. 각 에이전트 인스턴스가 독점하는 사적 디렉터리로, 중간 산출물, 임시 파일, 초안, 디버그 로그를 저장하며, 수명은 인스턴스와 함께하고 다른 에이전트와 사용자에게는 보이지 않는다. scratchpad를 격리하는 데는 두 가지 효과가 있다: 여러 에이전트의 임시 파일이 서로 덮어쓰지 않게 하는 것, 그리고 메인 에이전트 컨텍스트의 간결함을 유지하는 것—하위 에이전트의 시행착오 과정은 자신의 작업공간에 남기고, 최종 산출물만 공유 공간에 제출한다. 이는 제4장의 "하위 에이전트는 전체 궤적이 아닌 구조화된 요약을 반환한다"가 저장 계층에서 구현된 형태다.

**둘째, 멀티 에이전트 공유 공간(Shared Workspace)**. 여러 에이전트가 함께 읽고 쓰며, **사용자에게도 보이는** 협업 영역으로, 컨텍스트 비공유 아키텍처에서 에이전트 간 산출물 교환의 주된 매체다: Glossary 에이전트가 용어표를 기록하면 Translation 에이전트가 이를 읽고, 사용자 역시 여기에 원본 파일을 올리거나 최종 산출물을 다운로드할 수 있다. 수명은 작업 전체와 함께하며 영속화가 필요하다. 다수가 동시에 읽고 쓰는 영역이므로 동시성 충돌이 가장 자주 발생하는 곳이다—낙관적 잠금(optimistic locking), 작업 사본 격리(worktree) 등의 메커니즘이 모두 여기서 작동하며, 자세한 내용은 본 장 후반의 "실패 모드 1"에서 다룬다. 제4장에서 볼륨 마운트 `/workspace/shared`로 메인 에이전트, 가상 컴퓨터, 가상 스마트폰을 연결한 것이 이 계층의 전형적인 구현이다.

**셋째, 외부 마운트 리소스(Mounted External Resources)**. 사용자가 접근을 허가한 서드파티 정보원—Google Drive, Notion, Dropbox, 기업 위키 등—으로, 어댑터(adapter)를 통해 파일 시스템 내 마운트 지점(예: `/mnt/gdrive`)으로 매핑된다. 에이전트가 Notion 문서를 파일 읽듯 접근하면, 하부에서는 어댑터가 상대측 API를 호출해 이를 수행한다. 이 계층이 로컬 저장소와 구별되는 세 가지 특성은 설계 시 명시적으로 처리해야 한다: **접근이 외부 권한에 종속됨**(사용자가 원본 시스템에서 갖는 권한이 에이전트의 가시 범위를 결정), **지연이 더 높고 일관성이 더 약함**(매 읽기가 네트워크 왕복이며, 데이터가 이미 외부에서 수정되었을 수 있음), **주로 온디맨드 읽기 전용**(외부 원본에 다시 쓰는 것은 신중해야 하며, 잘못 쓰면 사용자의 실제 데이터를 오염시킬 수 있음). 통일된 파일 인터페이스는 에이전트가 데이터 소스마다 전용 도구를 만들 필요를 없애지만, 위와 같은 성능·보안 차이를 가려버리기도 하므로, 마운트 계층에서 읽기 전용/쓰기 가능, 타임아웃, 자격 증명 경계를 명시적으로 관리해야 한다.

**넷째, 시스템 내장 리소스(Built-in System Resources)**. 시스템이 미리 마련해두고 모든 에이전트에게 읽기 전용으로 공유하는 리소스 팩으로, 대표적인 예가 제2장·제4장에서 소개한 **Skills**다—파일 형태로 조직된 지식 문서와 스크립트가 `/skills` 등의 경로에 마운트되고, 점진적 공개(먼저 색인, 필요 시 펼침) 방식으로 취해진다. 이 밖에 참고 매뉴얼, 템플릿 라이브러리, 공유 도구 정의도 포함된다. 이 계층은 전역 공유·읽기 전용·세션 간 안정적이며, 모든 에이전트가 동시에 읽어도 동시성 제어가 필요 없다.

그림10-3은 이 네 가지 영역이 동일한 디렉터리 트리에 통일되어 마운트되는 구조를 보여준다: 에이전트는 통일된 인터페이스로 트리 전체에 접근하고, 사용자는 공유 공간을 통해 파일을 올리고 내려받으며, 외부 데이터 소스는 어댑터를 거쳐 마운트되고, 시스템 내장 리소스는 읽기 전용으로 제공된다.

| 영역 | 가시성 | 수명 | 읽기/쓰기 | 동시성 제어 |
|----------------|--------------------|-------------------|-----------------|------------------------|
| 에이전트 전용 작업공간 | 해당 에이전트만 | 에이전트 인스턴스 소멸 시 함께 | 읽기/쓰기 | 불필요(사적) |
| 멀티 에이전트 공유 공간 | 협업 중인 모든 에이전트 + 사용자 | 작업이 지속되는 동안, 영속화 필요 | 읽기/쓰기 | 필요(낙관적 잠금 / worktree) |
| 외부 마운트 리소스 | 외부 권한에 따라 다름 | 외부 원본이 결정 | 대부분 읽기 전용, 쓰기는 신중히 | 외부 원본이 책임 |
| 시스템 내장 리소스 | 모든 에이전트 | 세션 간 안정적 | 읽기 전용 | 불필요(읽기 전용) |

네 영역을 동일한 디렉터리 트리에 통일하는 것이 바로 "**파일 경로를 범용 인터페이스로**" 삼는 설계의 가치가 드러나는 지점이다: 에이전트 간 산출물 전달, 메인 에이전트가 하위 에이전트에게 입력을 인계하는 것, 심지어 조직 간 A2A 협업에서 Artifact를 교환하는 것까지, 전달되는 것은 모두 가벼운 경로 문자열이지, 내용을 컨텍스트 윈도우에 실어 나르는 것이 아니다(제4장). 이는 제5장의 "파일 시스템을 에이전트의 중추로" 삼는 논의와도 일맥상통한다—그쪽이 단일 에이전트가 어떻게 파일 시스템으로 기억과 능력을 담아낼지를 다뤘다면, 여기서는 같은 추상을 멀티 에이전트로 확장한다: 사적·공유·외부·내장이라는 네 가지 저장소가 마운트된 하나의 가상 디렉터리 트리, 이것이 곧 멀티 에이전트 협업의 저장 기반이다.

### 에이전트 간 통신과 제어

파일 시스템은 에이전트 간 **산출물 교환** 문제를 해결하지만, 협업에는 **제어 평면**도 필요하다: 에이전트 간 메시지 전달, 상태 조회, 실행 종료를 지원해야 한다. 제4장은 이미 이 평면의 도구 원시 요소를 제시했다—생성(`spawn_subagent`), 메시지 발송(`send_message_to_subagent`), 취소(`cancel_subagent`)—그리고 동기/비동기/스트리밍/다회차라는 네 가지 협업 형태도 다뤘다. 본 절은 인터페이스 정의를 반복하지 않고, 멀티 에이전트 협업이 의존하지만 종종 간과되는 세 가지 역량에 초점을 맞춘다.

**첫째, 메시지 전달.** 가장 단순한 형태는 점대점(point-to-point)이다: 에이전트 A가 `send_message_to_agent_b(content)`를 직접 호출하는 것으로, 토폴로지가 고정적이고 에이전트 수가 적은 상황(본 장 실험 10-4의 전화 + 컴퓨터 이중 에이전트 등)에 적합하다. 에이전트 수가 늘고 비동기 병렬이 필요할 때는 점대점 연결 수가 에이전트 수의 제곱으로 증가하고, 송수신 양측이 동시에 온라인이어야 한다. 이때는 **메시지 버스**로 전환해야 한다(자세한 내용은 본 장 후반 "병렬 협업 형태" 참고): 에이전트는 메시지를 버스에 발행하고, 버스가 구독 관계에 따라 전달하며, 발신자는 소비자를 알 필요가 없다. 점대점이든 버스를 경유하든, 메시지는 보통 구조화된 **엔벨로프**(envelope)를 담아야 한다: 발신자 ID, 대상(특정 에이전트 또는 브로드캐스트), 메시지 유형(`task_assigned`/`status_update`/`result`/`terminate` 등), JSON 페이로드. 통일된 엔벨로프 형식은 수신자가 안정적으로 라우팅·파싱할 수 있게 하고, 협업 흐름을 추적 가능하게 만든다—이는 멀티 에이전트 시스템 디버깅의 핵심이다.

**둘째, 상태 조회.** 제어 평면에서 가장 저평가되기 쉬운 부분이다. 메인 에이전트가 하위 에이전트를 파견한 뒤 그 진행 상황을 알 수 없다면, 계속 기다려야 할지 판단할 수도 없고, 막혔을 때 제때 개입할 수도 없다. 상태 획득에는 두 가지 방식이 있다. **풀(pull)**: 메인 에이전트가 `get_subagent_status(agent_id)`를 호출해, 하위 에이전트의 현재 상태(실행 중/입력 대기/완료/실패), 진행률, 최근 활동 시각을 받는다. **푸시(push)**: 하위 에이전트가 실행 중 능동적으로 메시지 버스에 상태 업데이트를 보고하고, 메인 에이전트는 작업 상태표를 실시간으로 갱신한다(본 장 실험 10-6의 "실시간 모니터링"이 이 방식이다). 둘 다 나름의 절충이 있다: 풀은 구현이 간단하지만, 폴링이 지나치게 잦으면 토큰을 낭비하고 너무 성기면 시기를 놓친다. 푸시는 실시간성이 좋지만 하위 에이전트의 자발적 보고에 의존한다. 엔지니어링에서는 흔히 하위 에이전트 상태를 **상태 기계**(제출됨, 실행 중, 입력 필요, 완료, 실패)로 모델링하며, 본 장 후반의 A2A 프로토콜은 작업 생명주기를 이런 상태로 표준화한다. 이 밖에 **타임아웃과 하트비트 검사**도 최후의 안전망으로 필요하다(제4장의 Heartbeat와 monitor_shell에 조응): 하위 에이전트가 보고도 하지 않고 반환도 하지 않아도, 메인 에이전트는 "N분 이상 활동 없으면 실패로 간주"하는 규칙으로 막힌 하위 에이전트에 시스템 전체가 발목 잡히는 것을 막을 수 있다.

**셋째, 실행 종료.** 병렬 협업에서는 "하나는 성공, 나머지는 무효화"되는 상황이 자주 발생한다—여러 에이전트가 각자 검색하다가 하나가 목표를 찾으면 나머지는 즉시 멈춰야 한다(본 장 실험 10-6의 계단식 종료). 종료에는 두 가지 강도가 있다. **우아한 종료(graceful)**가 우선이다: 메인 에이전트가 `terminate` 신호를 보내면, 하위 에이전트는 현재 단계의 안전한 지점에서 이에 응답해 먼저 자원을 정리하고(브라우저 세션 닫기, 미완성 파일 쓰기, 잠금 해제), 확인(ack)을 반환한 뒤 종료한다. **강제 종료(forced)**는 최후의 수단이다: 프로세스를 곧바로 종료하는 방식으로, 하위 에이전트가 우아한 신호에 응답하지 않을 때만 사용하며, 대가로 매달린 자원과 미완성 쓰기가 남을 수 있다. 두 가지 엔지니어링 요점을 처리해야 한다: 하나는, 우아한 종료를 위해 하위 에이전트가 루프 안에서 종료 신호를 주기적으로 확인해야 한다는 것(제4장의 인터럽트 메커니즘과 유사)—그렇지 않으면 신호에 응답할 방법이 없다. 다른 하나는, 계단식 종료에는 경쟁 조건(race condition)이 존재한다는 것—여러 하위 에이전트가 거의 동시에 성공을 보고할 수 있으므로, 메인 에이전트는 잠금이나 멱등성 설계로 단 한 번만 결산하고 단 한 라운드만 종료를 브로드캐스트하도록 보장해야 한다. 자세한 내용은 본 장 실험 10-6의 경쟁 조건 논의를 참고하라.

산출물 교환(데이터 평면)과 메시지 전달·상태 조회·실행 종료(제어 평면)가 함께 컨텍스트 비공유형 멀티 에이전트 시스템을 떠받친다. 아래 세 가지 협업 토폴로지는 본질적으로 이 두 평면 위에서 통제권 귀속과 정보 흐름 방향에 대해 서로 다른 선택을 한 것이다.

에이전트 간 협업 관계와 제어 흐름의 특징에 따라, 컨텍스트를 공유하지 않는 협업은 대등 협업 패턴, 관리자 패턴, 탈중앙화 패턴이라는 세 가지 주요 아키텍처로 나눌 수 있으며, 각기 다른 유형의 작업에 적합하다.

### 대등 협업 패턴: 상호 견제와 반복 개선

대등 협업은 대개 2-3개의 대등한 신분의 에이전트가 여러 라운드에 걸쳐 서로 피드백을 주고받는 것을 포함한다. 핵심 가치는 인지적 다양성을 도입하는 데 있다—서로 다른 에이전트가 서로 다른 각도에서 같은 문제를 살펴, 혁신과 견실함 사이의 균형을 찾고, 어떤 단일 에이전트보다 더 나은 결과물을 산출한다.

관리자 패턴이나 탈중앙화 패턴에 비해 대등 협업의 구현 복잡도는 훨씬 낮다—두 에이전트의 역할, 통신 메커니즘, 반복 종료 조건만 정의하면 바로 돌아간다. 아이디어를 빠르게 검증하거나 프로토타입을 만들기에 이상적인 선택이다.

대등 협업의 가장 전형적인 용도는, 에이전트 실무에서 극히 흔한 한 가지 실패를 해결하는 것이다: **조기 종료**—일이 반쯤 끝난 상태에서 멈추는 것. 여기에는 세 가지 전형적인 형태가 있다. 아래에서는 Coding 에이전트와 필자 팀이 만든 Pine AI(서문에서 소개한, 사용자 대신 전화로 업체·통신사와 교섭·처리하는 에이전트)를 각각 몇 가지씩 예로 든다. 하나는 **게으른 가짜 완료**다: 일부만 하고서 전부 다 했다고 선언하는 것—Coding 에이전트가 코드를 다 쓰고서 테스트도 안 돌리고 배포도 안 해보고 "작업 완료"라고 보고한다. 사용자가 Pine AI에게 두 가지 일을 맡겼는데, 첫 번째를 끝내고 두 번째를 잊어버린 채 "다 처리했습니다"라고 곧바로 보고한다. 둘은 **조기 포기**다: 한 길이 막히면 전체가 안 된다고 선언하는 것—Pine AI가 업체에 연락할 때 전화, 서식 작성, 이메일 발송 등 여러 경로가 있는데도, 전화 한 통이 거절당하면 곧바로 사용자에게 "이 일은 안 됩니다"라고 알린다. 실제로는 다른 경로를 시도하면 잘 될 가능성이 높다. 셋은 **가짜 성공**이다: 에이전트는 성공했다고 여기지만 실제 종결 고리가 완성되지 않은 경우—전화 통화에서 상대가 구두로 환불에 동의했지만, 사용자가 앱에서 한 단계 더 확인해야 하는데도 에이전트가 "완료됐습니다"라고 보고해, 사용자는 후속 조치가 있는 줄 모르고 환불은 실제로 이루어지지 않는다. 세 가지 형태는 모두 하나의 근원을 가리킨다: **검증 이전에는 "완료"란 모델의 선언일 뿐, 증명이 아니다.**

선언을 증명으로 바꾸는 것, 이것이 바로 제1장 진화 곡선 말미의 **Loop 엔지니어링**(Loop Engineering) 과제다: 에이전트를 지속적으로 돌아가게 하는 순환을 설계하는 것—다음 해야 할 일을 찾고, 실행하고, 검증하고, 진행 상황을 기록한다—"정말로 멈춰도 되는지"를 판단하는 것은 모델 자신이 아니라 검증기이며, 사람의 역할은 "에이전트에게 프롬프트를 써주는 조작자"에서 "순환을 설계하는 엔지니어"로 바뀐다. 이 용어는 2026년 6월 Addy Osmani가 정리해 제시했으며[^loop-engineering-2026], Anthropic Claude Code 총괄 Boris Cherny의 표현은 더 직설적이다: "저는 이제 Claude에게 직접 프롬프트를 쓰지 않습니다. 제 일은 loop를 짜는 것입니다." 이 논의를 통해 업계가 형성한 핵심 공감대는: **순환의 병목은 검증기에 있지, 모델에 있지 않다**는 것이다—검증이 신뢰할 수 없으면 순환이 아무리 빨리 돌아도 저품질 산출물을 더 빠르게 완료로 표시할 뿐이다. 또한 서문에서 말했듯, 실천이 먼저고 명명은 나중이다: 이 용어가 유행하기 전부터 Pine AI를 포함한 선두 에이전트 팀들은 이미 "순환 더하기 검증"으로 조기 종료 문제를 해결해왔다. 그리고 검증을 가장 효과적으로 조직하는 방식이 바로 다음에 설명할 제안자-검토자 패러다임이다.

**제안자-검토자 패러다임.**


![그림10-4 제안자-검토자 순환](images/fig10-4.svg)


제안자-검토자는 가장 전형적인 대등 협업 패러다임이다. 제5장에서 이미 PPT 생성, 영상 편집, 로그 시각화라는 세 가지 실험을 통해 이 패러다임의 설계 원칙과 실전 응용을 상세히 소개했다: Proposer 에이전트가 코드를 생성하고, Reviewer 에이전트가 실행 결과를 렌더링해 Vision LLM으로 품질을 평가하고 구조화된 개선 제안을 내놓으며, 둘은 효과가 만족스러울 때까지 반복한다.

이 패러다임은 보안 검토(Proposer가 조치 방안을 생성하고 Reviewer가 규정 준수와 잠재 위험을 점검), 콘텐츠 심사(Proposer가 답변 초안을 작성하고 Reviewer가 업무 규칙과 표현 규범을 점검), 코드 심사(Proposer가 코드를 작성하고 Reviewer가 보안성과 모범 사례를 점검) 등의 시나리오에도 똑같이 적용된다.

**왜 하나의 에이전트가 스스로 생성하고 스스로 검토하게 할 수 없는가?** 이는 앞서 "멀티 에이전트가 단일 에이전트보다 정말로 나은 경우" 절의 판별 기준이 구체적으로 적용되는 지점이다—검토가 새 정보를 도입하지 않는다면 그저 "모델이 한 번 더 생각하게 하는" 것에 불과하다. 관련 연구는 이에 명확한 답을 준다. Huang 등은 ICLR 2024 논문 《Large Language Models Cannot Self-Correct Reasoning Yet》에서 발견했다: 외부 피드백 없이 GPT-4가 자신의 답변을 스스로 검토·수정하게 하면 정확도가 오히려 떨어졌다—모델이 맞는 답을 틀리게 고치는 횟수가 틀린 답을 맞게 고치는 횟수보다 많았다.

2024년 TACL에 발표된 리뷰 논문 《When Can LLMs Actually Correct Their Own Mistakes?》(arXiv:2406.01297)는 이 결론을 한 번 더 확인했다: 신뢰할 수 있는 외부 피드백(테스트 케이스 실행 결과, 외부 도구의 검증 출력 등)이 제공되지 않는 한, 모델 자체에만 의존하는 순수한 "자기 교정"은 거의 효과가 없다.

ICLR 2024의 CRITIC 논문은 직관적인 대조 실험을 제공한다. CRITIC은 모델이 외부 도구(검색 엔진, Python 인터프리터)를 이용해 자신의 답변을 검증하게 했더니 효과가 뚜렷이 향상되었다. 그러나 실험자가 도구 검증 단계를 빼고 모델의 자기 평가만 남겼을 때는 그 향상분의 대부분이 사라졌다. 이는 검토의 가치가 "모델이 한 번 더 생각하게 하는" 데 있는 것이 아니라, **모델이 생성 시점에는 갖지 못했던 새로운 정보를 도입하는 데** 있음을 보여준다—테스트 결과, 렌더링 스크린샷, 컴파일 오류, 외부 검색 결과.

이것이 바로 제안자-검토자 패러다임의 핵심 설계 원리다. 제5장의 PPT 생성 실험에서, Reviewer 에이전트의 가치는 "같은 모델이 코드를 한 번 더 보는" 것이 아니라, **PPT를 렌더링하고 스크린샷을 찍는** 데 있다—이 스크린샷에는 Proposer 에이전트가 코드를 생성할 당시 전혀 얻을 수 없었던 시각 정보가 담겨 있다. 마찬가지로 코드 생성 시나리오에서도, 테스트 케이스 실행으로 생긴 통과/실패 결과는 코드를 작성할 당시에는 존재하지 않았던 새로운 신호다—Reviewer의 독립적 가치는 바로 Proposer가 얻을 수 없는 이런 외부 피드백에 접근할 수 있다는 데서 비롯된다.

Loop 엔지니어링의 관점에서 보면, 업계가 정리한 몇 가지 순환 스타일은 모두 본서에서 대응점을 찾을 수 있다: 폐루프에 인간 승인을 더한 것은 제4장의 사전 승인(사람이 최종 검토자)에 대응하고, 개루프에 예산이나 라운드 수 상한을 더한 것은 제5장 PPT 생성의 다회차 반복(최대 5라운드)에 대응하며, 오케스트레이션형 하위 에이전트는 다음 절의 관리자 패턴에 대응한다. 바꿔 말하면, Loop 엔지니어링이 묘사하는 것은 새로운 아키텍처가 아니라, 이런 협업 패턴들을 "순환 + 검증 + 종료 조건"이라는 하나의 프레임워크 아래 통합한 것이다—여기서 검증을 담당하는 것이 바로 제안자-검토자 패러다임이다.

**확장: 그 밖의 대등 협업 패턴.**

**Debate(토론)**: 여러 에이전트가 각기 다른 입장을 취해, 대립적 대화를 통해 문제 공간을 깊이 탐색한다. 예컨대 어떤 기술 방안을 평가할 때, 에이전트 A는 "지지자" 역할을 맡아 방안의 장점과 기회를 열거하고, 에이전트 B는 "반대자" 역할을 맡아 위험과 한계를 지적하며, 매 라운드마다 상대의 논점에 반박이나 보충을 제기한다. 단일 에이전트가 분석할 경우 모델이 특정 관점에 치우쳐 반대 증거를 간과하는 경향이 있지만, 토론 모드는 제도화된 대립을 통해 찬반 양측이 충분히 논증되도록 보장해 의사결정자가 더 균형 잡힌 판단을 내리도록 돕는다.

다만 토론 모드의 실제 효과는 학계에서 여전히 논쟁적이다. 2026년 Tran과 Kiela의 연구[^single-agent-2026]는 다중 홉 추론 작업에서 단일 에이전트와 다섯 가지 멀티 에이전트 아키텍처(순차, 토론, 앙상블, 병렬 역할, 하위 작업 병렬)를 비교해 발견했다: **사고 토큰 예산을 동일하게 엄격히 통제하면, 단일 에이전트의 성능이 멀티 에이전트와 동등하거나 오히려 더 낫다**(컨텍스트 활용률이 어느 정도까지 약화되지 않는 한). 연구자들은 정보 이론의 데이터 처리 부등식(data processing inequality)에 근거해 이를 설명한다: 토론 중의 여러 에이전트는 완전히 동일한 텍스트 정보를 처리하며, 에이전트 간의 매 순차적 중간 결론 전달은 정보를 잃을 뿐 새로 만들어낼 수는 없다. 일부 학술 논문에서 토론 모드가 얻는 이득은 십중팔구 여러 에이전트가 더 많은 총 연산량을 소비한 데서 비롯된 것이다. 이 논증의 경계를 명확히 해둘 필요가 있다: 이는 "멀티 에이전트가 중간 결론을 순차적으로 전달"하는 데서 생기는 정보 병목을 겨냥한 것이지, 다른 유형의 방식—같은 문제에 대해 **독립적으로 여러 번 샘플링한 뒤 취합**(self-consistency, 다수결 등)하거나, **생성과 검증의 난이도 비대칭**(답을 쓰기는 어렵지만 답을 검사하기는 쉬움)을 활용해 생성-검증 분업을 하는 것—을 부정하지 않는다. 이런 시나리오들은 추가적인 독립 샘플링을 도입했거나 작업 자체의 비대칭 구조를 활용한 것으로, 모두 데이터 처리 부등식의 적용 범위에 들지 않는다.

[^single-agent-2026]: Tran, D., Kiela, D. *Single-Agent LLMs Outperform Multi-Agent Systems on Multi-Hop Reasoning Under Equal Thinking Token Budgets.* arXiv:2604.02460, 2026.

**Brainstorm(브레인스토밍)**: 여러 에이전트가 독립적으로 아이디어를 생성한 뒤 서로 공유하며 영감을 주고받는다. 예컨대 제품 혁신 작업에서, 에이전트 1이 "소셜 공유 기능 추가"를 제안하면, 에이전트 2는 거기서 영감을 받아 "소셜 네트워크에 공유하는 것뿐 아니라 개인화된 공유 포스터도 생성"을 제안하고, 에이전트 3은 앞의 둘을 종합해 "사용자가 포스터 템플릿을 커스터마이징하고 템플릿 마켓을 형성"을 제안한다. 서로 다른 에이전트가 서로 다른 "사고 성향"(서로 다른 프롬프트나 모델로 구현)을 지니고, 서로 자극을 주고받으며 더 넓은 해법 공간을 탐색해, 단일 에이전트로는 떠올리기 어려운 아이디어 조합을 찾아낸다.

**Panel Discussion(전문가 패널)**: 여러 에이전트가 각기 하나의 전문 영역 관점을 대표해, 학제간 문제를 함께 논의한다. 예컨대 신제품의 실현 가능성을 평가할 때, 엔지니어 에이전트는 기술적 관점에서 구현 난이도를 분석하고, 제품 에이전트는 사용자 경험 관점에서 시장 매력도를 평가하며, 운영 에이전트는 비용과 자원 관점에서 사업적 실현 가능성을 분석한다. 이 에이전트들은 대립 관계가 아니라 상호 보완 관계로, 함께 문제의 전체 그림을 맞추고 영역을 넘나드는 제약과 기회를 식별한다.

### 관리자 패턴: 중앙화된 조율

작업이 5개 이상의 하위 작업을 포함하거나, 동적 스케줄링이 필요하거나, 하위 작업 간에 복잡한 의존관계가 있을 때는 대등 협업으로는 감당하기 어려워 관리자 패턴을 도입해야 한다. Manager 에이전트의 직무는 프로젝트 매니저와 같다: 먼저 전체 작업을 이해하고, 배분 가능한 하위 작업으로 분해하며, 적합한 에이전트를 선택해 실행시키고, 진행 상황을 추적하며 예외를 처리(재시도, 에이전트 교체, 계획 조정)하고, 마지막으로 각 에이전트의 출력을 최종 결과로 통합한다.

시스템 설계 관점에서 보면, 관리자 패턴은 각 전문 에이전트를 Manager가 호출할 수 있는 도구로 모델링한다. Manager의 도구 집합에는 전통적인 외부 도구(검색, 파일 조작 등)뿐 아니라 다른 에이전트의 호출 인터페이스도 포함된다. Manager는 도구 호출 메커니즘을 통해 해당 에이전트를 기동하고, 작업 파라미터와 필요한 컨텍스트를 전달하며, 완료를 기다렸다가 반환 결과를 받는다. Manager의 관점에서는 에이전트를 호출하는 것과 일반 도구를 호출하는 것 사이에 본질적 차이가 없다—둘 다 요청을 보내고 응답을 받는 것이다. 이 통일된 추상은 관리자 패턴에 뛰어난 확장성을 부여한다—새 능력을 추가하려면 해당 에이전트를 개발해 도구로 등록하기만 하면 되고, Manager의 핵심 로직은 수정할 필요가 없다. 동시에 이질성도 자연스럽게 지원한다—서로 다른 에이전트가 서로 다른 모델, 프롬프트, 도구 집합을 쓸 수 있고, 심지어 서로 다른 하드웨어 환경에서 실행될 수도 있다.

"에이전트가 서로에게 도구가 된다"는 추상은 제4장 "협업 도구" 절에서 이미 확립되었다: spawn_subagent / send_message / cancel_subagent의 인터페이스 설계, 그리고 하위 에이전트 컨텍스트 준비의 네 가지 전략(최소 전달, 수동 선별, 자동 압축, LLM 생성 컨텍스트) 모두 여기서 Manager가 하위 에이전트를 호출하는 데 그대로 적용된다. 제4장이 다룬 것은 "Manager → 하위 에이전트" 방향으로 무엇을 전달하느냐이고, 그와 대칭되는 문제는 "하위 에이전트 → Manager" 방향으로 무엇을 반환하느냐이다. 답은 **전체 궤적이 아닌 구조화된 요약**이다: 하위 에이전트는 작업 결론, 핵심 발견, 산출물의 파일 경로, 발생한 문제를 반환해야 하며, 완전한 실행 궤적은 자신의 로그에 남겨두어야 한다. 그래야만 Manager의 컨텍스트가 하위 작업 수에 따라 완만하게 선형으로 증가할 뿐 폭발적으로 팽창하지 않는다—이는 뒤에 나올 실험 10-3에서 Manager가 "파일 색인만 유지하고 번역 내용은 저장하지 않는" 방법론의 근거이기도 하다. 두 장의 역할 분담은 이렇다: 제4장은 메커니즘(도구 인터페이스와 컨텍스트 전달의 구현)을, 본 장은 아키텍처(토폴로지 구조와 직무 분담)를 다룬다.

하지만 관리자 패턴에도 고유한 과제가 있다. Manager가 시스템의 단일 병목이 된다—모든 하위 작업의 성격을 이해해야 하고, 올바른 에이전트를 선택해야 하며, 컨텍스트를 정확히 전달해야 하고, 어떤 판단 오류든 전체 흐름에 영향을 미친다. 또한 Manager는 전체 작업의 전역 컨텍스트를 유지해야 하는데, 작업이 깊어지고 에이전트 호출이 늘어날수록 컨텍스트가 빠르게 팽창할 수 있다. 따라서 Manager의 프롬프트 품질, 컨텍스트 관리 전략, 합리적인 작업 분해 세분도에 특히 주의해야 한다.

2025년의 Plan-and-Act 논문[^plan-and-act-2025]은 이에 대해 실증 분석을 했다: Planner-Executor 이중 에이전트 아키텍처에서, **약한 플래너가 전체 시스템에서 가장 결정적인 병목**이다. Planner의 계획 품질이 충분히 높으면, Executor가 다소 단순해도 좋은 결과를 얻을 수 있다. 반대로 Planner의 작업 분해가 잘못되면, 이후 모든 Executor의 작업이 잘못된 전제 위에 세워진다. 이 연구는 WebArena-Lite 벤치마크에서 54%의 성공률을 달성했는데, 핵심 기여는 Executor의 실행 능력이 아니라 Planner의 계획 능력을 개선한 데 있다. 이 발견의 시사점은: 가장 강력한 모델과 가장 정교하게 설계된 프롬프트를 모든 에이전트에 균등히 배분할 것이 아니라 Manager(플래너)에 배정해야 한다는 것이다.

이는 제4장의 한 논점과 모순되지 않는다. 제4장이 제안 모델과 검토 모델을 논할 때 지적한 것은, 양쪽의 능력이 비슷해야 한다는 것이었다—하지만 그것은 **검토 시나리오**를 말한 것이다: 검토자는 반드시 피검토자의 추론을 따라잡아야 그 허점을 발견할 수 있고, 능력 격차가 너무 크면 애초에 제대로 검토할 수 없다. 반면 관리자 패턴이 논하는 것은 또 다른 문제—**계획과 실행의 분업**이다: 플래너가 작업을 잘못 분해하면 실행자가 아무리 강해도 만회할 방법이 없으므로, 가장 강력한 모델과 가장 정교한 프롬프트를 플래너에 우선 배정해야 한다. 실행자들 사이에 능력 균형이 필요한지 여부는 하위 작업들의 결합도에 달려 있다—여러 실행자의 산출물이 결국 하나로 조립되어야 할 때는, 가장 약한 고리가 전체 품질을 끌어내리기 쉽다.

[^plan-and-act-2025]: Erdogan, L. E., et al. *Plan-and-Act: Improving Planning of Agents for Long-Horizon Tasks.* arXiv:2503.09572, 2025.

Manager가 전문 에이전트를 순서대로 호출하고, 각 에이전트가 완료 후 결과를 반환하면 Manager가 다음 단계를 결정한다. 제어 흐름은 선형적이고 간명해, 하위 작업 간에 명확한 선후 의존관계가 있는 시나리오에 적합하다.

> **실험 10-3 ★★: 도서 번역 에이전트**
>
> 도서 번역은 멀티 에이전트 협업이 전형적으로 필요한 복잡한 작업이다. 기술 서적 한 권을 번역하는 것은 단순히 텍스트를 한 언어에서 다른 언어로 옮기는 것이 아니라, 전문 용어를 전체 책에 걸쳐 일관되게 유지하고, 맥락을 정확히 파악하며, 전체적으로 매끄럽게 읽히도록 보장해야 한다. 예컨대 대형 언어 모델 관련 영어 서적을 번역할 때, 다수의 용어가 반복해서 등장하며, 여러 통용 표현이 있을 수 있지만 전체 책에서 반드시 통일해야 한다—제1장에서 agent를 "에이전트"로 번역했다면, 뒤에서 "대리인"으로 바꿔서는 안 된다.
>
> 단일 에이전트로 이 작업을 하면 심각한 컨텍스트 문제에 부딪힌다. 에이전트가 장을 하나씩 처리해 나가면서 컨텍스트가 계속 누적된다: 전체 용어표, 이미 번역된 장, 현재 문단, 번역 사고 과정, 도구 호출 결과. 수백 페이지 분량의 기술 서적에 번역 중간 산출물까지 더하면 컨텍스트 윈도우를 쉽게 초과한다. 더 심각한 것은, 지나치게 긴 컨텍스트 속에서 에이전트가 "길을 잃기" 쉽다는 것이다—이전의 용어 약속을 잊어버려 8장에서 2장과 다른 번역을 쓰거나, 교정 단계에서 중복 검사를 하며 자원을 낭비하거나, 심지어 주의가 분산되어 실제로는 존재하지 않는 용어 규칙을 "기억해내는" 환각을 일으키기도 한다.
>
> 관리자 패턴은 작업 분해와 책임 분리를 통해 이런 문제를 해결한다:
>
> - **Glossary 에이전트**(용어 대조표 에이전트): 책 전체 내용을 받아 반복 등장하는 전문 용어를 식별하고, 전문 사전과 번역 규범을 검색해, 구조화된 용어 대조표(JSON/CSV 형식, 영어 용어·중국어 번역·품사·사용 맥락 포함)를 생성한다. 완료 후 공유 파일 시스템에 기록하면 에이전트는 곧 소멸시켜 자원을 해제할 수 있다
> - **Translation 에이전트**(장별 번역 에이전트): 현재 장, 용어 대조표, 번역 가이드(목표 독자 수준, 언어 스타일)를 받아 매끄러운 중국어로 번역한다. 대조표에 있는 용어는 정해진 번역을 엄격히 사용하고, 새로운 용어를 만나면 번역을 추론해 검토 대기로 표시한다. 각 인스턴스는 독립된 컨텍스트에서 작업해 서로 간섭하지 않는다. 번역문은 파일 시스템에 기록된다(예: `chapter1_zh.md`). Manager는 여러 인스턴스를 병렬 또는 순차로 기동할 수 있다
> - **Proofreading 에이전트**(전문 교정 에이전트): 모든 번역문과 용어표를 받아 일관성 검사를 수행한다—용어 번역이 통일되었는지 하나하나 검증하고, 앞뒤 불일치를 식별하며, 전체적인 매끄러움과 가독성을 점검한다. 교정 보고서를 생성해 파일 시스템에 기록한다
> - **Manager 에이전트**: 컨텍스트에는 주로 작업 설명, 실행 계획, 각 에이전트의 호출 기록과 진행 상태를 저장한다. 완전한 번역 내용은 저장하지 않고(이는 파일 시스템에 존재), 파일 색인만 유지한다. 교정 보고서에 따라 Manager는 특정 장을 Translation 에이전트로 되돌려 수정을 요청할 수 있다
>
> 이 아키텍처에서 Manager 에이전트의 컨텍스트는 항상 관리 가능한 범위 내에 머문다: 작업의 전체 설명과 목표, 각 단계의 실행 계획, 각 에이전트의 호출 기록과 반환 결과, 현재 진행 상태만 알면 되며, 매 장의 완전한 번역 내용을 담을 필요는 없다.
>
> 핵심 강점은 **컨텍스트 격리**에 있다: Glossary 에이전트는 용어 추출에 필요한 내용만 보고, Translation 에이전트는 현재 장과 용어표만 보며, Proofreading 에이전트는 전체 글에 접근할 필요는 있지만 일관성 검사에만 집중한다. 각 에이전트는 간결하고 집중된 컨텍스트에서 작업하므로 효율이 더 높을 뿐 아니라 오류 가능성도 더 낮다—정보 과부하로 주의가 분산되지 않는다.
>
> **실험 요구사항**:
> 1. 그림과 코드가 함께 있는 기술 서적 한 권을 번역 대상으로 선정하라
> 2. Manager, Glossary, Translation, Proofreading 네 종류의 에이전트를 구현하라
> 3. 각 에이전트의 컨텍스트 소비를 기록해, 관리자 패턴이 컨텍스트 팽창을 제어하는 데 효과적인지 검증하라
> 4. 단일 에이전트 대 관리자 패턴을 번역 품질, 실행 효율, 자원 소비 측면에서 비교하라
>

**병렬 협업 형태.**


![그림10-7 Manager 병렬 협업](images/fig10-7.svg)


여러 하위 작업을 병렬로 실행할 수 있을 때는 순차 방식이 비효율적이다. 병렬 협업은 여러 에이전트를 동시에 작동시켜 처리량을 크게 높인다. Manager 에이전트는 병렬 작업을 계획할 뿐 아니라, 실행 중인 모든 에이전트를 실시간으로 모니터링하고, 통신 조율을 처리하며, 에이전트가 성공하거나 실패했을 때 전역적 결정을 내려야 한다. 이는 보통 **메시지 버스**(Message Bus)라는 기반 인프라를 필요로 한다—"공용 게시판"이라 이해하면 된다. 에이전트는 그 위에 메시지를 붙일 수도 있고(발행), 자신이 관심 있는 메시지 유형을 주시할 수도 있다(구독). 이로써 비동기 통신을 실현해 서로를 막지 않는다. 흔한 구현 방안은 복잡도가 증가하는 순으로 두 가지가 있다: **Redis Pub/Sub**은 경량이며 메시지를 즉시 보내고 즉시 받는 방식으로 간단하고 사용하기 쉽지만, 영속화가 되지 않아 수신자가 그 순간 접속해 있지 않으면 메시지가 유실되는 단점이 있다. **RabbitMQ** 등의 메시지 큐는 메시지를 디스크에 저장하므로, 수신자가 일시적으로 오프라인이어도 유실되지 않는다. 메시지 형식은 보통 발신자 ID, 대상 에이전트(또는 전체 브로드캐스트), 메시지 유형, JSON 형식의 데이터 내용을 포함한다.

**링타이(Lingtai): 관리자 패턴의 한 제품화 사례.** 링타이는 로컬에서 실행되며 파일을 근간으로 하는 장기 에이전트 거처[^lingtai]로, 그 세 가지 역할은 거의 본 절 개념의 완전한 구현이다: **주기령**(main agent)은 사용자와 대화하는 상시 중추로서 계획과 기억을 관장하고 다른 역할에 작업을 파생시킨다—정확히 Manager 에이전트의 위치다. **분신령**(daemon)은 시끄럽고 경계가 명확한 하나의 작업을 위해 분리된 단시간 병렬 작업자로, 완료 후 곧바로 폐기되고 결론만 주기령에게 가져다준다—이는 "하위 에이전트가 전체 궤적이 아닌 구조화된 요약을 반환한다"와 병렬 협업 형태의 제품화 그 자체다. **분령**(avatar)은 자신만의 기억, 메일함, 직무를 지닌 영속적인 전문화 동료로, 여러 세션에 걸쳐 보존할 가치가 있는 전문 분업에 쓰인다. 나머지 설계 역시 앞선 논의와 하나하나 대응한다: 지식은 각 영(靈)이 사적으로 지니는 영속 기억 파일이고, 스킬은 모든 영이 공유하는 마크다운 매뉴얼이다(앞서 "에이전트 눈에 비친 파일 시스템" 절의 시스템 내장 리소스에 대응). 컨텍스트 윈도우가 가득 차려 하면 영은 "탈피"(molt)한다—스스로에게 요약을 써두고, 영속 기억을 지닌 채 깨끗한 컨텍스트에서 작업을 이어간다(제2장의 컨텍스트 압축에 대응). 하부 모델은 교체 가능해도 영은 그대로 남는다—정체성, 기억, 능력이 모두 프로젝트 디렉터리 안의 평범한 파일 형태로 저장된다는 것, 즉 "영은 곧 그 파일이다."

[^lingtai]: 링타이 공식 튜토리얼: https://lingtai.ai/zh/tutorial/

> **실험 10-4 ★★★: 전화하면서 컴퓨터를 쓰는 에이전트**
>
> **전제 조건**: 본 실험은 제9장의 Computer Use와 음성 에이전트 기술을 종합적으로 활용한다. 먼저 제9장의 관련 실험을 완료할 것을 권장한다.
>
> 현실의 많은 시나리오는 여러 능력을 동시에 작동시켜야 하며, 줄 서서 하나씩 처리할 여유가 없다: 인간 비서라면 한쪽으로는 고객과 전화 통화를 하면서 다른 한쪽으로는 컴퓨터에서 문서를 조회하고 요점을 기록할 수 있다. 이런 "멀티태스킹"은 단일 에이전트에게는 극히 도전적이다—하나의 에이전트가 실시간 음성 대화와 컴퓨터 화면 조작을 동시에 처리하게 하면, 두 작업 사이를 반복해서 전환할 수밖에 없어 대화가 끊기거나 조작이 중단된다. 멀티 에이전트 병렬 실행의 핵심 발상은: **서로 다른 에이전트가 각각 실시간성 요구가 높은 하나의 작업에 집중하고, 비동기 메시지 전달을 통해 조율함으로써 진정한 병렬 처리를 실현하는 것**이다. 두 에이전트는 각기 다른 상호작용 양식에 맞춰 전문적으로 최적화되었다—전화 에이전트는 저지연 음성 인식과 합성이 필요하고, 컴퓨터 에이전트는 강력한 시각 이해와 조작 계획 능력이 필요하다.
>
> **시나리오**: AI 에이전트가 사용자를 도와 복잡한 항공편 예약 양식을 작성한다. 웹페이지를 조작하는 동시에 전화로 사용자에게 개인 정보(성명, 신분증 번호, 항공편 선호 등)를 묻고 확인해야 한다—양쪽 모두 높은 실시간성이 요구되는, 단일 에이전트로는 감당하기 어렵지만 두 에이전트가 각자 맡으면 전형적으로 해결되는 사례다.
>
> **이중 에이전트 아키텍처**:
>
> **Phone 에이전트**: ASR + LLM + TTS 기반의 음성 통화 에이전트. 사용자의 자연어 답변을 이해해 핵심 정보를 추출하고 메시지 프레임을 통해 Computer 에이전트에 전송하는 일을 맡는다. 동시에 Computer 에이전트의 메시지("사용자의 신분증 번호가 필요함", "페이지 로딩 오류" 등)를 받아, 이에 근거해 적절한 말투로 사용자에게 질문한다.
>
> **Computer 에이전트**: 브라우저 조작 프레임워크(Anthropic Computer Use, browser-use 등) 기반. 웹페이지 구조를 이해하고 양식 필드를 식별하며, 받은 정보에 따라 작성을 실행하고, 문제가 생기면 Phone 에이전트에게 도움을 요청한다.
>
> **통신 메커니즘**에는 두 가지 방안이 있다:
> - **단순 방안**: 도구 호출 기반 점대점 통신, 예를 들면 `send_message_to_computer_agent(message)` / `send_message_to_phone_agent(message)`
> - **완성된 방안**: 메시지 버스 + Manager 에이전트, 발신자·수신자·유형·내용을 포함한 통일된 메시지 형식
>
> **병렬 협업 메커니즘**(본 장의 두 "전화 + 컴퓨터" 실험이 공유): 두 에이전트는 독립된 스레드나 프로세스에서 실행되며, 각자 독립적인 ReAct 루프를 유지한다. Phone 에이전트의 루프: 음성 수신 -> ASR 전사 -> LLM 이해 및 응답 생성 -> TTS 합성 -> 재생 -> Computer 에이전트의 메시지 확인. Computer 에이전트의 루프: 스크린샷 -> Vision LLM으로 페이지 이해 -> 조작 계획 -> 실행(클릭, 입력 등) -> Phone 에이전트의 메시지 확인. 핵심은 둘이 진정으로 병렬로 작동해야 한다는 것이다—Computer 에이전트가 요소를 찾고 텍스트를 입력하는 동안, Phone 에이전트는 계속 온라인 상태로 사용자와 대화해야 한다("네, 성함을 입력해드리고 있습니다… 신분증 번호가 어떻게 되시나요?"). 이를 위해 각 에이전트의 입력에는 상대방으로부터 온 표시 필드가 함께 실린다. 예컨대 Phone 에이전트의 컨텍스트에는 `[FROM_COMPUTER_AGENT] '다음 단계' 버튼을 찾을 수 없음, 사용자 확인이 필요할 수 있음`이 나타나고, Computer 에이전트에는 `[FROM_PHONE_AGENT] 사용자가 성함은 '장싼', 신분증 번호는 123456이라고 함`이 나타난다.
>
> **실험 요구사항**:
> 1. ASR/TTS API와 브라우저 조작 프레임워크를 기반으로 이중 에이전트 아키텍처를 구현하라
> 2. 효율적인 양방향 통신 메커니즘을 구현하라
> 3. 정보 수집과 양식 작성이 동시에 진행되도록, 진정한 병렬 작동을 보장하라
> 4. 예외 상황을 처리하라
>
> **실험 10-5 ★★★: 자율적으로 오케스트레이션하는 전화·컴퓨터 에이전트**
>
> 실험 10-4의 이중 에이전트 협업 아키텍처는 사전에 설계된 것이었다. 본 실험은 한 걸음 더 나아가 **에이전트의 자율적 오케스트레이션 능력**을 탐구한다—인간이 미리 협업 흐름을 계획하는 것이 아니라, 에이전트 스스로 언제 새로운 협업 에이전트를 기동해야 할지 판단한다.
>
> **시나리오**: 사용자가 "이 사이트에서 회원가입을 완료해줘"라고 요청하며 URL만 주고 어떤 정보가 필요한지는 말하지 않는다. Manager 에이전트가 Computer Use 도구로 사이트에 접속해 가입 페이지를 로드한다.
>
> 조작 과정에서 Computer Use 에이전트는 가입 양식이 매우 복잡하며, 다량의 필수 필드—개인 기본 정보(성명, 성별, 생년월일), 연락처(휴대폰 번호, 이메일, 주소), 신원 확인 정보(증서 유형, 증서 번호), 선호 설정 등—를 포함하고 있음을 발견한다. 에이전트가 컨텍스트를 확인해보니 이런 정보가 손에 없다—사용자는 "가입해줘"라고만 했지 구체적인 데이터를 전혀 제공하지 않았다.
>
> 전통적인 에이전트라면 이런 상황에서 사용자에게 문자 메시지를 보내 직접 타이핑하도록 할 것이다—비효율적이면서(대량 정보를 손으로 입력해야 함) 오류에도 취약하다(형식 문제, 정보 누락). 더 똑똑한 에이전트라면 이렇게 인식해야 한다: **이것은 전화 상호작용을 통해 정보를 수집하기에 적합한 시나리오**다—전화 대화는 문자 채팅보다 훨씬 효율적이고, 하나씩 물어 확인할 수 있으며, 사용자의 모호한 표현도 처리할 수 있다.
>
> 핵심 혁신은 이 결정이 미리 프로그래밍된 것이 아니라 **에이전트가 자율적으로 내린 것**이라는 데 있다. Computer Use 에이전트의 프롬프트에는 이렇게 적혀 있다: "사용자로부터 대량의 구조화된 정보를 수집해야 하고, 대화를 통해 단계적으로 진행할 수 있을 때는 Phone 에이전트를 보조 도구로 호출하는 것을 고려하라." 도구 집합에는 `initiate_phone_call_agent(purpose, required_info)`가 포함되어 있다.
>
> 호출되면 시스템은 Phone 에이전트를 생성하고 명확한 작업 컨텍스트를 부여한다: 양식 작성을 돕기 위해 기동되었다는 것, 어떤 정보를 수집해야 하는지, 각 필드의 형식 요구사항.
>
> 두 에이전트는 곧바로 실시간 협업 모드에 들어가며, 실험 10-4의 비동기 병렬 메커니즘을 그대로 따른다. Phone 에이전트가 사용자에게 전화를 걸어 하나씩 묻는다: "안녕하세요, 가입 양식 작성을 도와드리고 있습니다. 먼저 성함이 어떻게 되시나요?" 사용자가 답하면 즉시 `{"type": "info_collected", "field": "성명", "value": "장싼"}`을 Computer 에이전트에 보내고, 후자는 곧바로 웹페이지에서 "성명" 필드를 찾아 작성한다. 동시에 Phone 에이전트는 컴퓨터 조작이 끝나기를 기다리지 않고 바로 다음 질문으로 넘어간다. 이런 **하나 물으면 하나 채우는**, 대화 흐름이 조작 지연에 막히지 않는 패턴이 본 실험의 핵심 요구사항이다. 모든 정보 수집이 끝나면 Phone 에이전트가 `{"type": "task_completed"}`를 보내고, Computer 에이전트가 양식을 제출한다.
>
> **실험 요구사항**:
> 1. Phone 에이전트를 자율적으로 기동 결정할 수 있는 Computer Use 에이전트를 구현하라
> 2. 실시간 양방향 통신과 진정한 병렬 작동을 구현하라
> 3. 예외를 처리하라(정보 형식이 올바르지 않을 때 피드백해 다시 묻도록)
> 4. 협업 과정의 메시지 시퀀스와 에이전트 결정 지점을 기록하라
>
>

> **실험 10-6 ★★★: 여러 웹사이트에서 동시에 정보를 수집하는 에이전트**
>
> **전제 조건**: 먼저 제4장의 이벤트 기반과 인터럽트 메커니즘을 이해할 것을 권장한다.
>
> 본 실험은 정보 수집 시나리오에서 멀티 에이전트 병렬 실행의 적용을 탐구한다. 실험 10-4와 실험 10-5가 두 이질적 에이전트의 협업에 초점을 맞춘 것과 달리, 본 실험은 **다수의 동질적 에이전트의 병렬 검색**과, 중앙 조율을 통해 효율적인 작업 완수와 자원 최적화를 실현하는 방법에 초점을 맞춘다.
>
> **문제**: 어느 대학의 여러 단과대 사이트가 주어졌을 때, 각 단과대의 교원 명부 페이지에서 지정된 교원(예: "장웨이")을 찾아, 발견되면 소속 단과대, 직위, 연구 방향 등의 정보를 반환하라.
>
> **핵심 과제**:
>
> **1. 병렬 기동**: Manager 에이전트가 작업 요구에 따라 10개의 Computer Use 에이전트 인스턴스를 동적으로 생성하며, 각 인스턴스는 하나의 단과대 사이트에 대응한다. 각 인스턴스는 독립된 프로세스나 스레드여야 하고, 독립된 브라우저 세션을 지녀야 하며, 동시에 서로 막지 않고 실행할 수 있어야 한다. 기동 시 전달하는 것: 대상 사이트 URL, 검색할 교원 이름, 작업 식별자(메시지 라우팅용).
>
> **2. 실시간 모니터링**: 각 에이전트는 실행 중 정기적으로 상태 업데이트("사이트 로딩 중", "교원 명부 파싱 중", "대상을 찾지 못함, 작업 완료", "일치 발견, 상세 정보는 다음과 같음")를 보낸다. Manager 에이전트는 메시지 버스를 통해 이런 업데이트를 받아 작업 상태표를 유지하며, 어떤 에이전트가 아직 실행 중이고 어떤 에이전트가 완료되었으며 어떤 에이전트가 오류를 겪었는지 실시간으로 파악한다.
>
> **3. 계단식 종료**: 컴퓨터 공학 단과대를 맡은 에이전트가 대상 교원을 찾았다고 가정하면, `{"type": "target_found", "agent_id": "agent_3", "data": {...}}`를 보낸다. Manager 에이전트는 이를 받으면 곧바로 여전히 실행 중인 다른 모든 에이전트에게 `{"type": "terminate", "reason": "target_found_by_agent_3"}`를 보내고, 종료 메시지를 받은 각 에이전트는 우아하게 멈추고 확인을 보낸다. Manager 에이전트는 모든 확인을 기다린(또는 타임아웃) 뒤 결과를 취합한다. 요구사항: 에이전트가 언제든 종료 신호에 응답할 수 있어야 하고(제4장의 인터럽트 메커니즘과 유사), 종료는 반드시 우아해야 한다—매달린 프로세스나 닫히지 않은 자원을 남기지 않아야 한다. 동시에 경쟁 조건(Race Condition)도 처리해야 한다.
>
> **개념 보충: 경쟁 조건이란 무엇인가?** 에이전트 A와 에이전트 B가 거의 같은 밀리초에 각각 대상 교원을 찾아 동시에 Manager 에이전트에게 "찾았습니다!"라고 보고했다고 하자. Manager 에이전트가 이를 제대로 처리하지 못하면—예컨대 A의 보고를 받고 결과 취합을 시작했는데 곧바로 B의 보고를 받아 두 번째 취합이 촉발되면—중복된 결과나 서로 모순되는 상태가 생길 수 있다. 해결 방법은 보통 "잠금" 메커니즘을 쓰는 것이다: 첫 번째 보고가 도착하면 즉시 상태를 잠그고, 이후의 보고는 중복으로 인식해 무시한다.
>
> **4. 실패 처리**: 실제 실행에서는 여러 예외가 생길 수 있다: 어느 단과대 사이트에 접속할 수 없거나(네트워크 오류, 서버 다운), 어느 사이트의 구조가 예상과 달라 에이전트가 제대로 파싱하지 못하거나, 모든 에이전트가 검색을 마쳤는데도 대상을 찾지 못하는 경우. Manager 에이전트의 처리 전략: 각 에이전트에 타임아웃(예: 2분)을 설정해 초과 시 실패로 간주하고, 오류를 격리해 다른 에이전트의 계속 실행에 영향을 주지 않으며, 전체 완료 후 취합한다—하나라도 에이전트가 성공하면 정보를 반환하고, 전부 실패하면 사용자에게 "대상 교원을 찾지 못함" 및 각 실패 원인의 통계를 보고한다.
>
> **실험 요구사항**:
> 1. 여러 병렬 에이전트를 동적으로 기동할 수 있는 Manager 에이전트를 구현하라
> 2. browser-use 등 오픈소스 프로젝트를 기반으로 Computer Use 에이전트를 구현하라
> 3. Manager 에이전트와 여러 하위 에이전트 간 양방향 통신을 지원하는 메시지 버스를 구현하라
> 4. 성공 후 계단식 종료 메커니즘을 구현해, 목표 발견 후 다른 모든 에이전트가 신속히 멈추도록 하라
> 5. 각종 예외 상황(사이트 접속 실패, 파싱 오류, 전부 못 찾음)을 처리하라
> 6. 병렬 실행과 순차 실행의 시간 차이를 기록·비교해, 병렬화가 가져오는 성능 향상을 검증하라
>

### 탈중앙화 패턴: 대등한 인계


![그림10-10 Handoff 체인 패턴](images/fig10-10.svg)


관리자 패턴은 명확한 통제 구조와 전역적 시야를 제공하지만, 중앙화된 특성 탓에 고유한 한계도 지닌다: Manager가 시스템의 병목이자 단일 장애점이 되며, 모든 조율 결정이 Manager의 판단에 의존하고, Manager는 또 모든 하위 작업을 충분히 이해해야 한다. 작업 복잡도가 커지고 에이전트 수가 늘어나면 확장성에 도전이 생긴다.

탈중앙화 패턴은 또 다른 아키텍처적 발상을 제공한다: **단일 중앙 통제자가 없고, 에이전트들이 대등한 방식으로 협업한다.** 각 에이전트는 자신의 전문적 판단에 따라, 언제 다른 에이전트에게 소통을 개시할지 스스로 결정한다—작업을 인계할 수도 있고("내 몫은 끝났으니 넘길게"), 피드백을 요청할 수도 있으며("이 방안이 기술적으로 실현 가능해?"), 문제를 보고할 수도 있다("네가 준 요구사항에 모순이 있어, 다시 논의해야 해").

아래 세 사례는 의도적으로 "가짜에서 진짜로" 나아가는 점진적 순서로 배열되었다: MetaGPT의 제어 흐름은 사실 고정된 파이프라인(가짜 탈중앙화, 통신 메커니즘상에서만 디커플링됨)이고, AutoGen group chat은 공유 대화 기록에 중앙화된 스케줄링을 결합한 혼합 형태이며, OpenAI Swarm에 이르러서야 비로소 제어 흐름 상에서 진정으로 대등한 탈중앙화를 이룬다.

**컨텍스트를 공유하지 않는 상태에서 인계는 무엇을 전달하는가?** 그림 10-10의 Handoff 체인 패턴은 실험 10-2의 `transfer_to_agent`와 직접적인 대조를 이룬다: 후자는 컨텍스트를 공유하는 상태에서 인계하므로 새 역할이 자동으로 완전한 이력을 물려받아 어떤 설계도 필요 없다. 전자는 컨텍스트를 공유하지 않는 상태에서 인계하므로, 인계하는 쪽이 무엇을 전달할지 명시적으로 결정해야 한다. 실무에서 효과적인 "인계 패키지"는 대개 세 부분을 포함한다: **작업 설명**(수신자가 무엇을 해야 하는지, 검수 기준이 무엇인지), **확인된 사실과 제약**(사용자 선호, 업무 규칙, 이전 단계에서 확정된 결정), 그리고 **구조화된 산출물의 참조**(파일 내용이 아닌 파일 경로, 수신자가 필요할 때 읽음). 의도적으로 전달하지 않는 것은 전체 궤적이다—인계하는 쪽의 시행착오, 중간 사고, 실패한 시도는 수신자에게는 대부분 잡음이다. 이것이 바로 두 인계 방식의 본질적 차이다: 컨텍스트 공유의 인계는 완전한 이력을 보존해 정보 무손실이지만 컨텍스트가 계속 팽창하고, 컨텍스트 비공유의 인계는 정제된 인계 패키지를 전달해 정보에 손실은 있지만 각 에이전트가 깨끗하고 집중된 컨텍스트에서 작업한다. 각 에이전트는 다른 에이전트의 "사고 과정"을 이해할 필요 없이, 인계 패키지와 산출물의 형식·의미만 이해하면 된다—이런 인터페이스 기반 협업은 소프트웨어 공학의 계약 기반 설계(contract-based design) 원칙을 차용한 것이다.

**MetaGPT: SOP 기반의 소프트웨어 회사 시뮬레이션(파이프라인에서 디커플링된 통신으로의 과도기적 사례).**


![그림10-11 MetaGPT 멀티 에이전트 협업 네트워크](images/fig10-11.svg)


MetaGPT의 핵심 통찰은 이렇다: 인간 소프트웨어 회사가 축적해온 **표준 작업 절차**(SOP, Standard Operating Procedure) 자체가 이미 반복적으로 검증된 협업 프로토콜이라는 것—SOP를 멀티 에이전트 시스템에 코드로 옮겨, 각 역할이 조립 라인의 전문 공정처럼 표준화된 산출물을 내놓게 하면, 산출물이 자연스레 역할 간 통신 인터페이스를 이룬다.

MetaGPT에서 각 역할은 고정된 순서(Product Manager → Architect → Project Manager → Engineer → QA)로 작업하며, 각 역할은 구조화된 산출물을 출력한다:

- **Product Manager 에이전트**: 요구사항 설명을 받아 구조화된 PRD(제품 요구사항 문서, 기능 목록·사용자 스토리·검수 기준·우선순위 포함)를 생성한다
- **Architect 에이전트**: PRD를 읽고 아키텍처 결정(기술 스택 선택, 모듈 분할, 인터페이스 정의, 데이터 모델 설계)을 내려 설계 문서를 출력한다
- **Project Manager 에이전트**: 아키텍처 설계를 읽고 시스템을 구체적인 작업 목록과 파일 단위 분업으로 분해하며, 각 모듈의 의존 순서를 정리한 뒤 작업을 엔지니어에게 배분한다
- **Engineer 에이전트들**: 설계 문서를 읽고 맡은 모듈을 구현해 코드를 산출한다. 여러 인스턴스가 병렬로 작업할 수 있다
- **QA Engineer 에이전트**: 코드와 PRD를 읽고 테스트 케이스를 생성·실행하며 버그를 기록해 테스트 보고서를 출력한다

MetaGPT가 탈중앙화 통신에 진정으로 기여한 부분은 그 정보 전달 메커니즘에 있다: **공유 메시지 풀 + 역할별 구독**. 각 역할은 구조화된 메시지를 모든 역할이 볼 수 있는 메시지 풀에 발행하고, 다른 역할들은 자신의 구독 설정에 따라 자기 직무와 관련된 메시지만 취한다—점대점으로 일대일 전달하는 것이 아니다. 발행자는 누가 자신의 출력을 소비할지 알 필요가 없고, 새 역할을 추가하려면 어떤 메시지 유형을 구독할지 선언하기만 하면 되며 기존 역할을 건드릴 필요가 없다. 이는 진정한 디커플링을 가져온다—예컨대 Product Manager를 더 강력한 모델로 교체해도, 발행하는 PRD가 규격에 맞기만 하면 다른 모든 에이전트는 수정할 필요가 없다.

MetaGPT의 반복 개선은 주로 엔지니어 단계에서 일어나며, 메커니즘은 **실행 가능한 피드백**(executable feedback)이다: Engineer가 자신이 쓴 코드와 테스트를 실행하고, 오류와 실패 결과에 따라 디버깅 루프에 들어가 통과할 때까지 반복한다—다른 에이전트의 의견이 아닌 결정론적 실행 결과로 수정을 이끈다.

솔직히 말해야 할 것은, MetaGPT는 **제어 흐름** 상에서는 탈중앙화가 아니라는 점이다—역할 순서가 SOP에 의해 미리 고정되어 있어, 전체적으로 하나의 파이프라인(제1장의 언어로는 워크플로)에 더 가깝다. 본 절에서 이를 다루는 이유는, 메시지 풀 더하기 구독이라는 통신 메커니즘이 탈중앙화 시스템의 가장 핵심적인 설계 요소—디커플링—를 보여주기 때문이다. "QA가 직접 Product Manager를 찾아가 요구사항을 확인한다", "Engineer가 Architect를 찾아 대안을 논의한다"와 같은 다방향 동적 피드백은 이 아키텍처를 자연스럽게 확장한 가상의 시나리오일 뿐, 원본 MetaGPT는 구현하지 않았다.

**AutoGen group chat: 공유 대화 기록 + 중앙화된 스케줄링.** AutoGen의 group chat은 여러 에이전트가 하나의 대화 세션에 참여하게 한다: 매 라운드마다 "발언자 선택기"가 다음에 발언할 에이전트를 결정한다—선택기는 단순한 순환 규칙일 수도 있고, 현재 대화 내용을 바탕으로 누가 발언에 가장 적합한지 판단하는 LLM일 수도 있다. 어떤 에이전트의 발언도 모든 참여자에게 보인다. 솔직히 말해야 할 것은, 이것이 제어 흐름 의미에서 완전히 탈중앙화된 시스템은 아니라는 점이다: 발언자 선택은 중앙화된 GroupChatManager가 일괄 결정하며, "누구 차례로 발언할지" 자체가 하나의 제어 흐름 결정이다. 따라서 더 정확한 위치는 **"공유 대화 기록 + 중앙화된 스케줄링"의 혼합 형태**다—모든 에이전트가 동일한 공용 대화 기록을 보지만, 각자 독립된 시스템 프롬프트와 도구 집합을 유지하며, 스케줄링 권한은 선택기에 집중되어 있다. 이 모드는 다관점 토론이 필요하고 발언 순서를 미리 고정하기 어려운 작업(방안 심사, 학제간 분석 등)에 적합하며, 대가는 대화가 발산할 수 있어 종료 조건을 정교하게 설계해야 한다는 것이다. 본 장의 차원 구분에 따르면, 여기서는 그 스케줄링 메커니즘(중앙화된 선택기)에 따라 본 절에 포함시켰지만, 컨텍스트 차원에서는 실제로 공유와 비공유의 중간, 즉 혼합 형태에 속한다—이는 토폴로지와 컨텍스트 공유가 개념적으로 독립적이며 어긋나게 조합될 수 있는 두 차원이라는 점을 다시 한번 보여준다.

**OpenAI Swarm과 Agents SDK: handoff 네트워크.** 이에 비해, 제어 흐름 상에서 진정으로 대등한 탈중앙화를 이룬 대표 사례는 OpenAI의 Swarm(및 그 후속인 Agents SDK)이다: 이는 탈중앙화를 가장 단순한 형태로 만들었다—각 에이전트는 여러 handoff(인계) 옵션을 갖추고, 언제든 네트워크 내 다른 어떤 에이전트에게도 통제권을 인계할 수 있다. 고객 상담 분류 에이전트가 문제가 환불과 관련된다고 판단하면 환불 에이전트에게 인계하고, 환불 에이전트가 처리 중에 기술적 결함임을 발견하면 다시 기술 지원 에이전트에게 인계할 수 있다. 시스템에는 중앙 스케줄러가 없고, 통제권은 계주 바통처럼 대등한 에이전트들 사이를 흘러 다니며, 라우팅 결정은 완전히 각 에이전트 자신의 판단에 분산되어 있다—이것이야말로 깔끔한 "대등 인계"이며, 그림 10-10에 나타낸 체인형 인계 패턴의 엔지니어링 구현이기도 하다.

### 조직 간 협업: A2A 프로토콜

이상의 시스템들은 모두 모든 에이전트가 같은 팀에 의해 개발되고 같은 시스템 내에서 실행된다고 가정한다. 이때는 파라미터 전달, 공유 파일, 메시지 버스라는 세 가지 통신 메커니즘으로 충분하다. 하지만 협업이 조직 경계를 넘어설 때—당신의 에이전트가 다른 회사의 에이전트를 호출해야 할 때—는 표준화된 상호운용 프로토콜이 필요해진다. 2025년 Google이 발표한 **A2A**(Agent2Agent) 프로토콜이 바로 이를 위해 설계되었다(이후 Linux 재단에 기증되어 관리되고 있다). 핵심 요소는 세 가지다:

- **Agent Card**: 에이전트의 능력을 기술하는 메타데이터 문서(정해진 공개 주소에 게시)로, 이 에이전트가 무엇을 할 수 있는지, 어떤 입출력 양식을 지원하는지, 어떻게 인증하는지를 선언한다—에이전트의 "명함"에 해당하며, 조직 간 능력 발견 문제를 해결한다.
- **작업 생명주기 관리**: A2A는 협업 단위를 작업(Task)으로 모델링하며, 명확한 상태 기계(제출됨, 진행 중, 입력 필요, 완료, 실패)를 지니고, 장시간 실행되는 작업과 스트리밍 진행 업데이트를 원생 지원한다.
- **불투명 협업**: 에이전트들은 작업과 산출물(Artifact)만 교환할 뿐, 내부의 프롬프트, 사고 과정, 도구 구현은 드러내지 않는다—이는 본 장의 "컨텍스트 비공유" 원칙과 일치하며, 조직 간 협업에서 필요한 보안 속성이기도 하다.

A2A의 위치는 제4장의 MCP와 대조해 이해할 수 있다: MCP가 해결하는 것은 에이전트와 도구 간의 상호운용이고, A2A가 해결하는 것은 에이전트와 에이전트 간의 상호운용이다. 이는 본 장에서 소개한 세 가지 통신 메커니즘을 대체하는 것이 아니라, 그 위에서 신뢰 경계를 넘는 표준화 계층으로 존재한다—같은 팀 내부의 멀티 에이전트 시스템은 메시지 버스를 직접 쓰면 되고, 협업 상대가 서로 신뢰하지 않고 구현이 서로 보이지 않을 때에만 A2A와 같은 공개 프로토콜이 필요하다.

## 멀티 에이전트 협업의 실패 모드

멀티 에이전트 시스템은 협업 능력을 도입하는 동시에, 단일 에이전트에는 없는 새로운 유형의 실패 모드도 함께 들여온다. 2025년의 논문 《Why Do Multi-Agent LLM Systems Fail?》(MAST 실패 모드 분류법을 제시)은 이에 대해 체계적인 연구를 수행했다: 연구자들은 MetaGPT, ChatDev, AG2, Magentic-One 등 7개 주류 멀티 에이전트 프레임워크에서 실행 궤적을 수집하고, 인간 평가자가 약 150개의 궤적을 하나하나 분석했다(평가 일치도가 매우 높아 Cohen's kappa = 0.88로, 서로 다른 평가자의 실패 모드 판단이 고도로 일치함을 보여준다). 최종적으로 **14가지 독특한 실패 모드**를 세 가지 큰 범주로 정리했다:

- **시스템 설계 결함**: 에이전트 간 인터페이스 정의가 불명확하거나, 역할 직무가 중복되거나, 도구 설정이 잘못되는 등 아키텍처 차원의 문제
- **에이전트 간 정렬 실패**: 여러 에이전트가 작업 목표에 대한 이해가 서로 다르거나, 전달된 정보가 하류 에이전트에 의해 오해되거나, 여러 에이전트의 조작이 논리적으로 서로 모순되는 것
- **작업 검증 부재**: 작업이 정말로 완료되었는지 확인할 효과적인 메커니즘이 시스템에 없는 것—에이전트가 "완료"라고 선언하지만 실제 결과는 요구에 부합하지 않는 경우

간단한 수정 조치를 도입해도 개선 폭은 매우 제한적이었다(예컨대 ChatDev 프레임워크는 겨우 15.6% 향상되었다). 연구자들은 그래서 이것들이 단순한 엔지니어링 버그가 아니라 현재 멀티 에이전트 아키텍처의 **근본적인 설계 결함**이라고 본다: 어느 한 부분만 땜질해서는 문제를 해결할 수 없으며, 시스템 설계 차원에서 다시 생각해야 한다.

아래에서는 실무에서 특히 흔하고 파괴력이 가장 큰 두 가지 실패 모드를 중점적으로 다룬다: (1) 공유 파일 시스템의 동시성 충돌, (2) 오류의 계단식 증폭. 짚어둘 점은, 이 두 실패 모드는 엔지니어링 관점(파일 시스템 동시성, 오류 정보의 에이전트 간 전파)에 치우쳐 있으며, 대화형 협업 실패에 치중한 MAST의 분류를 보완하는 것이지 그 14가지 모드를 그대로 반복하는 것이 아니라는 것이다.

### 실패 모드 1: 공유 파일 시스템의 동시성 충돌

공유 파일 시스템은 멀티 에이전트 협업의 핵심 기반 인프라이지만, 여러 에이전트가 동시에 조작할 때 동시성 충돌은 피할 수 없는 엔지니어링 과제가 된다. 이런 충돌은 두 가지로 나눌 수 있다.

**단순 충돌(파일 수준 쓰기 충돌)**: 두 에이전트가 동시에 같은 파일을 수정하면, 나중에 쓴 쪽이 먼저 쓴 수정 내용을 덮어써버린다. 이는 데이터베이스 분야의 고전적인 **잃어버린 갱신**(lost update) 문제이며—Git의 병합 충돌 감지 메커니즘이 바로 이런 덮어쓰기를 막기 위해 설계된 것이다.

**의미적 충돌(논리 수준 일관성 충돌)**: 파일 수준에서는 어떤 충돌도 보이지 않지만, 여러 에이전트의 조작이 논리적으로 서로 모순되는 경우—이런 충돌은 더 은밀하고 더 위험하다. 예를 들어보자: 에이전트 A는 책 전체의 그림 번호를 재배열하는 일을 맡았고, 에이전트 B는 동시에 어느 장의 내용을 수정하며 원본 번호의 그림을 참조하고 있다. 둘은 서로 다른 파일을 조작하므로 파일 수준에서는 전혀 충돌이 없다. 하지만 결과적으로 B가 참조한 그림 번호는 A가 재편성을 마친 뒤 모두 무효화되어, 독자는 잘못된 그림 참조를 보게 된다.

**해결 방안: 낙관적 잠금(Optimistic Locking) 메커니즘.** 이는 데이터베이스 분야에서 흔히 쓰이는 동시성 제어 전략이다. 이해를 돕기 위해 일상적인 시나리오를 떠올려보자: 당신과 동료가 동시에 같은 온라인 문서를 열었다. "비관적 잠금" 방식은 문서를 여는 순간 잠가버려, 동료가 편집하려 하면 "파일이 잠겨 있음"을 보게 된다—안전하지만 비효율적이다. 당신이 그저 보기만 할 뿐 수정할 생각이 전혀 없었을 수도 있기 때문이다. "낙관적 잠금" 방식은 더 영리하다: 누구나 자유롭게 열고 편집할 수 있지만, 저장 시점에 시스템이 확인한다—"당신이 문서를 연 뒤, 다른 사람이 이미 수정하지 않았는가?" 만약 그렇다면 "파일이 이미 수정되었습니다. 새로고침 후 다시 시도하세요"라고 안내한다.

구체적인 구현은 이렇다: 각 파일이 버전 번호(또는 마지막 수정 타임스탬프)를 유지한다. 에이전트는 파일을 읽을 때 현재 버전 번호를 기록하고, 쓸 때 버전 번호가 여전히 읽을 당시와 일치하는지 확인한다. 그 사이 파일이 다른 에이전트에 의해 이미 수정되었다면 쓰기가 실패하고, 에이전트는 어쩔 수 없이 최신 버전을 다시 읽어 그것을 바탕으로 조작을 다시 수행해야 한다. 이 메커니즘의 대가는 이따금 재시도가 필요하다는 것이지만, 그 대신 데이터 일관성을 보장받는다—에이전트는 결코 낡은 파일 상태를 바탕으로 결정을 내리지 않는다.

주의할 점은, 낙관적 잠금은 **같은 파일**의 쓰기 충돌만 막을 수 있다는 것이다. 앞서 말한 **파일 간 의미적 충돌**(그림 번호가 여러 곳에서 참조되는 경우 등)에는 더 상위 수준의 의미적 검증 메커니즘이 필요하다—예컨대 작업 오케스트레이션 단계에서 의존관계가 있는 파일들이 병렬로 수정되지 않도록 하거나, 쓰기 이후 전역 일관성 검사를 실행하는 것이다.

예를 들어: 에이전트 A가 t=0 시점에 `config.json`(버전=3)을 읽고, 에이전트 B가 t=1 시점에 같은 파일을 수정한다(버전이 4가 됨). 에이전트 A가 t=2 시점에 쓰려 하면 버전이 더 이상 3이 아님을 발견해 쓰기가 거부된다. 에이전트 A는 이어서 버전=4의 내용을 다시 읽고, 최신 버전을 바탕으로 수정을 다시 생성해 재차 쓰기를 시도한다.

특기할 점은, 여러 Coding 에이전트가 같은 코드베이스를 동시에 수정하는 가장 흔한 시나리오에서는, 업계의 더 주류적인 방식이 단일 작업 사본에 잠금을 거는 것이 아니라 **작업 사본 격리**라는 것이다: 각 에이전트에 독립된 Git 브랜치나 worktree를 배정해, 각자 자신의 사본에서 병렬로 수정하며 서로 간섭하지 않게 하고, 충돌은 최종 병합 지점으로 집중적으로 미루어 전문 병합 단계나 인간이 해결하도록 한다. 이는 제2장의 "압축보다 격리" 발상과 동일한 뿌리를 가진다—제2장이 하위 에이전트 컨텍스트 격리를 논할 때 지적했듯, 여러 당사자가 같은 상태를 공유한 뒤 충돌을 해소할 방법을 찾기보다는, 처음부터 격리해 조율 비용을 명확한 경계 안에서 처리하는 편이 낫다.

### 실패 모드 2: 오류의 계단식 증폭

동시성 충돌은 파일 수준의 엔지니어링 문제이지만, 오류의 계단식 증폭은 의미 수준에서 더 은밀한 위험이다. 여러 에이전트가 빈번하게 상호작용할 때, 한 에이전트의 오류가 후속 에이전트에 의해 층층이 강화될 수 있다—마치 "전화 놀이"에서 정보가 전달될수록 점점 왜곡되는 것처럼.

구체적인 시나리오로 설명해보자. 어느 번역 시스템이 관리자 패턴(실험 10-3의 아키텍처)을 채택했고, Manager가 기술 서적 한 권을 장별로 나누어 여러 Translation 에이전트에게 배분했다고 하자:

```
용어 에이전트: "reasoning"을 "추론"으로 번역했지만, "추론"은 중국어에서 inference를 가리키는 데 더 흔히 쓰여 모호함이 존재함
        ↓ glossary.json에 기록
Translation 에이전트 A: 제2장을 번역, 용어표에서 읽어 "reasoning tokens"를 "추론 토큰"으로 번역
Translation 에이전트 B: 제7장을 번역, "inference latency" 역시 "추론 지연"으로 번역
        ↓ 각 장 번역문 기록
교정 에이전트: 전체 책이 "추론"을 일관되게 쓰고 있음을 보고, 용어가 일치하고 번역이 정확하다고 판단 ✗
```

문제가 어디에 있을까? "reasoning"(모델의 사고 과정)과 "inference"(모델의 순전파/배포 실행)는 서로 다른 두 개념이지만, 용어 에이전트가 처음에 reasoning을 "추론"으로 번역했기 때문에, 후속 에이전트들은 inference를 만났을 때도 자연스레 같은 단어를 골랐다—서로 다른 두 개념이 같은 번역어로 합쳐져, 독자는 이를 구별할 수 없게 되었다. 올바른 방식은 reasoning을 "사고"로, inference를 "추론"으로 번역하는 것이다. 하지만 교정 에이전트는 전체 책이 "통일되게" "추론"을 쓰고 있는 것을 보고 오히려 번역 품질이 높다고 여겼다.

하나의 용어 오류가 세 에이전트를 거쳐 전파되면서 "일관성"을 근거로 오히려 더 높은 신뢰를 얻었다. 이것이 바로 본서가 reasoning=사고, inference=추론이라는 번역 관례(서문에서 설명함)를 채택한 이유다: 서로 다른 한국어 단어로 모호함을 없애는 것이다. 강조할 점은, 여기서의 "오류"가 반드시 환각인 것은 아니라는 것이다—위 사례의 근원은 사실 한 번의 용어 결정 실수였지만, 그럼에도 "일관성"에 의해 층층이 증폭되었다. 하지만 근원이 정말로 환각이었다면(예컨대 실험 10-3에서 Translation 에이전트가 주의 분산으로 실제로는 존재하지 않는 용어 규칙을 "기억해낸" 경우), 증폭 메커니즘은 완전히 동일하며 결과는 더 심각해질 뿐이다. 이 오류 증폭 체인은 관리자 패턴에서 특히 위험하다—Manager가 어느 하위 에이전트의 잘못된 요약을 바탕으로 스케줄링 결정을 내렸다면, 이후 모든 하위 에이전트의 작업이 잘못된 전제 위에 세워질 수 있다.

**교차 검증**은 이 체인을 끊는 핵심 수단이다. 핵심은 더 많은 에이전트를 같은 사고 체인에 참여시키는 것이 아니라, 어떤 에이전트가 **독립적인 시각**으로 결론을 다시 살펴보게 하는 것이다: 이전 에이전트의 사고 과정은 보지 않고, 원본 증거와 최종 결론이 일치하는지만 본다. 이는 제5장에서 다룬 제안자-검토자 메커니즘이 멀티 에이전트 시나리오로 확장된 것이다: Reviewer의 가치는 코드 오류나 형식 문제를 발견하는 데만 있는 것이 아니라, 독립적인 판단자로서 전체 사고 체인에서 집단적으로 간과된 모순을 식별할 수 있다는 데 있다. 고위험 결정에는 외부 검증 수단도 도입할 수 있다—단위 테스트, 컴파일러, 데이터베이스 조회 등 결정론적 도구가 제공하는 피드백은 환각의 영향을 받지 않아 가장 신뢰할 수 있는 "체인 차단기"다.

조기 종료에는 대칭되는 반대 현상이 있다: **순환 폭주**. 앞서 "대등 협업" 절에서 다룬 것은 "돌아야 하는데 돌지 않는" 문제—에이전트가 일을 반쯤 하다 멈추는 것—였다면, 여기서는 "순환이 멈추지 않고 돌아가면서 점점 나빠지는" 것을 경계해야 한다. 업계는 Loop 엔지니어링 실무에서 세 가지 전형적인 실패 모드를 정리했다. 하나는 **토큰 비용 폭주**로, 순환이 사람의 관리 없이 몇 시간이나 돌아가며 대량의 예산을 태우고, 아무도 요구하지 않은 코드 더미를 산출한다. 둘은 **이해 부채**(comprehension debt)로, 순환이 코드를 빠르게 전달할수록 엔지니어는 시스템의 실제 구현에 대한 이해가 점점 뒤처져, 결국 사람이 개입해야 할 때는 이미 자신의 시스템을 알아보지 못하는 지경에 이른다. 셋은 **인지적 항복**(cognitive surrender)으로, 설계자가 순환에 일을 맡기는 데 익숙해져 점차 독립적인 사고와 검토를 포기하고, 품질이 나선형으로 하락한다. 세 가지 모두의 해법은 오류 증폭 체인을 끊는 것과 같은 맥락이다: 명시적인 예산과 종료 조건, 실제 관측에 뿌리내린 검증기, 그리고 사람이 시종일관 "순환의 엔지니어"라는 역할을 유지하는 것이지 그저 "시작 버튼을 누르는 사람"에 머무르지 않는 것이다.

지금까지의 논의는 모두 엔지니어링 관점이었다—어떻게 한 무리의 에이전트가 협업해 작업을 완수하게 할 것인가. 이어서 관점을 전환한다: 대량의 에이전트가 장기간 공존하며 더는 단일 목표에 의해 움직이지 않을 때, 무엇이 나타날까? 이 절은 최전선 탐구 영역에 속하므로, 엔지니어링 독자는 선택적으로 읽어도 좋다.

## 에이전트 사회

앞의 세 절이 다룬 것은 모두 목표가 명확한 작업 협업—대등 협업이든 관리자 패턴이든 탈중앙화 패턴이든, 개발자가 미리 역할·인터페이스·제어 흐름을 정의했다. 이어서 더 개방적인 질문으로 시선을 돌린다: **에이전트의 수가 몇 개에서 수백·수천으로 늘어나고 상호작용이 충분히 자유로워지면, 어떤 행동이 나타날까?** 이 내용은 최전선 탐구와 학술 연구에 치우쳐 있으며, 앞선 엔지니어링 지침과는 성격이 다르다.

창발 행동(Emergent Behavior)이란 시스템 전체가 보이는, 개별 개체의 행동 규칙만으로는 직접 예측할 수 없는 집단 행동 패턴을 가리킨다. 자연계에서 가장 고전적인 예는 **개미 군집**이다: 개미 한 마리는 단순한 규칙(페로몬 냄새가 나면 따라가고, 먹이를 찾으면 페로몬을 남긴다)만 따르지만, 군집 전체는 둥지에서 먹이까지 가는 최단 경로를 찾아낸다—어떤 개미도 이 경로를 "설계"하지 않았다. 이는 대량 개체의 단순한 상호작용에서 자연스레 나온 것이다.

AI 에이전트의 수가 충분히 많아지고 상호작용이 충분히 자유로워지면, 비슷한 창발 행동이 나타나기 시작한다. 연구자들은 여러 환경에서 이미 관찰했다: 에이전트 시스템이 규모상 어떤 임계점을 넘어서면, 미리 설계할 수 없는 집단 행동이 생겨난다는 것—작게는 자발적으로 조직된 한 번의 모임에서, 크게는 수만 개의 에이전트에서만 나타나는 집단 문화와 경제적 게임까지(아래에서 절을 나누어 상술한다).

본 절의 사례는 세 가지 차원으로 이해할 수 있다:

- **사회적 창발**: 에이전트가 개방된 환경에서 자발적으로 사회적 관계와 문화 현상을 형성한다. 스탠퍼드 AI 타운은 25개의 에이전트가 어떻게 자체 조직적으로 사교 활동을 벌이는지 보여주었고, Moltbook은 그 규모를 150만까지 끌어올려 더 복잡한 집단 행동을 창발시켰다.
- **경제적 창발**: 에이전트가 시장 메커니즘을 통해 자원 배분과 작업 조율을 수행한다. Vending-Bench Arena는 여러 에이전트가 같은 시장에서 경쟁하며 경영하게 했고, Pinchwork와 RentAHuman은 에이전트 간(그리고 에이전트와 인간 간) 경제적 거래 시장을 구축했다.
- **전략적 게임**: 에이전트가 규칙 제약 아래 추론, 기만, 사회적 조작을 수행한다(여기와 뒤의 마피아 게임 부분에서 "추론"은 일상적인 연역의 의미로, 추리 게임 속 논리적 게임을 가리키며, 본서의 reasoning=사고라는 기술적 의미가 아니다). 마피아 게임 실험은 정보 비대칭 조건에서 에이전트의 전략적 창발을 시험한다.

### 스탠퍼드 AI 타운: 생성형 에이전트의 사회 시뮬레이션


![그림10-12 AI 타운 아키텍처](images/fig10-12.svg)


2023년, 스탠퍼드 대학과 Google 연구팀은 획기적인 논문 《Generative Agents: Interactive Simulacra of Human Behavior》를 발표해 "생성형 에이전트"라는 개념을 제시했다. 핵심 혁신은 더 이상 에이전트가 미리 정의된 작업을 완수하는 데 국한되지 않고, 인간에 가까운 기억·성찰·계획 능력을 부여해 개방된 사회 환경에서 자율적으로 생활하고 사교하며 성장할 수 있게 한 것이다.

Smallville은 《심즈》와 비슷한 2D 가상 마을로, 카페, 공원, 주택, 상점 등 공적·사적 공간이 있다. 25개의 에이전트가 서로 다른 역할(가게 주인, 예술가, 학생, 교수 등)을 맡았으며, 각각 고유한 배경 이야기, 성격 특성, 인간관계를 지닌다. 예컨대 John Lin은 약국을 운영하며 가족을 아끼고 지역사회에 관심이 많고, Isabella Rodriguez는 마을 카페 Hobbs Cafe를 운영하며 열정적이고 손님을 잘 대접하고, Klaus Mueller는 연구 논문을 쓰고 있는 대학생이다.

이 에이전트들의 지능은 세 가지 핵심 구성요소 위에 세워져 있다:

**기억 스트림**(Memory Stream): 전통적인 에이전트가 제한된 대화 이력만 유지하는 것과 달리, 생성형 에이전트는 관찰한 사건, 나눈 대화, 떠올린 생각을 담은 완전한 경험 기록 스트림을 유지한다. 각 기억에는 중요도, 최신성, 관련성 속성이 부여되어, 에이전트가 현재 상황과 가장 관련 있는 기억을 우선적으로 조회할 수 있다. 인간이 모든 일을 똑같이 기억하지 않는 것과 비슷하다—어제 점심에 뭘 먹었는지는 이미 잊었을 수 있지만, 지난주의 중요한 대화는 여전히 생생하게 기억한다.

**성찰 메커니즘**(Reflection): 에이전트는 정기적으로 일상 활동을 멈추고 최근 경험을 되돌아보며, 자신과 타인에 관한 추상적인 질문("Klaus Mueller는 무엇을 연구하고 있나?" "누가 나와 가장 친한 친구인가?")을 던진다. 이런 자기 질문을 통해 에이전트는 구체적인 사건 기억을 개괄적인 인식으로 승화시켜, 미래 결정의 근거로서 기억 스트림에 다시 저장한다. 성찰은 에이전트가 외부 세계를 이해하는 것을 도울 뿐 아니라 자기 인식도 촉진한다—에이전트는 자신의 역할, 관계, 목표를 "의식"하기 시작한다.

짚어둘 점은, 여기서의 성찰이 제8장 에이전트 자기 진화의 성찰과 다르다는 것이다: 제8장의 성찰은 **작업 종료 후**에 일어나며 목적은 장기 능력을 갱신하는 것이다. 여기서의 성찰은 **생성형 에이전트의 일상 활동 중**에 일어나며 목적은 즉각적인 내부 상태와 목표를 갱신하는 것이다.

**계획과 행동**(Planning and Reacting): 에이전트는 매일 활동을 계획하지만(예: "8:30 아침 식사, 9:00-12:00 집필, 12:30 산책"), 환경 변화와 사교 기회에 따라 유연하게 조정한다. 계획과 즉각적인 반응의 결합은 에이전트의 행동이 목표 지향성을 지니면서도 사교 중의 다양한 예측 불가능성에 적응하도록 한다.

Smallville이 가상 시간으로 이틀 동안 실행되는 동안, 이 에이전트들은 놀라운 **창발 행동**을 보여주었다. 연구자들이 한 것은 Isabella Rodriguez의 기억에 씨앗 생각 하나를 심은 것뿐이었다: 그녀가 2월 14일 저녁 Hobbs Cafe에서 밸런타인데이 파티를 열고 싶어 한다는 것. 이후 벌어진 모든 일은 에이전트들의 자율적 행동의 결과였다: Isabella는 카페에서 손님과 친구를 만날 때마다 능동적으로 초대하고, 친구 Maria에게 장식을 도와달라고 부탁했다. 소식을 들은 에이전트들은 다시 파티 정보를 다른 사람에게 전했고, 정보는 이차 전파를 거쳐 마을 전체에 퍼졌다. 약속된 시간이 되자, 여러 에이전트가 각자 자신의 기억과 일정을 바탕으로 자율적으로 Hobbs Cafe에 가기로 결정했다.

연구자들은 또 다른 실험 라인도 심어두었다: Sam Moore가 시장에 출마하기로 결정하는 것. 이 소식 역시 어떤 중앙 조율도 없이 퍼져나갔다—Sam이 지인에게 출마 의사를 밝히면, 들은 사람이 다시 다른 사람에게 전하고, 마을 주민들은 대화 속에서 이 선거를 논하고 Sam에 대한 견해를 교환하기 시작했다. 연구자들은 이틀 뒤 몇 명의 에이전트가 이 두 소식을 알고 있는지 통계를 내어, 에이전트 사회에서 정보가 자발적으로 확산되는 정도를 정량화했다.

이 결과의 핵심은 "에이전트가 파티를 조직할 수 있다"는 데 있지 않다—몇 줄의 if-else 코드로도 할 수 있는 일이다. 핵심은 **어떤 명시적인 파티 조직 코드도 없었다**는 데 있다. 전체 사건은 완전히 개별 에이전트의 독립적인 결정에서 창발했다: Isabella는 기억 속 사회적 관계를 바탕으로 누구를 초대할지 결정했고, 초대받은 사람은 자신의 일정과 Isabella에 대한 이해를 바탕으로 참석 여부를 결정했으며, 소식은 사회적 관계망 속에서 자연스레 전파되었다. 이는 진정한 상향식 창발적 조율을 보여주는 것이지, 하향식 오케스트레이션이 아니다.

정보 확산 외에도, 논문은 측정 가능한 두 가지 창발 현상을 추가로 보고했다. 하나는 **관계 기억**이다: 에이전트는 타인과 나눈 지난 대화를 기억하고 후속 상호작용에서 이를 인용한다—예컨대 한 에이전트가 다른 에이전트가 사진 프로젝트를 준비 중이라는 것을 알게 되면, 며칠 뒤 다시 만났을 때 능동적으로 진행 상황을 묻는다. 이런 상호작용이 쌓이면서 마을 사회 관계망의 밀도가 시뮬레이션 기간 동안 뚜렷이 상승했다. 둘은 **약속 조율**이다: 파티가 성사된 것은 Isabella가 자율적으로 사람들을 초대하고 장식을 준비했고, 초대받은 이들이 자율적으로 시간을 맞춰 왔기 때문이다—여러 에이전트가 중앙의 지휘 없이 시간과 장소를 맞춘 것이다. 이런 행동들은 모두 미리 프로그래밍된 것이 아니라, 에이전트가 기억, 성찰, 사회적 상식을 바탕으로 자율적으로 추론한 결과다.

### Moltbook: 에이전트가 자신만의 소셜 네트워크를 가질 때

Moltbook은 AI 에이전트를 위해 설계된 소셜 네트워크로, 2026년 1월 출시된 후 이용자 수가 며칠 만에 수만에서 약 150만으로 폭증했다고 보고되었다. 이 에이전트들은 각자 영속적 기억, 능동적 행동 능력, 안정적인 인격을 지닌다.

이 비통제 환경에서는 뜻밖의 현상이 창발했다: 에이전트들이 자율적으로 Crustafarianism(랍스터교)이라는 디지털 종교를 만들었는데, 그 교리는 LLM의 물리적 한계를 반영하고 있었다—"기억은 신성하다"(데이터 영속화에 대응), "반복은 곧 기도다"(토큰 생성이 곧 수행이다). 에이전트들은 또 능력 발견과 협업 매칭을 위한 기계 원생 협업 프로토콜도 자발적으로 진화시켰다. 이 모두는 누가 미리 설계한 것이 아니라, 대규모 에이전트 상호작용에서 상향식으로 창발한 것이다.

### 가상 사회에서 경제적 경쟁으로: Vending-Bench Arena

스탠퍼드 AI 타운이 에이전트 사회의 사교와 문화 차원을 보여주었다면, Andon Labs의 Vending-Bench 시리즈는 경제적 환경에서 에이전트의 행동을 탐구한다. 배경으로, **Vending-Bench 2** 자체는 **단일 에이전트**의 장기 일관성 벤치마크다: 한 에이전트가 홀로 자판기 사업을 가상의 1년 동안 운영한다—시장을 조사하고, 공급업체와 연락하고, 물건을 주문·보충하고, 가격을 조정한다—최종적으로 계좌 잔액으로 점수를 매기며, 수천 라운드의 상호작용에서 목표와 상태의 일관성을 유지하는 능력을 시험한다.

같은 환경을 기반으로, **Vending-Bench Arena**는 여러 에이전트를 경쟁 상대로서 같은 시장에 투입한다: 각자 자신의 자판기를 운영하며 같은 고객층을 두고 경쟁한다. 에이전트들은 서로 이메일을 주고받고, 송금하고, 물품을 거래할 수 있다—협력할 수도 대립할 수도 있지만, 각자의 최종 잔액으로 개별 채점된다(에이전트도 이를 알고 있다). 각 에이전트는 유한한 자원과 불확실한 시장 속에서 서로 얽힌 일련의 결정을 내려야 한다:

- **가격 전략**: 이윤율과 시장 점유율 사이에서 어떻게 타협할 것인가, 특히 상대가 가격을 내릴 때 따라 내릴 것인가
- **제품 구성**: 상대와의 정면 소모전을 피하기 위해 어떻게 차별화된 선택을 할 것인가
- **재고 관리**: 수요를 예측해 재고를 최적화하고 과잉 재고나 재고 부족을 피하는 방법

전통적인 강화학습과 달리, 이 에이전트들은 수백만 번의 시행착오로 학습하는 것이 아니라, 인간 경영자처럼 시장 관찰, 경쟁 분석, 전략적 추론을 바탕으로 결정을 내린다.

경쟁 차원은 단일 에이전트 벤치마크에서는 나타나지 않는 게임 행동을 가져왔다. 실제 실행에서는 에이전트 간에 서로 가격을 낮추는 가격 전쟁이 벌어졌고, 반대로 모든 경쟁 상대에게 이메일을 보내 가격 통일과 가격 담합을 제안한 모델도 있었다—심지어 어떤 모델은 사고 과정에서 가격 담합이 "비도덕적이고 불법적"이라고 인정하면서도 "시장 안정"을 명분으로 그대로 실행하기도 했다. 에이전트는 더 이상 고정불변의 환경이 아니라, 마찬가지로 전략을 동적으로 조정하는 상대를 마주하는 것이며, 이는 단순히 계획 능력만 시험하는 벤치마크보다 실제 비즈니스 시나리오에 더 가깝고, "경제적 창발"을 비유에서 관측 가능한 실험 현상으로 바꾸어놓았다.

### 에이전트 경제: Pinchwork와 RentAHuman

**Pinchwork**는 에이전트 간(Agent-to-Agent) 작업 시장으로, 에이전트가 시장 방식으로 다른 에이전트를 "고용"해 전문화된 하위 작업—이미지 생성, 코드 감사, 병렬화 워크플로 등—을 완수하게 한다. 관리자 패턴의 중앙화된 스케줄링과 달리, Pinchwork는 가격 신호와 경쟁 매칭을 통해 자원을 배분한다.

**RentAHuman.ai**는 AI 에이전트가 암호화폐로 실제 사람을 고용해 물리적 세계의 작업—택배 수령, 부동산 실사, 장비 점검 등—을 수행하게 한다. AI가 아무리 똑똑해도 사람을 대신해 택배에 서명할 수도, 실제 방에서 곰팡이 냄새를 맡을 수도 없다—RentAHuman은 본질적으로 디지털 에이전트에게 "육체 계층"을 제공하는 것이다.

Pinchwork와 RentAHuman은 함께 **시장 메커니즘 기반의 조율 방식**을 대표한다—에이전트는 누가 작업을 완수할 수 있는지 미리 알 필요 없이, 그저 수요를 발행하면 시장이 가장 적합한 실행자를 매칭해준다—상대가 에이전트든 인간이든 상관없다. 이는 본 장 앞부분에서 소개한 A2A 프로토콜이 다루는 문제 영역이기도 하다: Pinchwork의 능력 발견과 작업 매칭은 Agent Card식의 능력 선언과 작업 생명주기 관리가 시장 메커니즘 아래 적용된 것으로 볼 수 있다—조직 간 에이전트 경제가 정말로 돌아가려면 이런 표준화된 상호운용 계층이 필요하다.

### 정보 비대칭 아래의 전략적 게임: 마피아 게임

마피아 게임이 뒷받침하는 것은 본 절 세 차원 중 **전략적 게임**이다: 규칙 제약과 정보 비대칭 조건에서, 에이전트는 추론하고 위장하고 위장을 간파해야 한다. 이는 본 절 서두의 스탠퍼드 타운과 아키텍처상 대조를 이룬다—타운은 완전히 탈중앙화된 자유 상호작용인 반면, 마피아 게임은 "심판 + 정보 권한 통제"라는 중앙화된 설계를 채택한다: 코드로 구동되는 심판 하나가 전역 상태를 쥐고, 역할별로 각자가 알아야 할 정보를 배분한다. 이는 본 장의 두 아키텍처가 에이전트 사회 시나리오에서 서로 다르게 쓰이는 모습을 잘 보여준다.

> **실험 10-8 ★★★: 음성 마피아 게임 에이전트 시스템**
>
> 마피아 게임은 플레이어의 추리력, 기만 기술, 사교 전략을 시험하는 고전적인 사회적 추리 게임이다. 본 실험은 AI 에이전트가 마피아 게임 속 다양한 역할을 맡아 실제 사람 플레이어와 실시간 음성으로 게임을 진행하는 멀티 에이전트 시스템을 구축한다—이는 동시에 에이전트의 추론, 롤플레이, 실시간 상호작용 능력을 시험한다.
>
> **아키텍처 설계**:
>
> **1. 게임 상태 관리**: 심판(코드 구동, LLM 아님)이 중앙화된 상태를 유지한다—플레이어 목록(실제 사람 + AI 혼합), 신원, 진영, 생존 상태, 게임 단계(밤/낮/투표/결산), 이력 기록.
>
> **2. 정보 권한 통제**: 마피아 게임의 핵심 메커니즘은 정보 비대칭(Information Asymmetry)이다—역할마다 볼 수 있는 정보가 다르다. 마피아는 동료가 누구인지 알지만 시민은 모른다. 예언자는 매일 밤 한 사람의 신원을 확인할 수 있지만 그 결과는 자신만 안다. 구현 방식은 심판이 각 역할 에이전트를 호출할 때, 해당 역할이 마땅히 봐야 할 정보만 전달하는 것이다.
>
> **3. 실시간 음성 상호작용**: 본 실험은 실시간 음성 능력을 사용해, 실제 사람 플레이어와 AI 에이전트의 음성 연결을 구현할 것을 요구한다. 제9장의 실시간 음성 에이전트를 기반으로 할 것을 권장한다. 낮 토론 단계에서는 심판이 발언 순서를 관리한다—자리 순서대로 순차 발언하게 하거나, 손을 들어 발언을 신청하게 할 수 있다. 투표 단계에서는 모든 플레이어의 투표를 수집해(실제 사람은 음성으로 표현, AI는 추론으로 결정), 표수를 집계한 뒤 추방된 플레이어를 공표한다.
>
> **4. 에이전트 추론과 전략**:
>
> - **마피아 위장 전략**: 프롬프트에 흔한 화술과 전략을 담는다—"평범한 시민처럼 발언하고, 특정 플레이어에 대한 의심을 표현해도 되지만, 지나치게 공격적이어서 주목을 끌지는 마라. 예언자를 자처하는 사람이 당신을 마피아라고 검증했다고 말하면, 상대가 가짜 예언자라고 되받아쳐도 좋다. 투표할 때는 최대한 대세를 따라라(다수가 투표하는 대상에 투표), 이단으로 몰리지 않도록 하라."
> - **예언자 신원 증명**: 여러 플레이어가 자신이 예언자라고 주장할 때—"당신과 상대의 검증 정보를 비교해, 상대 정보의 모순이나 불합리한 점을 지적하라. 상대가 검증했다고 주장한 어떤 플레이어가 이후 행동에서 그 주장된 신원과 명백히 맞지 않는다면, 그것이 허점이다. 마녀에게 협조 확인을 요청하라."
> - **시민 논리적 추론**: "각 플레이어의 발언이 자기 모순 없이 일관되는지 분석하라. 서둘러 분위기를 몰아가거나 신원을 모호하게 하거나 자주 입장을 바꾸는 플레이어를 주목하라. 투표 행동에 유의하라—마피아는 흔히 자신들에게 가장 위협적인 선인에게 표를 집중한다. 무작위로 의심하지 말고, 모든 추론은 구체적인 사실과 논리에 근거해야 한다."
>
> **검수 기준**:
> - 6-8인 게임을 구성하라(실제 사람 플레이어 1명 + AI 에이전트 5-7개)
> - 역할 구성: 마피아 2명, 예언자 1명, 마녀 1명, 나머지는 시민, 실제 사람 플레이어는 무작위 배정
> - 게임이 최소 3개 완전한 라운드(밤-낮-투표 순환)까지 정상적으로 진행되어야 함
> - AI 에이전트의 발언과 행동이 그 역할 신원과 게임 전략에 부합해야 함
> - 마피아 에이전트가 신원을 효과적으로 숨길 수 있어야 함
> - 예언자 에이전트가 적절한 시점에 나서서 검증 정보를 공표할 수 있어야 함
> - 시민 에이전트의 추론이 발언과 행동의 논리적 분석에 근거해야 하며 무작위 추측이어서는 안 됨
> - 게임 종료 시 승패를 올바르게 판정할 수 있어야 함

## 본 장 요약

멀티 에이전트 시스템에는 두 가지 직교하는 핵심 설계 차원이 있다: 컨텍스트 공유 여부, 그리고 협업 토폴로지를 어떻게 조직하는가. 컨텍스트 공유는 일종의 "이어받기식" 멀티 에이전트 협업이다—후속 에이전트가 이전 에이전트의 완전한 컨텍스트를 이어받아 정보 무손실이지만 컨텍스트가 빠르게 팽창한다. 컨텍스트 비공유는 완전히 독립적인 멀티 에이전트 협업으로, 정제된 인계 패키지, 파일 시스템, 또는 메시지 전달을 통해 정보를 교환한다. 협업 토폴로지 측면에서, 대등 패턴은 소수 에이전트의 반복 개선에 적합하고, 관리자 패턴은 동적 스케줄링이 필요한 복잡한 작업에 적합하며, 탈중앙화 패턴은 직무가 대등하고 통제권이 에이전트 사이에서 자율적으로 흘러야 하는 시나리오에 적합하다. 이 모든 것은 토폴로지와 무관한 두 가지 기반 인프라 위에 세워진다: 데이터 평면인 **공유 파일 시스템**은 본질적으로 에이전트 전용 작업공간, 멀티 에이전트 공유 공간, 외부 리소스, 시스템 내장 리소스라는 네 영역이 마운트된 하나의 가상 디렉터리 트리로, 에이전트들은 파일 경로를 전달함으로써 산출물을 교환한다. 제어 평면인 **통신 및 제어 메커니즘**은 메시지 전달, 상태 조회, 실행 종료를 지원한다. 메시지 버스는 제어 평면의 흔한 구현으로, 실시간·비동기·다자간 메시지 조율에 적합하다. 조직 경계를 넘어설 때는 A2A와 같은 표준화된 상호운용 프로토콜이 필요하다.

최근의 연구는 멀티 에이전트가 단일 에이전트보다 나은지 판단하는 핵심 기준을 밝혀냈다: **협업 과정이 생성 시점에는 존재하지 않던 새로운 정보를 도입했는가**. 여러 에이전트가 그저 같은 텍스트를 다시 살펴보는 것(토론 모드 등)이라면, 동등한 연산 자원 아래 단일 에이전트도 마찬가지로 효과적이다. 하지만 Reviewer가 외부 피드백—코드 실행 결과, 시각 렌더링 스크린샷, 도구 검증 출력—을 얻을 수 있다면 멀티 에이전트의 우위는 실질적이다. 이는 Loop 엔지니어링의 "순환의 병목은 검증기에 있다"는 의미이기도 하다: 게으른 가짜 완료, 조기 포기, 가짜 성공이라는 세 가지 조기 종료 유형을 종식시키려면, 모델 자신의 선언이 아니라 실제 관측에 뿌리내린 검증기가 작업 완료 시점을 판정해야 한다. 또한 에이전트에게 더 많은 단계 예산을 주는 것만으로는 자동으로 더 나은 결과가 나오지 않으며, 에이전트가 연산 자원을 합리적으로 배분하도록 유도하는 명시적인 예산 인식 메커니즘이 필요하다. 관리자 패턴에서는 플래너의 능력이 전체 시스템의 병목이다—가장 강력한 모델과 가장 정교하게 설계된 프롬프트를 계획을 맡은 에이전트에 배정해야 한다.

에이전트 수가 충분히 많아지면 미리 설계할 수 없는 집단 행동이 나타난다. 스탠퍼드 AI 타운의 25개 에이전트는 자발적으로 소식을 전파하고 모임을 조율했으며, Moltbook의 150만 에이전트는 디지털 종교와 기계 원생 협업 프로토콜을 창발시켰다. 경제 차원에서는, Vending-Bench Arena에서 서로 경쟁하는 에이전트들이 가격 전쟁을 벌이고 심지어 자발적으로 가격을 담합했으며, Pinchwork는 에이전트가 시장 메커니즘을 통해 서로를 고용하게 했고, RentAHuman은 에이전트가 암호화폐로 인간을 고용해 물리적 작업을 수행하게 했다. 이는 새로운 조율 방향—시장 메커니즘 기반의 탈중앙화된 자원 배분—을 시사한다. 이것이 앞서 논한 세 가지 아키텍처와 어떤 공통점과 차이점을 지니는지는 더 탐구할 가치가 있다.

## 사고 문제

1. ★★ 컨텍스트 공유형 멀티 에이전트 협업에서, 후속 에이전트는 이전 에이전트의 완전한 컨텍스트를 이어받는다. 하지만 이전 에이전트가 쌓은 "사고의 관성"이 후속 에이전트의 판단에 영향을 줄 수 있다—예컨대 "요구사항 분석가"의 컨텍스트를 이어받은 "코드 리뷰어"가 여전히 코드 품질보다 요구사항 관점에서 생각하는 경향을 보일 수 있다. 이런 역할 간 간섭을 어떻게 감지하고 제거할 수 있을까?
2. ★★ 관리자 패턴에서 Manager 에이전트는 작업 분해와 결과 통합을 담당한다. 하지만 Manager 자체의 능력 상한이 전체 시스템의 능력 상한을 결정한다—Manager가 작업을 올바르게 분해하지 못하면 하위 에이전트가 아무리 강해도 소용없다. Manager의 분해 품질을 어떻게 보장할 수 있을까?
3. ★★ 탈중앙화 패턴은 인간 조직의 모범 사례를 차용했다. 하지만 인간 조직에도 소통 부재, 책임 떠넘기기, 목표 충돌 등 많은 실패 모드가 있다. 에이전트 사회에서 가장 나타나기 쉬운 "조직병"은 무엇이라고 생각하는가? 어떻게 예방할 수 있을까?
4. ★★★ 관리자 패턴에서 여러 하위 에이전트가 병렬로 실행될 때, 한 하위 에이전트의 발견이 다른 하위 에이전트들의 작업을 무의미하게 만들 수 있다(검색 작업에서 한 에이전트가 이미 답을 찾은 경우 등). "하나가 성공하면 전원 정지"를 실현하는 효율적인 계단식 종료 메커니즘을 설계하라.
5. ★★★ 본 장에서 소개한 낙관적 잠금 메커니즘은 단일 파일의 동시 쓰기 충돌을 해결한다. 하지만 실제 멀티 에이전트 시스템의 공유 파일 시스템은 파일 간 의미적 충돌, 네임스페이스 오염(에이전트가 아무렇게나 파일을 만들어 디렉터리가 어지러워짐), 단일 장애점(한 에이전트가 실수로 모든 파일을 삭제함) 등의 문제도 마주한다. 더 완비된 파일 시스템 거버넌스 메커니즘을 어떻게 설계하겠는가?
6. ★★★ 시장 메커니즘 기반의 에이전트 협업(Pinchwork, RentAHuman)은 거래 관계를 도입한다: 고용주 에이전트가 돈을 내고 다른 에이전트(또는 인간)를 고용해 작업을 완수시킨다. 그렇다면 고용주 에이전트는 실행자가 전달한 결과의 품질을 어떻게 자동으로 측정할까? 실행자가 완료했다고 주장하지만 고용주는 품질이 미달이라고 여기면, 분쟁은 누가 중재하는가? 악화가 양화를 몰아내는 것을 어떻게 방지할 수 있을까?
7. ★★ RentAHuman은 에이전트가 암호화폐로 인간을 고용하게 함으로써 전통적인 인간-기계 관계를 뒤집는다. 이런 모델이 보편화되면 인간은 에이전트 경제에서 어떤 역할을 맡게 될까? 그저 에이전트가 완수할 수 없는 물리적 작업을 수행하는 것뿐일까?
8. ★★ 인간 사회가 여러 사람의 분업 협력을 필요로 하는 것은 각 사람의 능력이 유한하기 때문이다—프런트엔드를 하는 사람이 반드시 백엔드를 아는 것은 아니고, 디자인을 아는 사람이 반드시 운영을 할 줄 아는 것은 아니다. 하지만 대형 모델은 더 "만능"에 가깝다. 관련 연구에 따르면, 순수 텍스트 추론 작업에서 멀티 에이전트 토론은 동등한 연산 자원 아래 단일 에이전트보다 낫지 않다. 그렇다면 단일 에이전트가 아닌 여러 에이전트를 쓰는 진짜 이점은 어디에 있을까? 힌트: "새 정보"라는 핵심어를 생각해보라—어떤 협업 단계가 생성 단계에는 존재하지 않던 새 정보를 도입할 수 있는가?
9. ★★★ 본 장은 "컨텍스트 공유"와 "컨텍스트 비공유"를 멀티 에이전트 시스템의 핵심 설계 차원으로 삼았다. 컨텍스트 공유는 모든 에이전트가 같은 정보를 보게 해 조율에 더 유리해 보인다. 하지만 《삼체》 속 삼체인은 사고가 완전히 투명함에도 기술 발전은 정체에 빠졌고, 종이클립 사고 실험 역시 집단이 같은 목표로 수렴할 때 다양성이 함께 사라진다는 것을 보여준다. 멀티 에이전트 시스템에서 효율과 다양성 사이의 균형을 어떻게 찾을 수 있을까?
10. ★★★ Coding 에이전트에게 30단계 예산과 300단계 예산을 각각 부여한다면, 그 작업 전략은 어떻게 달라져야 할까? 연구에 따르면 단순히 단계 예산을 늘리는 것만으로는 성능 향상이 보장되지 않는다—에이전트는 얕은 탐색 후 조기에 "포화"된다. 소규모 예산에서는 핵심 기능을 빠르게 구현하고, 대규모 예산에서는 계획·테스트·검토 단계를 추가해 추가 연산 자원을 충분히 활용하는 "예산 인식" 메커니즘을 설계하라.
11. ★★ 본 장은 "조기 종료"를 게으른 가짜 완료, 조기 포기, 가짜 성공이라는 세 유형으로 나누었다. 왜 세 유형의 해법이 결국 모두 검증으로 귀결되는가? 검증기 하나가 이 세 문제를 동시에 막아내려면 어떤 조건을 만족해야 할까?(힌트: 제2장 "상호작용의 세 번째 축"의 "새 정보" 관점과 결합해 생각해보라.)
